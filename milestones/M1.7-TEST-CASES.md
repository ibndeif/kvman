# M1.7 — Deadlines, cancellation, supervision: test cases

Read: `02` §2.9, `03` §3.4 (deadlines), §3.5 (abort), §3.6; ADRs 0066 (onAbort on deadline moved here), 0067 (worker loss), 0071 (loading), 0078 (kernel host), 0079 (who may cancel), 0080 (quarantine storage), 0081 (drift reason), 0082 (crash charging, lazy restart), 0083 (cancel semantics), 0084 (deadlines end attempts, aborts close ctx), 0085 (depth limit), 0086 (pending messages of a quarantined extension).

Tests that run extension code live in `packages/testkit/test/supervision/` and use the M1.6 host harness (real worker threads, fixture extensions, a manual kernel clock that fires the scheduler's and the host manager's timers). Pure kernel logic is tested in `packages/kernel/test/supervision/`, and protocol shapes in `packages/protocol/test/`. "A person" is `user:local`.

## Happy path

### M1.7-H1 — cancelling a message cancels a ctx.command call and a deferred command it caused
- **Given** `notes.cascade`, which calls `ctx.command('notes.ask')` (it defers) and `ctx.command('counter.wait')` (it defers too) at once and waits for both
- **When** a person cancels `notes.cascade` with `kernel.cancel { messageId }`
- **Then** the reply is `{ cancelled: 3 }`: `notes.cascade` (running), `notes.ask` (awaiting), and `counter.wait` (awaiting) are `cancelled` with the reply `CANCELLED`; the kernel sends `notes.ask`'s onAbort `notes.question.expire { commandId, reason: 'cancelled' }`, which runs; the running handler's signal fires, its waiting calls end, and its result is discarded
- Test: `packages/testkit/test/supervision/cancel.test.ts`

### M1.7-H2 — cancelling a finished message returns { cancelled: 0 }
- **Given** a `done` `notes.add`
- **When** a person cancels it
- **Then** the reply is `{ cancelled: 0 }` and the row is still `done`
- Test: `packages/testkit/test/supervision/cancel.test.ts`

### M1.7-H3 — a crashing handler is redelivered with attempts + 1
- **When** `notes.crash.once { mode: 'exit' }` ends its worker on its first attempt
- **Then** the row is `pending` with `attempts` 1, and after the backoff it runs again on a new worker and is `done`
- Test: `packages/testkit/test/supervision/crashes.test.ts`

### M1.7-H4 — three crashes in 10 minutes quarantine the extension with HOST_FAILURES
- **When** `@acme/counter` crashes its worker three times within 10 minutes of the kernel clock
- **Then** its `extensions` row is `quarantined` with reason `HOST_FAILURES`, `kernel.extension.quarantined { name: '@acme/counter', reason: 'HOST_FAILURES' }` is stored in the events log, and a new `counter.increment` is refused `HANDLER_UNAVAILABLE`
- Test: `packages/testkit/test/supervision/quarantine.test.ts`

### M1.7-H5 — a handler that exceeds its timeoutMs is retried with a fresh timeout
- **Given** `counter.slow.once` declares `timeoutMs: 1000` and hangs on its first attempt only
- **When** 1 s of kernel time passes after its claim
- **Then** its signal fires, the attempt ends `HANDLER_TIMEOUT` (row `pending`, `attempts` 1), and the retry gets a new invocation deadline 1 s after its own claim and is `done`
- Test: `packages/testkit/test/supervision/deadlines.test.ts`

### M1.7-H6 — a message whose deadline passes in its lane queue fails DEADLINE_EXCEEDED without retry
- **Given** `notes.edit.slow { id: 'x' }` running in the lane `note:x`, and a second `notes.edit.slow { id: 'x' }` with `deadlineAt` now + 2 s waits behind it
- **When** 2 s pass
- **Then** the waiting message is `failed` with `DEADLINE_EXCEEDED`, `attempts` 0, and is never run
- Test: `packages/testkit/test/supervision/deadlines.test.ts`

### M1.7-H7 — a running message whose deadline passes fails DEADLINE_EXCEEDED without retry
- **Given** `counter.hang` (it never returns) sent with `deadlineAt` now + 1 s
- **When** 1 s passes
- **Then** its signal fires with `DEADLINE_EXCEEDED`, and the row is `failed` with `DEADLINE_EXCEEDED`, `attempts` 0, and never retried
- Test: `packages/testkit/test/supervision/deadlines.test.ts`

### M1.7-H8 — ctx.send does not inherit the parent's deadline; ctx.command does
- **Given** `notes.deadlines.check` runs with an invocation deadline D (its `timeoutMs`)
- **When** it sends `counter.increment` with `ctx.send`, and calls `counter.increment` with `ctx.command` without a deadline and with `deadlineAt` D + 10 s
- **Then** the sent command has no `deadlineAt`; both called commands have `deadlineAt` D
- Test: `packages/testkit/test/supervision/deadlines.test.ts`

### M1.7-H9 — a deferred command whose deadline passes sends its onAbort
- **Given** `notes.ask` sent with `deadlineAt` now + 5 s, awaiting with `onAbort: 'notes.question.expire'`
- **When** 5 s pass
- **Then** it is `failed` with `DEADLINE_EXCEEDED`, a waiter gets that reply, and `notes.question.expire { commandId, reason: 'deadline' }` runs, sent by the kernel
- Test: `packages/testkit/test/supervision/deadlines.test.ts`

## Edge cases

### M1.7-E1 — cancel by correlation
- **Given** `notes.family` (done), whose correlation holds a running `notes.edit.slow`, a pending `counter.increment` timer, and an awaiting `notes.ask`, and the person's `kernel.cancel` sent in another correlation
- **When** the person cancels `{ correlationId }`
- **Then** those three are `cancelled`, `notes.family` stays `done`, and the reply counts 3
- Test: `packages/testkit/test/supervision/cancel.test.ts`

### M1.7-E2 — who may cancel
- **Given** `counter.wait` sent by a person (awaiting) and `counter.wait` sent by `@acme/notes` (awaiting)
- **When** `@acme/audit` (no grant) cancels the first, `@acme/notes` cancels the second, and `@acme/audit` with `kernel.admin` granted cancels the first
- **Then** the first call fails `CAPABILITY_DENIED` and cancels nothing; the second and third succeed; no call needs a `calls` grant for `kernel.cancel`
- Test: `packages/testkit/test/supervision/cancel-permissions.test.ts`

### M1.7-E3 — cancel payloads and unknown messages
- **When** `kernel.cancel` is sent with `{}`, with both fields, and with the id of a message that does not exist
- **Then** the first two fail `VALIDATION_FAILED` at admission; the third answers `{ cancelled: 0 }`
- Test: `packages/testkit/test/supervision/cancel-permissions.test.ts`

### M1.7-E4 — a cancelled timer never runs
- **Given** `counter.increment` sent with `delayMs: 60000`
- **When** it is cancelled and 60 s pass
- **Then** it is `cancelled` and never runs (the counter's total stays 0)
- Test: `packages/testkit/test/supervision/cancel.test.ts`

### M1.7-E5 — a cancelled deferred command answers its continuation
- **Given** `notes.start { id }` sent `notes.ask` with `onReply: 'notes.answer.record'`
- **When** `notes.ask` is cancelled
- **Then** `notes.answer.record` receives `{ reply: { ok: false, problem: CANCELLED } }` and `notes.question.expire` receives `{ reason: 'cancelled' }`
- Test: `packages/testkit/test/supervision/cancel.test.ts`

### M1.7-E6 — a cancelled running handler's ctx is closed and its result discarded
- **Given** `notes.cancel.probe` streams a live chunk, writes a document, and waits until its signal fires, then records `ctx.signal.reason`'s code and tries `ctx.send`
- **When** it is cancelled
- **Then** its live address gets `{ reset: true }` for its run; its write is not stored; the recorded codes are `CANCELLED` for both the signal and the send; the row stays `cancelled`
- Test: `packages/testkit/test/supervision/cancel.test.ts`

### M1.7-E7 — a cancelled lane holder frees its lane
- **Given** `notes.edit.slow { id: 'x' }` running and a second one pending behind it
- **When** the first is cancelled
- **Then** the second runs at once, although the first handler has not returned
- Test: `packages/testkit/test/supervision/cancel.test.ts`

### M1.7-E8 — queued transient deliveries in scope are cancelled
- **Given** `notes.touch` published two transient `notes.touched` deliveries for the same note, the first running and the second queued behind it in `audit`'s lane
- **When** the `notes.touch` message is cancelled
- **Then** the reply counts 2, the running delivery's signal fires, and the queued delivery never runs
- Test: `packages/testkit/test/supervision/cancel.test.ts`

### M1.7-E9 — a stuck host is stopped; its collateral returns without penalty
- **Given** on a one-worker pool, `counter.hang` (`timeoutMs: 1000`, `maxAttempts: 1`) that ignores its signal, and `notes.crash.once { mode: 'wait' }` running on the same worker
- **When** 1 s passes, then 2 s more
- **Then** at 1 s `counter.hang`'s attempt ends `HANDLER_TIMEOUT` and, at its last attempt, it is `dead` with `MESSAGE_DEAD`; at 3 s the worker is stopped, `@acme/counter` is charged one host failure, and `notes.crash.once` is `pending` again with `attempts` 0 and runs to `done` on a new worker
- Test: `packages/testkit/test/supervision/stuck.test.ts`

### M1.7-E10 — a query past its timeout answers QUERY_TIMEOUT
- **When** a person asks `notes.slow.get` (its timeout is the default 5 s) and 5 s pass
- **Then** the answer is `QUERY_TIMEOUT`, and the query is not asked again
- Test: `packages/testkit/test/supervision/deadlines.test.ts`

### M1.7-E11 — the invocation deadline and defaults
- **When** `notes.describe.deadline` (no `timeoutMs`) runs, and `counter.slow.once` (`timeoutMs: 1000`) runs with `deadlineAt` now + 500 ms
- **Then** the first sees `ctx.deadlineAt` = claim + 60 s; the second sees claim + 500 ms, and when it passes, the outcome is `DEADLINE_EXCEEDED`, not `HANDLER_TIMEOUT`
- Test: `packages/testkit/test/supervision/deadlines.test.ts`

### M1.7-E12 — deadline timers survive a restart
- **Given** an awaiting `notes.ask` with `deadlineAt` now + 5 s and a pending `counter.increment` with `delayMs: 10000` and `deadlineAt` now + 5 s
- **When** the runtime is stopped and a new one opens on the same database, and 5 s pass
- **Then** both are `failed` with `DEADLINE_EXCEEDED`, and `notes.question.expire` runs
- Test: `packages/testkit/test/supervision/deadlines.test.ts`

### M1.7-E13 — a continuation has no deadline
- **Given** `notes.archive` sends `counter.increment` with `deadlineAt` now + 5 s and `onReply`
- **When** the continuation is delivered
- **Then** the continuation row has no `deadlineAt`
- Test: `packages/testkit/test/supervision/deadlines.test.ts`

### M1.7-E14 — the nested ctx.command depth limit
- **When** a person sends `notes.nest { n: 8 }` and `notes.nest { n: 9 }` (each level calls `notes.nest { n: n - 1 }` until 0)
- **Then** the first is `done`; the second fails `VALIDATION_FAILED` with `params { limit: 'depth', max: 8 }` raised by the invocation at depth 8, and no ninth-level row is stored
- Test: `packages/testkit/test/supervision/depth.test.ts`

### M1.7-E15 — a quarantine is kept across a restart, and queued messages wait
- **Given** `@acme/counter` quarantined while a `counter.increment` with `delayMs: 1000` is pending
- **When** 1 s passes, and then the runtime restarts on the same database
- **Then** the pending message is still `pending` and never claimed; after the restart `counter.increment` is still refused `HANDLER_UNAVAILABLE`
- Test: `packages/testkit/test/supervision/quarantine.test.ts`

### M1.7-E16 — manifest drift quarantines with EXT_MANIFEST_INVALID
- **When** `drift.run` fails to load
- **Then** it fails `EXT_MANIFEST_INVALID` without retry, and `@acme/drift` is quarantined with reason `EXT_MANIFEST_INVALID`
- Test: `packages/testkit/test/supervision/quarantine.test.ts`

### M1.7-E17 — the crash window is 10 minutes
- **Given** a failure counter for one extension
- **When** failures are charged at 0 and 5 minutes, then at 11 minutes, then at 12 minutes
- **Then** the third charge does not quarantine (only two within 10 minutes), and the fourth does
- Test: `packages/kernel/test/supervision/host-failures.test.ts`

### M1.7-E18 — a crash charges every extension running on the worker
- **Given** `counter.slow.once` (waiting on its first attempt, its timeout not reached) and `notes.crash.once { mode: 'exit' }` running on one worker
- **When** `notes.crash.once` ends the worker
- **Then** both messages are `pending` with `attempts` 1, and `@acme/counter` and `@acme/notes` are each charged one host failure (two more crashes of the counter within 10 minutes quarantine it)
- Test: `packages/testkit/test/supervision/crashes.test.ts`

### M1.7-E19 — a call from an aborted invocation is refused with its abort problem
- **Given** `notes.cancel.probe` cancelled while running
- **When** the handler, after its signal, calls `ctx.command`
- **Then** the call throws `CANCELLED` in the host, and no row is stored for it
- Test: `packages/testkit/test/supervision/cancel.test.ts`

### M1.7-E20 — kernel commands run in the kernel host
- **When** a person sends `kernel.cancel`
- **Then** its row is stored with handler `kernel`, it runs without any worker thread starting, and it is `done` with its reply stored
- Test: `packages/testkit/test/supervision/cancel-permissions.test.ts`

### M1.7-E21 — kernel protocol shapes
- **When** the cancel request, cancel result, and `kernel.extension.quarantined` payload schemas parse valid and invalid examples, and `invoke` without `deadlineAt` and an `abort` frame are parsed
- **Then** the valid ones parse; `{}`, both fields, an unknown reason, and an `invoke` without `deadlineAt` fail
- Test: `packages/protocol/test/kernel-commands.test.ts`
