# M3.1 — `kvman --pipe`: test cases

Read: `01` §1.2; `02` §2.9 (trust), §2.14; `14` §14.2; `12` §12.1; ADR 0038, 16 to 20.

The child-process tests run kvman as M1.8's do (`packages/cli/test/support/kvman-child.ts`): a temporary `--home`, start folder, and user folder, `--port 0`, and `--no-open`. They add `--pipe`, read stdout as lines, each parsed as JSON, and write to or close the child's stdin. A test that is about trust leaves out `--yes`.

A line is one JSON object followed by `\n`. "Exactly these lines" means stdout holds nothing else.

## Happy path

### M3.1-H1 — `kvman --pipe` writes one `running` line and nothing else
- **Given** a preset with the app extension
- **When** kvman starts with `--pipe` in a folder
- **Then** stdout is exactly one line, `{ "kind": "running", "url", "port" }`: `port` is the port it listens on, and `url` is `http://127.0.0.1:<port>/?workspace=<id>` of that folder's workspace (`kernel.workspace.list`)
- Test: `packages/cli/test/pipe/pipe-run.test.ts`

### M3.1-H2 — closing the input stops kvman as the first Ctrl+C does
- **Given** kvman running with `--pipe`, with one waiting async job that has retries left and one that has none
- **When** its stdin is closed
- **Then** it exits 0 and `kvman.lock` is gone; at the next start the job without retries is `failed` with `INTERRUPTED` after 1 attempt, and the other runs again
- Test: `packages/cli/test/pipe/pipe-run.test.ts`

### M3.1-H3 — an input that closes while kvman starts lets the start finish
- **Given** a preset with the app extension
- **When** kvman is spawned with `--pipe` and its stdin is closed at once, before any line
- **Then** it writes the `running` line, then exits 0, and `kvman.lock` is gone
- Test: `packages/cli/test/pipe/pipe-run.test.ts`

### M3.1-H4 — an unaccepted version writes a `trust` line, and `{ "trust": true }` loads and remembers it
- **Given** the in-test registry serving `@acme/hello@1.0.0`, a preset naming it `npm:1.0.0`, and stdin a pipe (no terminal)
- **When** kvman starts with `--pipe` and no `--yes`, and the test writes `{"trust":true}` after the `trust` line; then kvman is stopped and started again the same way
- **Then** the first line is `{ "kind": "trust", "language": "en", "versions": [{ "name": "@acme/hello", "version": "1.0.0", "source": "npm:1.0.0" }] }`, the `running` line follows the answer, and `hello.version` answers `1.0.0`; the second start writes no `trust` line
- Test: `packages/cli/test/pipe/pipe-trust.test.ts`

### M3.1-H5 — `{ "trust": false }`, any other line, and a closed input decline
- **Given** the same registry and preset
- **When** kvman starts with `--pipe` three times, and after the `trust` line the test writes `{"trust":false}`, then `y`, then closes stdin
- **Then** each time the next line is `{ "kind": "failed", "language": "en", "problem": { "code": "EXTENSION_INVALID", … } }`, no `running` line comes, and kvman exits 1
- Test: `packages/cli/test/pipe/pipe-trust.test.ts`

### M3.1-H6 — `--yes` writes no `trust` line
- **Given** the same registry and preset
- **When** kvman starts with `--pipe --yes`
- **Then** stdout is exactly the `running` line, and `hello.version` answers
- Test: `packages/cli/test/pipe/pipe-trust.test.ts`

### M3.1-H7 — a second `kvman --pipe` writes `joined`, or `failed` with `KVMAN_RUNNING`
- **Given** kvman running on a home with preset `one`
- **When** a second kvman starts on that home with `--pipe` in another folder, then a third with `--pipe` and a preset named `two`
- **Then** the second's stdout is exactly `{ "kind": "joined", "url", "port" }` with the running kvman's port and that folder's workspace, which is open in the running kvman, and it exits 0; the third's stdout is exactly a `failed` line with `KVMAN_RUNNING` and no `language` key, and it exits 1
- Test: `packages/cli/test/pipe/pipe-join.test.ts`

### M3.1-H8 — a taken port writes `failed` with `PORT_IN_USE` and the language
- **Given** a server listening on a port of 127.0.0.1
- **When** kvman starts with `--pipe --port <that port>` on a new home
- **Then** stdout is exactly `{ "kind": "failed", "language": "en", "problem": { "code": "PORT_IN_USE", … } }`, and it exits 1
- Test: `packages/cli/test/pipe/pipe-join.test.ts`

### M3.1-H9 — `kernel.restart` writes `restarting`, then `running`
- **Given** kvman running with `--pipe`
- **When** `kernel.restart` is called
- **Then** stdout is exactly `running`, `restarting`, `running`, in that order, and the last line's port answers `kernel.health.get`
- Test: `packages/cli/test/pipe/pipe-run.test.ts`

### M3.1-H10 — `kvman uninstall --pipe` fails `VALIDATION_FAILED`
- **Given** the arguments `uninstall --pipe`
- **When** they are parsed
- **Then** it fails `VALIDATION_FAILED`
- Test: `packages/cli/test/arguments.test.ts`

### M3.1-H11 — without `--pipe`, a closed input doesn't stop kvman
- **Given** kvman running without `--pipe`
- **When** its stdin is closed
- **Then** it keeps answering `kernel.health.get`, its stdout is still the printed URL sentence, and Ctrl+C then stops it with exit 0
- Test: `packages/cli/test/pipe/pipe-run.test.ts`

## Edge cases

### M3.1-E1 — the flag and the usage text
- **Given** the arguments `--pipe`, and none
- **When** they are parsed
- **Then** `pipe` is `true`, and `false`; `--pipe` leaves `open` `true`; the usage text has `[--pipe]` on the run line and a `--pipe` option line
- Test: `packages/cli/test/arguments.test.ts`

### M3.1-E2 — a line is one strict JSON object and a newline
- **Given** each of the five lines
- **When** it is encoded
- **Then** the text is `JSON.stringify` of the object plus `\n`, with no other newline; a `failed` line without a language has no `language` key, and a Problem without `params` has no `params` key
- Test: `packages/cli/test/pipe/pipe-lines.test.ts`

### M3.1-E3 — only `{ "trust": true }` accepts
- **Given** the texts `{"trust":true}`, `{"trust":false}`, `{"trust":"yes"}`, `{"trust":true,"more":1}`, `y`, `true`, and the empty text
- **When** each is read as an answer
- **Then** only the first accepts
- Test: `packages/cli/test/pipe/pipe-lines.test.ts`

### M3.1-E4 — the stored language: the global value, else the preset's, else `en`
- **Given** a home whose database has the global setting `kernel.language` `ar`; one with none and a preset value `fr`; one with none and no preset value
- **When** the stored language is read
- **Then** it is `ar`, `fr`, and `en`
- Test: `packages/kernel/test/settings/stored-language.test.ts`

### M3.1-E5 — a stored value that isn't text is skipped
- **Given** a database whose global `kernel.language` row holds `5`, and a preset value `ar`; and a preset value `7` with no row
- **When** the stored language is read
- **Then** it is `ar`, and `en`
- Test: `packages/kernel/test/settings/stored-language.test.ts`

### M3.1-E6 — a home with no database yet
- **Given** a home folder with no `kvman.db`, and a preset value `ar`
- **When** the stored language is read
- **Then** it is `ar`, and no `kvman.db` was made
- Test: `packages/kernel/test/settings/stored-language.test.ts`

### M3.1-E7 — the `failed` line carries the global language
- **Given** a home where `kernel.language` was set to `ar` globally in an earlier run, and a taken port
- **When** kvman starts with `--pipe --port <that port>`
- **Then** the `failed` line has `"language": "ar"`
- Test: `packages/cli/test/pipe/pipe-join.test.ts`

### M3.1-E8 — a preset that can't be read fails with no language, and stderr is as before
- **Given** `--preset` naming a file that doesn't exist
- **When** kvman starts with `--pipe`
- **Then** stdout is exactly a `failed` line with `VALIDATION_FAILED` and no `language` key, stderr has the terminal's failure text (`VALIDATION_FAILED: …` and its hint), and it exits 1
- Test: `packages/cli/test/pipe/pipe-join.test.ts`

### M3.1-E9 — a line when no question is open is ignored
- **Given** kvman running with `--pipe`
- **When** the test writes `{"trust":true}` and `nonsense` to its stdin
- **Then** it keeps answering `kernel.health.get`, and stdout is still the one `running` line; closing stdin then exits 0
- Test: `packages/cli/test/pipe/pipe-run.test.ts`

### M3.1-E10 — a signal still stops a piped kvman whose input is open
- **Given** kvman running with `--pipe`, its stdin left open
- **When** it gets SIGINT
- **Then** it exits 0 and `kvman.lock` is gone
- Test: `packages/cli/test/pipe/pipe-run.test.ts`

### M3.1-E11 — a decline at a restart undoes the edit, with no `failed` line
- **Given** kvman running with `--pipe` and no `--yes`, and a `path:` extension added to the preset with `kernel.extensions.install`
- **When** `kernel.restart` is called, and the test answers the `trust` line with `{"trust":false}`
- **Then** the lines after the first `running` are `restarting`, `trust` (naming that extension), and `running`; no `failed` line is written; `kernel.health.get` has `rolledBack` with `EXTENSION_INVALID`; and the extension is not in `kernel.preset.get`
- Test: `packages/cli/test/pipe/pipe-trust.test.ts`

### M3.1-E12 — an accepted answer at a restart loads the extension
- **Given** the same start and the same edit
- **When** `kernel.restart` is called, and the test answers the `trust` line with `{"trust":true}`
- **Then** the lines after the first `running` are `restarting`, `trust`, and `running`, and the extension is in `kernel.extensions.list`
- Test: `packages/cli/test/pipe/pipe-trust.test.ts`

### M3.1-E13 — the install page and the README have the flag
- **Given** the user guide's install page and the root README
- **When** they are read
- **Then** the install page has the usage text as `--help` prints it and a `--pipe` row in its flags table, and the README's usage line has `[--pipe]`
- Test: `packages/cli/test/docs.test.ts`
