# M3.3 — Installers, updates, and the release: test cases

Read: `14` §14.3, §14.7, §14.8; `01` §1.2 (installing); ADR 0026, 8 to 10; ADR 0038, 31 to 33, 40, and 51 to 53.

What each layer can reach (ADR 0038, 36 and 53):

- **The build's own programs** (`release/desktop`, TypeScript run by Node) are tested with vitest: which Node archive a system gets, its checksum, the layout of what the app holds, and the run of the bundle with no window. A test never downloads anything: the archive comes from a function the test gives.
- **The session and the update's choices** (Rust) are tested as in M3.2.
- **The page's update line** is tested with `happy-dom`.
- **The updater plugin itself** (asking for `latest.json`, comparing versions, checking the signature, replacing the app) is Tauri's and has no test here. The scenarios test what the app does with its answers.
- **The workflow and the app's configuration** are read as files.
- An installer is built and tried by hand on the developer's OS; the other systems are built by the release (ADR 0038, 51).

## Happy path

### M3.3-H1 — the app starts with no Node and no npm on the `PATH`
- **Given** a prepared runtime folder (a Node, its npm, and kvman with its production dependencies), and a `PATH` that has no Node
- **When** the bundle is run with no window, as the release does
- **Then** kvman starts with the bundled Node and writes its `running` line, `kernel.health.get` answers, and `npm --version`, run with kvman's `PATH`, answers the bundled npm's version; the app's Rust side finds the bundled Node and kvman's entry in its resources, for Linux and macOS and for Windows
- Test: `test/release/try-runtime.test.ts`; `packages/desktop/src-tauri/tests/runtime.rs`

### M3.3-H2 — a person's own Node and npm come first
- **Given** a `PATH` that has a Node of the person's own
- **When** the command to start the bundled kvman is built
- **Then** kvman's `PATH` is theirs, then the bundled Node's folder
- Test: `packages/desktop/src-tauri/tests/runtime.rs`

### M3.3-H3 — a newer version shows on the home screen, and none shows nothing
- **Given** the updater's answer "version 0.4.0 is available", and its answer "nothing newer"
- **When** the home screen asks for the update
- **Then** the first gives the offer `{ version: "0.4.0", action: "install" }` and the page shows "kvman 0.4.0 is available." with "Install and restart" above the title; the second gives none and the page shows no line
- Test: `packages/desktop/src-tauri/tests/updates.rs`; `packages/desktop/test/update.test.ts`

### M3.3-H4 — a check that fails shows nothing
- **Given** an updater whose check fails
- **When** the home screen asks for the update
- **Then** there is no offer, the page shows no line, and the rows and "Open a folder…" work as before
- Test: `packages/desktop/src-tauri/tests/updates.rs`; `packages/desktop/test/update.test.ts`

### M3.3-H5 — kvman is stopped only after the update is downloaded and its signature holds
- **Given** a session on the home screen that owns its kvman
- **When** "Install and restart" is pressed; then, once, the download succeeds, and once, it fails
- **Then** pressing says only to download; a download that succeeded says to stop kvman, and kvman's end then says to install the update and start again, with no quit and no dialog; a download that failed says nothing to kvman, and the page shows "The update could not be installed." with the list still usable
- Test: `packages/desktop/src-tauri/tests/session.rs`; `packages/desktop/test/update.test.ts`

### M3.3-H6 — a `.deb` install's button is "Download"
- **Given** the app on Linux started from an AppImage, and started any other way; and the app on macOS and Windows
- **When** a newer version is offered
- **Then** the AppImage, macOS, and Windows offers have the action `install`; the other Linux offer has `download`, its button reads "Download", and pressing it opens `https://github.com/ibndeif/kvman/releases/latest` in the system's browser and downloads nothing
- Test: `packages/desktop/src-tauri/tests/updates.rs`; `packages/desktop/test/update.test.ts`; `packages/desktop/src-tauri/tests/session.rs`

### M3.3-H7 — the run of the bundle fails the job when kvman doesn't run
- **Given** runtime folders whose kvman writes no `running` line and exits, whose kvman writes `running` with a port nothing answers on, and whose kvman doesn't exit after its input closes
- **When** each is run as the release runs the bundle
- **Then** each run fails, saying which of the three it was
- Test: `test/release/try-runtime.test.ts`

### M3.3-H8 — a Node build whose checksum differs fails the build
- **Given** the pinned checksum of a system's Node archive, and an archive with one byte changed
- **When** the archive is checked
- **Then** the true archive passes, and the changed one fails, naming the file and both checksums, before anything is unpacked
- Test: `test/release/runtime-plan.test.ts`

## Edge cases

### M3.3-E1 — each system's Node archive
- **Given** the pinned Node version
- **When** the archive is asked for Linux x64, macOS arm64, macOS x64, and Windows x64; and for Linux arm64
- **Then** the first four are `node-v<version>-linux-x64.tar.xz`, `…-darwin-arm64.tar.xz`, `…-darwin-x64.tar.xz`, and `…-win-x64.zip` under `https://nodejs.org/dist/v<version>/`, each with a pinned checksum of 64 hex digits; the fifth fails, naming the system
- Test: `test/release/runtime-plan.test.ts`

### M3.3-E2 — what the app holds, per system
- **Given** the runtime's layout for Linux and macOS, and for Windows
- **When** it is read
- **Then** on Linux and macOS Node is `node/bin/node` and npm is the launcher `node/bin/npm` beside it; on Windows they are `node/node.exe` and `node/npm.cmd`; kvman's entry is `kvman/dist/main.js` on both; the folder with Node is the one added to kvman's `PATH`
- Test: `test/release/runtime-plan.test.ts`; `packages/desktop/src-tauri/tests/runtime.rs`

### M3.3-E3 — the npm launcher
- **Given** the launcher written for Linux and macOS
- **When** it is read
- **Then** it runs the Node beside it with that Node's own `npm-cli.js` and passes its arguments on, and it is executable
- Test: `test/release/runtime-plan.test.ts`

### M3.3-E4 — the runtime holds no link and no development leftovers
- **Given** a deployed kvman folder with a `node_modules/.bin` of links and pnpm's own files
- **When** it is cleaned for the bundle
- **Then** `.bin`, `pnpm-lock.yaml`, and `pnpm-workspace.yaml` are gone, no symbolic link is left anywhere in it, and `dist/main.js` and the dependencies stay
- Test: `test/release/runtime-plan.test.ts`

### M3.3-E5 — the app runs the bundled runtime when it has one
- **Given** a resources folder with a runtime, and one without
- **When** the app chooses what to run
- **Then** with a runtime it is the bundled Node and kvman; without one it is the repository's kvman and the Node on the `PATH`
- Test: `packages/desktop/src-tauri/tests/runtime.rs`

### M3.3-E6 — an update while the app has joined a kvman
- **Given** a session on the home screen of a kvman it joined
- **When** the update's download succeeds
- **Then** it says to install and start again at once, and nothing is stopped
- Test: `packages/desktop/src-tauri/tests/session.rs`

### M3.3-E7 — an update that can't be installed after kvman stopped
- **Given** a session whose kvman was stopped for an update
- **When** the install fails
- **Then** the app shows the stopped dialog's sibling, "The update could not be installed.", and its button quits
- Test: `packages/desktop/src-tauri/tests/session.rs`

### M3.3-E8 — the update line's states
- **Given** the home screen with an offer to install
- **When** the button is pressed
- **Then** the button is disabled while the update downloads, so it can't be pressed twice; rows and "Open a folder…" stay usable; a workspace chosen meanwhile is not entered once the download has succeeded
- Test: `packages/desktop/test/update.test.ts`; `packages/desktop/src-tauri/tests/session.rs`

### M3.3-E9 — the app's configuration for installers and updates
- **Given** the app's configuration
- **When** it is read
- **Then** the installers are `deb`, `appimage`, `dmg`, and `nsis`; the Windows installer installs for the current user; the macOS signing identity is `-`; the runtime folder is a resource; updater artifacts are made; the updater's endpoint is `https://github.com/ibndeif/kvman/releases/latest/download/latest.json` and it has a public key; the icons it names exist
- Test: `packages/desktop/test/release-rules.test.ts`

### M3.3-E10 — the release workflow builds the installers into a draft
- **Given** `.github/workflows/release.yml`
- **When** it is read
- **Then** it still runs on a version tag only; the npm job is unchanged; a second job runs on four runners (Linux x64, macOS arm64, macOS Intel, Windows x64), each of which prepares the runtime, runs the bundle with no window, and only then builds; the release it writes to is a draft named by the tag; only that job may write contents; the updater's key comes from the two secrets; every action is pinned to a commit
- Test: `packages/cli/test/release-workflow.test.ts`

### M3.3-E11 — the page may ask for the update, and for nothing more
- **Given** the app's capability and build script
- **When** they are read
- **Then** the page's functions are the home screen's four and the update's three (check, install, download), granted to the app's own page only
- Test: `packages/desktop/test/page-rules.test.ts`

### M3.3-E12 — the install page says how to get, pass the warnings of, update, and remove the app
- **Given** the user guide's install page
- **When** it is read
- **Then** it has a desktop section with the four systems' downloads, the macOS and Windows warnings and how to pass each, how the app updates (and the `.deb`'s "Download"), and how to remove it, saying that `~/.kvman` stays
- Test: `packages/cli/test/docs.test.ts`

### M3.3-E13 — the update texts
- **Given** the shell's catalogs
- **When** they are read
- **Then** `en` and `ar` both have the offer with `{version}`, "Install and restart", "Download", and "The update could not be installed."
- Test: `packages/desktop/test/update.test.ts`
