# M1.5 — Async jobs and schedules: test cases

Read: `02` §2.1 (rows, retention), §2.3, §2.4, §2.14 (stop), §2.15; `12` §12.2; ADR 0009 (M1.5: what retries, the settling test clock, `restart()`, cancel, dropped stopping handlers, rows written by the main thread).

Tests run in `packages/testkit/test/` with the fake clock: `await kernel.clock.advance(ms)` fires due retries and schedules and resolves once no job is running or due. `kernel.waitForJob(id)` resolves with the finished `Job`. `kernel.restart()` stops the kernel as Ctrl+C does and starts it again on the same home.

## Happy path

### M1.5-H1 — a failing job retries three times with 1, 2, and 4 s backoff, then ends failed
- **Given** a command that always throws a plain `Error` (default `retries: 3`)
- **When** it is queued with `execAsync`, and the clock advances 999 ms, 1 ms, 2 s, and 4 s
- **Then** attempt 1 runs at once; attempt 2 runs only at 1 s, attempt 3 at 3 s, attempt 4 at 7 s; the job ends `failed` with `HANDLER_FAILED` and `attempts: 4`
- Test: `packages/testkit/test/async/retries.test.ts`

### M1.5-H2 — a cancelled job ends cancelled once its handler returns, and its nested sync job sees the abort
- **Given** a queued command that calls a nested command, which waits for its `ctx.job.signal` to abort and records that it saw it
- **When** the job is cancelled while the nested call waits
- **Then** the job ends `cancelled` after the handler returns, and the nested job recorded the abort
- Test: `packages/testkit/test/async/cancel.test.ts`

### M1.5-H3 — a cron schedule runs at each due time, a missed one runs once, and a key keeps one schedule
- **Given** a command scheduled on `* * * * *` (every minute)
- **When** the clock advances a minute, then another; then the kernel restarts after the clock moved five minutes while stopped; and the same key is scheduled twice
- **Then** a job is queued at each minute; after the restart, the missed run is queued once, not five times; the second schedule with the key replaces the first and keeps its id
- Test: `packages/testkit/test/async/schedules.test.ts`

### M1.5-H4 — failed jobs queue one kernel.job.failed handler job, and handler chains never loop
- **Given** an extension with a `kernel.job.failed` handler that records each call, and whose own handler fails, runs a failing nested job, and queues a failing async job and a failing one-time schedule when asked to
- **When** a sync job fails, an async job fails, and each of the handler's failing paths runs
- **Then** the sync and the async failure each queue exactly one handler job, with the base fields, `problem`, and `attempts`; none of the handler's own failures (nor what it queued) triggers the handler; `kernel.started` handlers ran once per start
- Test: `packages/testkit/test/async/handler-points.test.ts`

### M1.5-H5 — closing mid-job interrupts the attempt; reopening resumes only what should run
- **Given** three commands running: one with retries left, one with `retries: 0`, and a finished one
- **When** the test kernel restarts while the first two run
- **Then** their attempts failed `INTERRUPTED`; after the restart, the first runs again and succeeds, the second has ended `failed` with `INTERRUPTED`, and the finished job never reruns
- Test: `packages/testkit/test/async/resume.test.ts`

### M1.5-H6 — the execAsync benchmark meets its target
- **Given** a no-op command
- **When** `pnpm bench:check` queues and waits for a batch of them
- **Then** throughput is at least 500 jobs/s (`12` §12.3)
- Test: `bench/exec-async.ts` (run by `pnpm bench:check`)

## Edge cases

### Async jobs (`02` §2.1, §2.3, ADR 0009, 14, 17) — `packages/testkit/test/async/*.test.ts`

| Id | Given | Then |
|---|---|---|
| M1.5-E1 | `execAsync` of a query, and `ctx.execAsync`/`ctx.schedule` inside a query | `NOT_A_COMMAND`; `READ_ONLY` (`jobs.test.ts`) |
| M1.5-E2 | five jobs queued in order on one worker with concurrency 1 | they start in the order they were queued (`jobs.test.ts`) |
| M1.5-E3 | an async job | its row has the caller, workspace, `attempts`, `retries`, output, and ISO times; `rootId` inside it equals its id (`jobs.test.ts`) |
| M1.5-E4 | a job whose handler throws `ctx.problem(…)`, and one whose input fails its schema | each ends `failed` after one attempt, without a retry (`retries.test.ts`) |
| M1.5-E5 | a job that times out, and one whose worker crashes | each is retried, then ends `failed` with `TIMEOUT` or `WORKER_CRASHED` (`retries.test.ts`) |
| M1.5-E6 | cancelling a queued job, a finished job, and an unknown id | the queued one ends `cancelled` without running; the finished one is unchanged; the unknown id fails `NOT_FOUND` (`cancel.test.ts`) |
| M1.5-E7 | a running job that ignores its signal, cancelled | ends `cancelled` at its timeout (`cancel.test.ts`) |
| M1.5-E8 | a running sync job, cancelled by another job with `ctx.cancel` | the caller gets `CANCELLED` (`cancel.test.ts`) |
| M1.5-E9 | finished jobs older than `kernel.jobs.retentionDays` | are deleted at start and then hourly; queued and running jobs never are (`retention.test.ts`) |
| M1.5-E10 | a progress chunk over 64 KiB | `ctx.job.progress` fails `TOO_LARGE` with the limit (`jobs.test.ts`) |

### Schedules (`02` §2.4) — `packages/testkit/test/async/schedules.test.ts`

| Id | Given | Then |
|---|---|---|
| M1.5-E11 | a one-time schedule `{ at }` | queues its job when due, in the scheduling job's workspace with the extension as caller, and its row is deleted |
| M1.5-E12 | `schedule.cancel` of a schedule, of another extension's schedule, and of an unknown id | the first is gone; the others fail `NOT_FOUND` |
| M1.5-E13 | an invalid cron expression, and a schedule of a query | `VALIDATION_FAILED`; `NOT_A_COMMAND` |

### Handler points (`02` §2.15) — `packages/testkit/test/async/handler-points.test.ts`

| Id | Given | Then |
|---|---|---|
| M1.5-E14 | an unknown point, and two handlers of one extension for one point | the load fails `EXTENSION_INVALID` |
| M1.5-E15 | an async job that succeeds, and one that is cancelled | queue one `kernel.job.succeeded` and one `kernel.job.cancelled` handler job, with the base fields (and `reason`); a sync success queues none |
| M1.5-E16 | handler jobs | have the caller `{ kind: 'kernel' }`, the job's workspace, and run with the handler's retries |
| M1.5-E17 | `kernel.started` handlers of `a` and of `b`, which depends on `a` | run once per start, `a`'s before `b`'s, before the kernel is ready; one that fails is logged, and the kernel still starts |
| M1.5-E18 | `kernel.stopping` handlers | run at the start of shutdown, before running jobs are aborted; one still running at the end of shutdown ends `failed` with `INTERRUPTED` and doesn't run again (ADR 0009, 18) |
