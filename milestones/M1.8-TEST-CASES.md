# M1.8 — Lifecycle and minimal adapters: test cases

Read: `03` §3.8 (health, shutdown, started), §3.9–§3.10, `12` §12.1–§12.3, §12.5, §12.8–§12.9, `13` §13.1–§13.3, `00` R-Q4; ADRs 0066 (late HTTP caller moved here), 0073 (Pino behind the kernel logger), 0087 (daemon entry and start report), 0088 (lock: bind first, a live owner is a conflict, `processStart`), 0089 (boot scope), 0090 (`kvman stop`, `kernel.shutdown`, requests during shutdown), 0091 (interrupted attempts), 0092 (degraded health), 0093 (log rotation), 0094 (HTTP replies and statuses), 0095 (`NOT_FOUND`, `PORT_UNAVAILABLE`), 0096 (CLI output), 0097 (`--port`), 0098 (event stream rules), 0099 (kernel types need no workspace).

Where the tests live:

- **Real daemons** started through the `kvman` CLI: `packages/cli/test/`. Their registry holds only the kernel types (ADR 0089).
- **An in-process kernel** booted with `bootKernel` in a temporary home folder, with the M1.6 fixture extensions on real worker threads, a manual kernel clock, and a real HTTP listener: `packages/testkit/test/daemon/` and `packages/testkit/test/adapters/`.
- **Pure kernel pieces** (home check, lock, ports, log file, status table, stream writer): `packages/kernel/test/daemon/` and `packages/kernel/test/adapters/`.
- **Protocol shapes**: `packages/protocol/test/`.

"A person" is `user:local`. "The served origin" is `http://127.0.0.1:<port>`.

## Happy path

### M1.8-H1 — a second kvman start fails DAEMON_CONFLICT
- **Given** `kvman start --home A` has returned and its daemon runs
- **When** `kvman start --home A` runs again
- **Then** it prints `DAEMON_CONFLICT: Another kernel owns this home folder` on stderr and exits 1, and the first daemon still answers `/health` with the same `instanceId`
- Test: `packages/cli/test/lifecycle.test.ts`

### M1.8-H2 — a stale lock is taken over
- **Given** home A's `daemon.lock` names a PID that has exited
- **When** `kvman start --home A` runs
- **Then** it prints `kvman is running at http://127.0.0.1:<port> (home A)`, and the lock holds the new daemon's PID, `processStart`, and nonce
- Test: `packages/cli/test/lifecycle.test.ts`

### M1.8-H3 — a home folder with other files and no kvman.db is refused HOME_INVALID
- **Given** home A holds `notes.txt` and no `kvman.db`
- **When** `kvman start --home A` runs
- **Then** it prints `HOME_INVALID: The home folder holds other files` on stderr and exits 1; A still holds only `notes.txt` (no lock, no database, no `logs/`)
- Test: `packages/cli/test/lifecycle.test.ts`

### M1.8-H4 — kvman start returns once /health answers while the daemon keeps running
- **When** `kvman start --home A` runs in a missing folder A
- **Then** the CLI exits 0 after printing the running line; afterwards `GET /api/v1/health` on the lock's port answers `{ status: 'ok', version, instanceId, processStart, uptimeMs, port, home: A }`, where `instanceId` and `processStart` equal the lock's `nonce` and `processStart`; `kvman status --home A` prints that JSON and exits 0
- Test: `packages/cli/test/lifecycle.test.ts`

### M1.8-H5 — a command still running after wait answers 202 and its reply arrives on the stream
- **Given** a browser stream S is open with client C
- **When** the person posts `notes.relay { id: 'h5' }` (it waits in a `ctx.command` for `notes.ask`) with `wait: 1000`, `X-Kvman-Stream: S`, and `X-Kvman-Client: C`, the kernel clock passes 1 s, and then the person answers the question
- **Then** the POST answers `202 { id, state: 'running' }`; after the answer, stream S receives exactly one `reply { clientId: C, id, ok: true, data: { answer } }`
- Test: `packages/testkit/test/adapters/commands.test.ts`

### M1.8-H6 — a reconnect with Last-Event-ID replays missed events
- **Given** stream S subscribed with sid `n` to `notes.*`, received the durable `notes.added` with `id: <seq1>`, and then disconnected
- **When** two more `notes.added` events commit, and S reconnects with the header `Last-Event-ID: <seq1>`
- **Then** `hello.subscriptions` is `['n']`, and S receives both missed events in seq order as `event { sid: 'n', seq, event }` with `id: <seq>` lines, and nothing before `seq1`
- Test: `packages/testkit/test/adapters/events.test.ts`

### M1.8-H7 — a request with a foreign Host gets 403
- **When** a request reaches the kernel with `Host: evil.example:<port>` (DNS rebinding)
- **Then** it answers 403 with the Problem `HOST_FORBIDDEN`, for `GET /health`, `POST /commands/:type`, and `GET /events` alike
- Test: `packages/testkit/test/adapters/edge.test.ts`

### M1.8-H8 — a reply reaches a caller whose request already ended, through GET /messages/:id
- **Given** the person posted `notes.relay { id: 'h8' }` with `wait: 0` and no stream header, and got `202 { id, state: 'pending' }`
- **When** the question is answered and the relay finishes
- **Then** `GET /api/v1/messages/<id>` answers `{ id, type: 'notes.relay', state: 'done', reply: { answer } }`
- Test: `packages/testkit/test/adapters/messages.test.ts`

### M1.8-H9 — a second kernel in another home starts on the next free port, and the CLI finds each through its lock
- **When** `kvman start --home A` and then `kvman start --home B` run
- **Then** the two daemons run on different ports in 4173–4199 (other test files hold ports too, so the exact numbers vary; the order of the range is M1.8-E14); `kvman status --home A` and `--home B` each print the health of their own daemon (their own `home`, `port`, and `instanceId`, equal to their locks)
- Test: `packages/cli/test/lifecycle.test.ts`

### M1.8-H10 — a POST with a foreign Origin fails HOST_FORBIDDEN while a POST without Origin succeeds
- **When** the person posts `kernel.cancel { messageId }` once with `Origin: https://evil.example` and once with no `Origin`
- **Then** the first answers 403 `HOST_FORBIDDEN` (M1.8-E46 shows that nothing is stored); the second answers `200 { id, reply: { cancelled: 0 } }`
- Test: `packages/cli/test/lifecycle.test.ts`

## Edge cases

**Home folder (`03` §3.9 step 0, R-Q4, ADR 0089)**

### M1.8-E1 — a missing home folder is created with mode 0700
- **When** the kernel boots in a folder that does not exist
- **Then** the folder exists with mode 0700 and holds `kvman.db`, `daemon.lock` (0600), and `logs/`
- Test: `packages/kernel/test/daemon/home-folder.test.ts`

### M1.8-E2 — an empty home folder is initialized
- **Given** an existing empty folder with mode 0755
- **When** the home is checked
- **Then** it is accepted, and its mode becomes 0700
- Test: `packages/kernel/test/daemon/home-folder.test.ts`

### M1.8-E3 — a folder with only daemon.lock and logs/ is accepted
- **Given** a folder holding `daemon.lock` and a `logs/` folder, and no `kvman.db`
- **Then** the check accepts it; the same folder with a file named `logs` instead of a folder is refused `HOME_INVALID`
- Test: `packages/kernel/test/daemon/home-folder.test.ts`

### M1.8-E4 — a folder with kvman.db may hold anything else
- **Given** a folder with `kvman.db` and other files
- **Then** the check accepts it and leaves it unchanged
- Test: `packages/kernel/test/daemon/home-folder.test.ts`

### M1.8-E5 — a home path that is a file is refused HOME_INVALID
- **Then** the check fails `HOME_INVALID` and the file is unchanged
- Test: `packages/kernel/test/daemon/home-folder.test.ts`

### M1.8-E6 — the home is --home, else KVMAN_HOME, else ~/.kvman
- **When** `kvman status` runs with `--home X` and `KVMAN_HOME=Y`, then with only `KVMAN_HOME=Y`, then with neither (`HOME=Z`)
- **Then** each run reports the daemon started in X, Y, and `Z/.kvman` respectively, and a relative `--home` is resolved from the current directory
- Test: `packages/cli/test/home.test.ts`

### M1.8-E7 — a newer database schema refuses to start with SCHEMA_TOO_NEW
- **Given** a home whose `kvman.db` records a kernel schema version newer than the code
- **When** the kernel boots
- **Then** boot fails `SCHEMA_TOO_NEW`, the lock is released, the port is closed, and the database is unchanged
- Test: `packages/testkit/test/daemon/boot.test.ts`

**Lock and ports (`03` §3.10, `12` §12.5, ADRs 0088, 0095, 0097)**

### M1.8-E8 — the lock record
- **Then** the lock is a 0600 file `{ pid, processStart, nonce, port, startedAt }` that parses with `daemonLockSchema`; `processStart` equals `ps -o lstart= -p <pid>` read with `LC_ALL=C`; `nonce` is a UUID v4
- Test: `packages/kernel/test/daemon/daemon-lock.test.ts`

### M1.8-E9 — a live owner is a conflict, whether or not it answers
- **Given** a lock naming this test process with its real `processStart` and a port where nothing listens
- **When** the lock is acquired
- **Then** it fails `DAEMON_CONFLICT` and the lock is unchanged
- Test: `packages/kernel/test/daemon/daemon-lock.test.ts`

### M1.8-E10 — a reused PID with another start time is stale
- **Given** a lock naming this test process's PID with a different `processStart`
- **Then** acquiring takes it over and writes the new record
- Test: `packages/kernel/test/daemon/daemon-lock.test.ts`

### M1.8-E11 — a lock that does not parse is stale
- **Given** a `daemon.lock` holding `not json`
- **Then** acquiring takes it over
- Test: `packages/kernel/test/daemon/daemon-lock.test.ts`

### M1.8-E12 — release removes only its own lock
- **Given** a lock was acquired, and the file was then replaced by a record with another nonce
- **When** the first holder releases
- **Then** the other record stays; releasing a lock whose nonce matches removes the file
- Test: `packages/kernel/test/daemon/daemon-lock.test.ts`

### M1.8-E13 — two starts at once on one home: exactly one runs
- **When** two `kvman start --home A` run at the same time
- **Then** exactly one exits 0 with the running line and the other exits 1 with `DAEMON_CONFLICT`; one daemon runs and the lock names it
- Test: `packages/cli/test/lifecycle.test.ts`

### M1.8-E14 — the port is the first free one in the range
- **Given** a range of two ports whose first is taken by another server
- **When** the kernel binds in that range
- **Then** it binds the second; with both taken it fails `PORT_UNAVAILABLE` with `{ from, to }`
- Test: `packages/kernel/test/daemon/port-binding.test.ts`

### M1.8-E15 — --port binds exactly that port, without fallback
- **When** `kvman start --home A --port P` runs with P free, and `kvman start --home B --port P` runs while A holds P
- **Then** A runs on P; B prints `PORT_UNAVAILABLE: No port is free for the kernel` and exits 1, and B's home has no lock
- Test: `packages/cli/test/lifecycle.test.ts`

**Boot and recovery (`03` §3.9, ADRs 0089, 0091)**

### M1.8-E16 — a running row after a crash redelivers with attempts + 1
- **Given** `notes.edit.slow { id: 'e16' }` is running when the kernel stops without a shutdown (a crash)

- **Then** the row is `pending` with `attempts` 1, and it is claimed again at once

### M1.8-E17 — a crashed row at maxAttempts becomes dead
- **Given** `counter.hang` (`maxAttempts: 1`) is running when the kernel crashes

### M1.8-E18 — recovery keeps lane order
- **Given** `notes.edit.slow { id: 'lane' }` A is running and a second one B waits in the same lane when the kernel crashes

### M1.8-E19 — boot ends with kernel.started and kvman.version

### M1.8-E20 — requests wait until boot finishes
- **Given** the port is bound and the lock written, and boot has not finished

**Shutdown (`03` §3.9, ADRs 0090, 0091)**

### M1.8-E21 — kvman stop stops the daemon through kernel.shutdown
- **When** `kvman stop --home A` runs against a running daemon
- **Then** it prints `kvman stopped` and exits 0; the daemon process has exited and the lock is gone; `kvman status --home A` then prints `kvman is not running` and exits 1, and `kvman stop --home A` prints `kvman is not running` and exits 0
- Test: `packages/cli/test/lifecycle.test.ts`

### M1.8-E22 — SIGTERM shuts a foreground daemon down, repeated signals are harmless
- **When** `kvman start --foreground --home A` runs, `/health` answers, and SIGTERM is sent twice to the daemon
- **Then** the daemon exits 0 once, the lock is gone, and the CLI exits 0; the foreground stdout carried the kernel's JSON log lines
- Test: `packages/cli/test/lifecycle.test.ts`

### M1.8-E70 — kernel.shutdown answers {} and then shuts the kernel down
- **When** the person posts `kernel.shutdown {}`
- **Then** it answers `200 { id, reply: {} }`, the kernel shuts down (its lock is released), and the stored message is `done` with the reply `{}`
- Test: `packages/testkit/test/daemon/shutdown.test.ts`

### M1.8-E23 — an invocation that finishes within 10 s commits
- **Given** `notes.nap { ms: 200 }` is running
- **When** shutdown starts
- **Then** it finishes and commits (`done`) before the database closes
- Test: `packages/testkit/test/daemon/shutdown.test.ts`

### M1.8-E24 — an invocation still running after 10 s returns to pending without an attempt
- **Given** `notes.cancel.probe` has published a live chunk and holds on its signal
- **When** shutdown starts and the kernel clock passes 10 s
- **Then** its live address receives `{ reset: true }` for its run, its row is `pending` with `attempts` 0, and after the next boot it runs again
- Test: `packages/testkit/test/daemon/shutdown.test.ts`

### M1.8-E25 — a request during shutdown gets KERNEL_STOPPING; /health still answers
- **Given** shutdown has started and waits for a running handler
- **When** a command, a query, and a subscription are posted, and `GET /health` is asked
- **Then** the first three answer 503 `KERNEL_STOPPING` (retryable) and `/health` answers 200 (the listener stays open until the end of shutdown)

### M1.8-E26 — a request waiting for a reply answers 202 at close, and streams get close shutdown
- **Given** a POST of `notes.relay` is waiting for its reply, and stream S is open

### M1.8-E27 — kernel.shutdown is for people only
