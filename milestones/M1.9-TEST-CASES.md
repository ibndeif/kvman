# M1.9 — Fault injection, model tests, benchmarks: test cases

Read: `14` §14.2–§14.3, §14.6; ADRs 0001 (throughput spike), 0091 (interrupted attempts), 0100 (fault points), 0101 (live previews after a kernel crash), 0102 (the model test), 0103 (the benchmark baseline), 0104 (benchmark scope and method), 0105 (durable command latency and throughput).

Where the tests live:

- **Fault harness**: `packages/testkit/test/faults/`. A child-process kernel (`Kernel.boot` in a temporary home, the `@acme/ledger` fixture extension on a shared host, real clock and timers) is started with `KVMAN_FAULTS`. It dies at the point, and the harness restarts it on the same home without the variable. It then replays the workload as a client that retries with its idempotency keys, lets everything settle, stops the kernel, and checks the invariants in the database file.
- **Model test**: `packages/kernel/test/model/`.
- **Benchmarks**: the runner in `packages/testkit/bench/`, checked by the gate `pnpm bench:check`; its pure rules in `packages/testkit/test/bench/`.
- **Protocol shapes**: `packages/protocol/test/`.
- **Pure kernel pieces**: `packages/kernel/test/faults/`.

**The ledger workload.** It runs in phases, and each phase waits for its replies. Its commands send `wait: 5000`.

1. **Posts.** `ledger.post { account, n }` for accounts `a`, `b`, `c` and n = 1…4, in lane `account:{{ $payload.account }}`, sent in n order per account, with the accounts in parallel. Each post:
   - adds 1 to kv `balance:<account>`;
   - appends `{ account, n, messageId }` to its account's log `postings:<account>`;
   - sends `ledger.audit.record`;
   - publishes the durable `ledger.posted`.
2. **Transfer.** `ledger.transfer { id }` calls `ctx.command('ledger.post', { account: 't', n: 1 })`.
3. **Charge.** `ledger.charge { id }` runs `ctx.step('charge', …)`, which is not retry-safe.
4. **Refund.** `ledger.refund { id }` runs `ctx.step('refund', …, { retrySafe: true })`.
5. **Hold and release.** `ledger.hold { id }` defers. Once it answers 202, `ledger.release { holdId }` replies `{ released: true }` to it.
6. **Stream.** `ledger.stream { id }` publishes one live chunk on `ledger.progress.streamed:<id>`, stamped with a token its worker drew at start, then returns.

**The invariants** of `14` §14.3 that M1 reaches (ADR 0100), checked after the settled replay:

- **(1)** Each account's `balance` equals its done posts and its postings entries, and each post's message id appears exactly once in the postings logs.
- **(2)** Every command is in exactly one final state with one stored reply, and the replies the client received equal the stored ones.
- **(3)** Each done post has exactly one `ledger.audit.record` (key `<post>:send:0`) and one `ledger.posted` event, and the transfer's post exists once (key `<transfer>:command:1`).
- **(4)** Per account, `postings:<account>` lists n = 1…4 in order, and the posts' `seq` follows n.
- **(6)** A step that started without recording fails its command with `EFFECT_INDETERMINATE` unless it is retry-safe.
- **(8)** Checked at the live point as ADR 0101 states it.

"The kernel died at the point" means the child exited by `SIGKILL` and nothing else sends that signal.

## Happy path

### M1.9-H1 — admit.before-commit: the admitted command is lost with the crash and stored once by the client's retry
- **Given** a ledger kernel with `KVMAN_FAULTS=admit.before-commit`
- **When** the workload's first post is admitted and the kernel dies at the point
- **Then** the database file holds no row for that post. After the restart, the replayed workload stores it once, and invariants 1, 2, 3, 4, and 6 hold.
- Test: `packages/testkit/test/faults/admission.test.ts`

### M1.9-H2 — admit.after-commit: the stored command is not stored twice when its client retries
- **Given** a ledger kernel with `KVMAN_FAULTS=admit.after-commit`
- **When** the first batch of posts commits and the kernel dies before answering (group commit may store the three lanes' first posts together)
- **Then** the file holds every post of that batch as `running`: they were claimed in the transaction that stored them (ADR 0105). After the restart, each client's retry answers with the same message id, each post runs once, with the crash counted (`attempts` 1, ADR 0091), 13 posts exist in all, and invariants 1, 2, 3, 4, and 6 hold.
- Test: `packages/testkit/test/faults/admission.test.ts`

### M1.9-H3 — claim.after: a claimed message is recovered and runs once
- **Given** a ledger kernel with `KVMAN_FAULTS=claim.after@3`
- **When** the kernel dies after its third claim
- **Then** the file holds that message as `running` with no `postings` entry. After the restart it is done with `attempts` 1, and invariants 1, 2, 3, 4, and 6 hold.
- Test: `packages/testkit/test/faults/scheduling.test.ts`

### M1.9-H4 — invoke.before: a message that never reached its host is recovered and runs once
- **Given** a ledger kernel with `KVMAN_FAULTS=invoke.before@5`
- **When** the kernel dies before its fifth invoke frame
- **Then** that message is `running` in the file and its handler never ran. After the restart it is done with `attempts` 1, and invariants 1, 2, 3, 4, and 6 hold.
- Test: `packages/testkit/test/faults/scheduling.test.ts`

### M1.9-H5 — step.after-begin: a started step that is not retry-safe surfaces EFFECT_INDETERMINATE
- **Given** a ledger kernel with `KVMAN_FAULTS=step.after-begin`
- **When** the charge's step row is committed as `started` and the kernel dies
- **Then** the file holds the step as `started`. After the restart, the charge fails with `EFFECT_INDETERMINATE` (params `{ step: 'charge' }`), and invariants 1, 2, 3, 4, and 6 hold.
- Test: `packages/testkit/test/faults/steps.test.ts`

### M1.9-H6 — step.before-record: an effect that ran without its record surfaces EFFECT_INDETERMINATE
- **Given** a ledger kernel with `KVMAN_FAULTS=step.before-record`
- **When** the charge's effect ran and the kernel dies before the `done` row
- **Then** the file holds the step as `started`. After the restart, the charge fails with `EFFECT_INDETERMINATE`, and invariants 1, 2, 3, 4, and 6 hold.
- Test: `packages/testkit/test/faults/steps.test.ts`

### M1.9-H7 — command.after-send: a redelivered caller re-awaits its stored command
- **Given** a ledger kernel with `KVMAN_FAULTS=command.after-send`
- **When** the transfer's `ctx.command` committed its post and the kernel dies
- **Then** the file holds that post under key `<transfer>:command:1`. After the restart, the transfer is done with the post's reply, exactly one post for account `t` exists, and invariants 1, 2, 3, 4, and 6 hold.
- Test: `packages/testkit/test/faults/calls.test.ts`

### M1.9-H8 — uow.before-commit: a unit of work that did not commit leaves no trace and commits once on redelivery
- **Given** a ledger kernel with `KVMAN_FAULTS=uow.before-commit@2`
- **When** the second handler unit is applied and the kernel dies before `COMMIT`
- **Then** the file holds none of that unit's writes, sends, or events, and its message is `running`. After the restart it commits once, and invariants 1, 2, 3, 4, and 6 hold.
- Test: `packages/testkit/test/faults/units.test.ts`

### M1.9-H9 — uow.after-commit-before-notify: a committed unit is kept and its client gets the stored reply
- **Given** a ledger kernel with `KVMAN_FAULTS=uow.after-commit-before-notify@2`
- **When** the second handler unit commits and the kernel dies before telling anyone
- **Then** the file holds that message as `done` with its writes. After the restart, it does not run again, the client's retry answers its stored reply, and invariants 1, 2, 3, 4, and 6 hold.
- Test: `packages/testkit/test/faults/units.test.ts`

### M1.9-H10 — defer.before-reply: a deferred command is answered exactly once after the crash
- **Given** a ledger kernel with `KVMAN_FAULTS=defer.before-reply`
- **When** the release's unit replying to the hold is applied and the kernel dies before `COMMIT`
- **Then** the file holds the hold as `awaiting`. After the restart, the release runs again and the hold is done with `{ released: true }` as its one reply, and invariants 1, 2, 3, 4, and 6 hold.
- Test: `packages/testkit/test/faults/calls.test.ts`

### M1.9-H11 — live.after-publish-before-commit: no chunk of the dead attempt survives the restart
- **Given** a ledger kernel with `KVMAN_FAULTS=live.after-publish-before-commit`, and a stream S subscribed to `ledger.progress.streamed:<id>`
- **When** the stream's handler publishes its chunk and the kernel dies
- **Then** after the restart, S reconnects and gets a `hello` that lists no subscription. Re-subscribing yields a ring holding only chunks of the retried attempt: the same `run`, starting at n = 1, stamped with the new worker's token. Invariants 1, 2, 3, 4, and 6 hold.
- Test: `packages/testkit/test/faults/live.test.ts`

### M1.9-H12 — the model test runs 1,000 sequences clean
- **Given** the reference model of ADR 0102 and the kernel's scheduling core on a real SQLite file
- **When** fast-check runs 1,000 random sequences of sends (with and without lanes, with and without `onReply`), results, retryable and final failures, deferrals and replies, cancels, time moves, and crashes with restarts
- **Then** after every step, the kernel's claims, states, replies, and continuations agree with the model
- Test: `packages/kernel/test/model/lanes-and-replies.test.ts`

### M1.9-H13 — the stored baseline holds every M1.9 benchmark and meets its targets
- **Given** `bench/baseline.json`
- **When** it is read and validated
- **Then** it describes the machine. It holds `p50Ms` and `p99Ms` for `command.round-trip`, `query.indexed`, and `live.latency`, and `perSecond` for `command.sustained`. Every value meets its target, as ADRs 0104 and 0105 set them.
- Test: `packages/testkit/test/bench/baseline.test.ts`

## Edge cases

**Fault settings (ADR 0100)**

### M1.9-E1 — every point of 14 §14.3 is a valid setting, with or without a hit
- **When** `faultSettingSchema` parses each of the 24 names, and `uow.before-commit@3`
- **Then** each parses to `{ point, hit: 1 }`, and the second to `{ point: 'uow.before-commit', hit: 3 }`
- Test: `packages/protocol/test/faults.test.ts`

### M1.9-E2 — malformed settings are refused
- **When** `faultSettingSchema` parses each of these settings:
  - `uow.before-commits`;
  - `claim.after@0`;
  - `claim.after@x`;
  - `claim.after@`;
  - `claim.after,invoke.before`;
  - `@2`.
- **Then** each fails
- Test: `packages/protocol/test/faults.test.ts`

### M1.9-E3 — an unknown fault point refuses the daemon's start with VALIDATION_FAILED
- **Given** `KVMAN_FAULTS=uow.before-commits`
- **When** `kvman start --home A` runs
- **Then** it prints `VALIDATION_FAILED: The request does not match its schema` on stderr, then a hint that names `KVMAN_FAULTS` and lists the known points, and exits 1. The start report's Problem has the issue path `KVMAN_FAULTS`. Home A is not created: the setting is checked before the home.
- Test: `packages/cli/test/faults.test.ts`

### M1.9-E4 — only the named point's n-th hit kills, and it kills once
- **Given** active fault points for `uow.before-commit@3` with a recording kill function
- **When** these are reached, in order:
  - `admit.before-commit` three times;
  - `uow.before-commit` twice;
  - `uow.before-commit` a third time;
  - `uow.before-commit` a fourth time.
- **Then** the kill function ran exactly once, at the third `uow.before-commit`. The inert fault points never kill.
- Test: `packages/kernel/test/faults/fault-points.test.ts`

**Crash harness (`14` §14.2–§14.3, ADRs 0091, 0100)**

### M1.9-E5 — step.after-begin in a retry-safe step runs the step again
- **Given** a ledger kernel with `KVMAN_FAULTS=step.after-begin@2`, so the kernel dies in the refund's step
- **When** the kernel restarts
- **Then** the refund's step runs again and records `done`, the refund is done, and invariants 1, 2, 3, 4, and 6 hold
- Test: `packages/testkit/test/faults/steps.test.ts`

### M1.9-E6 — a message that kills the kernel on every attempt ends dead after maxAttempts crashes
- **Given** `ledger.fragile` (`maxAttempts: 2`) is pending, and the kernel starts with `KVMAN_FAULTS=invoke.before`
- **When** the kernel dies invoking it, restarts with the same setting and dies again, then restarts without it
- **Then** after the second restart the message is `dead`: `attempts` 2, reply `MESSAGE_DEAD`, and `kernel.message.dead-lettered` published for it (ADR 0091). It never ran.
- Test: `packages/testkit/test/faults/scheduling.test.ts`

### M1.9-E7 — a crash mid-lane keeps the lane's later posts behind the recovered one
- **Given** a ledger kernel with `KVMAN_FAULTS=uow.before-commit`, and account `a`'s posts 1–4 queued at once with `wait: 0` before the usual phases
- **When** post a-1's unit is applied and the kernel dies before `COMMIT`
- **Then** the file holds a-1 as `running` and a-2…a-4 as `pending`. After the restart, a-1 is done with `attempts` 1, `postings:a` lists a-1…a-4 in that order, and invariants 1, 2, 3, 4, and 6 hold.
- Test: `packages/testkit/test/faults/units.test.ts`

**Benchmark rules (ADRs 0103, 0104)**

### M1.9-E8 — a metric more than 20% worse than its baseline fails, and exactly 20% passes
- **Given** baseline `p99Ms` 10 and `perSecond` 5,000
- **When** checks compare `p99Ms` 12.01 and 12, and `perSecond` 3,999 and 4,000
- **Then** 12.01 and 3,999 are regressions, and 12 and 4,000 pass. Lower is better for `Ms` metrics and higher is better for `perSecond`.
- Test: `packages/testkit/test/bench/comparison.test.ts`

### M1.9-E9 — a metric that misses its target fails even within 20% of its baseline
- **Given** baseline `command.round-trip.p50Ms` 9.5 (the M1.9 target is ≤ 10 ms, ADR 0105)
- **When** a check measures 10.2
- **Then** the check fails, naming the target 10
- Test: `packages/testkit/test/bench/comparison.test.ts`

### M1.9-E10 — a benchmark or metric without a baseline value fails
- **Given** a baseline without `live.latency`, and one without `query.indexed.p99Ms`
- **When** checks run against complete results
- **Then** each fails, naming what is missing
- Test: `packages/testkit/test/bench/comparison.test.ts`

### M1.9-E11 — a metric is the median of its 5 rounds
- **Given** 5 rounds with `p99Ms` 3, 3.1, 40, 2.9, 3
- **When** the value is taken
- **Then** it is 3: one slow round does not move it
- Test: `packages/testkit/test/bench/comparison.test.ts`

### M1.9-E12 — recording refuses to write a baseline that misses a target
- **Given** results where `command.sustained.perSecond` is 900 (the M1.9 target is ≥ 1,000/s, ADR 0105)
- **When** a baseline is recorded from them
- **Then** nothing is written, and the refusal names the metric and its target
- Test: `packages/testkit/test/bench/comparison.test.ts`

### M1.9-E13 — a malformed baseline file is refused with its path
- **When** the baseline has `command.round-trip.p50Ms: "fast"`
- **Then** reading it fails with the issue path `benchmarks["command.round-trip"].p50Ms`
- Test: `packages/testkit/test/bench/baseline.test.ts`
