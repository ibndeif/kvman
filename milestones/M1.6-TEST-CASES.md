# M1.6 — Shared hosts and `ctx` messaging: test cases

Read: `03` §3.2, §3.5 (shared pool, host protocol, handler rules), `02` §2.3, §2.5, §2.8, `05` §5.4, §5.9, §5.12; ADRs 0060 (host interface), 0062 (stored dead replies), 0063 (lanes held by running messages), 0066 (scope), 0067 (worker loss), 0068 (live subscriptions), 0069 (transient deliveries), 0070 (recorded ids and times, schema 2), 0071 (pool and loading), 0072 (`ctx.command`), 0073 (`ctx.log`), 0074 (misuse codes, schema checks), 0075 (`ctx.workspace`), 0076 (frames, bad frames, closed `ctx`, event inputs).

Host tests that run extension code live in `packages/testkit/test/hosts/` (the kernel's tests may use `@kvman/sdk` for types only, so fixture extensions live where the SDK may be imported, as the M1.3 recording tests do). They run the real kernel runtime (router, commit pipeline, pending index, scheduler, host manager, live bus) on a real database file, with real worker threads that import fixture extensions from `packages/testkit/test/hosts/fixtures/extensions/`. The live bus, the pool with fake threads, and bad frames are tested in `packages/kernel/test/hosts/`. The fixtures are recorded into manifests with `recordExtension` and given to the registry; their entry paths are given to the host manager as data (ADR 0071). Scheduler timers are manual, so retry backoffs are advanced by the test. The pool tests use fake threads. "A person" is `user:local`.

## Happy path

### M1.6-H1 — a command runs in a shared worker and its reply is stored
- **Given** the `notes` fixture enabled in workspace A
- **When** a person sends `notes.add { text: 'hi' }`
- **Then** the handler runs in a worker thread (not the main thread), writes its document, and returns `{ id }`; the message row is `done` with the reply `{ ok: true, value: { id } }`, and awaiting the reply of the submission returns it
- Test: `packages/testkit/test/hosts/commands.test.ts`

### M1.6-H2 — a query answers with data and stores nothing
- **Given** a stored note
- **When** a person asks `notes.list {}`
- **Then** the answer holds the note, and no message row exists for the query
- Test: `packages/testkit/test/hosts/queries.test.ts`

### M1.6-H3 — a durable event reaches its subscriber through an inbox row
- **Given** `notes` publishes the durable `notes.added` from `notes.add`, and the `audit` fixture subscribes to it with a grant
- **When** `notes.add` commits
- **Then** the event is in the events log and `audit`'s delivery row runs its handler, which writes the note id to its own store; the row is `done`
- Test: `packages/testkit/test/hosts/events.test.ts`

### M1.6-H4 — a transient event reaches its subscriber without a row
- **Given** `notes` publishes the transient `notes.touched`, and `audit` subscribes to it
- **When** `notes.touch` commits
- **Then** `audit`'s handler runs with the payload, and no message row or events-log row exists for the event or its delivery
- Test: `packages/testkit/test/hosts/events.test.ts`

### M1.6-H5 — `ctx.command` waits for another command's result
- **Given** `notes.summarize` calls `ctx.command('counter.increment', { by: 2 })` of the granted `counter` fixture
- **When** a person sends `notes.summarize`
- **Then** the handler receives `{ total: 2 }` and returns it; the child command row is caused by the parent, has the key `<parentId>:command:1`, and is `done`
- Test: `packages/testkit/test/hosts/request-reply.test.ts`

### M1.6-H6 — a continuation delivers a reply as a new command
- **Given** `notes.archive` sends `counter.increment` with `onReply: { type: 'notes.archive.record', context: { note: 'n1' } }`
- **When** the send commits and `counter.increment` finishes
- **Then** `notes.archive.record` runs with `{ reply: { ok: true, value: { total: 1 } }, context: { note: 'n1' } }`, sent by the kernel with the key `<counterCommandId>:reply`
- Test: `packages/testkit/test/hosts/request-reply.test.ts`

### M1.6-H7 — a deferred reply completes a command; a second reply fails
- **Given** `notes.ask` stores a question and returns `ctx.defer({ onAbort: 'notes.question.expire' })`
- **When** a person answers with `notes.question.answer`, which calls `ctx.reply(askId, { answer: 'yes' })`, and then a second `notes.question.answer` replies again
- **Then** `notes.ask` is `awaiting` with `on_abort` stored until the first answer commits, then `done` with `{ answer: 'yes' }`, and a waiter on its reply gets it; the second answer's unit rolls back (its write is not stored) and its message fails `REPLY_NOT_AWAITING`, not retried
- Test: `packages/testkit/test/hosts/deferred.test.ts`

### M1.6-H8 — a query cannot write
- **Given** the query `notes.list.touch`, which writes its store
- **When** a person asks it
- **Then** the answer is `CAPABILITY_DENIED` and nothing is stored
- Test: `packages/testkit/test/hosts/queries.test.ts`

### M1.6-H9 — `ctx.ids.new()` and `ctx.now()` repeat on redelivery
- **Given** `notes.stamp` calls `ctx.ids.new()` and `ctx.now()` twice each, passes them to a step, then fails with a retryable problem on its first attempt
- **When** the backoff passes and the message is redelivered
- **Then** the second attempt gets the same two ids and the same two times, in the same order, and `recorded_values` holds them numbered 1 and 2
- Test: `packages/testkit/test/hosts/recorded-values.test.ts`

### M1.6-H10 — a live event of another extension cannot be published
- **Given** `counter` registers the live event `counter.progress.updated`
- **When** a `notes` handler calls `ctx.live('counter.progress.updated', 'k', { value: 0.5 })`
- **Then** the call throws `CAPABILITY_DENIED`, and nothing reaches the live bus
- Test: `packages/testkit/test/hosts/live.test.ts`

### M1.6-H11 — a subscription to its own live event fails recording
- **Given** an extension that registers the live event `demo.tokens.generated` and subscribes to it
- **When** it is recorded
- **Then** recording fails `EXT_MANIFEST_INVALID` with an issue at `subscriptions.0.event`
- Test: `packages/testkit/test/recording/live-subscriptions.test.ts`

### M1.6-H12 — a crashed attempt's live events are reset before the retry publishes again
- **Given** `notes.stream` publishes two text chunks on `notes.text.streamed:a` and one on `notes.text.streamed:b`, then its first attempt kills its worker
- **When** the attempt is retried
- **Then** each of the two addresses gets `{ reset: true }` with `run` = the message id before any chunk of the second attempt, whose chunks carry the same `run`
- Test: `packages/testkit/test/hosts/live-resets.test.ts`

### M1.6-H13 — a reset never removes another run's chunks
- **Given** runs `r1` and `r2` each published chunks on `notes.text.streamed:a`
- **When** `r1` is reset
- **Then** the ring for that address keeps every chunk of `r2`, drops `r1`'s, and ends with the reset chunk for `r1`; chunk numbers keep increasing
- Test: `packages/kernel/test/hosts/live-bus.test.ts`

### M1.6-H14 — a stored reply reaches `ctx.command` and a continuation
- **Given** `counter.fail` fails with the registered non-retryable `counter/NEGATIVE`
- **When** one `notes` handler awaits it with `ctx.command` and another sends it with `onReply`
- **Then** the stored reply of each `counter.fail` row is `{ ok: false, problem }` with code `counter/NEGATIVE`; `ctx.command` rejects with a ProblemError carrying that same problem, and the continuation receives it as `reply`
- Test: `packages/testkit/test/hosts/request-reply.test.ts`

## Edge cases

### M1.6-E1 — the handler's input is parsed with its full Zod schema
- **Given** `notes.add` has `text: z.string().refine(…)` rejecting `'forbidden'` and `tags: z.array(z.string()).default([])`
- **When** a person sends `{ text: 'forbidden' }`, then `{ text: 'ok' }`
- **Then** the first passes the kernel's JSON Schema check but fails `VALIDATION_FAILED` in the host, not retried (`attempts` 1, state `failed`); the second handler receives `tags: []`
- Test: `packages/testkit/test/hosts/commands.test.ts`

### M1.6-E2 — a result that fails the output schema
- **When** `notes.broken` returns `{ id: 42 }` against `output: { id: string }`
- **Then** the message fails `VALIDATION_FAILED`, not retried, and its writes are not stored
- Test: `packages/testkit/test/hosts/commands.test.ts`

### M1.6-E3 — a registered problem takes its definition
- **When** `counter.fail` throws `ctx.problem('counter/NEGATIVE', { params: { by: -1 }, detail: 'below zero' })`
- **Then** the stored problem has the registered title and hint, `retryable: false`, the params and detail, the correlation id, and the message id; the message is `failed` after one attempt
- Test: `packages/testkit/test/hosts/problems.test.ts`

### M1.6-E4 — a registered retryable problem is retried
- **When** `counter.flaky` throws its registered retryable `counter/BUSY` on the first attempt and returns on the second
- **Then** the message is pending again with `attempts` 1 and is `done` after the backoff
- Test: `packages/testkit/test/hosts/problems.test.ts`

### M1.6-E5 — an unregistered code of its namespace is delivered as it is
- **When** a handler throws `ctx.problem('counter/UNKNOWN')`
- **Then** the stored problem has `title: 'counter/UNKNOWN'` and `retryable: false`, and the kernel logger receives a warning naming the code and the extension
- Test: `packages/testkit/test/hosts/problems.test.ts`

### M1.6-E6 — any other thrown value is INTERNAL, retryable
- **When** a handler throws `new TypeError('boom')` on each attempt
- **Then** each attempt fails `INTERNAL` (the error text is not in the problem), the message is retried, and it is `dead` after 3 attempts with `MESSAGE_DEAD`
- Test: `packages/testkit/test/hosts/problems.test.ts`

### M1.6-E7 — a rethrown child problem passes through
- **When** `notes.summarize.strict` does not catch the rejection of `ctx.command('counter.fail', …)`
- **Then** its own reply is the child's `counter/NEGATIVE` problem, unchanged
- Test: `packages/testkit/test/hosts/request-reply.test.ts`

### M1.6-E8 — a redelivered `ctx.command` re-awaits the same command
- **Given** a handler that calls `ctx.command('counter.increment')` and then fails retryably on its first attempt
- **When** it is redelivered
- **Then** its second call returns the stored reply of the same child; exactly one `counter.increment` row exists and it ran once
- Test: `packages/testkit/test/hosts/request-reply.test.ts`

### M1.6-E9 — `ctx.command` into a lane its chain holds fails at once
- **Given** `notes.edit` runs in the lane `note:{{ $payload.id }}`
- **When** it calls `ctx.command('notes.edit', { id: same })`
- **Then** the call rejects with `LANE_REENTRANT` and no child row is stored
- Test: `packages/testkit/test/hosts/request-reply.test.ts`

### M1.6-E10 — a `ctx.command` refused at admission
- **When** a handler calls `ctx.command('counter.secret')`, an `internal` command of another extension
- **Then** it rejects with `CAPABILITY_DENIED` (`calls` never reaches another extension's `internal` command, `02` §2.4), and no row is stored
- Test: `packages/testkit/test/hosts/request-reply.test.ts`

### M1.6-E11 — a command that dies reaches its waiters with MESSAGE_DEAD
- **Given** `counter.broken` throws a TypeError on every attempt
- **When** a handler awaits it with `ctx.command`, and another sends it with `onReply`
- **Then** after its third attempt the `ctx.command` rejects with `MESSAGE_DEAD` and the continuation receives `{ ok: false, problem: MESSAGE_DEAD }`
- Test: `packages/testkit/test/hosts/request-reply.test.ts`

### M1.6-E12 — `ctx.query` from a handler
- **When** `notes.count.check` calls `ctx.query('counter.total.get', {})` (granted) and `ctx.query('counter.missing.get', {})`
- **Then** the first returns the data; the second rejects with `TYPE_NOT_FOUND`
- Test: `packages/testkit/test/hosts/queries.test.ts`

### M1.6-E13 — a query may read and query, and nothing else
- **When** a query handler calls, one per query, `send`, `publish`, `command`, `live`, `defer`, `reply`, and `step`
- **Then** each throws `CAPABILITY_DENIED`; a query handler that calls `ctx.query` answers normally
- Test: `packages/testkit/test/hosts/queries.test.ts`

### M1.6-E14 — `ctx.send` with an idempotency key sends once across invocations
- **When** two invocations of `notes.remind` each send `counter.increment` with `idempotencyKey: 'daily'`
- **Then** one `counter.increment` row exists and both units commit
- Test: `packages/testkit/test/hosts/request-reply.test.ts`

### M1.6-E15 — a refused send rolls back the unit
- **When** a handler writes a document and sends `counter.nothing` (unknown type) without `onReply`
- **Then** the unit rolls back (the document is not stored) and the message fails `TYPE_NOT_FOUND`, not retried
- Test: `packages/testkit/test/hosts/commands.test.ts`

### M1.6-E16 — a live publish through `ctx.publish` is refused
- **When** a handler calls `ctx.publish('notes.text.streamed', …)` for its own live event
- **Then** the unit rolls back and the message fails `CAPABILITY_DENIED`
- Test: `packages/testkit/test/hosts/live.test.ts`

### M1.6-E17 — `ctx.live` checks
- **When** a handler calls `ctx.live` with its durable event `notes.added`, with a `{ value: 0.5 }` chunk on its text event, and with `{ reset: true }`
- **Then** the first throws `CAPABILITY_DENIED`, the other two `VALIDATION_FAILED`; a `{ text }` chunk on its text event reaches the live bus as `{ type, key, run, n, chunk }` with `run` = the message id
- Test: `packages/testkit/test/hosts/live.test.ts`

### M1.6-E18 — `defer` checks
- **When** a subscription handler calls `ctx.defer()`, and a command handler calls `ctx.defer({ onAbort: 'notes.add' })` (not internal) and `ctx.defer({ onAbort: 'counter.reset' })` (another extension's)
- **Then** each throws `VALIDATION_FAILED`
- Test: `packages/testkit/test/hosts/deferred.test.ts`

### M1.6-E19 — `ctx.reply` to another extension's command
- **Given** `counter.wait` is awaiting
- **When** a `notes` handler replies to it
- **Then** the `notes` unit rolls back and fails `CAPABILITY_DENIED`; `counter.wait` stays `awaiting`
- Test: `packages/testkit/test/hosts/deferred.test.ts`

### M1.6-E20 — `ctx.reply` to a command that is not awaiting
- **When** a handler replies to a `done` command and to a command still `running`
- **Then** each unit rolls back with `REPLY_NOT_AWAITING`
- Test: `packages/testkit/test/hosts/deferred.test.ts`

### M1.6-E21 — a deferred command frees its lane
- **Given** `notes.ask` in the lane `question:q1` defers
- **When** a second `notes.ask` for `q1` is pending
- **Then** it runs while the first is `awaiting`

### M1.6-E22 — a deferred reply reaches the command's continuation
- **Given** `notes.ask` was sent by `notes.start` with `onReply: { type: 'notes.answer.record' }`
- **When** `notes.question.answer` replies
- **Then** `notes.answer.record` runs with the reply in the same transaction as the reply
- Test: `packages/testkit/test/hosts/deferred.test.ts`

### M1.6-E23 — a transient delivery that fails is not retried
- **When** `audit`'s handler of `notes.touched` throws a TypeError
- **Then** it runs once and is never retried, and no row is left for it
- Test: `packages/testkit/test/hosts/events.test.ts`

### M1.6-E24 — a transient delivery keeps its lane and limits
- **Given** `audit` subscribes to `notes.touched` with the lane `note:{{ $payload.id }}`
- **When** two touches of one note commit
- **Then** the second delivery runs only after the first settles
- Test: `packages/testkit/test/hosts/events.test.ts`

### M1.6-E25 — a delivery of its own event is parsed with Zod
- **Given** `notes` subscribes to its own `notes.added`, whose payload schema has a default
- **When** the event is published without that field
- **Then** its handler receives the default
- Test: `packages/testkit/test/hosts/events.test.ts`

### M1.6-E26 — steps through the host
- **Given** `notes.fetch` runs `ctx.step('fetch', …)` and then fails retryably
- **When** it is redelivered
- **Then** the step's effect ran once and the second attempt receives its recorded result; a step begun and never ended fails `EFFECT_INDETERMINATE` on redelivery
- Test: `packages/testkit/test/hosts/recorded-values.test.ts`

### M1.6-E27 — values are stored with the first journaled write
- **When** a handler calls `ctx.ids.new()`, then begins a step, then `ctx.now()`, then `ctx.command`
- **Then** the id row is stored before the step's effect runs, and the time row before the command is admitted
- Test: `packages/testkit/test/hosts/recorded-values.test.ts`

### M1.6-E28 — a storage conflict resets the run's live events and reruns it
- **Given** `notes.bump` reads a kv entry, publishes a live chunk, and writes the entry, while a second writer changes the entry before the first commits
- **When** the first unit conflicts
- **Then** its address gets `{ reset: true }` for its run and the handler runs again at once (`attempts` unchanged) and commits
- Test: `packages/testkit/test/hosts/live-resets.test.ts`

### M1.6-E29 — a worker that exits fails its running attempts and is replaced
- **Given** two invocations running on one worker and a query waiting on it
- **When** one handler exits its worker
- **Then** both commands fail as retryable `INTERNAL` (`attempts` 1, pending with backoff); the query answers `INTERNAL`; the next dispatch starts a new worker and the retries succeed
- Test: `packages/testkit/test/hosts/worker-loss.test.ts`

### M1.6-E30 — setup that records something else fails loading
- **Given** the registry holds a manifest for `drift` that differs from what its `setup` records
- **When** a person sends a `drift` command
- **Then** it fails `EXT_MANIFEST_INVALID` naming the first differing path, not retried
- Test: `packages/testkit/test/hosts/module-loading.test.ts`

### M1.6-E31 — an extension loads once per worker
- **When** three `notes` commands run one after another on a one-worker pool
- **Then** `setup` ran twice in that worker (the recording and its determinism check) and never again, so the module was loaded once and its functions bound once
- Test: `packages/testkit/test/hosts/module-loading.test.ts`

### M1.6-E32 — pool placement
- **Given** a pool of size 3 with fake threads
- **When** invocations are dispatched
- **Then** no thread starts before the first dispatch; each dispatch goes to the thread with the fewest in-flight invocations, preferring on a tie one that loaded the extension; at most 3 threads start; the load reported is that thread's `{ inFlight, cap: 64 }`
- Test: `packages/kernel/test/hosts/worker-pool.test.ts`

### M1.6-E33 — pool size
- **When** the pool is sized for 1, 2, 5, and 16 cores
- **Then** it holds 1, 1, 4, and 4 threads
- Test: `packages/kernel/test/hosts/worker-pool.test.ts`

### M1.6-E34 — an invalid frame is a worker loss
- **When** a worker sends a `complete` frame whose outcome does not match the schema
- **Then** the kernel stops that worker, its running attempts fail retryable `INTERNAL`, and the log names the issue path but not the frame's content

### M1.6-E35 — `ctx` is closed after the handler settles
- **When** a handler returns while an unawaited `ctx.command` is not yet sent, and another handler keeps its `ctx` and calls `ctx.send` from a later timer
- **Then** both calls throw `INTERNAL` ('the invocation has ended') in the host, and no row is stored for them
- Test: `packages/testkit/test/hosts/closed-context.test.ts`

### M1.6-E36 — `ctx.message`, `ctx.context`, and `ctx.workspace`
- **Given** workspace A's row `{ path: '/w/a', name: 'A' }`
- **When** a person sends `notes.describe`, and a `notes` handler calls `ctx.command('notes.describe', {}, { context: { sessionId: 's1' } })` (people add no context keys: the HTTP body has none, `12` §12.2)
- **Then** the person's call sees its message (id, type, source `user:local`), `context` `{ locale: 'en' }`, and `workspace { id, path: '/w/a', name: 'A' }`; the nested call sees source `ext:@acme/notes` and `context` `{ locale: 'en', sessionId: 's1' }`; a global-scope command sees no workspace
- Test: `packages/testkit/test/hosts/context.test.ts`

### M1.6-E37 — a message whose workspace has no row

- **Then** it fails `WORKSPACE_INVALID`, not retried

### M1.6-E38 — `ctx.log` lines are attributed and redacted
