# M1.6 — Workspaces, kernel API, localization, hot reload: test cases

Read: `02` §2.6, §2.7, §2.8, §2.9 (hot reload), §2.11, §2.12, §2.16; ADR 0009 (M1.6: workspace identity, JSON Schema, ownership and scope, catalogs, hot reload, processes, the extension list, health and secrets, process logs, unknown languages, the reserved namespace, a process that can't start, stopping as a write).

Integration tests run the real kernel through `createTestKernel` in `packages/testkit/test/`, on temporary `path:` extensions (the M1.4 harness, which can now add extra files such as `locales/fr.json`). The `kernel.*` calls go through `kernel.exec`, as the user unless the scenario says otherwise. Hot reload and process exits are real file-system and OS events, so tests wait for them with `vi.waitFor` on what's public: a revision, a log line, or a process list (ADR 0009, 26). Tests of the kernel's own start (catalogs, leftover processes) run `startKernel` in `packages/kernel/test/`.

## Happy path

### M1.6-H1 — workspaces open, list, close, and reopen with their data
- **Given** a test kernel and two temporary folders
- **When** both are opened, one is opened again, a command stores a value in the first, the first is closed and then reopened, and Home is closed
- **Then** opening an open folder answers the same workspace; the list is Home, then both in the order they were opened, and the closed one leaves it; the reopened workspace has its old id and the stored value; closing Home fails `VALIDATION_FAILED`
- Test: `packages/testkit/test/workspaces/workspaces.test.ts`

### M1.6-H2 — a closed workspace's queued job and due schedule wait, and run once it's reopened
- **Given** a workspace with a one-time schedule a minute ahead, and a queued job whose first attempt failed, so it waits for its 1 s retry
- **When** the workspace is closed and the clock moves two minutes; then the workspace is reopened
- **Then** the job is still queued after one attempt, and the schedule queued nothing; after reopening, the job succeeds on its second attempt, and the schedule's job runs once, created at the reopening
- Test: `packages/testkit/test/workspaces/pausing.test.ts`

### M1.6-H3 — settings resolve by scope, and `kernel.settings.*` sets, resets, and lists them
- **Given** an extension key with both scopes, a preset value, and a default
- **When** the user sets it globally, then in a workspace, lists, and resets the workspace value
- **Then** `kernel.settings.list` gives each key's JSON Schema, scopes, value, and source (`workspace`, then `global` after the reset, in that workspace; `preset` in Home before any set); the kernel's keys are listed too
- Test: `packages/testkit/test/kernel-api/settings.test.ts`

### M1.6-H4 — `kernel.secrets.list` never returns a value, and `kernel.secrets.set` is sync only
- **Given** an extension that reads its secret
- **When** the user sets it with `kernel.secrets.set`, lists, deletes it; and queues `kernel.secrets.set` with `execAsync` and from an extension's `ctx.schedule`
- **Then** the extension reads the value; the list is `[{ extension, name }]` with no value; after the delete it reads `undefined`; the queued and scheduled calls fail `VALIDATION_FAILED`; no job row and no log line contains the value
- Test: `packages/testkit/test/kernel-api/secrets.test.ts`

### M1.6-H5 — `kernel.jobs.*` and `kernel.files.*` answer for the call's workspace
- **Given** async jobs in Home and in a workspace, and files an extension wrote in each
- **When** each list and get runs in each workspace
- **Then** `kernel.jobs.list` and `kernel.files.list` give this workspace's rows, newest first, and `status` filters jobs; `kernel.jobs.get` finds a job of any workspace; `kernel.files.get` of another workspace's file fails `NOT_FOUND`
- Test: `packages/testkit/test/kernel-api/jobs-files.test.ts`

### M1.6-H6 — `kernel.extensions.list` and `kernel.health.get` describe the run
- **Given** an extension with a public command, a private query, a setting, and a handler
- **When** both are called
- **Then** the extension is listed with its version, `path:` source, revision 0, namespace, commands and queries (private too) with JSON Schemas, `[{ key, description, scopes }]`, and `[{ point, description }]`, and the kernel isn't listed; health gives `0.1.0`, `test`, `web`, the pool size, the uptime on the fake clock, and the languages
- Test: `packages/testkit/test/kernel-api/extensions-health.test.ts`

### M1.6-H7 — an edited `path:` extension serves new registrations while a running job finishes on the old code
- **Given** an async job running on the old code, waiting for the test's release
- **When** the entry is edited to add a query and to change the job's answer, and the reload is seen
- **Then** the new query answers; the released job ends `succeeded` with the old code's answer; a job queued after the reload gets the new answer
- Test: `packages/testkit/test/reload/reload.test.ts`

### M1.6-H8 — a broken edit keeps the old code
- **Given** a loaded extension
- **When** its entry is edited to throw
- **Then** the log has `extension reload failed` with `EXTENSION_INVALID`; the old command still answers, and the revision stays 0
- Test: `packages/testkit/test/reload/reload.test.ts`

### M1.6-H9 — a reload reruns the `kernel.started` handlers of the extension and its dependents, and raises its revision
- **Given** `a`, `b` depending on `a`, and `c` independent, each with a `kernel.started` handler that counts its runs and logs its order
- **When** `a` is edited
- **Then** `a`'s revision is 1, `b`'s and `c`'s stay 0; `a`'s and `b`'s handlers ran a second time, `a`'s before `b`'s; `c`'s ran once
- Test: `packages/testkit/test/reload/started-again.test.ts`

### M1.6-H10 — opening a new path triggers `kernel.workspace.opened` once; reopening doesn't
- **Given** an extension with a `kernel.workspace.opened` handler that records each workspace id
- **When** a new home starts, a folder is opened, opened again, closed, reopened, and the kernel restarts
- **Then** the handler ran for `home` once and for the folder once, in that workspace
- Test: `packages/testkit/test/workspaces/opened.test.ts`

### M1.6-H11 — an extension's `fr` catalog makes `fr` selectable, and a missing key falls back to `en`
- **Given** an extension with `locales/en.json` (two keys) and `locales/fr.json` (one of them)
- **When** `kernel.language` is set to `fr`, and the kernel's `fr` catalog is read
- **Then** health lists `ar`, `en`, `fr`; the set succeeds; the `fr` catalog has the French text for the translated key and the English text for the other; a key in no catalog isn't in it, so the UI shows the key (ADR 0009, 25)
- Test: `packages/kernel/test/localization/catalogs.test.ts` (catalog); `packages/testkit/test/kernel-api/language.test.ts` (setting and health)

### M1.6-H12 — a process logs its output, survives a reload, triggers `kernel.process.exited`, and a second start fails
- **Given** an extension whose command starts a Node process that prints a line and waits for input on a file, and a `kernel.process.exited` handler that records its input
- **When** it's started, started again, the extension is reloaded, then the process is made to exit with code 3
- **Then** the log has the line; the second start fails `PROCESS_RUNNING`; the process has the same pid after the reload; after it exits, the handler got `{ extension, workspaceId, name, exitCode: 3, signal: null }`, and the list is empty
- Test: `packages/testkit/test/processes/processes.test.ts`
