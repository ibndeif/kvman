# M2.4 — kvcoder: test cases

Read: `08` (all); `07` §7.1 (`kvai.complete`, its deltas); `06` §6.4 (custom components, the injected `kvman`); `02` §2.3 (cancel), §2.4 (keyed schedules), §2.6 (short-lived processes), §2.15 (handler points, `fromHandler`); `12` §12.2 (invariants 3 and 5), §12.3 (the prompt-build benchmark); ADR 0005; ADR 0008 (26–36, 59–67, 70–75); ADR 0009 (81, M2.4: 88–107).

Kinds of tests:
- **Kernel** (`extensions/kvcoder/test/`): the testkit with kvai, kvwebui, kvcoder, and throwaway fixture extensions written to a temporary folder (a `todo` extension that registers a commands connector, sections, and session handlers), with the fake OpenAI server as kvai's custom provider `fake` (`fake/m1` text and image, `fake/m2` text only). The fake model's scripts are queued per request, so each step's answer is known; `requests()` shows exactly what reached the model. Real-shell tests run the OS's branch (bash here) in the test kernel's Home folder.
- **Unit** (`extensions/kvcoder/test/unit/`): the line parser, truncation, result text, help text, the prompt builder, and the OS branches of the shell lookup and the tree kill.
- **Components** (`extensions/kvcoder/test/web/`): kvcoder's Vue components mounted with `@vue/test-utils` in happy-dom, with a fake injected `kvman` (calls recorded and answered from tables; `stream(jobId)` driven by the test).
- **End to end and crash** (`extensions/kvcoder/test/e2e/`, `extensions/kvcoder/test/crash/`): a real kvman child with kvai, kvwebui, and kvcoder bundled and the fake OpenAI server added over HTTP; Chromium for the page, SIGKILL for the crash.

## Happy path

### M2.4-H1 — a turn runs a shell call and a connector command in parallel, asks a question, suspends, and continues after the answer
- **Given** `kvcoder.approval: 'auto'`, `todo` registered as a commands connector (`todo add` → `todo.item.add`, which waits on a gate until both calls have started), and the fake model scripted: step 1 calls `bash { command: 'echo hi' }`, `bash { command: "todo add '{\"text\":\"a\"}'" }`, and `bash { command: "ask text '{\"prompt\":\"Name?\"}'" }`; step 2 answers "done"
- **When** the person sends a message, step 1 ends, and `kvcoder.question.answer { questionId, answer: { text: 'Ada' } }` runs
- **Then** the message started a turn and sent `{ type: 'follow', jobId }`; both calls ran at once (the gate opened); the session is `waiting`, with no job running, and the turn's `pending` holds the question with its input; the card chunk `{ type: 'component', component: 'kvcoder.question', props }` was sent; the answer returns the next step's job id, whose request to the model holds the three results in the model's call order (`hi\n[exit code 0]`, the item's JSON indented, `{"text":"Ada"}` with exit 0); the turn ends `done`, the session is `idle`, and the turn records 2 steps, its usage, and its time
- Test: `extensions/kvcoder/test/turn.test.ts`

### M2.4-H2 — a suspended turn survives a restart, and answering it continues
- **Given** the turn of H1 waiting on its question
- **When** the test kernel restarts, then the question is answered
- **Then** the session is still `waiting` with the same pending question after the restart; the answer queues the next step, which sees all three results, and the turn ends `done`
- Test: `extensions/kvcoder/test/restart.test.ts`

### M2.4-H3 — a message sent while waiting dismisses the question and denies the approval, then runs the next step
- **Given** a turn waiting on an `ask choice` question and a shell approval (`kvcoder.approval: 'ask'`)
- **When** the person sends "skip that"
- **Then** the next step's request holds `dismissed by the user` for the question and `denied by the user` for the shell call (§8.1; the card's Skip gives `{ "dismissed": true }`, §8.5), then the user message; the answer to the old question fails `kvcoder/QUESTION_NOT_FOUND`
- Test: `extensions/kvcoder/test/questions.test.ts`

### M2.4-H4 — two subagents run in parallel and return their answers
- **Given** step 1 calls `subagent run '{"task":"A","mode":"fresh"}'` and `subagent run '{"task":"B","mode":"fork"}'`, and each child's model call is held until both children have sent their requests
- **When** the turn runs
- **Then** both child requests reached the model before either answered; the fresh child's request has the base prompt, the sections, and the task only, while the fork's starts with the parent's messages; the parent waits (`pending` of kind `subagent` with each `childSessionId`), then its next step has each child's last answer as its result, in call order; the children are hidden from `session.list`, use the parent's model and thinking, and their usage is added to the parent's totals
- Test: `extensions/kvcoder/test/subagents.test.ts`

### M2.4-H5 — a denied shell call reaches the model as denied
- **Given** approval `ask` and step 1 calls `bash { command: 'touch made.txt' }`
- **When** the approval is answered `{ confirmed: false }`
- **Then** the next step's request has `denied by the user` for that call; `made.txt` doesn't exist; the turn record's pending held `{ kind: 'approval', question: { command, description } }`
- Test: `extensions/kvcoder/test/questions.test.ts`

### M2.4-H6 — an `--async` connector result arrives as a message and starts a turn
- **Given** step 1 calls `todo add --async '{"text":"a"}'` and step 2 answers "waiting"
- **When** the turn ends and the `kvcoder.connector.run` job finishes
- **Then** the step's result was `started <jobId>` with exit 0; after the job ends a `user` message with `source: { kind: 'job', jobId }` and the text `The background call ... (job <jobId>) finished:` plus the result is appended, and a new turn starts, whose request ends with that message
- Test: `extensions/kvcoder/test/async-connectors.test.ts`

### M2.4-H7 — a global section reaches a second workspace's prompt
- **Given** `todo` sets `{ id: 'guide', global: true }` from Home and a workspace section `local` in Home
- **When** a second workspace is opened and `kvcoder.prompt.get` runs for a session there
- **Then** its prompt holds `guide` and not `local`; Home's prompt holds both, in `order`
- Test: `extensions/kvcoder/test/sections.test.ts`

### M2.4-H8 — a note shows in the current language, and notes and notices never reach the model
- **Given** a test kernel, and a chat that holds a note added with `kvcoder.note.add` (the welcome session that opened this scenario is removed: QA 33, ADR 0022, 1)
- **When** the person sends a message after a cancelled turn left a notice
- **Then** the model's request holds neither the note nor the notice; the conversation shows the note's translated text in the language of `kernel.language` (component test with `ar`)
- Test: `extensions/kvcoder/test/no-welcome.test.ts`, `extensions/kvcoder/test/web/conversation-messages.test.ts`

### M2.4-H9 — compaction keeps the last 10 messages
- **Given** `kvcoder.compactAt: 0.0001` and a session with 14 messages, and the fake model answers the summary call with "SUMMARY"
- **When** the next step runs
- **Then** a `summary` message `{ text: 'SUMMARY', coversThroughSeq }` is stored; the step's model request is the summary followed by exactly the last 10 messages; the stream had `{ type: 'compaction', state: 'started' }` and `'done'` around the summary's deltas; all messages stay in `message.list`
- Test: `extensions/kvcoder/test/compaction.test.ts`

### M2.4-H10 — cancel stops the children and the questions
- **Given** a parent waiting on a subagent whose child waits on an `ask text` question, and an `--async` connector job still running
- **When** `kvcoder.turn.cancel { sessionId }` runs
- **Then** the parent's and the child's turns end `cancelled`, both sessions are `idle`, a `CANCELLED` notice is in the parent; answering the child's question fails `kvcoder/QUESTION_NOT_FOUND`; the async job still runs and reports back as a message
- Test: `extensions/kvcoder/test/cancel.test.ts`

### M2.4-H11 — an image attachment reaches an image model, and fails for a text-only one
- **Given** an uploaded PNG file in Home
- **When** `message.send { fileIds: [id] }` runs in a session on `fake/m1`, then in a session configured to `fake/m2`
- **Then** the first step's request carries the image (its base64 data and `image/png`); the second fails `VALIDATION_FAILED` and starts nothing
- Test: `extensions/kvcoder/test/images.test.ts`

### M2.4-H12 — the conversation reattaches to a running step after a reload
- **Given** a real kvman whose fake model streams a few text deltas and then holds its answer
- **When** a message is sent in Chromium, the first deltas show, and the page reloads
- **Then** the reloaded conversation finds the session's `stepJobId`, shows the running answer's later deltas in one bubble, and shows the final answer when the model is released
- Test: `extensions/kvcoder/test/e2e/reattach.test.ts`

### M2.4-H13 — crash invariants 3 and 5
- **Given** a real kvman with kvcoder, one session waiting on a question and another whose step is held in its model call
- **When** kvman is SIGKILLed and started again
- **Then** (3) the waiting session and its question survive, and answering continues the turn to `done`; (5) the held step's job ended `failed` with `INTERRUPTED`, its turn is `interrupted` with an `INTERRUPTED` notice, and the session is `idle`
- Test: `extensions/kvcoder/test/crash/crash.test.ts`

### M2.4-H14 — the prompt-build benchmark meets its target
- **Given** a session with 10 sections (4 KB each) and 10 connectors
- **When** `bench:check` builds the prompt repeatedly through `kvcoder.prompt.get`
- **Then** p99 ≤ 50 ms
- Test: `bench/kvcoder-prompt.ts`

## Edge cases

### Sessions
- **M2.4-E1** An unknown `sessionId` (or one of another workspace) fails `kvcoder/SESSION_NOT_FOUND` for `session.get`, `rename`, `configure`, `delete`, `compact`, `export`, `fork`, `message.send`, `message.inject`, `note.add`, `message.list`, `turn.list`, `turn.cancel`, and `prompt.get`. — `extensions/kvcoder/test/sessions.test.ts`
- **M2.4-E2** Every command naming a subagent session fails `VALIDATION_FAILED` (send, inject, note, rename, configure, delete, fork, compact, export, cancel); reads work. — `extensions/kvcoder/test/subagent-rules.test.ts`
- **M2.4-E3** `session.compact` while a step runs fails `kvcoder/SESSION_BUSY`. — `extensions/kvcoder/test/compaction.test.ts`
- **M2.4-E4** `session.list { limit }` returns top-level sessions newest first; `limit` over 1000 fails `VALIDATION_FAILED`; `session.count { status: 'waiting' }` counts waiting top-level sessions. — `extensions/kvcoder/test/sessions.test.ts`
- **M2.4-E5** Titles: until the first turn ends the title is the first 60 characters of the first message; then the private `kvcoder.session.title` job (no tools, `maxTokens` 30) sets the model's title; a renamed session is never retitled; a failed title call keeps the placeholder. — `extensions/kvcoder/test/titles.test.ts`
- **M2.4-E6** `session.configure` changes the model and thinking from the next step; an unknown model makes that step fail `kvai/MODEL_UNKNOWN`, and the turn ends `failed` with a notice naming the code (ADR 0009, 107). — `extensions/kvcoder/test/sessions.test.ts`
- **M2.4-E7** `session.fork { throughSeq }` copies the messages through `throughSeq` and the summary, not per-session sections; without `throughSeq` it copies all; the `kvcoder.session.forked` point gets `{ fromSessionId, toSessionId, throughSeq }`. — `extensions/kvcoder/test/fork-export.test.ts`
- **M2.4-E8** `session.export` writes a kernel file holding `{ session, turns, messages, subagents }`, named from the title with `/ \ : * ? " < > |` replaced and cut to 100 characters; a `{ key }` title gives `<sessionId>.json`. — `extensions/kvcoder/test/fork-export.test.ts`
- **M2.4-E9** `session.delete` cancels its turn, deletes its subagent sessions and per-session sections, and fires `kvcoder.session.deleted`. — `extensions/kvcoder/test/sessions.test.ts`

## KVC-08 — short-lived process cancellation (ADR 0039)

These extend the existing milestone's cancellation contract, not a new milestone. Shared scenarios run for both `runShell` and `runProgram`. Test: `extensions/kvcoder/test/unit/process-cancellation.test.ts`.

### M2.4-E65 — pre-cancellation prevents process creation
- **Given** a signal aborted before the runner is called
- **When** the shell or program is invoked
- **Then** it rejects with the cancellation reason, calls neither spawner, and creates no timer or abort listener.

### M2.4-E66 — cancellation during preparation is checked at spawn
- **Given** preparation of shell arguments or program arguments aborts the signal
- **When** preparation returns
- **Then** the final pre-spawn check rejects with the cancellation reason and creates no child or timer.

### M2.4-E67 — cancellation during spawn is not lost
- **Given** spawn creates a controlled child and aborts before returning it
- **When** the runner attaches tracking
- **Then** it kills the child's tree once, waits for close, rejects with the cancellation reason, and removes timers/listeners.

### M2.4-E68 — running cancellation waits for shutdown
- **Given** a controlled running child
- **When** the signal aborts, then the child closes
- **Then** its tree is killed once, the promise stays pending until close (an error with a pid is not shutdown), and cancellation rather than timeout or ordinary failure is returned with no resource left behind. Assert explicit abort-listener removal on terminal cancellation as well as normal settlement.

### M2.4-E69 — normal success remains unchanged
