# M1.1 — Storage engine: test cases

Read: `04` §4.1–§4.2, §4.8 (kernel part), `03` §3.11; ADRs 0001 (driver), 0031 (unit-of-work writes), 0032 (encodings, limits), 0033 (types), 0034 (failed-send rows).

All tests live in `packages/kernel/test/storage/` and use the real `better-sqlite3` driver on a temporary folder. Where a test must make storage fail at a chosen point, it wraps the real driver in a test driver that implements the same driver interface and throws at that point; production code has no test branch.

Admission of sends (`03` §3.3 steps 3–6) is built in M1.4; the commit pipeline reaches it through an admission interface, and these tests give it a small admitter that knows a fixed set of types. Liveness checks, deferred replies, blob references, config, and secrets join the pipeline in the milestones that build them (M1.6, M1.7, M2.3, M2.5); publishes joined with admission in M1.4 (ADR 0053).

## Happy path

### M1.1-H1 — a unit is applied completely or not at all
- **Given** a unit with a kv write, two document writes, a log append, and a send, and a test driver that fails the third statement of that unit
- **When** the unit is committed
- **Then** its result is a storage failure (`STORAGE_UNAVAILABLE`, retryable), and none of its rows exist; the same unit committed without the injected failure leaves all of them
- Test: `packages/kernel/test/storage/commit-pipeline.test.ts`

### M1.1-H2 — a conflicting version rolls back only that unit
- **Given** three units in one batch, the second writing a document with a stale `expectedVersion`
- **When** the batch commits
- **Then** the first and third are committed, the second is `STORAGE_CONFLICT` with none of its rows
- Test: `packages/kernel/test/storage/commit-pipeline.test.ts`

### M1.1-H3 — batching commits many units in one transaction
- **Given** 64 units enqueued together, then 65, then 3
- **When** they commit
- **Then** 64 units use one transaction, 65 use two, and 3 are committed together once 2 ms have passed
- Test: `packages/kernel/test/storage/commit-pipeline.test.ts`

### M1.1-H4 — a newer schema refuses to open and writes no data
- **Given** a database whose `schema_versions` row for `kernel` is higher than the code knows
- **When** it is opened
- **Then** opening fails with `SCHEMA_TOO_NEW`; `kvman.db` is byte-for-byte unchanged and `kvman.db-wal` is empty or absent (ADR 0035)
- Test: `packages/kernel/test/storage/database.test.ts`

### M1.1-H5 — a failed send with onReply commits the sender's unit and delivers the failure
- **Given** a unit that sends a command of an unknown type with `onReply: { type: 'agent.tool.record', context }`
- **When** the unit commits
- **Then** the unit is committed; the send is stored as a command in state `failed` with a `TYPE_NOT_FOUND` result and `handler` `''`; and a continuation `agent.tool.record` is stored as pending with payload `{ reply: { ok: false, problem }, context }` and idempotency key `<failed command id>:reply`
- Test: `packages/kernel/test/storage/failed-sends.test.ts`

### M1.1-H6 — a failed send without onReply fails the unit
- **Given** the same unit without `onReply`
- **When** it commits
- **Then** the unit is rejected with `TYPE_NOT_FOUND` (not retryable) and none of its rows exist
- Test: `packages/kernel/test/storage/failed-sends.test.ts`

## Edge cases

### Opening and migrating (`04` §4.1, §4.8) — `packages/kernel/test/storage/database.test.ts`

| Id | Given | Then |
|---|---|---|
| M1.1-E1 | a folder without a database | opening creates `kvman.db` with mode 0600, runs the kernel migrations, and records `schema_versions` `kernel` = 1 |
| M1.1-E2 | the opened database | `journal_mode` is `wal`, `synchronous` is FULL, `foreign_keys` is on, `busy_timeout` is 5000; after the first write the `-wal` file has mode 0600 too |
| M1.1-E3 | the database after migration | every kernel table of `04` §4.1 exists, and the unique idempotency and notification-key indexes exist |
| M1.1-E4 | an existing database at the current version | reopening runs no migration and keeps the data |
| M1.1-E5 | a read-only connection from the factory | it reads committed data and fails to write |

### Writes and versions (ADRs 0031, 0032) — `packages/kernel/test/storage/store-writes.test.ts`

| Id | Given | Then |
|---|---|---|
| M1.1-E6 | kv and document writes without `expectedVersion` | inserted at version 1, then overwritten with version + 1 |
| M1.1-E7 | `expectedVersion: 0` on a key that exists, and on one that does not | conflict; inserted at version 1 |
| M1.1-E8 | `expectedVersion: n` on a key at version n, at another version, and on a missing key | written at n + 1; conflict; conflict |
| M1.1-E9 | deletes without, with a matching, and with a stale `expectedVersion`, and `expectedVersion: 0` on an existing key | deleted; deleted; conflict; conflict |
| M1.1-E10 | a log append at a free seq and at a taken seq; `truncate-before` and `drop` | appended; conflict; older entries removed; every entry removed |
| M1.1-E11 | a `global` write and a `workspace` write of the same key | stored under `ws` `''` and under the invocation's workspace, owned by the invocation's extension |

### The pipeline (`04` §4.2, ADR 0032) — `packages/kernel/test/storage/commit-pipeline.test.ts`

| Id | Given | Then |
|---|---|---|
| M1.1-E12 | units whose invocation outcome is a value, a problem, and deferred | the invocation's message ends `done` with `{ ok: true, value }`, `failed` with `{ ok: false, problem }`, and `awaiting` with no result |
| M1.1-E13 | a unit with 1,001 sends, and one with more than 8 MB of writes | rejected with `PAYLOAD_TOO_LARGE` and params `{ limit: 'messages', max: 1000 }` / `{ limit: 'writes', max: 8388608 }`; nothing stored |
| M1.1-E14 | a batch whose `COMMIT` fails | every unit of the batch fails with `STORAGE_UNAVAILABLE` and nothing is stored |
| M1.1-E15 | a storage failure reported as a full disk | the unit fails with `STORAGE_FULL` (not retryable) |
| M1.1-E16 | an adapter-originated message (a unit without an invocation) | stored as `pending` in its own transaction, with `priority` 0 for `interactive`, 1 for `normal`, 2 for `background`, and `lane` stored as `<extension>|<rendered lane>` |
| M1.1-E17 | a committed unit | its result lists the message rows it inserted, for the pending index |

### Failed sends (`04` §4.2, ADR 0034) — `packages/kernel/test/storage/failed-sends.test.ts`

| Id | Given | Then |
|---|---|---|
| M1.1-E18 | a send with `onReply` to a known type whose payload fails validation | the failed command keeps its owner as `handler` and its problem as result; the continuation is delivered |
| M1.1-E19 | a send with `onReply` whose continuation itself cannot be admitted | the whole unit is rejected with that problem and nothing is stored |

### Identifiers (`02` §2.2) — `packages/kernel/test/ulid.test.ts`

The kernel needs ULIDs for message ids and for the correlation ids of the problems it reports, so the generator comes with the storage engine.

| Id | Given | Then |
|---|---|---|
| M1.1-E20 | ULIDs generated at a fixed clock time and across later times | each matches the protocol's ULID schema; ids of the same millisecond strictly increase; ids of a later millisecond sort after earlier ones |
