# 00 — Decisions (source of truth)

## Vision

kvman is a local platform where **everything is an extension that talks through messages**. Developers extend it with small declarative packages, non-technical users customize it by picking presets, and kvman can extend itself with an LLM-driven builder. The AI coding agent is one application on top of this platform.

## Principles

1. **Lean kernel.** The kernel's only job is to deliver messages to handlers reliably and commit their effects atomically. Product features live in extensions.
2. **One communication model.** Every interaction is a typed message with a kernel-assigned source, a correlation ID, and a schema.
3. **Declarative first.** Pages and presets are data. What an extension registers is recorded as data (its manifest) before any handler runs. So everything can be validated, previewed, shared, and generated by an LLM.
4. **Everything replaceable.** Core extensions use the same public API as third-party ones and can be disabled or replaced.
5. **Durable where it matters, fast everywhere else.** Commands and durable events are durable; queries, transient events, and live events never touch disk.
6. **Visible power.** What an extension can do (capabilities) is declared, shown to the user, and enforced.
7. **Honest boundaries.** Where kvman cannot enforce something (e.g. raw shell), the plan says so and the UI says so.

## Decision table

Decisions are numbered in reading order. Other files cite them as `D<n>`.

### Architecture (`01`)

| # | Decision |
|---|---|
| D1 | **Actor model.** All communication is by messages between actors: extensions, users (browser clients), processes acting through job tokens, and the kernel's own API. There are no other channels (no direct extension-to-extension calls, no feature-specific HTTP routes). |
| D2 | **Microkernel.** The kernel owns routing, scheduling, execution hosts, process supervision, storage, registry/validation, extension loading, workspaces/trust, capabilities, the LLM service (D49), the UI registry (D42), user preferences, the notification tray (D45), adapters, secrets, and observability. It contains no product feature. The **daemon** is the OS process that `kvman start` runs; the kernel is the kvman code inside it. Extensions run in hosts the kernel starts: worker threads inside the daemon, or sandboxed child processes. |
| D3 | **The kernel is the substrate, not a replaceable actor.** It exposes its own API as reserved `kernel.*` message types. `ui.*` types are reserved commands handled by the kernel that deliver one-way messages to the user actor (D40, D45). `frame.*` names are reserved for the shell's frame slots (D37). |
| D4 | **kvman = actor runtime + UI shell.** The agent is one application (`agent` extension). A preset defines an application for a workspace. |
| D5 | **Scope of v2.** One local user; the address `user:<id>` exists from day one for future multi-user support. Extensions are TypeScript only; the protocol is JSON + JSON Schema so non-JS actors can be added later. |

### Messaging (`02`)

| # | Decision |
|---|---|
| D6 | **Three message kinds:** `command` (do X, exactly one handler, returns its result), `query` (read X, exactly one handler, read-only), `event` (X happened, zero or more subscribers, never answered). A reply is not a kind: it is a command's result, stored with the command and delivered to whoever waits. Everything the kernel pushes to people (events, live events, late replies, `ui.*`) travels over the one SSE stream, so it needs no kind of its own. Extensions extend each other by calling commands and subscribing to events (e.g. prompt sections and guards of the agent, `09` §9.5–§9.6). (`02` §2.3) |
| D7 | **Routing by type.** Every type belongs to one namespace. Only one extension may own a namespace in a workspace at a time. Commands and queries have exactly one handler; events have any number of subscribers. |
| D8 | **Durability and delivery classes.** Commands (and their replies) are always durable (SQLite inbox, at-least-once). Each event type is registered as `durable` (the default; inbox rows, at-least-once, resumable), `transient` (memory only, sent at commit), or `live` (sent at once, before commit, to screens only, keyed as `<type>:<key>`, with a ring buffer and kernel resets when the sender does not commit; used for tokens and progress). Queries are direct in-memory calls and never persisted. (`02` §2.5) |
| D9 | **Ordering lanes.** A handler declares a lane template (`lane: 'file:{{ $payload.fileId }}'`), which the kernel renders at admission without running extension code; the lane is `(extension, rendered lane)`. One in-flight message per lane; different lanes run in parallel. Waiting on your own lane, or on a lane held by an ancestor in the causation chain, fails immediately with `LANE_REENTRANT`. |
| D10 | **Idempotency.** `(source, idempotencyKey)` is unique within retention. The same request digest returns the original message and reply; a different digest fails `IDEMPOTENCY_MISMATCH`. Kernel-derived keys make `ctx.command` and continuations idempotent across redelivery. |
| D11 | **Request/reply.** Three patterns: in-handler `ctx.command` (waits for the result; journaled, bounded by the handler deadline), continuation `send(..., {onReply})` for long waits, and deferred replies (`ctx.defer()` then `ctx.reply()`) for replies that arrive in a later handler. All carry absolute deadlines. |
| D12 | **Tracing context.** Every message carries `correlationId`, `causationId`, and a small inherited `context` map (e.g. `sessionId`). The kernel sets `context.locale` on every message that does not inherit one. The messages table is the trace store. |
| D13 | **Naming grammar.** Type names do not encode their kind; the kind is declared and shown in the registry. Instead each kind has a grammar, checked by `kernel.validate` with fix hints: commands `<ns>[.<entity>].<verb>` (imperative), queries end in a read verb (`get`, `list`, `search`, `count`, `preview`, `validate`), events (of every delivery class) end in a past participle, a live event is addressed as `<type>:<key>`, and multi-word segments are kebab-case. One name is never used for two kinds. (`02` §2.4) |
| D14 | **Payloads.** Inline payloads ≤256 KB; larger payloads (≤16 MB) spill transparently to blob storage. Bytes such as files always travel as blob IDs. |

### Kernel and execution (`03`)

| # | Decision |
|---|---|
| D15 | **Scheduler.** Priority classes (`interactive` > `normal` > `background`), fairness across workspaces and lanes, timers (`notBefore`), declared schedules, retries with backoff, max attempts, dead letters. |
| D16 | **Execution hosts.** A shared worker pool (size `min(4, cores-1)`, the default for built-in extensions), a dedicated worker, or a sandboxed child process under the Node permission model with `node:sqlite` turned off, because the permission model does not cover it (the default for every other extension, and mandatory for builder-generated ones). Lower isolation for a non-built-in extension is a user grant. Hosts load extensions lazily and unload idle ones. Handlers are stateless; all state lives in storage. |
| D17 | **Supervision.** A crashed or stuck host is restarted and its in-flight messages are redelivered. An extension is quarantined (unavailable in every workspace, with a visible notice) when it crashes or hangs hosts 3 times in 10 minutes, when its snapshot fails the integrity check, or when a data migration fails part-way; the recovery page offers the fixes that fit the reason (`03` §3.6). |
| D18 | **Process supervisor in the kernel.** `ctx.process.spawn` runs OS processes in their own process groups with recorded identity, capped logs, deadline kill, an exit notification for background processes (`onExit`), and boot reconciliation. The agent's bash tool is the `shell` extension built on it. |
| D19 | **Deadlines and cancellation.** Every invocation has an absolute `deadlineAt` and an `AbortSignal`. `kernel.cancel {messageId}` cancels that message and every unfinished message it caused (its causation descendants); `kernel.cancel {correlationId}` cancels every unfinished message of the correlation. Late results after cancel or deadline are discarded. |

### Storage (`04`)

| # | Decision |
|---|---|
| D20 | **One SQLite database** (`~/.kvman/kvman.db`, WAL mode) holds the inbox, step journal, extension storage, registry, workspaces, presets, preferences, and notifications. Blobs are content-addressed files. Secrets live in `~/.kvman/secrets.json` (0600). |
| D21 | **Atomic unit of work.** A handler's storage writes, emitted durable messages, reply, and inbox state commit in one transaction. If the handler fails, nothing is committed and the message is redelivered. |
| D22 | **Store primitives:** kv, collections (declared indexes, declarative filter language), append-only logs, and blobs, with one simple shape each (`ctx.store.kv`, `.collection()`, `.log()`, `.blobs`, `.global`). Reads return plain arrays; there is no pagination anywhere in kvman (filters, `limit`, and hard caps that fail loudly instead). Versions are tracked automatically, so read-then-write is safe without extra code. Scopes are `global` and `workspace`. An extension reads and writes only its own data; cross-extension reads go through queries. A blob is readable only by an extension that holds a ref to it or received it in a `z.blobId()` field. |
| D23 | **Step journal.** `ctx.step(name, fn)` records external side effects. On redelivery, a completed step returns its recorded result. A started but unfinished step fails `EFFECT_INDETERMINATE` unless it is declared retry-safe. |
| D24 | **Single writer with group commit.** The kernel applies units of work in batched transactions (one savepoint each). Hosts read through read-only connections. Optimistic version checks turn write conflicts into `STORAGE_CONFLICT`, which is retried. |
| D25 | **Versioned schemas.** The kernel and each extension have forward migrations. A newer schema than the code understands fails `SCHEMA_TOO_NEW` without writing data (ADR 0035). |

### Extensions (`05`, `06`)

| # | Decision |
|---|---|
| D26 | **`defineExtension(meta, setup)` with explicit registration.** `setup(ext)` registers everything with one explicit call each: `ext.registerCommand`, `ext.registerQuery`, `ext.subscribe`, `ext.registerConfig`, `ext.registerCollection`, `ext.registerPage`, `ext.registerProvider`, `ext.requestCapability`, and so on. Handlers use a separate `ctx`. `setup` is synchronous, deterministic, and has no I/O: the kernel runs it at install in a sandboxed loader and records the calls as a static manifest, and a host re-runs it at load to bind functions; a mismatch quarantines the extension. The kernel keeps only the registry, never in-memory listeners. (`05` §5.1–§5.3) |
| D27 | **Namespaces and contracts.** An extension owns one namespace. `implements: '<contract>@<major>'` lets an alternative (e.g. a different agent) replace a core extension while keeping pages and callers working. |
| D28 | **Capabilities** are requested with `ext.requestCapability` (runtime powers such as `calls`, `tools`, `llm`, `process`) or derived from registrations (`subscribes` to foreign events, `provides-llm`). They are granted by the user, together with isolation, at enable or preset apply, enforced by the kernel on every `ctx` call and message delivery, and enforced by the Node permission model for sandboxed extensions. (`05` §5.7) |
| D29 | **Sources**: exact npm version, git commit, `builtin` (bundled with kvman), `dev` (builder projects), `local` (an installed snapshot by digest). Staging runs with install scripts disabled into content-addressed snapshots that are verified at every load. Core extensions use this same pipeline. |
| D30 | **Lifecycle**: enable per workspace through its preset, hot reload without restart, version history, and rollback when the data schema allows it. There is no global enable: a `global`-scope type is handled while its extension is enabled in at least one workspace. An upgrade that needs new capabilities is a user-confirmed grant. There is **one active version of each extension** for the whole home folder: a preset that needs another version switches it everywhere, and its apply preview says so. (`06`, `07` §7.4) |
| D31 | **Access.** Every command and query declares `access` (default `all`): `all` (people and extensions), `user` (only a person, so an extension, a process, or a widget can never answer or approve on a person's behalf), `extensions` (only extension code and its processes, for APIs one extension offers others), or `internal` (only its own extension and the kernel: continuations, timers, schedules; hidden from the UI, agent tools, and other extensions). The kernel checks it against the kernel-assigned source. Commands with access `all` or `user` may declare `slash` metadata to appear in the agent's slash menu. (`02` §2.4, `05` §5.5) |
| D32 | **Requirements** are declared as message types (`ext.requireTypes(['ocr.extract'])`) and public components (`ext.requireComponents`), not package names, and are checked at enable and preset apply. |

### Workspaces and presets (`07`)

| # | Decision |
|---|---|
| D33 | **Workspace** = canonical real path → SHA-256 ID. A default Home workspace (`~/kvman`) is created on first run. Every message carries its `workspaceId` (or is global). The builder uses **preview workspaces** (`~/.kvman/previews/<name>/`) created only by the kernel; they are hidden from the switcher and hold throwaway data. (`07` §7.1) |
| D34 | **Trust gate.** Reading `<ws>/.kvman/**` (rules, skills, a repo preset) requires trust: a preview of exact files and hashes, a short-lived token, and `once`/`always`. Any file change re-prompts. Enforced at the kernel's workspace I/O edge. |
| D35 | **Presets are apps.** A preset holds extensions (source, `integrity`: the reproducible pin of the package, enabled, capability grants), frame layout and item order, hidden contributions, home page, branding, label overrides per language, its own pages, nav groups, and nav items with their own catalogs, and non-secret config. Presets are shareable (no secrets, paths, or loose versions), stored in a DB catalog, and applied with one confirmation that installs missing extensions, validates every reference, and commits atomically. |

### UI (`08`)

| # | Decision |
|---|---|
| D36 | **Hybrid UI.** Declarative views by default, plus sandboxed iframe widgets as an escape hatch. Extensions ship their own components in two forms, both registered with `ext.registerComponent`: **composite components** (named, reusable view trees with a props schema, rendered natively by the shell) and **widget components** (sandboxed iframes). Components are `private` (owner's views only) by default or `public` (usable by others that declare `ext.requireComponents`). Composite components expose events as `z.action()` props. An action is checked against the owner of the view where it is written; public components cannot contain command actions of their own, so a component never borrows its user's grants. Upgrading a component owner re-validates its dependents' views. Extensions never ship native code into the shell in v2. (`08` §8.9) |
| D37 | **The frame is code; its content is data.** The shell owns no features. It provides the frame, component library, renderer, data layer, theming, right-to-left layout, formatting, routing, and a built-in recovery page that works even when every extension is broken. The frame's regions are typed slots (`frame.sidebar` accepts `navGroup`, `navItem`, `separator`; `frame.topbar.*` `toolbarItem`; `frame.main` pages; `frame.statusbar.*` `statusItem`; `frame.overlay` `panel`). Shell-only zones (brand, workspace switcher, notifications, toasts, connection, kvman menu, risk banner, grant dialog, command palette, shortcuts) accept no contributions. The kernel registers no UI; it validates UI against the frame slot catalog and component specs in `@kvman/protocol`. (`08` §8.2–§8.3) |
| D38 | **Contribution kinds and slots.** Kinds: `page`, `navGroup`, `navItem`, `separator` (presets), `toolbarItem`, `statusItem`, `panel`, plus `action` (on entity types), `renderer` (on targets), `component`, and settings sections. **Every container declares what it accepts**: frame slots, extension slots (`ext.registerSlot` with `accepts: ['panel' \| 'toolbarItem']`), and components (`children`). Validation rejects anything else before it runs. Contribution ids are `<ns>.<name>`, unique within an extension across all UI kinds; page routes are unique within a workspace (`ROUTE_CONFLICT`). A contribution aimed at a slot, entity, or renderer target of an extension that is not enabled in the workspace is inactive, not an error. An extension's views may send only its own types, types covered by its granted `calls`, and the `kernel.*` types its capabilities allow (`03` §3.8); grant commands only through the grant dialog. (`08` §8.4, §8.7) |
| D39 | **View language**: components with bindings (`$item.x`, `$form.x`, `$query.x`, `$state.x`, `$route.x`, …) and declarative conditions. No expressions or code. Forms are generated from command input schemas. Live data through `refreshOn` (refetch a query when an event arrives) and `live` props (show a live event). (`08` §8.7) |
| D40 | **The user is an actor; extensions own their prompts.** There is no kernel prompt primitive. When a handler needs a person, it defers its reply, stores the pending prompt in its own storage, shows it with its own UI (a page, a slot panel, or `frame.overlay`), and receives the answer as its own `access: 'user'` command, which completes the deferred reply. The kernel only offers the one-way `ui.toast`, `ui.notify`, `ui.dismiss`, and `ui.navigate`. (`08` §8.13) |
| D41 | **Shell grant dialog.** Power-granting kernel commands (`kernel.trust.grant`, `kernel.extension.enable`, `kernel.extension.reload` with new grants, `kernel.preset.import`, `kernel.preset.apply`, `kernel.preset.update` touching extensions) are confirmed only in a dialog drawn by the shell from kernel data: extension, source, digest, isolation, and capabilities in plain words with their reasons. Any view (extension or preset) can open the dialog; only its Confirm button sends the command. An extension can never draw its own "Allow" button for power. (`08` §8.13) |
| D42 | **UI registry; UI is registered, never pushed.** The kernel computes each workspace's UI registry from its applied preset and the manifests of its enabled extensions and serves it with an ETag (`GET /api/v1/ui`); page views and catalogs load separately. The shell refreshes it on `kernel.preset.changed` (every write to the applied preset), `kernel.extension.reloaded`, and `kernel.extension.quarantined`; there is no "UI changed" event. UI that appears at runtime (a question, an approval) is registered at install and made visible by data (`visibleIf` over a live query); there is no `ctx.ui.show`. Only the one-way `ui.toast`, `ui.notify`, `ui.dismiss`, and `ui.navigate` are pushed. (`08` §8.6, §8.10) |
| D43 | **Localization.** The language and theme are user preferences owned and saved by the kernel (`kernel.user.preferences`, `access: 'user'` to set), switched live in every tab. The language never depends on the URL: no route prefix, query parameter, cookie, or browser storage (`08` §8.16). The language reaches handlers as `context.locale` / `ctx.locale`. Extensions and presets register ICU MessageFormat catalogs (`ext.registerTranslations`); keys are namespaced automatically; views use `$t` keys; notices, problems, and agent notices carry keys and parameters and are rendered by the shell, so stored text changes language too. `description` fields stay English. Right-to-left is built in from the start (mirrored frame, logical CSS enforced by lint, `<bdi>` isolation). v2 ships `en` and `ar`. (`08` §8.16) |
| D44 | **Visibility is not authority.** Presets hide, order, and relabel contributions; capabilities and grants decide what code can do. Hidden pages stay reachable through "Show hidden pages" and their routes. The kvman menu and the recovery page cannot be hidden, and the apply dialog lists what a preset hides. Platform extensions have no special status: they can be hidden or disabled like any other. (`08` §8.17) |
| D45 | **Notifications are part of the UI contract.** Extensions send `ui.toast` (transient) and `ui.notify` (stored in the tray) with a level, translated text, an optional `key` for replacement, a problem, up to two action buttons, and `attention` for things that need the person; `ui.dismiss` removes their own. The shell draws them in shell-only zones with the sender's name. Action buttons are checked at admission like view actions. The kernel stores the tray, applies rate limits and muting, and notifies the person itself about quarantine, failed migrations, and dead-lettered user actions. Errors from a person's own click are shown by the shell automatically. (`08` §8.11) |
| D46 | **Transport.** Clients send everything over HTTP (generic command and query endpoints, subscriptions, blobs). The kernel pushes everything over one Server-Sent Events stream per browser (durable and transient events, live events, late replies, one-way `ui.*`), shared by its tabs. Durable events carry their sequence as the SSE event ID, so reconnects resume with `Last-Event-ID`. No WebSocket. (`12`) |

### Agent (`09`, `10`)

| # | Decision |
|---|---|
| D47 | **The agent is a core extension.** A turn is a chain of short committed steps in the lane `session:<id>`. Steering works through the lane queue, cancel is a command, and compaction happens in place (session ID stays the same). |
| D48 | **Tools are commands or queries** flagged `agentTool` and enabled by the preset: a tool that only reads is a query, a tool that changes something is a command. The agent reaches them through the `tools` capability. Tool modes: `bash` (one shell tool plus `kv` CLIs) or `direct` (each tool exposed to the model). The agent exposes an API that other extensions use: **prompt sections** (`agent.prompt.section.set`: an extension such as `rules` registers and refreshes its own section of the system prompt; the agent reads stored sections at each step and never calls other extensions during a turn) and **guards** (an extension is a guard when its granted manifest subscribes to `agent.tool.call.created` and may send `agent.tool.call.review`; until it registers its guards with `agent.guards.set` it covers every call, so nothing runs unguarded; it receives `agent.tool.call.created` for calls it covers, and answers `agent.tool.call.review` allow or deny, deciding by itself whether to ask the person; a call runs when every covering guard allowed it; with no guard it runs, except `dangerous` tools, which the agent's own approval panel asks the person about). `agent.tool.call.completed` is published after every call. (`09` §9.5–§9.6) |
| D49 | **LLM access is a kernel service.** The kernel owns the provider and model registry, model defaults per workspace and purpose, the call path (`ctx.llm.complete`, journaled like `ctx.command`), streaming relay, retries, and usage accounting. It contains no provider SDK: extensions implement providers with `ext.registerProvider` and `ext.registerModel`. The core `llm-providers` extension is the only user of pi-ai. (`05` §5.11, `10` §10.1) |
| D50 | **Subagents** run through `agent.child.run` with a deferred reply, depth ≤2, a token budget, and a tool allowlist. |

## Global rules

1. **No feature-specific kernel code.** If a change to the kernel mentions sessions, chat, prompts, tools, PDFs, or any product concept, it belongs in an extension. LLM completion is a generic platform service like processes: the kernel routes requests to providers and records usage, but never builds prompts or knows why a model is called.
2. **No hidden channels.** Extensions interact only through messages and their own storage.
3. **Every write path is a unit of work.** Nothing outside a unit of work mutates kernel or extension state, except kernel boot/migration and the step journal.
4. **Secrets never leave home.** Secrets are never in presets, messages, logs, or exports.
5. **Every registered thing is documented.** Types, entities, components, contributions, and config fields without a description fail validation.
6. **Text is keys until it is drawn.** User-facing text is stored and sent as translation keys with parameters and turned into words only by the shell (or by `ctx.i18n.t` for text that leaves kvman). Descriptions for developers and LLMs stay in English.

## Resolved questions

| # | Question | Decision |
|---|---|---|
| R-Q1 | SQLite driver | **`better-sqlite3`**. Mature, synchronous, fast, works in worker threads, proven durability. `node:sqlite` is still under active development in Node 24. The storage engine keeps a driver interface so a later switch is one ADR and one adapter. Milestone M0.5 measures throughput and worker-thread use and records the numbers. |
| R-Q2 | Network restriction for sandboxed extensions | Node 24's permission model enforces file system, child process, worker, and native addon access, but not network. **Network is declared and disclosed, not enforced, on Node 24.** At startup the kernel checks whether the running Node supports network permission flags and enforces them automatically when it does. The UI states the current level ("can access the network — not restricted on this Node version"). |
| R-Q3 | Code highlighting under the Markdown sanitizer | **Shiki with `transformerStyleToClass`.** The CSS for the bundled light and dark themes is generated at build time and served as a static stylesheet, so no inline styles reach the DOM and the CSP stays `style-src 'self'`. Only bundled themes and languages are available. |
| R-Q4 | Home folder safety | kvman keeps everything in one home folder: `--home <dir>`, else `KVMAN_HOME`, else `~/.kvman`. **kvman never writes into a folder it did not create:** at start, a home folder that holds anything other than `daemon.lock` and `logs/` but has no `kvman.db` is refused with `HOME_INVALID`. An empty or missing folder is initialized. |
| R-Q5 | Trusted native shell components | **Not in v2.** The built-in library grows through shell releases; extensions add composite components (declarative) and widget components (sandboxed) (D36). |
| R-Q6 | Non-JS actors | **Not in v2** (D5). The protocol stays language-neutral. |
| R-Q7 | Multiple users, remote access, authentication | **Not in v2** (D5). Single local user, localhost only; `user:<id>` addressing is ready for later. |
| R-Q8 | LLM provider library | **pi-ai** (`@earendil-works/pi-ai@0.87.1`, ADR 0003), used only inside `llm-providers` (D49); nothing outside `llm-providers` depends on it. |

There are no open questions. Only private names and the internal module layout inside a package are left to the implementer. Anything else the plan does not specify (behavior, a public shape, a dependency, security, stored data), or two sections that seem to disagree, is asked of the product owner, never assumed; the answer is recorded as an ADR in `plan/adr/` and the plan is corrected before the code lands.
