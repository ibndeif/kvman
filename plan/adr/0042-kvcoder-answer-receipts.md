# ADR 0042 — atomic kvcoder answers and idempotent receipts

Status: accepted by the product owner through choice and confirmation on 2026-10-10, before source. This records KVC-01/20 contracts, not implementation completion.

## Decisions

1. Keep `kvcoder.question.answer` user-only with input `{ questionId, answer }` and output `{ jobId: string | null }`. The first valid applied answer is final. Repeating the same normalized answer acknowledges it without applying it again; a different normalized answer fails the existing `VALIDATION_FAILED` clearly, without changing the old answer, executing work or leaking either answer. Do not add a new public error code, response field, approval policy or default.
2. Add the workspace-only collection `answer-receipts`, exposed internally as `answerReceipts`. IDs remain kernel-generated. New records require every field, without defaults: string `questionId`, `sessionId`, `turnId`, `toolCallId`; `questionKind` text|choice|confirm|approval; `answerFingerprint`, a 64-character hexadecimal SHA-256 digest; ISO `createdAt`. No phase, jobId, launch payload, raw answer or copied question/options. No new table, raw SQL, Home index or JSON unique index.
3. Re-read the question and receipt in the same synchronous store transaction that validates the exact active session/turn/pending binding, validates the answer, saves its held result/decision, deletes the question, updates pending and inserts the receipt. If the turn becomes runnable, prepare its next step intent in that transaction. Delegate approval requires a saved launch intent/permit before enqueue, with the additional KVC-04 permit data separately approved. No external enqueue, cancel, notification or effect inside the transaction. Failure rolls back the whole application. Serialized transaction rechecking enforces one receipt per question, not a separate read-then-write dedupe.
4. Receipt presence proves that the application committed, not that external work finished or an approval is reusable. Fingerprint the validated normalized approval boolean or ask value, with stable object-key ordering and preserved text/array order. Retain existing answer-validation/choice rules; do not treat arbitrary text/tool output as JSON. Approval dismissal and denial normalize to the same false decision. This digest identifies a retry; it is not a guarantee against guessing every secret from a hash.
5. After question deletion, the saved questionKind allows answer-shape normalization without reconstructing the prompt or options. A matching fingerprint is an acknowledgment only; a differing one is a conflict. An answer matching the original validated fingerprint does not need a new choice/options approval. With neither question nor receipt, retain `kvcoder/QUESTION_NOT_FOUND`; do not repair or replay unprovable lost legacy answers.
6. Returned jobId is only a hint for the current reference in the receipt's same turn, otherwise null. A stale retry never attaches the UI to a newer turn or replays work. Existing follow ownership/current-state verification from ADR0041 remains required.
7. Receipts remain with their turn. Keep-all has no hidden expiry. Delete them only with turn/session cleanup after owned work is confirmed stopped under KVC-05/31; active or uncertain tracking remains protected. No public DTO/status/outcome changes or cross-workspace API are approved here.
8. This ADR does not approve parent-start-permit, child-terminal-receipt or deleting-state fields for KVC-04–06. Present those separately before specification/source. The KVC-20 in-memory draft/ACK work is related but not completed by adding a receipt schema.

## Verification

Before source, update specification08 and Given/When/Then scenarios. Use native isolated stores and deterministic gates to check atomic application/rollback, concurrent same/different answers, schema/fingerprint/normalization, partial waits and last-pending intent preparation, delegate launch durability, cancel/stale-turn binding, legacy missing receipts, workspace ownership, retry after turn end/new turn, and retention/keep-all. No production fault hooks, sleeps, skips, masking retries or timeout increases. Run only related checks during implementation; all release gates after every selected change. User staged files/index, live home/settings/server3737 and release versions stay untouched.
