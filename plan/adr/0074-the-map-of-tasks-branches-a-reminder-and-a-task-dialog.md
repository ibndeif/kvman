# ADR 0074 — the map's nodes are tasks, branches drawn from real dependencies, a reminder to keep it live, and a task's dialog

Status: accepted by the product owner on 2026-10-13, before source. It amends ADR 0064 (2, 5, 6, and 12), ADR 0072 (2 and 5), and plan 08 §8.2, §8.3, §8.5, and §8.7.

## Context

The owner asked: "the step/node in the execution map considered a task, optimize the execution map and branching/parallism instuctions and the agent should follow it/update it when needed and mark the live progress so the user can track also when the user clicks on any step/task it should see the details in a popup for better exeperience".

The five maps in the owner's own chats show what the wording produced: the agent does change statuses (4 to 13 `update` calls a map), but four maps are a straight chain and the fifth has two roots and then a chain of ten. Nothing told the agent what makes one step wait on another, so it drew the order it thought of them in.

## Decisions

1. **A node of the map is a task, in words only** (asked; chosen over renaming the field and the stored data to `tasks`, and over keeping "step"). The screen and the agent's instructions say "task": the head of a task's dialog ("Task · In progress"), the line "{count} tasks of the execution map are not done.", the closed line "Map task", the connector's line in Configuration, the connector's and its commands' descriptions, the descriptions of the payload's fields, and every refusal the model reads. The payload's field `steps`, the stored `steps`, `kvcoder.map.get`, the command names (`kvcoder.map.step.update`), and the catalog keys are unchanged, so nothing stored is converted. The Plan part of the method says once that the tasks are the `steps` of the call.
2. **A press on a task opens a dialog over the page** (asked, with mockups; chosen over a bubble anchored to the task inside the panel). It replaces the detail under the diagram (ADR 0072, 2). The dialog's head has the word "Task" with the status, the task's title, and a Close button; then the rows About, After, Uses, Check, Evidence, and Note, each only when the task has it (Check always). Escape, a press on the backdrop, or Close closes it; Tab stays inside it; it takes the focus when it opens. It shows the task as the map has it now, so a change of status shows while it is open, and it closes when a new map no longer has the task.
3. **Branches come from real dependencies** (asked; chosen over a worker for every branch, and over one reply with no workers). The Plan part says: a task comes after another only when it needs that task's result (its file, its output, or its decision), never because of the order the agent thought of them in; tasks that touch separate files or parts and need nothing from each other are branches, given the same `after` or none, so the map shows them side by side; where branches meet, a task that joins them comes after every branch it needs; a chain is right only when each task needs the one before it; the project's own checks end the map, after everything they cover.
4. **The agent judges how ready tasks run** (same question). The Execute part says: small ready tasks are done together in one reply, and a large separate branch goes to a worker that runs beside the lead, as Delegate says; each is marked `doing` when it starts.
5. **The map is how the agent works, and it always says where the work is.** The Execute part says: take the tasks the map's calls return as ready, and never work on one the map does not have; mark a task `doing` before the first call on it, in the same reply as that call; mark it `done` with evidence as soon as its check passed, before the next task, never saved for the end; a task that can't be finished is `failed` with a note and one that turned out unneeded is `skipped` with a note; when the plan itself changes, set the map again before going on. A set that changes the tasks is confirmed again (ADR 0072, 3, unchanged).
6. **kvman reminds, and blocks nothing** (asked; chosen over instructions only, and over refusing a change while no task is marked). After the calls of a reply of the chat's own agent ran, kvman adds one line to the text the model reads for the last change of that reply, when all of these hold: the reply has a change that ran at once and succeeded (`fs write`, `fs edit`, or `shell exec`); the reply has no `execution-map set` or `update`; the chat's map has a task that is `todo` or `failed`; and no task is `doing`. The line follows a blank line: `[kvman: the execution map has <n> unfinished task(s) and none is marked doing. Mark the task this work belongs to with execution-map update, or set the map again when the plan changed.]`, with "task" for one and "tasks" for more. It is in the stored result's text and not in what the call's card shows.
7. **Once a reply, not once a call** (the smallest way to carry out 6; the owner may overrule). The option the owner chose said the line is added to "that call's result". It is added once, to the last such change of the reply, and not at all when the reply also tends the map: the map's calls of a reply run beside its changes, so a reply that marks a task `doing`, changes a file, and marks it `done` would otherwise be reminded wrongly, and five edits would carry five copies.

## Limits

- A change that waited for the person's approval, or was held back behind one, runs after its reply and carries no reminder. A worker's own changes carry none, and neither does a `delegate run`: the turn waits on it and its result is the worker's answer.
- A `shell exec` that only reads counts as a change, since kvman can't tell.
- Whether the agent draws real branches is still its judgement: kvman checks the map's shape (ADR 0064, 2), not whether a dependency is real.
