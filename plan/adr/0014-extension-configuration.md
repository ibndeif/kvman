# ADR 0014 — Each extension's configuration, on its own page

The product owner asked (2026-10-05) that the Settings page show only the general settings, that each extension be configured from the Extensions page, and that an extension's details be its configuration, not its API ("kvcoder should show the connectors list, with enable and disable"); then, that each extension manage its own configuration UI. Decisions 1 to 8 were asked with alternatives and mockups. Decisions 9 to 13 are the smallest way to carry them out; the product owner may overrule any of them.

## Decisions

1. **The Settings page holds kvman's own settings only** (asked; chosen over keeping kvwebui's keys there too). It lists the `kernel.*` keys and nothing else. Those keys are global only, so the page has no scope switch, and it no longer has a Secrets section or a list of groups. Its search box stays (ADR 0013, 6).
2. **An extension gives its configuration in `<namespace>.ui.get`** (asked; chosen over a custom component for everything, and over a link to one of the extension's normal pages). The answer gains an optional field, `configuration: View`: a view tree like a page's, on a page without params. The extension decides what is in it and in what order.
3. **A new built-in view component, `setting { key }`** (asked, with decision 2). It shows one of the extension's own settings as a row: its title, description, a control built from its schema, saving as it changes, "Changed" with a reset, and its details (ADR 0013, 2 to 5). An answer is invalid when a `setting` names a key that isn't one of the extension's own, or when a `setting` is anywhere but in `configuration` (a page, a panel, a list item, or a tree given to `kvman.View`).
4. **An extension has its own page** (asked; chosen over opening inside the card). The Extensions page is a list: each extension's title (`<namespace>.title`, else the namespace), package name, version, and source, as a link to `/kvwebui/extension/<namespace>`. That page has a link back, the same facts, "Remove", the switch "All workspaces | Only <workspace>" (ADR 0013, 2), the extension's configuration, and its secrets. A namespace that isn't loaded shows "page not found". The page isn't the target of a `navigate` or `link`, and can't be `kvwebui.home`.
5. **The Extensions page no longer lists an API** (asked; chosen over a closed "For developers" section). Commands, queries, handlers, their counts, and the "Public" badge leave the UI. `kvman extensions-list` and the documentation pages still give them.
6. **Secrets are on each extension's page** (asked; chosen over leaving them on the Settings page, and over a `secrets` view component the extension places). kvwebui adds a Secrets section at the end of every extension's page: that extension's secret names, masked, with Delete and "Add a secret" (a name and a password field). kvwebui renders it, since only `kernel.secrets.*` sets a secret and no value is ever shown.
7. **Any connector can be turned off** (asked; chosen over all but `ask`, and over only the added ones). The setting `kvcoder.connectors.disabled` is a list of connector names, `[]` by default, with the global and workspace scopes (asked; chosen over `kvcoder.connector.enable` and `disable` commands with kvcoder's store, which a preset couldn't set). A connector named in it is, for every session of the workspace, as if it weren't there: it is left out of the prompt's connector index, a call to it gets `There is no connector <name>. The connectors are: …`, and a subagent can't be given it. It applies from the next step. A name that no connector has is ignored. The base prompt isn't changed: with `ask`, `artifact`, or `subagent` off, the model learns it from that answer.
8. **`kvman.scope`** (asked, with "the switch follows the page"; chosen over a global-only key). The `kvman` object of a custom component gains `scope`, a live read-only ref: `'global'` or `'workspace'`, what the extension's page is set to save to. Outside an extension's page it is `'global'`. kvcoder's connectors list writes `kvcoder.connectors.disabled` in that scope with `kernel.settings.set`.
9. **`kvcoder.connector.list` says whether each connector is on.** Each row gains `enabled`. The list is still the registered connectors and the `kvcoder.connectors` programs; kvcoder's own six aren't rows of it.
10. **kvcoder's configuration** is four cards: Agent (`kvcoder.model`, `kvcoder.thinking`, `kvcoder.maxSteps`, `kvcoder.compactAt`), Shell (`kvcoder.shell.approval`, `kvcoder.shell.path`), Chats (`kvcoder.sessions.keep`, `kvcoder.welcome`), and Connectors (the custom component `kvcoder.connectors`, then `kvcoder.connectors`, the programs to add). The connectors list shows kvcoder's six, each with a catalog description, then the others with the description the agent reads and their owner, each with a switch. On "All workspaces" while the workspace has its own list, the switches are disabled and a line says so; a list set in the scope being edited shows "Changed" and a reset.
11. **kvai's configuration** is one card with `kvai.defaultModel` and a link to its Models page. kvcustomizer has no settings and gives no configuration.
12. **kvwebui's own configuration is built in**, since kvwebui is the host and has no `ui.get`: Appearance (`kvwebui.theme`), Navigation (`kvwebui.nav.order`, `kvwebui.nav.hidden`), and App (`kvwebui.title`, `kvwebui.home`, shown locked).
13. **An extension without a configuration** shows "This extension has nothing to configure." above its secrets, and no scope switch. The Extensions page's search box filters the extensions by title or package name.

## Consequences

- Plan 06 §6.3, §6.4, and §6.6, and plan 08 §8.2 to §8.4, §8.6, and §8.7 are corrected.
- `@kvman/sdk/web` gains the `setting` view and `Kvman.scope`.
- The catalog keys `kvwebui.extensions.commands`, `.queries`, `.settings`, `.handlers`, and `.public` are removed.
