# ADR 0044 — Execution-time connector permissions

The owner selected KVC-10 in the 34-item review: an earlier tool listing or approval must not authorize a connector that is no longer permitted when execution is attempted. This records that decision using existing data only; it does not approve additional KVC-04–06 data.

## Contract

1. Prompt construction and execution share the existing grant predicate: loaded connector ownership, current registration/setting presence, workspace disabling, top-level opt-in, stored child connector scope, passed binary checks, and MCP/worker presence. A child never has `delegate`; `ask` bypasses its connector list but never global disabling. Workspace settings continue to override global settings.
2. Immediate calls, help, and approved held calls recheck permissions and exact canonical step authority. Prepare settings/kernel metadata asynchronously, then reread the session/root, current turn/intent and registry rows in a synchronous store transaction. Resolve the command from those current rows, not the prompt's cached target. Held execution additionally requires the exact held call still belongs to that turn.
3. Ordered file/artifact work reserves its queue slot synchronously in the model-order map, before independently awaited permission preparation. It checks again after the queue wait, directly before inline `ctx.exec`. A target or approval requirement that changes after initial evaluation cannot silently reuse the earlier dispatch decision; return an existing explicit validation error asking for a fresh call. Normal held approvals still resolve current permitted targets under the existing name-based approval contract; no registration fingerprint is added.
4. A withdrawn grant returns an explicit existing error result through normal call/held-result settlement. No effect is dispatched, the turn may continue normally, and an existing card need not be proactively removed. Do not undo effects already begun. Existing risky/default/approval policies and legacy shell-call denial remain unchanged.
5. Child instructions and captured `session.connectors` remain snapshots (ADR0021, 7/24/29); no retroactive intersection with edited worker configuration is introduced. Top-level opt-in inheritance remains live (ADR0027, 10), with no new disable API. Missing/cyclic ancestry cannot prove a grant and is refused rather than looping.
6. Delegation must also check after asynchronous worker selection before creation/dispatch. Approved delegation uses its existing question/pending identity. A separately queued foreground program can prove current waiting-turn membership using an unambiguous exact `runId`/`toolCallId` pending binding; recorded argv stays captured. Publishing `jobId` after enqueue is not a prerequisite for legitimate early execution.

## Bounded implementation and limits

The first implementation slice is immediate/held/help/ordered connector dispatch. The next bounded slice rechecks after worker selection and in creation transactions; foreground starts retain the exact waiting/open turn and complete pending binding across asynchronous grant preparation. Positive delegate approval retains its originating question/turn identity after the existing question-consumption transaction, rather than resolving whichever current turn happens to share a tool-call ID. Revocation settles only an exact still-current binding with an explicit error; stale bindings do not mutate a newer turn. A queued program rereads its running row and current grants after metadata preparation immediately before spawn. A foreground run requires unambiguous exact worker pending membership; a background run can check current grants only, not its unrecorded origin. Current enabled worker name/kind and saved passed checks remain prerequisites, but captured instructions, scope and argv are not replaced by newly edited configuration. These boundaries remain unverified until implemented and tested; neither slice alone completes KVC-10.

Background worker/child/process records do not retain originating turn/call authority. Their durable origin approval and exactly-once start cannot be reconstructed from current data; additional04–06 data remains unapproved. Kernel/settings state cannot be atomically locked with kvcoder store validation, and an inline-dispatch guard does not fence every downstream asynchronous effect. No claim of atomic revocation of already dispatched work or sandbox enforcement is made.

Terminal program completion and job-loss handling must not bypass these existing foreground bindings: capture the exact pending resource/turn in the terminal read transaction and revalidate it before deferred settlement, and decide handler termination with exact run membership in one synchronous transaction. This fences newer turns without adding parent receipts, atomic normal child-delivery semantics, background origin fields or KVC-06 completeness.

No public input/output, collection, persisted field, migration, default, retry/backoff, proactive-card invalidation, retention, or process-lifetime redesign is introduced.
