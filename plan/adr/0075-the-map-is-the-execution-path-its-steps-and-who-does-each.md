# ADR 0075 — the map is the execution path: its steps, and who does each

Status: accepted by the product owner on 2026-10-13, before source. It amends ADR 0074 (1, 3, 4, and 6), ADR 0072 (7), ADR 0065 (the Delegate part), and plan 08 §8.2, §8.5, and §8.7.

## Context

After ADR 0074 the owner wrote: "there is a misunderstanding about execution map … the execution map is the execution steps that the agent generates to complete the task (like a todo concept but it is not a todo), using the execution map the agent says that after my analysis and discovery I found that that this execution path is the best practical and fastest way to accomplish the user requirements using the existing connectors like ui/ux, architect, etc... and the agent should update its progress using it. so treat the execution map as an implementation plan".

Three things in the prompt were against that. ADR 0074, 1 had renamed a node to "task". ADR 0072, 7 made a step "the file or the few files that change together, a test, or a command", so a map read as a list of file edits: in every map of the owner's chats the steps use only `fs` and `shell`, though the chat has the workers `ui-ux`, `architect`, `tester`, and `reviewer`. And the Delegate part allowed a worker "only when it is separate work that runs beside yours, or a fresh review", which keeps a designer or an architect out of the path.

## Decisions

1. **A node of the map is a step, in every word** (asked; chosen over keeping "task"). ADR 0074, 1 is undone: the screen, the connector's and its commands' descriptions, the payload's field descriptions, the refusals, and the method say "step" again ("Step · In progress", "{count} steps of the execution map are not done.", "Map step"). The reminder of ADR 0074, 6 reads `[kvman: the execution map has <n> unfinished step(s) and none is marked doing. Mark the step this work belongs to with execution-map update, or set the map again when the plan changed.]`. ADR 0074's dialog, its branches, its Execute rules, and the reminder's conditions stay.
2. **The map is the agent's execution path.** The Plan part says what the map claims: the steps that, from what the agent found, are the best, most practical, and fastest way to deliver what the person asked with the connectors and workers it has. It is still the implementation plan the person reads and agrees to (ADR 0072, 3), made only after the agent looked (ADR 0070, 3), and detailed, not an outline.
3. **A step is one stage of the path** (asked; chosen over keeping the file-level rule). It says what gets done, who does it, and how it is checked. It may cover the few files that change together; it is always concrete, something the agent can name before it starts, never a phase such as "implement" or a whole feature. This replaces "the file or the few files that change together, a test, or a command to run" of ADR 0072, 7; the limits (1 to 40 steps) stay.
4. **Who does a step is chosen by fit, and named in `uses`** (asked; chosen over always starting with an architect and ending with a reviewer on larger work, and over leaving the delegate rules). For each step the agent chooses whoever does it best and fastest: itself, with a connector, for an ordinary change; a worker of the `delegate` connector whose description fits when the step needs that skill, such as a designer for a screen or flow whose design is a real choice, an architect for a structure decision that spans several parts, a tester for tests that are a piece of work of their own, or a reviewer for a finished change that is risky or wide. The prompt names roles, not worker names, since the workers are a setting. A worker starts with none of the conversation, so a step goes to one only when its skill, or its running beside the lead, is worth that, and never for a small change.
5. **The Delegate part allows it.** Its first sentence becomes: a step goes to a worker when the worker does it better or faster than the lead would: a specialist whose skill the step needs, separate work that runs beside the lead's, or a fresh review of a finished change. The rest is unchanged: not what a few calls would do, one review of a piece of work, the brief, and checking what comes back.
6. **Execute follows `uses`.** A step whose `uses` names a worker is handed to that worker with `delegate run`, and the lead checks the answer before it marks the step done.

7. **A branch means delegation** (the owner's own proposal: "what about making branching means delegation?"; asked, and chosen as an instruction over kvman refusing a map whose side-by-side steps name no worker, and over leaving branches as steps that don't depend on each other). It replaces ADR 0074, 3 and 4. Steps side by side on the map run at the same time, each done by a worker. The lead's own steps are one line, each after the one before, in the order it will do them. It draws a branch only for a piece of work it hands to a worker: one that needs nothing from the other branches, touches files or parts no other branch touches, is large enough to be worth a worker that starts with none of the conversation, and whose step names the worker in `uses`. Branches that start together have the same `after`, or none; small independent changes are not split into branches. Where branches meet, a step that joins them comes after every branch it needs. In Execute, steps that are ready together are branches: the lead marks each `doing` and starts them all in one reply, one `delegate run` each. The sentences "a step comes after another only when it needs its result", "a chain is right only when each step needs the one before", and "do small ready steps together in one reply" are removed.

## Limits

- Which specialist fits, and whether one is worth its cost, is the agent's judgement; kvman checks neither.
- Decision 7 is a rule of the prompt. `execution-map set` still takes side-by-side steps that name no worker (ADR 0064, 2), and kvman doesn't check that two branches keep to separate files.
- A worker can't ask the person (ADR 0063), so a branch's questions come back in its answer for the lead to ask.
