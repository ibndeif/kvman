# ADR 0080 — the builder knows kvman, builds on what exists, and never edits kvman itself

Status: accepted by the product owner on 2026-10-14, before source. It amends ADR 0010 (2, 9, 15–17), ADR 0022 (7), ADR 0023 (4), ADR 0027 (13), ADR 0030 (8 and 9), plan 09 §9.1 to §9.4, and plan 10.

## Context

The owner asked for a review of building kvman extensions and presets: "optimize the prompts and the docs so the agent knows everything needed to build kvman extensions and presets. kvman's source code is never edited under any circumstances, and the extensions must use the available APIs of kvman or of existing extensions. The builder should be able to depend on existing extensions to deliver the person's needs, or build something new, and understand everything so it can architect and develop the person's requirements clearly and explicitly."

The review found:

- Nothing told the agent that kvman's own code is off limits. `fs` is limited to the workspace folder, but in the Home workspace that folder holds `~/.kvman` (the database, `secrets.json`, the presets), a project's `node_modules/@kvman/*` is inside the workspace, and so is a checkout of kvman's source.
- Nothing said that an extension reaches kvman only through the SDK and the public names of the kernel and the installed extensions, or what to do when a need isn't offered.
- The agent could not learn the input and output of another extension's public commands and queries: `extensions-list` gives names only, and an extension without docs pages gives nothing more.
- A project that declares a `kvman.dependencies` entry could never pass `ext check`: `kvman-check` and the scaffold's test load the project alone ("notes depends on @kvman/kvai, which is not in this run."), and a published extension can't be loaded as `path:`, since its `src/` isn't shipped. The preview loads kvai and kvwebui only, so a project that depends on kvcoder didn't start there. So no project could register a kvcoder connector, section, or slash command and pass its checks.
- The `sdk` guide left out the format of `kvman.dependencies`, `ctx.files`, `ctx.processes`, `ctx.schedule`'s `key` and `cancel`, `ctx.cancel`, `syncOnly`, the size limits, `progress`, `kernel.workspace.deleted` and every handler point's input, `ctx.settings.set`, and the testkit's workspace, clock, async, and restart calls.
- Nothing mapped a need to the extension that serves it (a page to kvwebui, a model call to kvai, something the agent can do to kvcoder), and the guide didn't tie building to the execution map the lead agent already makes (ADR 0075).
- `building` was out of date: "Six commands change the app" left out `preset-set`, `preset-reset`, and `preset-save`; `health-get` lacked `rolledBack`; its Read step left out `conventions`.
- The rule that keeps kvman's words from the person applied to developers too, so a developer's design couldn't be stated exactly.

## Decisions

1. **kvman itself is never edited** (the owner's rule; asked how, and chose strict rules in the prompts over adding a hard guard to kvcoder's `fs`). The `/build-kvman` guide, the `conventions` guide, and the scaffold's `AGENTS.md` name what the agent never writes, deletes, or moves, with `fs` or the shell, in any workspace and for any reason:
   - kvman's packages, wherever they are: the `kvman` program and every `@kvman/*` package (kernel, sdk, cli, testkit, kvai, kvwebui, kvcoder, kvbuilder), in the global install, in any `node_modules`, or as source checked out in the workspace;
   - kvman's home folder (`~/.kvman`, or `KVMAN_HOME`): its database, `secrets.json`, presets, logs, and installed extensions;
   - a project's `dist/` and `node_modules/`.

   The running app changes only through the `kvman` connector; what a bundled or installed extension does changes only through its settings, its public commands, or a new extension built on its public names. A request that none of those can meet is answered plainly: what can't be done, and what can.
2. **Only the public APIs.** An extension uses `@kvman/sdk`'s `ctx` and the public commands, queries, and registries of the kernel and of the installed extensions. It never imports the kernel or another extension's code (beyond `import type`, or a subpath a declared dependency exports), never reads or writes kvman's database, `secrets.json`, or another extension's files, and never runs `kvman` or the kernel itself. When what it needs isn't offered, there is no workaround: the agent says what is missing.
3. **`kvman extensions-get { name }`** (asked; chosen over documenting `query-get` of `kernel.extensions.list`, and over docs pages only). The public query `kvbuilder.app.extensions.get { name }` → `{ name, version, source, namespace, commands, queries, settings }` gives one running extension by package name, from `kernel.extensions.list` and `kernel.settings.list`: its public commands and queries as `{ name, description, input, output }` with their JSON Schemas, and its settings as `{ key, description, scopes, schema }`. Private commands and queries are left out, since another extension can't call them. An unknown name fails `NOT_FOUND`. It never asks the person. It is the exact companion of the installed index and of an extension's docs pages; the name and version it gives are what a dependency on the extension declares.
4. **Dependencies load from the project's `node_modules`** (asked; chosen over an explicit testkit option, and over documenting the limit). A project installs each extension it declares in `kvman.dependencies` as an exact devDependency (`npm install --save-dev --save-exact <name>@<version>`), which also gives it typed calls (plan 03 §3.2). `createTestKernel` then loads every declared dependency that `extensions` doesn't name, and their own, found in a `node_modules` folder at or above the dependent's folder, by its `main`, as a bundled extension loads. So `kvman-check` and the project's tests load them with no new option. A declared dependency that isn't installed is, in `kvman-check`, one finding per dependency that names the npm line to run; `createTestKernel` leaves it to the kernel's own `EXTENSION_INVALID`.
5. **The preview adds bundled dependencies** (asked; chosen over documenting a preset for them). The generated preset of `kvman-preview` adds, as `bundled`, each bundled extension that a previewed project declares in `kvman.dependencies`, and those that such a bundled extension declares, read from the project's installed copy. A given preset is used as it is, with the dev extensions added (ADR 0009, 119). The testkit knows the bundled names as a constant, which a test checks against the `kvman` package's dependencies.
6. **The four guides hold the knowledge** (asked; chosen over a fifth `architecture` guide). The built-in topics stay `conventions`, `i18n`, `presets`, and `sdk`. `sdk` becomes the complete reference of the extension API and its tests; `conventions` gains "Never edit kvman" and "Use what exists", a map from a need to the extension or API that serves it, with the page to read; `presets` and `i18n` are checked against the plan.
7. **The guide of `/build-kvman`** keeps its order (ADR 0023, 4; ADR 0030, 9) and gains two parts: after the rules for a person, **kvman itself is never changed** (decisions 1 and 2), and before the method, **Design first**: from the installed index, `extensions-get`, and the docs pages, decide what the work reuses and what it adds, which extensions it depends on, and what it registers, then put that in the execution map in the person's words. The method gains the dependency steps (decision 4) and `extensions-get`.
8. **Match the person** (asked; chosen over plain words with everyone). The agent speaks in plain words by default. When the person uses kvman's own words first (extension, preset, setting key, command), they are a developer, and the agent may use those words too, in replies, questions, call descriptions, and the execution map.
9. **`building` is corrected**: the nine commands that change the app, `health-get`'s `rolledBack`, `conventions` in the Read step, and the new parts above. The scaffold's `AGENTS.md` gains decisions 1, 2, and 4.
