# ADR 0009 — Implementation decisions

Status: accepted, 2026-09-30. Questions that came up while building, decided with the product owner milestone by milestone.

## M1.1 Monorepo

1. **TypeScript 6.0.3.** The latest TypeScript (7.0.2, the native compiler) has no compiler API, and typescript-eslint supports only TypeScript below 6.1. The monorepo uses TypeScript 6.0.3 for typecheck, build, and lint, and the kvdev scaffold pins the same version. It moves to 7 when typescript-eslint supports it. This is an exception to "latest stable" (`CLAUDE.md` §5).
2. **Tooling.** Pinned exactly: ESLint 10.11.0 with typescript-eslint 8.71.0, Vitest 5.0.2 with its Vite 8.3.1 peer, @changesets/cli 3.0.3, and @types/node 24.19.0 (matching Node 24). The import walls are a rule of the repository's own (`eslint/`), as in archive/v2, not a plugin. There is no turbo: `pnpm -r` runs the package scripts in dependency order.
3. **The 300-line limit covers every file, tests included.** A big test suite splits into several files by topic.

## M1.2 SDK

4. **Collections take a schema.** `ctx.store.collection(name, schema)` takes a zod schema for its documents (without `id`). `insert` and `update` check the document against it (`VALIDATION_FAILED`), and every read parses through it, so a stored document that no longer fits fails `VALIDATION_FAILED` loudly. Documents are typed from the schema. Storage is unchanged: JSON text in the kernel's SQLite table, which extensions never see. `kv` stays untyped: `get` returns the JSON value, or `undefined` for a missing key.
5. **Times** in kernel rows (jobs, files, schedules, processes) are ISO 8601 strings, such as `2026-09-30T03:00:00.000Z`.
6. **Manifest checks.** Every extension lists `@kvman/sdk` in `peerDependencies`; a missing peer fails `EXTENSION_INVALID`. An unknown key in the `kvman` field fails `EXTENSION_INVALID` too.
7. **Shapes.**
   - `Workspace` is `{ id, name, path }`.
   - `Caller` is `{ kind: 'user' }`, `{ kind: 'extension', name }`, or `{ kind: 'kernel' }`.
   - `Job` is `{ id, name, input, workspaceId, caller, status, attempts, retries, output?, problem?, createdAt, startedAt?, endedAt? }`, with `status` one of `queued`, `running`, `succeeded`, `failed`, `cancelled`.
   - `File` is `{ id, name, type, size, owner, workspaceId, createdAt }`, with `owner` `{ kind: 'user' }` or `{ kind: 'extension', name }`.
   - `Problem` is `{ code, message, params? }`, with `params` a record of JSON values. `ctx.problem()` returns a `ProblemError` (an `Error` carrying `.problem`); throwing it fails the job with that Problem.
   - The envelope is `{ ok: true, …data }` or `{ ok: false, problem, jobId? }`.
   - `kv.get(key)` returns the value or `undefined`; `collection.get(id)` returns the document or `undefined`.
   - A `find` or `count` filter is equality on top-level fields, with `string`, `number`, `boolean`, or `null` values.
   - `ctx.files.write(name, data, type)` takes `data` as a `Uint8Array` or a string.
   - `ctx.secrets.get(name)` returns the string or `undefined`; `set(name, value)` takes a string.
   - `ctx.settings.get(key)` is typed through an augmentable `Settings` map, like `Commands`, and returns `unknown` for an undeclared key.
8. **Smaller shapes, settled while writing the SDK** (following the plan's wording):
   - `transaction` is on `ctx.store` only; its `tx` reaches the home-wide scope through `tx.global`, so one transaction covers both.
   - `ctx.job.progress(data)` returns nothing; an over-long chunk throws `TOO_LARGE` at once.
   - `ctx.processes.log(name, { tail? })` resolves to the text of the last lines.
   - `ctx.files.get(id)` of a missing id fails `NOT_FOUND`, like `kernel.files.get`.
   - The `kernel.job.cancelled` point's `reason` is a string; `kernel.process.exited` gives `exitCode` and `signal`, each `null` when absent (as Node reports them).
   - A preset's `settings` is optional, and an unknown preset key fails `VALIDATION_FAILED`, like the manifest's `kvman` field.
   - Namespaces are lowercase with kebab-case words (`kvai`, `kv-ai`), matching the naming rule for names.
   - The SDK's `Json` type lets an object field be `undefined`, which JSON leaves out, so schemas with optional fields (which zod infers as `field?: T | undefined`) fit the store, progress, and job calls.

## M1.4 Extensions and workers

9. **Versions.** kvman's packages start at 0.1.0, which signals pre-1.0 while nothing is published. The bundled extensions' `@kvman/sdk` peers and `kvman.dependencies`, the presets, and the kvdev scaffold use `^0.1.0`; the plan's examples are changed to match. 1.0.0 comes with the first stable release.
10. **Test workers.** `createTestKernel` uses `kernel.workers` 1 unless the test's `settings` set it; everything else is the kernel's default.
11. **Test Home.** A test kernel's Home workspace is a temporary folder of its own, beside the temporary kvman home, and both are removed on `close()`. Tests never touch the user's files.
12. **Registrations are sealed** when an extension's entry returns. A later `register*` call (for example, inside a handler) fails `EXTENSION_INVALID`, naming the extension, so every worker keeps the same registrations.
13. **Testkit options.** `settings` are the test run's preset settings (so required keys can be set), and `secrets` is `{ "<extension package>": { "<name>": "<value>" } }`, written to the temporary `secrets.json` before the extensions load.

## M1.5 Async jobs and schedules

14. **What retries.** An async attempt that fails `HANDLER_FAILED` (a thrown non-Problem), `TIMEOUT`, `WORKER_CRASHED`, or `INTERRUPTED` is retried with backoff while retries remain. Every other Problem, the kernel's or an extension's, ends the job `failed` at once: running it again would fail the same way.
15. **The test clock settles.** `await kernel.clock.advance(ms)` moves the fake time, fires the due retries and schedules, and resolves once no job is running or due; `advance(0)` waits for the current work.
16. **Test restart.** `await kernel.restart()` stops the test kernel as Ctrl+C does (unfinished attempts fail `INTERRUPTED`), then starts it again on the same home, Home folder, extensions, and settings, and resolves when it's ready. The fake clock carries over. `restart({ stoppedForMs })` moves the fake clock while the kernel is stopped, as time passes while kvman isn't running.
17. **Cancel.** A queued job ends `cancelled` at once, and its handler never runs. Cancelling a finished job does nothing. An unknown id fails `NOT_FOUND`. A running root job, sync or async, is aborted and ends `cancelled` when its handler settles, or at its timeout if it ignores the signal. A nested sync job's id is not a root and isn't cancellable on its own; it shares its root's signal.
18. **Dropped stopping handlers.** A `kernel.stopping` handler job that hasn't finished by the end of shutdown ends `failed` with `INTERRUPTED` and is never retried, so it is dropped, not resumed.
19. **Where rows are written.** Every job and schedule row is written by the main thread, which owns the kernel's clock, so ids, FIFO order, retries, and schedules follow one clock (the fake one in tests). A worker checks a call (the name, `NOT_A_COMMAND`, `NOT_PUBLIC`, `READ_ONLY`) and asks the main thread to queue it.
20. **V8's wasm code GC is off.** Worker threads crashed the process now and then (SIGSEGV, about one test file run in ten). gdb showed V8's wasm code GC freeing the machine code of a wasm module shared across isolates while another isolate still ran it (`NativeModule::FreeCode` from `Runtime_TierUpWasmToJSWrapper`). The wasm is Node's TypeScript stripper, which every worker runs to load `.ts` files. The kernel calls `v8.setFlagsFromString('--no-wasm-code-gc')` once at start, before any worker: 0 crashes in 54 runs. Stripping works as before; its compiled code (a few MB, shared) is never reclaimed. It is removed once a Node release fixes the V8 bug.
21. **SQLite syncs at `NORMAL`.** With `synchronous = FULL`, every commit waited for an fsync, and queued jobs ran at 324 jobs/s against the 500 target. With `NORMAL`, SQLite's usual setting for WAL mode, they run at about 700 jobs/s. A kvman crash or kill loses nothing, so every crash invariant (§12.2) holds; only a power loss or an OS crash can lose the last commits, and the database is never corrupted.

## M1.6 Workspaces, kernel API, localization, hot reload

22. **Workspace identity.** A workspace's id is a UUIDv7 and its name is its folder's basename (Home's too; the UI may label the id `home` with a translated key). `kernel.workspace.open` resolves the path with `realpath`, so a symlink or a trailing slash reopens the same workspace, and opening Home's own folder answers Home. `kernel.workspace.list` gives Home, then the others in the order they were first opened.
23. **JSON Schema.** `kernel.extensions.list` and `kernel.settings.list` convert zod schemas with zod's own `z.toJSONSchema`: inputs and settings in its `input` mode, outputs in its `output` mode. A part JSON Schema can't express (`z.date()`, `z.custom`, a transform's output) becomes `{}`. Validation stays zod's, so only a UI form gets vaguer.
24. **Ownership and scope.** `ctx.settings.set` of another extension's key, and unlinking a file the caller doesn't own, fail `NOT_PUBLIC`. `ctx.files.*`, `kernel.files.get`, `kernel.files.list`, and `kernel.files.unlink` see only the files of the call's workspace (`NOT_FOUND` otherwise). `kernel.jobs.get` finds a job of any workspace by id, as `GET /api/jobs/:id` does.
25. **Catalogs.** `locales/<lang>.json` is a flat JSON object of strings, `{ "<namespace>.x.y": "text" }`, and every key starts with its owner's namespace (`kernel.` for the kernel). An unreadable catalog, or a key outside the namespace, fails the load with `EXTENSION_INVALID`. The catalog of a language is `en` overlaid with that language; the last fallback, to the key itself, is the UI's (vue-i18n shows a missing key). Placeholders use vue-i18n's `{name}` syntax.
26. **Hot reload.** File events are batched until 200 ms (real time) pass without one; then one reload runs. It logs `extension reloaded` (with the extension and its revision) or `extension reload failed` (with the Problem's code). A reloaded extension whose own manifest now breaks a start rule (its namespace, its sdk range, its own dependencies) fails the reload and keeps the old code; only dependents' ranges and dropped names merely warn. Tests wait with `vi.waitFor` on what's public: a revision in `kernel.extensions.list`, or the log line. The testkit gains nothing.
27. **Processes.**
    - `cwd` defaults to the workspace folder, and a relative `cwd` resolves against it. `env` is merged over kvman's own environment.
    - Each start truncates the process's log, so the log shows the current run. `log`'s `tail` defaults to 100 lines.
    - `list()` and `kernel.processes.list` show running processes only: a process's row is deleted when it exits.
    - `stop` of an unknown or exited name fails `NOT_FOUND`, and `stop` resolves once the process has exited. `log` of a name that never ran fails `NOT_FOUND`; an exited process's log can still be read.
    - `kernel.process.exited` is delivered for every process that exits by itself. A process isn't a job, so the `fromHandler` mark doesn't apply.
28. **Extension list.** In `kernel.extensions.list`, `settings` is `[{ key, description, scopes }]` and `handlers` is `[{ point, description }]`. Private commands and queries are listed too (each carries `public`). The kernel itself isn't listed.
29. **Health and secrets.** In `kernel.health.get`, `version` is kvman's version (the kernel's), `preset` is the preset's name, `mode` is `web` (the only mode now; a test kernel reports `web` too), `workers` is the pool size, and `uptimeMs` is measured on the kernel's clock (the fake one in tests). `kernel.secrets.set` and `kernel.secrets.delete` name an extension of the run (`NOT_FOUND` otherwise), and deleting a missing secret does nothing, like `ctx.secrets.delete`.
30. **Process logs per workspace.** A process's name is unique per extension and workspace, so its log is `logs/processes/<extension>/<workspaceId>/<name>.log` (fixing `02` §2.16 and `01` §1.3, which shared one log across workspaces). A process name is lowercase kebab case, such as `preview` or `web-watch`; anything else fails `VALIDATION_FAILED`, so a name can't leave its folder.
31. **Unknown languages.** Only the languages in `kernel.health.get` have a catalog. The catalog of any other code fails `NOT_FOUND`, as `kernel.language` refuses such a code.
32. **The `kernel` namespace is reserved.** The kernel's names, keys, and error texts live under `kernel`, so an extension whose namespace is `kernel` fails the load with `EXTENSION_INVALID`, as when two extensions claim one namespace.
33. **A process that can't start.** `ctx.processes.start` whose command can't be started (not on the PATH, not executable, or a missing `cwd`) fails `VALIDATION_FAILED`, with the process name in `params` and the OS reason in the English message. No log file is kept for it.
34. **Stopping is a write.** `ctx.processes.stop`, like `start`, runs only in commands (`READ_ONLY` in queries); `list` and `log` are reads.

## M1.7 HTTP

35. **HTTP tests come with the CLI.** Plan 12 §12.1 runs HTTP tests against a real kvman child process, which only exists once the CLI does (M1.8). M1.7 writes every HTTP scenario, builds the routes, and unit-tests the pure parts (the Host and Origin check, body parsing and caps, the event stream's format, static paths); the route scenarios are tested in M1.8 through the CLI. The HTTP benchmark runs in M1.7, in-process, against a real listener.
36. **Origin matches its Host.** `Host` must be `127.0.0.1:<port>` or `localhost:<port>`. An `Origin`, when present, must be exactly `http://` plus that same Host, so a page on one name can't call the other. `Origin: null` is rejected.
37. **File routes name their workspace.** `POST /api/files` and `GET /api/files/:id` both require `?workspaceId=` (missing: `VALIDATION_FAILED`); a file of another workspace is `NOT_FOUND`. Commands and queries keep the Home default.
38. **Downloads are attachments.** `GET /api/files/:id` answers with the file's type, `Content-Disposition: attachment` with its name, and `X-Content-Type-Options: nosniff`, so a browser saves a file and never renders it on kvman's origin.
39. **Uploads.** An upload without `Content-Type` is stored as `application/octet-stream`. A missing or empty `name` fails `VALIDATION_FAILED`. Over 1 GiB fails `TOO_LARGE`, and the partial file is removed.
40. **Bodies.** The command or query is resolved before the body is read: an unknown name, the wrong route, or a private name fails `NOT_FOUND` or `NOT_PUBLIC`. The raw body is capped at the target's `maxInputBytes` and read no further past it (`TOO_LARGE`). A body that isn't JSON gets status 400 with the envelope (`VALIDATION_FAILED`). A JSON body of the wrong shape (strict `{ input, workspaceId?, async? }`; the queries route has no `async`) fails `VALIDATION_FAILED` at 200. A failure before a job starts carries no `jobId`.
41. **The web home.** When kvman's HTTP server starts (web mode, only through the CLI), the extension whose namespace is `kernel.web.home` must exist and declare `kvman.web`; otherwise the start fails `EXTENSION_INVALID`. A test kernel has no HTTP, so it isn't checked. A miss outside `/api` is a plain 404; an unknown `/api/…` route is the envelope with `NOT_FOUND`.
42. **The stream.** Each event is `event: progress`, `result`, or `problem`, whose `data:` is the JSON (`{ source, data }`, the output, or the Problem); then the stream closes. An unknown id, or a sync job's (which has no row), gets the envelope with `NOT_FOUND` instead of a stream. There is no heartbeat. A cancelled job ends with a `problem` event (`CANCELLED`).

## M1.8 CLI

43. **The lock.** `kvman.lock` is JSON, `{ "pid": <n> }` from start step 1, and `{ "pid": <n>, "port": <n> }` once kvman listens. It's taken with an exclusive create; a lock whose pid isn't alive is replaced. A second kvman that finds a live lock without a port (the first is still starting, for example at the trust prompt), or whose port doesn't answer (the pid was reused), fails `KVMAN_RUNNING` with the pid in `params`. kvman removes its lock when it stops or fails to start.
44. **Hand-over compares only given flags.** A bare `kvman` hands its folder to whatever kvman runs. A given `--preset` is resolved and its file's `name` compared with `kernel.health.get`'s `preset`; a given `--mode` is compared with its `mode`. A difference fails `KVMAN_RUNNING`. `--port` and the other flags aren't compared.
45. **Preset names and files.** A `--preset` value that contains `/` or `\`, or ends in `.json`, is a file path, relative to the start folder; any other value is a name, looked up in the bundled presets and `<home>/presets/<name>.json`. An unknown name or a missing file fails `VALIDATION_FAILED`, like an invalid preset. A preset's `name` needn't match its file name. Until M2.5 adds `coder` and `dev`, kvman has no bundled preset, so a bare `kvman` fails `VALIDATION_FAILED`; the rule for a name found both bundled and in `<home>/presets/` is tested on the preset lookup itself until then.
46. **`--port 0`** lets the OS pick a free port; the printed URL and `kvman.lock` carry the real one. The `kernel.port` setting stays 1–65535.
47. **npm installs skip peers.** npm installs peer dependencies, so it would fetch every extension's `@kvman/sdk` peer, which the kernel replaces with its own copy (and `--omit=peer` still fetches it). The install is `npm install --ignore-scripts --omit=dev --legacy-peer-deps --prefix extensions/<name>@<version> <name>@<version>`, which skips peers. A failed install (npm missing, an unknown package or version, the network) fails `EXTENSION_INVALID` with the name and version, and removes the partial folder. Tests point npm at the in-test registry with npm's own environment (`npm_config_registry`, `npm_config_cache`).
48. **Trust.** Refusing (no terminal and no `--yes`) and answering anything but `y` both fail `EXTENSION_INVALID`, listing the versions not accepted in `params`. An accepted npm version is remembered as its name, version, and `npm:<version>`; a `path:` one as its name, its `package.json` version, and `path:<absolute folder>`, so the same relative path in another preset asks again. A test kernel accepts every version.
49. **The terminal.** stdout gets the URL line and the trust prompt. stderr gets each log record at `--log-level` as one line, `HH:MM:SS LEVEL message`, and a failure's Problem (`CODE: message`) with a hint for its code. Terminal text is English, like Problem messages and logs (the UI translates by code). `--log-level` filters both `logs/kvman.log` and the terminal.
50. **Signals, exit codes, and the browser.** Ctrl+C (SIGINT) and SIGTERM both run the stop sequence, then kvman exits 0. A second signal exits 130 at once, removing `kvman.lock`. A failed start exits 1. If the browser command fails, a warning is logged and kvman keeps running (the URL is already printed).

## M2.1 kvai

51. **pi-ai is `@earendil-works/pi-ai` 0.99.1.** `@mariozechner/pi-ai` is deprecated in favor of `@earendil-works/pi-ai`, and its last version (0.73.1) doesn't list `claude-sonnet-5-5`. kvai uses `@earendil-works/pi-ai` 0.99.1, pinned exactly: its built-in list has `anthropic/claude-sonnet-5-5`, so the presets keep that default. It brings `@earendil-works/pi-telemetry`, type contracts that make no network calls. This replaces ADR 0003, 4.
52. **Every built-in provider is listed.** `kvai.provider.list` and `kvai.model.list` show all of pi-ai's built-in providers and their chat models. Providers that need more than a key (Amazon Bedrock, Google Vertex, Azure OpenAI, the Cloudflare ones, OpenAI Codex) are listed too, and a call to one fails `kvai/KEY_MISSING` or `kvai/PROVIDER_ERROR` until a later phase configures them.
53. **Keys.** A built-in provider needs its kvai secret `<id>.apiKey`: without it, `kvai.complete` fails `kvai/KEY_MISSING` before any request, so pi-ai never falls back to an environment variable. A custom `api` provider sends its key when the secret is set; otherwise it sends the placeholder key `none`, since pi-ai's wire APIs refuse a request without a key, and keyless servers (Ollama, vLLM) ignore it. A delegate provider never needs one. `kvai.provider.list` shows `key: 'set'` or `'missing'` by whether the secret exists. (Changed by 79: `status` replaces `key`.)
54. **Model ids.** `kvai.model.list` returns `id` as the full `<provider>/<model>`, the value `kvai.complete` and `kvai.defaultModel` take, and `kvai.model.remove { id }` takes it too. `kvai.model.add { provider, id, … }` takes the model's own id, so the full id is `<provider>/<id>`. A full id splits at its first `/`: provider ids never contain one, and model ids may (`openrouter/anthropic/claude-sonnet-5.5`).
55. **Custom models belong to custom providers.** `kvai.model.add` names a custom provider (an `api` one or a delegate); a built-in provider fails `kvai/BUILT_IN`, and an unknown one fails the new code `kvai/PROVIDER_UNKNOWN`. A model id already in pi-ai's list is built-in (`kvai/BUILT_IN`). A custom model's `cost` defaults to zero.
56. **Custom wire APIs.** A custom `api` provider speaks one of the five APIs that need only a base URL and a key: `openai-completions`, `openai-responses`, `anthropic-messages`, `google-generative-ai`, `mistral-conversations`. Anything else fails `VALIDATION_FAILED`. `compat` is a JSON object passed to pi-ai as the models' `compat`.
57. **Removing.** Removing a provider or model that doesn't exist does nothing, like deleting a missing secret. Replacing a custom provider keeps its models. A delegate is checked when a call reaches it: a failed delegate call (NOT_FOUND, NOT_PUBLIC, or the delegate's own Problem) fails `kvai/PROVIDER_ERROR`, with the delegate's code in `params.cause` (63).
58. **The message.** `kvai.complete` returns pi-ai's AssistantMessage with its core fields only: `role`, `content` (text, thinking, and toolCall blocks with their signatures, so a harness can send them back), `api`, `provider`, `model`, `responseId?`, `usage`, `stopReason`, and `timestamp`. `diagnostics` (which can hold stack traces) and every other field are dropped. The input `messages` accept the same assistant shape, plus pi-ai's user and toolResult messages.
59. **Defaults.** `thinking` defaults to `off`, and `maxTokens` to pi-ai's default for the model. `usage.cost` is pi-ai's total cost in US dollars. `stopReason` is `stop`, `length`, or `toolUse`; pi-ai's `error` becomes a failure, and a cancelled call ends as the kernel cancels any job. kvai turns pi-ai's own request retries off, since the harness decides whether to call again.
60. **Usage totals.** `kvai.usage.total.get {}` → `{ tokens, cost }` is a new public query, for the status item: the workspace's input, output, cache-read, and cache-write tokens summed, and its cost. The Models page's default-model picker is a row action on each model, which calls `kernel.settings.set { key: 'kvai.defaultModel', value: <id>, scope: 'global' }`.
61. **Testkit progress.** The testkit's `exec` and `execAsync` take `onProgress?: (chunk: { source, data }) => void`, which receives the progress chunks of that call's root job.
62. **The fake OpenAI server** is `@kvman/testkit/fake-openai`, a published subpath of the testkit that uses only `node:http` and listens on 127.0.0.1. `startFakeOpenAI()` returns `{ baseUrl, reply(script), requests(), close() }`: each queued script answers one `/chat/completions` request with text, thinking, and tool-call chunks and a usage chunk, or with an error status and body.
63. **Problem params.** Extension Problems carry only a code and `params`, so kvai's params name what failed: `KEY_MISSING { provider }`; `MODEL_UNKNOWN`, `RATE_LIMITED`, and `CONTEXT_TOO_LONG { model }`; `BUILT_IN { id }`; `PROVIDER_UNKNOWN { provider }`; `PROVIDER_ERROR { model, reason }`, where `reason` is the provider's error text with the key replaced by `[secret]`, cut to 1000 characters, or `{ model, cause }` for a failed delegate call. `NO_MODEL` has none. None of it is logged. A 429 (pi-ai's `429:` error text, or its rate-limit wording) is `RATE_LIMITED`; pi-ai's `isContextOverflow` decides `CONTEXT_TOO_LONG`.
64. **Setting keys are camelCase.** A setting key is `<namespace>.<segment>…`, where each segment is lower camelCase: a lowercase letter, then letters and digits (`kvai.defaultModel`, `kvcoder.shell.approval`). Command and query names keep their lowercase kebab-case rule (ADR 0001, 68). This fixes the M1.4 kernel, which checked setting keys with the command-name rule and refused the plan's own keys.
65. **Built-in models without a price are left out.** pi-ai marks a price that varies with negative rates (OpenRouter's `openrouter/auto` and `openrouter/auto-beta`), which its cost formula would turn into a negative cost. kvai leaves out every built-in model with a negative rate: `kvai.model.list` doesn't list it, and a call to it fails `kvai/MODEL_UNKNOWN`.

## M2.2 kvwebui frame

Decided with the product owner on 2026-09-30, after a design review of the screens (the "kvwebui UX proposal" canvas: the frame, kvai's Models and provider pages, Arabic in dark mode, Settings, Extensions, and the menus, dialogs, toasts, and error states).

66. **Tooling and dependencies.** kvwebui's components are Vue single-file components. Its build and test dependencies, pinned exactly, are `vue` 3.5.43, `vue-router` 5.3.1, `vue-i18n` 11.4.12, `tailwindcss` and `@tailwindcss/vite` 4.3.3, `@lucide/vue` 1.49.0, `markdown-it` 15.0.2 with `@types/markdown-it` 14.2.0, `dompurify` 3.4.16, `@vitejs/plugin-vue` 6.0.9, `vue-tsc` 3.3.11 (typecheck), `eslint-plugin-vue` 10.11.1 and `vue-eslint-parser` 10.4.1 (so the lint rules cover `.vue` files), the fonts `@fontsource/ibm-plex-sans`, `@fontsource/ibm-plex-sans-arabic`, and `@fontsource/ibm-plex-mono` 5.3.0 (bundled into the app, which works offline), `@vue/test-utils` 2.5.1, `happy-dom` 20.14.5, and `playwright` 1.63.0. `lucide-vue-next` is deprecated in favor of `@lucide/vue`, which keeps the icon names. The libraries the app runs (Vue, vue-router, vue-i18n, lucide, markdown-it, DOMPurify, and the fonts) are `dependencies`; the build and test tools are `devDependencies`. The app ships built, in `dist/web`.
67. **Playwright runs inside Vitest.** The end-to-end tests drive Chromium with the `playwright` library from ordinary Vitest files, so `pnpm test` runs them. A Vitest global setup builds kvwebui first, because `pnpm test` runs before `pnpm build`.
68. **No `tabs` component.** kvwebui's built-in components don't include `tabs`; an extension that wants tabs ships a custom component. kvai's Models page is redesigned without it (79).
69. **Built-in pages.** Settings and Extensions are the pages `kvwebui.settings` and `kvwebui.extensions`, at `/kvwebui/<page>`. They can be `kvwebui.home` and the target of a `navigate` or `link`, and they always sit below the nav's divider, outside `kvwebui.nav.order` and `kvwebui.nav.hidden`. There is no built-in Jobs page and no running-jobs status item: an extension that wants them contributes its own. The one built-in status item is kvman's health: its version with a green dot, or a red "offline" while `kernel.health.get` fails.
70. **Forms from JSON Schema.** `string` gives a text field, `number` and `integer` a number field, `boolean` a checkbox, `enum` a select, and a nullable field is `null` when left empty. An array of strings or numbers is one item per line; a nested object is a group of its fields. A top-level `anyOf` of objects gives one form with every variant's fields, each required only when every variant requires it. A string marked `writeOnly: true` (zod's `.meta({ writeOnly: true })`) is a password field. Anything else is a JSON text field. A form clears after its command succeeds.
71. **Marked fields.** On `VALIDATION_FAILED`, whose params are `{ issues: [{ path, message }] }`, each field named by an issue path's first segment turns red and shows `kvwebui.form.invalid` ("This value isn't valid."). zod's English messages aren't shown. The toast adds "Check the marked fields."; issues that name no field show only in the toast.
72. **More invalid `ui.get` answers.** Besides the plan's rules, an answer is invalid when a nav item's `page` isn't one of the extension's own pages, an id repeats within `pages`, `nav`, `panels`, or `status`, an icon isn't a lucide name, a form's command isn't a known public command (the kernel's own, or one in `kernel.extensions.list`), or a `$param` names a param its page doesn't declare. A `link` or `navigate` to a page that doesn't exist shows a "page not found" card when it's followed. The kernel's own queries count as public queries.
73. **Status items.** A status item whose query fails shows a small error mark, with the translated Problem as its tooltip. Status items and the health item rerun every 30 s and after every command the UI runs.
74. **Workspaces in the browser.** Reloading a browser tab keeps its workspace, and a new tab opens in the workspace chosen last. Each tab keeps its workspace in `sessionStorage`, and the last choice also goes to `localStorage` for new tabs; the open panel is kept the same way. `?workspace=<id>` wins at load and is removed from the URL; an id that isn't open falls back to Home.
    - The picker lists each workspace's name and folder (Home is shown as "Home"), with a close button on each but Home, and "Open a folder…", which opens a dialog for an absolute path.
    - Closing the tab's own workspace moves it to Home. A tab whose workspace was closed elsewhere moves to Home when an answer is `NOT_FOUND` with `params.workspaceId` equal to its workspace, with a toast saying so.
    - The browser tab's title is `<page> · <workspace> · <app title>`.
75. **Presentation.**
    - Toasts sit at the bottom end corner. `info` and `success` close after 5 s; `warning` and `error` stay until closed. A `then` toast's level defaults to `success`.
    - A button's `confirm` opens an in-app dialog.
    - Formats use `Intl` in the UI language: `number` is grouped, `date` is a medium date with a short time, and `bytes` is 1024-based (B, KB, MB, GB). A new `boolean` format shows a check mark or a dash, with a translated "Yes" or "No" for screen readers. `text` shows `null` or a missing value as a dash, and an object as JSON.
    - Errors read as a plain sentence (the translated `<ns>.errors.<CODE>`), with a "Details" disclosure holding the code, the English message, and the params. A failed query's card has "Try again". Loading shows placeholder rows, and an empty table or list shows an icon and its `empty` text (default `kvwebui.empty`).
    - The nav can collapse to icons only, which `localStorage` remembers. The language menu names each language in itself (`Intl.DisplayNames`), and the theme menu offers System, Light, and Dark.
76. **Tables.** Once a table has more than 10 rows, it shows a search box (a case-insensitive match on the shown text) and its first 10 rows, and "Show more" adds 25. Table columns and detail fields are `{ field, title, format?, secondary?, badges? }`:
    - `secondary` names a second field, shown under the first as a muted line;
    - `badges` maps values to `{ text, tone }` (`tone`: `neutral`, `info`, `success`, `warning`, or `danger`), and a mapped value shows as a colored badge with the translated text, while a value with no mapping shows nothing; the value is matched as a string, so `true` matches `"true"`.
    - `rowLink?: { page, params? }` makes each row open a page (with `$row` references), shown with a chevron at the row's end.
77. **Settings page.** Keys are grouped by namespace, kvman's own first. A group's heading is `<namespace>.title` with the namespace beside it, or the namespace alone.
    - Each key shows its title (`<key>.title`, else the key), its description (`<key>.description`, else the English one), and the key itself, with a control made from its schema (70).
    - "Applies to: All workspaces | This workspace" chooses among the key's scopes.
    - A badge says where the value comes from: "Default", "Set by the <preset> preset", "Set for all workspaces", or "Set for this workspace". A value set in the chosen scope can be reset.
    - A preset-only key is shown locked, with "Set by the <preset> preset" (or "Default").
    - The Secrets section lists `kernel.secrets.list`, masked, with Delete (after a confirmation), and "Add a secret": the extension, the name, and a password field.
78. **Extensions page.** One card per extension: its name, version, source ("Bundled", "npm", or "Local folder"), and counts; it opens to list its commands and queries (with a "Public" badge and `<name>.description`, else the English one), settings, and handlers. A search box filters commands and queries. When `/` has no home page, the page shows at `/` with the `HOME_UNAVAILABLE` card, which includes the failing extension's Problem.
79. **kvai's pages and API** (changes `07` §7.3). The pages:
    - **Models:** the default model (a `detail` of `kvai.model.default.get`), the providers table (name with its id under it, model count, a status badge, and a row link to the provider's page), and a "Connect your own server" card that links to the add page.
    - **Provider** (`params: ['providerId']`): the provider, an API key form with a Remove button, and its models (name with id, thinking, context window, a "Default" badge, and "Make default").
    - **Add a provider:** the provider form and the model form.

    The API:
    - `kvai.provider.list` rows become `{ id, title, builtIn, status, models }`, where `status` is `ready` (its key is set), `needsKey` (a built-in without a key), or `noKey` (a custom provider without a key: an `api` one sends the placeholder, a delegate needs none). `status` replaces `key`.
    - `kvai.provider.get { id }` gives one row, and an unknown id fails `kvai/PROVIDER_UNKNOWN`.
    - `kvai.provider.key.set { provider, key }` is sync only (80), and its `key` is `writeOnly`. `kvai.provider.key.delete { provider }` deletes the key (a missing key does nothing). Both write kvai's secret `<provider>.apiKey`, and fail `kvai/PROVIDER_UNKNOWN` for an unknown provider.
    - `kvai.model.default.get {}` gives `{ id, name, ready }`: `kvai.defaultModel` in the workspace, the model's name (`null` when unset or unknown), and whether its provider can be called (`ready` or `noKey`).
    - `kvai.model.list` rows gain `isDefault`.
80. **Sync-only commands for extensions.** `registerCommand` takes `syncOnly?: boolean`, like the kernel's `kernel.secrets.set`: queueing or scheduling such a command (`execAsync`, `schedule`, or HTTP `async: true`) fails `VALIDATION_FAILED`, so its input never lands in a job row. A command that takes a secret must be sync only.
81. **kvcoder's `jobs` connector** (changes `08` §8.5, detailed at M2.4). The agent can see the async jobs it started, and get their status and details or cancel them: `jobs list`, `jobs get <id>`, and `jobs cancel <id>`.

## M2.3 kvwebui custom components and effects

Decided with the product owner on 2026-10-01.

82. **Custom props.** A `custom` view's `props` values may hold `{ "$param": name }` and `{ "$row": field }` references, resolved like inputs; an undeclared `$param` makes the answer invalid (72). `component` is `<namespace>.<name>`, both lowercase kebab case, and the namespace must be a loaded extension: one extension may show another's component. Whether the file exists is known only when it loads (84).
83. **The injected `kvman`.** A component reads it with `inject('kvman')`, typed by `@kvman/sdk/web`'s `Kvman`.
    - `exec(name, input)` and `execAsync(name, input)` return promises and reject with a `ProblemError`; kvwebui shows no toast for them. `exec` of a command counts as a command the UI ran: queries rerun and its effects apply; `exec` of a query doesn't.
    - `stream(jobId)` is an async iterable of `{ type: 'progress', source, data }`, then one `{ type: 'result', output }` or `{ type: 'problem', problem }`, after which it ends. A stream a component opened closes when the component unmounts.
    - `follow(jobId)` resolves once the job has ended and its reruns and effects are done.
    - A job started with `execAsync` is followed as if by `follow`: when it ends, the page's queries and the status items rerun and its effects apply.
    - `workspace` is a live, read-only ref: `workspace.value` is the tab's `{ id, name, path }` and changes on a switch. `@kvman/sdk/web` types it structurally (`{ readonly value: Workspace }`), since it imports nothing but the SDK. A switch doesn't remount the page (only a new URL does), so a component that keeps data watches `workspace`, as the built-in views rerun their queries.
    - `toast(text, params?, level?)` defaults to `info`. `panel(id, open)` with an unknown panel does nothing; `navigate(page, params?)` to an unknown page shows the "page not found" card, like a link.
    - `View` checks its tree like a `ui.get` view (its shape, public queries, known form commands, and custom namespaces); an invalid tree shows an error card with `VALIDATION_FAILED` and its issues.
84. **A component that fails.** While its module loads, the component shows placeholder rows. A module that can't be loaded, has no default export, or throws (while rendering, or anywhere else it leaves an error uncaught) shows the error card with `kvwebui/COMPONENT_FAILED` (`params: { component }`; the English message says how it failed) in its place; the rest of the page keeps working. There is no "Try again", since the browser keeps a failed module until the page is refreshed.
85. **Theme variables.** Besides the plan's `--kv-color-*` (background, surface, text, muted, border, primary, danger, warning, success), `--kv-space-sm/md/lg` (8, 16, and 24 px), and `--kv-radius` (12 px), kvwebui defines `--kv-color-on-primary` (text on primary) and `--kv-font-mono`, for light and dark.
86. **Effects at a failed end.** kvwebui calls `kvwebui.effect.take` at every end of a job the UI started or follows, success or failure, and applies the effects in order. For a button or form they come after `then` (on success) or the error toast (on failure).
87. **An effect's time.** Handlers see real time only (the testkit's clock doesn't reach `Date`), so kvwebui dates an effect by its root job id: job ids are UUIDv7, stamped from the kernel's clock. `kvwebui.effect.clean` deletes the effects whose root job id is more than 1 hour older than its own job id.

## M2.4 kvcoder

Decided with the product owner on 2026-10-01, the screens after a design review (the "kvcoder UX proposal" canvas: a running turn, waiting on approvals and a question, subagents, the Chat page, the welcome chat in Arabic, and the small pieces).

88. **The `jobs` connector** (details ADR 81). It covers the work this session started with `--async`: connector calls (`kvcoder.connector.run` jobs) and async subagents, whose id is the child session's id. Its words are plain, not JSON: `jobs list` prints the newest 50 as `[{ id, kind: 'connector' | 'subagent', call, status, startedAt, endedAt? }]` (`status` is the job's, or `running`, `succeeded`, `failed`, or `cancelled` for a child's turn); `jobs get <id>` prints that row plus `output` or `problem`; `jobs cancel <id>` cancels the job or the child's turn and prints `{ "cancelled": true }`. An id this session didn't start fails `kvcoder/JOB_NOT_FOUND` (exit 1).
89. **Background results.** When an `--async` call or an async subagent ends, its result is appended as a `user` message with `source: { kind: 'job', jobId }` (a subagent's: `{ kind: 'subagent', sessionId }`). The model reads `The background call `<call>` (job <id>) finished:`, then the result as the call would have printed it. The conversation shows it as a small "Background job finished" card. It doesn't dismiss pending questions; it waits for the next step, and starts a turn only when the session is idle.
90. **A message while waiting on subagents.** When the turn waits only on subagents, a message is queued like a steering message (it's read at the next step, once they end), and the subagents go on. Pending questions and approvals are still dismissed and denied (ADR 0008, 28).
91. **Answering one of several.** Each pending item is answered on its own. `kvcoder.question.answer` returns `{ jobId: string | null }`: the new step's job id for the answer that resolves the last pending item, and `null` before that.
92. **Error codes.** `kvcoder/SESSION_NOT_FOUND` (an unknown `sessionId` in the job's workspace), `kvcoder/SESSION_BUSY` (`kvcoder.session.compact` while a step runs), and `kvcoder/JOB_NOT_FOUND` (88), besides `kvcoder/NAME_TAKEN` and `kvcoder/QUESTION_NOT_FOUND`. Each has `en` and `ar` texts.
93. **What a call returns to the model.** One plain text format for every shell and connector call: the output (cut at 30 KB with the marker), then a last line `[exit code N]`. A connector call's output is its JSON, indented by 2 spaces. A timeout adds `[timed out after N s; the process tree was killed]` and exits 124. A denied call returns `denied by the user`. The card's fields `{ command, exitCode, output, durationMs, timedOut? }` go in the toolResult's `details`, which the model doesn't see.
94. **Sections.** Ids belong to their owner: two extensions may both have `guide`, and `section.remove` touches only the caller's. `kvcoder.section.set` fails `TOO_LARGE` over 16 KB, or when the global sections, the job's workspace's sections, and (with `sessionId`) that session's would pass 64 KB together. A global section can't see other workspaces, so a prompt build that still finds more than 64 KB leaves out the last sections by `order` and logs a warning.
95. **Interrupted children and background jobs.** Nothing is queued from kvcoder's `kernel.job.failed` handler, since a job it queued carries the `fromHandler` mark and its own failure would never be seen. A subagent's step that is interrupted ends the child's turn and its parent's turn (`interrupted`, with a notice in the root session). An `--async` job that is interrupted or cancelled reports back as a message (89) but doesn't start a turn.
96. **`runConnector`** runs connector lines only: commands connectors, `-h` (the built-ins' `ask -h`, `subagent -h`, and `jobs -h` too), stdin JSON, and non-standalone lines, exactly as in a turn. `ask`, `subagent`, and `jobs` calls return exit 1 with "runs only inside a turn", and a plain shell line returns exit 1 with "not a connector call". It never starts a shell.
97. **The status item** reads a new public query, `kvcoder.session.count { status? }` → `{ count }`, which counts the workspace's top-level sessions (its text: 109).
98. **Web dependencies.** kvcoder's components are Vue files built with Vite (`vue` external) into `dist/web/components/`. kvcoder uses kvwebui's pinned versions (66) of `vue`, `@vitejs/plugin-vue`, and `vue-tsc` for the build, `@vue/test-utils`, `happy-dom`, and `playwright` for tests, and `@lucide/vue` 1.49.0 for icons, bundled into its components. Markdown goes through `kvman.View`.
99. **Marker chunks.** Besides kvai's deltas and its own `follow` and `component` chunks, a step sends `{ type: 'compaction', state: 'started' | 'done' }` around an automatic summary (the conversation shows "Summarizing earlier messages…" and hides that text) and `{ type: 'subagent', sessionId, jobId }` when a child starts (the conversation streams the child's chain in its card). Titles are made by a private async job, `kvcoder.session.title`, whose stream nobody reads.
100. **Connector calls.**
    - The parser accepts both stdin forms on every OS: a bash heredoc (`ext new <<'EOF'` … `EOF`, also `<<EOF` or `<<"EOF"`, the body taken literally) and a PowerShell here-string (`@'` … `'@ | ext new`). `--async` may stand anywhere after the connector word.
    - A call stands alone when it's one simple command: no `|` (except the here-string form), `&&`, `||`, `;`, `&`, `>` or `<` redirection, `$( )`, backticks, or a second line. A connector word counts only where a command name goes (`echo ext` is plain shell).
    - Connector and connector command names are lowercase kebab case. `ask`, `subagent`, and `jobs` are kvcoder's own, so registering them fails `kvcoder/NAME_TAKEN`. A `kvcoder.connectors` entry with a registered connector's name is ignored, with a logged warning.
    - Errors print `error <code>: <message>` with exit 1: an unknown command of a connector (`NOT_FOUND`), JSON that doesn't parse (`VALIDATION_FAILED`), or the command's own Problem.
    - `<connector> -h` prints `<name>: <description>`, one line per command (its name and description), and a hint to run `<connector> <command> -h`. `<connector> <command> -h` prints the description, the input and output JSON Schemas, and each example as a ready-to-copy line.
    - `kvcoder.connector.run` registers `retries: 0` and `timeoutMs` 3 600 000, so the command's own timeout comes first.
101. **The shell.** A shell call's stdin is empty, and it inherits kvman's environment. A `timeoutMs` over 600 000 is cut to 600 000. Tool arguments that don't fit `{ command, description, timeoutMs? }` return an error result naming the problems. Binary checks run without approval, with a 5 s timeout, pass on exit 0, and are stored in the session at its first step.
102. **Turns, subagents, and questions.**
    - A message sent while a step runs waits in the session's queue: `kvcoder.message.list` returns it last, with `queued: true` and no `seq`. It gets its `seq` when the step's results are appended, so it always follows them.
    - The step that reaches `kvcoder.maxSteps` still appends its tool results; then the turn ends `maxSteps` with a notice.
    - A child that ends `done` returns its last answer's text; any other outcome returns `subagent ended <outcome>` and that text, with exit 1.
    - `connectors` that aren't the parent's, or that include `subagent`, give an error result. With `shell: false`, real-shell calls and binary connectors return "shell calls are off for this subagent". An async run prints `started <childSessionId>`.
    - Subagent sessions are for reading: every command that names one fails `VALIDATION_FAILED`, except `kvcoder.question.answer`. They're cancelled and deleted through their parent.
    - A pending item carries `question`: the `ask` input with its `kind` (`text`, `choice`, or `confirm`), or `{ command, description }` for an approval, so the card shows again after a reload.
    - Answers are checked against their question (`VALIDATION_FAILED`). A choice's `selected` names its options, exactly one when `multiple` is false unless an `other` text is given, and `other: true` in the call allows that text. An approval takes `{ confirmed }` or `{ dismissed: true }`; `false` and a dismissal both mean "denied by the user".
103. **Images, export, and retention.**
    - `fileIds` accept PNG, JPEG, GIF, and WebP images. A file deleted after it was sent reaches the model as `[image <name> was deleted]`, and the step goes on.
    - The export file holds `{ session, turns, messages, subagents: [{ session, turns, messages }] }`. Its name is `<title>.json`, with `/ \ : * ? " < > |` replaced by `-` and cut to 100 characters; a `{ key }` title exports as `<sessionId>.json`.
    - `kvcoder.session.prune` runs daily at 03:00 local time (`0 3 * * *`) and does nothing while `kvcoder.sessions.keep` is 0. Deleting a session deletes its per-session sections. Handler-job ids are kept 7 days.
    - Every new workspace gets the welcome session, Home on a new home's first start included, so test kernels have one too.
104. **The UI.**
    - **The Chat page** shows the chat list and the conversation with no session: a large input asks "What should we build in <workspace>?", and sending creates the chat (`kvcoder.session.create`, then `kvcoder.message.send`) and opens its page. "New chat" comes back here.
    - **The chat list** is kvcoder's custom component `kvcoder.sessions`: translated titles, the status (a spinner while running, "Needs you" while waiting), times grouped into Today and Earlier, and the open chat highlighted.
    - **Tabs.** The conversation draws its own tabs, Chat and Prompt; Prompt shows `kvcoder.prompt.get` with each section's owner, reach, and size, and a Copy button. kvwebui stays without `tabs` (68).
    - **The chat's menu** offers Rename, Fork into a new chat, Export as JSON, Summarize earlier messages now, and Delete (after a confirmation); each message offers "Fork from here".
    - The approvals of one reply share one card, with Allow or Deny per command and "Allow all"; a subagent is a card that streams its steps, with its approvals and questions inside.
105. **User only.** `kvcoder.message.send` and `kvcoder.question.answer` called by an extension fail `NOT_PUBLIC`; extensions use `kvcoder.message.inject`.
106. **The owner only.** `kvcoder.connector.unregister` of another owner's connector fails `kvcoder/NAME_TAKEN`, as registering it would; a name nobody registered does nothing. Each extension has its own handler per point, so `kvcoder.handler.unregister` only ever removes the caller's (and does nothing when it has none).
107. **An unknown model.** `kvcoder.session.configure` checks only that `model` is a non-empty id. The next step's `kvai.complete` then fails `kvai/MODEL_UNKNOWN`, and the turn ends `failed` with a notice naming the error, like any failed step.
108. **Watching a job in tests.** The testkit gains `kernel.watch(jobId, onProgress)` → `stop`: it receives the job's progress chunks from then on, as `GET /api/jobs/:id/stream` does over HTTP, so kernel tests can see a job they didn't start (a kvcoder step's question card, compaction, and subagent chunks).
109. **The waiting status text** reads "Waiting for you: {count}" (Arabic "بانتظارك: {count}"), which reads right for every count; kvwebui fills status texts with named params only, so it has no plural forms.
110. **Handler jobs.** kvcoder queues each session handler as its own private job, `kvcoder.handler.run`, which records its id and then runs the handler's command nested inside it. A message the command injects then always has a recorded `rootId`, even when it runs before `execAsync` returns; recording the id of a job queued straight to the command would race with it.
111. **Store transactions take the write lock at their start** (`BEGIN IMMEDIATE`, waiting out the busy timeout). A deferred transaction that read first failed at once with "database is locked" when it then wrote after another connection had committed (WAL's stale snapshot), which kvcoder's read-then-write transactions met under load.
112. **A job a handler queues starts after the handler has its id.** The main thread answers a worker's `execAsync` before it starts the new job (on the next turn of its event loop), so a handler that reports the id, as a kvcoder step's follow chunk does, always does so before the new job's own chunks. Jobs queued from outside a worker (HTTP, the testkit) still start at once.

## M2.5 kvdev, presets, and the walkthrough

113. **The scaffold's packages in tests.** `ext new` runs a plain `npm install`, so tests give kvman an in-test registry through npm's own `npm_config_registry`. At setup it packs kvman's packages (`@kvman/sdk`, `@kvman/kernel`, `@kvman/testkit`, built first) and every package the scaffold installs from the monorepo's installed copies, and serves them on 127.0.0.1. No test reaches the network (plan 12 §12.1).
114. **Workers see the main thread's `process.argv`.** In a worker thread, `process.argv[1]` is the worker's own file. The kernel copies the main thread's `process.argv` into each worker when it starts, so `process.argv[1]` is kvman's entry file in every handler. The preview also passes `process.execArgv` (which workers inherit), so a kvman run from source previews from source too.
115. **The RSS benchmark uses the reference pool.** It runs the bundled `coder` preset plus `kernel.workers: 3`, the 4-core reference machine's default (cores − 1), so its result doesn't depend on the machine's core count. Measured: 234 MB with 3 workers, 850 MB with 15.
116. **`kvman-check`.** `@kvman/testkit` has a bin, `kvman-check`, and the scaffold's script is `"check": "kvman-check"`. Run in a project, it loads the extension in a test kernel and prints readable findings; with `--json`, it prints the `[{ file?, message, hint }]` array that `ext check` reads. It exits 1 when it finds an error and 0 when it finds only warnings; every finding has a hint. It reports:
    - the failed load, when the kernel refuses the extension (an invalid registration, a name outside the namespace, a missing description, a bad catalog): the load stops at its first error, so one at a time;
    - each top-level input field of a public command or query with no description, since forms and connector `-h` show it;
    - missing locale keys: a key in one shipped catalog but not another (both ways), every translation key the `<namespace>.ui.get` answer uses (titles, texts, toasts), `<namespace>.title`, and each setting's `<key>.title`;
    - warnings from a text scan of `src/**/*.ts`, skipping comments: every `setInterval(`, and every `setTimeout(` whose statement doesn't start with `await`.
117. **Findings.** A TypeScript error is `{ file: "src/index.ts:12:5", message: "TS2322: …", hint }`, with paths relative to the project. `ext check` runs `npx tsc --noEmit --pretty false`, then `npm run check -- --json`, and returns the TypeScript findings first.
118. **The scaffold's sample.** Every scaffold has a public query `<namespace>.greeting.get` (a sentence), a `<namespace>.ui.get` with a page `hello` and a nav item that shows the greeting, and their `en` and `ar` keys. `web: true` adds the Hello component to the same page. Its `kvman.dependencies` is `{}` (see 128).
119. **The preview's home page** is `kvwebui.extensions`, which always exists; the new extension's pages are in the nav. A given preset keeps its own `kvwebui.home`.
120. **Links in result cards.** kvcoder's result card turns `http://127.0.0.1:<port>…` and `http://localhost:<port>…` URLs in any output into links that open in a new tab, so `preview start`'s URL is one click away. Other text is unchanged.
121. **Where `ext new` writes.** `folder` resolves against the workspace folder and must stay inside it (`VALIDATION_FAILED`). It must not exist or must be empty (`kvdev/FOLDER_NOT_EMPTY`). A failed `npm install` fails `kvdev/NPM_FAILED` with the last lines of its output and keeps the written files.
122. **`preset check`** returns `[{ file, message, hint }]`:
    - **extensions:** a `bundled` name must be a bundled extension (the four are always loaded while kvdev runs); a `path:` folder, relative to the preset file, must hold a package.json with a `kvman` field; an `npm:` source is checked for its format only;
    - **settings:** a key's namespace must be `kernel` or one of the preset's extensions'; a loaded extension's key must be registered, and its value must match its schema (zod's `z.fromJSONSchema`);
    - **pages:** `kvwebui.home` must be a built-in page, a page from a loaded extension's `ui.get`, or a page under an unloaded extension's namespace.
123. **`preset new`** writes `{ "name": <name>, "extensions": { "@kvman/kvai": "bundled", "@kvman/kvwebui": "bundled" }, "settings": { "kvwebui.home": "kvwebui.extensions" } }`, which runs as-is. `file` resolves against the workspace folder and must stay inside it; an existing file fails `kvdev/FILE_EXISTS`. It returns `{ file }`.
124. **`preview start` returns when the preview answers.** It runs `npm run web:build` once in each project that has a `web:watch` script, starts each `web:watch` and then the preview kvman, and returns once the preview answers `kernel.health.get`. After 30 s, or when the preview exits first, it stops what it started and fails `kvdev/PREVIEW_FAILED` with the last log lines.
125. **The preview's home** is `<os temp>/kvman-preview-<workspaceId>`: emptied at each `preview start`, and removed by `preview stop` and when the preview exits by itself. After a kvman stop or crash it stays until the next preview start in that workspace.
126. **Small rules.**
    - **Outputs.** `ext new` → `{ folder, name, namespace, web }`; `ext list` is sorted by folder, relative to the workspace folder (`.` for the folder itself); `ext test` → `{ passed, exitCode, output }`, with the last 30 KB of the output; `preview stop` → `{}`; `preview status` → `{ running: false }` or `{ running: true, url, extensions, startedAt }`.
    - **`ext list`** walks the workspace folder, itself included, skipping `node_modules` and dot-folders, and doesn't look inside a project it found.
    - **Folders.** `ext check` and `ext test` folders resolve inside the workspace folder (`VALIDATION_FAILED`); a folder whose package.json has no `kvman` field fails `kvdev/NOT_A_PROJECT`.
    - **`ext new` input.** `name` is an npm package name (lowercase, with an optional `@scope/`), and `namespace` follows the kernel's namespace rule.
    - **Timeouts.** `kvdev.ext.new` 10 minutes, `kvdev.ext.check` 5, `kvdev.ext.test` 10, and `kvdev.preview.start` 5; every kvdev command has `retries: 0`.
    - **npm.** `npm` or `npx` missing from the PATH fails `kvdev/NPM_FAILED`.
    - **Codes.** `kvdev/FOLDER_NOT_EMPTY`, `kvdev/FILE_EXISTS`, `kvdev/NOT_A_PROJECT`, `kvdev/NPM_FAILED`, `kvdev/NO_FREE_PORT` (ports 3738 to 3837 all taken), and `kvdev/PREVIEW_FAILED`, each with `en` and `ar` texts. A second `preview start` fails the kernel's `PROCESS_RUNNING`; `preview stop` with none running fails `NOT_FOUND`.
    - **Processes.** The preview kvman is `preview`, and each `web:watch` is `web-<n>`; `preview stop` stops them all. A given preset's `path:` entries are made absolute, since the generated preset lives in the preview's home, and a dev extension replaces an entry of the same name.
    - **The command line.** `process.execPath`, `process.execArgv`, `process.argv[1]`, then `--home <preview home> --port <n> --yes --no-open`, with the workspace folder as its working folder.
    - **Exit.** kvdev's `kernel.process.exited` handler cleans up when the preview exits by itself: it stops the `web:watch` processes and removes the preview's home.
    - **Docs and the section.** The six guides are English Markdown (text for the model, plan 02 §2.11) in kvdev's `docs/` folder. The section is `guide`, order 20, global, and set at each kvdev start.
    - kvdev's connector commands are public, as the connector rule requires.
    - **Pins.** The scaffold's versions are a kvdev constant, and a test checks them against the monorepo (`@kvman/sdk`, `@kvman/testkit`, `typescript`, `vite`, `@vitejs/plugin-vue`, `vue`).
    - **The web template** builds each component in its own Vite build (its own `.js` and `.css`), as kvcoder does; `web:watch` rebuilds on change.
    - **Benchmarks.** Cold start is the median of 5 runs, each with a new home, from spawn to the printed URL; idle RSS is `VmRSS` read 5 s after the URL, also the median of 5 runs (`bench:check` runs every benchmark 5 rounds and keeps each metric's median). Both run the built CLI, on Linux.
    - The presets are named `coder` and `dev`; kvdev's catalogs add `kvdev.app.title` ("kvman Dev").
    - Tests that npm-install a scaffold build the packages first (`pnpm build`), as the end-to-end setup does.
127. **Node's types in the scaffold.** The scaffold's devDependencies also hold `@types/node`, pinned to the monorepo's version (24.19.0), so `src/` and `test/` type-check with Node's APIs; the scaffold's own test imports `node:test`.
128. **The web scaffold declares no dependency** (this replaces the kvwebui dependency first proposed in 118). kvwebui isn't published on its own, so a declared `@kvman/kvwebui` would make the project's own test kernel and `kvman-check` fail to load it. Nothing in the project imports kvwebui: the component gets `vue` from kvwebui's import map, and kvwebui calls `ui.get` itself. Every scaffold's `kvman.dependencies` is `{}`.
129. **Connector commands may name queries.** A connector's `command` is a public command or query of the registering extension: kvcoder runs it through `ctx.exec`, which runs either, and `-h` reads its schemas from `kernel.extensions.list` either way. So `ext list`, `preview status`, and `docs get` stay the read-only queries `kvdev.ext.list`, `kvdev.preview.status`, and `kvdev.docs.get`. A query with `--async` returns `error VALIDATION_FAILED`, since only commands are queued. This corrects plan 08 §8.4, which said "a public command".

## QA pass 1: the whole app in Playwright

A Playwright pass over a real `dev` kvman (every page, a full chat turn, approvals, questions, the chat menu, settings, workspaces, Arabic, a phone-width window) found these; each was fixed with a test.

130. **The chat page fills its window.** The session list and the conversation sit side by side whenever the window is wider than the list plus 30 rem, and stack below that. A horizontal `stack` grows to the page's height and never past it, so the conversation scrolls inside itself and its send box stays at the bottom. kvcoder's two components stretch to the stack's height. (Before, the conversation's content width made the stack wrap, and the page scrolled instead.)
131. **The waiting count follows the steps.** When a step's stream ends, the conversation calls `kvman.follow` for that job, so the status bar's "Waiting for you" reruns then (plan 06 §6.2: it reruns when a job the UI follows ends). Before, it stayed stale until the 30 s rerun. A step that ends before the page attaches its stream has no job to follow; 138 covers that.
132. **Times and numbers use the UI language.** kvcoder's components format with `Intl` in the page's language (`document.documentElement.lang`, which kvwebui sets), not the browser's. The `kvman` object stays as plan 06 §6.4 lists it.
133. **A failed step's notice keeps the Problem's params.** The `STEP_FAILED` notice's params are `{ code, details }`, `details` being the Problem's params, and the UI translates `<ns>.errors.<CODE>` with `details`. Before, "The call to {model} failed." showed with an empty model. `details` come from the Problem as kvai redacts them, so they hold no secret.
134. **Narrow windows.** Below 768 px the nav is an icon rail (68 px, as when collapsed) and its toggle opens the full nav as an overlay over the page, which closes when the person picks a page. Above 768 px it is as plan 06 §6.2 says. No page scrolls sideways at 360 px.
135. **A rejected setting says why.** When saving a setting row fails `VALIDATION_FAILED`, the row shows the first issue's English `message` under its field, besides the toast (plan 06 §6.7 does this for form fields only).
136. **The model picker groups by provider.** kvcoder's header picker lists, under each provider's title, the models of providers that are ready, plus the session's own model whatever its provider. This changes no API.
137. **Small fixes.** The session list's time doesn't wrap; the chat menu's labels align to the start; a question card's "other" input fills the card; Markdown tables have borders and fit their column.
138. **`kvman.refresh()`.** The injected `kvman` object (`@kvman/sdk/web`, plan 06 §6.4) gains `refresh(): void`: it reruns the page's queries and the status items now, as after a command the UI ran. kvcoder's conversation calls it whenever a reload shows the session's status changed, so the waiting count never lags, whatever the model's speed.
139. **A running job's stream replays its recent chunks.** The kernel keeps each running root job's last 256 KiB of progress chunks (JSON size; the oldest are dropped first) and sends them to a client that connects late, before the live ones; a finished job's buffer is dropped and its stream answers with the result only. This changes plan 04 §4.4 ("chunks aren't stored") and adds a limit to plan 02 §2.17. The conversation then shows an answer's first words after a reload or a late attach.

## QA pass 3: a real model in the running app

The product owner ran the `coder` preset by hand and listed four problems (a long model list with no search, a lag after answering a question, a conversation that shows nothing until the answer lands, and no workspace path, tokens, or cost in the status bar). A Playwright pass against OpenRouter, with `openrouter/z-ai/glm-5.3-flash` only, confirmed them and found the causes: after an answer the card stays until the *next* step ends, and a click while it stays fails with "already answered"; a step shows no sign of life before its first token, thinking is folded shut, and the tool call's arguments reach the page only after the step; a status item can't format numbers or know the open chat.

140. **The model picker is a searchable popover.** kvcoder's header shows the session's model as a button. It opens a popover with a search input (focused), the provider groups of ADR 136 (ready providers and the session's own model), the current model checked, and a line "N of M models". Every word typed must appear in the model's name or id (case-insensitive); no match shows "No models match". Up and Down move the highlight, Enter picks and closes, Esc and a click outside close, and focus returns to the button. This replaces the native `<select>`; no API changes.
141. **An answer is felt at once.** When the person answers a question or approval, its card leaves the conversation immediately (the answer buttons are disabled first), the conversation reads the session again without waiting for the next step to end, and the live view (ADR 142) shows the next step. A failed answer brings the card back with the toast. An answer that is already taken (`NOT_FOUND`) drops the card quietly. Before, the card stayed until the next step ended.
142. **The live view.** While a session is `running` the conversation shows an activity line from the moment the step starts: "Waiting for the model…" with elapsed seconds, then "Thinking…", "Writing…", or the tool call's title and description (ADR 143) with "Running…" once its arguments are complete. Thinking shows open while it streams and folds when the answer text or a tool call starts; a stored answer keeps it folded. The activity line is kvcoder's own view of the chunks it already follows (plan 08 §8.7); the seconds come from the page's clock.
143. **The shell tool has a `title` and a `description`.** The tool is `bash { title, description, command, timeoutMs? }` (`powershell` the same), all three of `title`, `description`, and `command` required, listed in that order so the model writes them first. `title` is two to six words in the imperative ("Create the todo file"); `description` is one sentence saying what the command does and why, for the person. A call without a title fails `VALIDATION_FAILED` as any invalid call does. The approval's `question` becomes `{ title, command, description, timeoutMs }`, the shell result's `details` gain `title` and `description`, and the approval card, the running card, and the result card show the title, the description under it, and the command in monospace; a stored call with no title shows its command. This changes plan 08 §8.2, §8.3, and §8.5.
144. **kvai's `toolcall` chunk carries arguments as they complete.** `{ type: 'toolcall', name }` still marks a call's start; then `{ type: 'toolcall', name, arguments }` follows each time one more argument is complete (every key but the one being written), and once more with all of them when the call ends. `arguments` is an object of the completed values only, so a chunk never holds half a string and its size stays small. This changes plan 07 §7.1's list of deltas.
145. **The status bar starts with the workspace's path.** kvwebui's first status item is the current workspace's folder: the person's home folder shown as `~`, the full path as its tooltip, cut with an ellipsis when the bar is full. It is built in (the kernel and kvwebui hold no product concept, and every preset needs it), sits before the contributed items, and follows the tab's workspace.
146. **Status items may format and may use the page.** In `status[]` (plan 06 §6.3): a param `{ $output: field }` may add `format: 'compact' | 'usd'` (compact number, or US dollars, both with `Intl` in the UI language; without `format` a param is filled as before), and `field` may be a dotted path into the output (`usage.input`). An item's `input` may use `{ $param: name }`, read from the current page's route params; an item whose param is missing on the current page isn't shown.
147. **Tokens and cost in the status bar.** Costs show two decimals, four under one cent, and one significant digit when smaller than that (`$0.00004`); zero shows `$0.00`; tokens show compactly (`3.6K`, `٣٫٦ ألف` in Arabic). kvai's existing item becomes "Workspace {tokens} · {cost}" with those formats, and kvcoder adds "Chat ↑ {input} ↓ {output} · {cost}" for the open chat (its `kvcoder.session.get` through `$param: sessionId`), shown only on a chat page. The chat header's totals use the same formats.
148. **A shell call ends when its shell exits, and stops what it left behind.** Found when a model started a web server with `cd app && nohup python3 -m http.server 8000 &`: the call waited until its 120 s timeout, because the server held the call's output open, and then the timeout killed it anyway. Now, on Linux and macOS, the call ends as soon as the shell process exits: whatever is left in the shell's process group is killed (`SIGKILL`), the output written so far is kept, and when something was killed the result gains the line `[background processes were stopped when the command ended]` before the exit code. A process that left the group (`setsid`) can't be stopped, so the output is given at most 1 s to drain after the shell exits and is then closed. On Windows, Node has no job objects and `taskkill /T` needs the parent alive, so the call ends when the shell exits, the output is closed after the same 1 s, and a leftover process keeps running. This changes plan 08 §8.3.
