# 08 — UI Model and UI Contract

This file is the **UI contract**. It defines what the shell provides, what extensions and presets register, what the kernel serves, and the rules that connect them. The SDK calls are listed in `05` §5.3; their shapes and behavior are defined here.

## 8.1 Principles

1. **The frame is code; what fills it is data.** The shell (the web UI) ships the frame, the component library, the renderer, and the recovery page. Everything a user sees inside the frame is registered by extensions and presets and served as data: pages, nav, panels, toolbar and status items. The shell has no feature pages except the recovery page.
2. **The kernel serves, it does not draw.** The kernel stores what extensions registered, validates it, and serves each workspace's UI registry (§8.6). It registers no UI of its own and does not know what a sidebar looks like.
3. **Every container declares what it accepts.** Frame regions, extension slots, and components each declare which kinds of children they take. Validation rejects anything else at install, enable, or preset apply, never at render time.
4. **UI is registered, never pushed.** All UI is registered in `setup` and checked before anything runs. What changes at runtime is data: a registered panel appears when its query returns something (§8.10). The only runtime pushes are one-way messages with no layout: toasts, notifications (§8.11), and `ui.navigate`.
5. **Views are data; queries compute.** Pages are JSON trees of components with bindings. There is no code and there are no expressions. Filtering, formatting, and joins live in query handlers that return data shaped for the view.
6. **Text is keys until it is drawn.** Views, notices, and problems carry translation keys and parameters. The shell turns them into text in the user's language when it renders, so switching language re-renders everything, including stored notifications (§8.16).
7. **Escape hatch, not a back door.** What components cannot express is built as a sandboxed widget (§8.15).
8. **The user is an actor; extensions own their prompts.** People act by sending commands from views. When an extension needs an answer, it shows its own prompt and receives the answer as its own user-only command (§8.13).
9. **Only people click.** The view language has no triggers that fire without a user gesture, and widgets act as their extension, never as the user. This is what makes `access: 'user'` meaningful (`02` §2.4).
10. **Visibility is not authority.** Presets decide what is shown; capabilities decide what code can do. Hiding something never blocks it, and showing something never grants anything (§8.17).

## 8.2 The three layers

```
┌──────────────────────── shell (@kvman/shell — Vue, ships with kvman) ───────────────────────┐
│ frame: topbar · sidebar · main (≤2 panes) · statusbar · overlay · dialogs · toasts · palette │
│ shell-only zones: brand · workspace switcher · notifications · connection · kvman menu ·     │
│                   risk banner · grant dialog                                                  │
│ built-in components · renderer · data layer · widget host · formatting · right-to-left       │
│ recovery page · first-run · offline · shell catalogs (en, ar)                                 │
└───────────────▲──────────────────────────────────────────────────────────────────────────────┘
                │ GET /api/v1/ui (UI registry + ETag) · page views per route · catalogs per locale
┌───────────────┴──────────────────────────── kernel ─────────────────────────────────────────┐
│ registry: manifests of enabled extensions + the workspace's applied preset                   │
│ validation at install / enable / apply: slot accepts, components, bindings, keys, authority  │
│ computes and serves the UI registry per workspace · user preferences · notification tray     │
└───────────────▲──────────────────────────────────────────────────────────────────────────────┘
                │ ext.registerPage · registerNavItem · registerPanel · registerComponent · …
┌───────────────┴──────────────────────── extensions and presets ─────────────────────────────┐
│ core pages (settings, extensions, presets, inspector) · agent chat · pdf · UI kits · presets  │
└──────────────────────────────────────────────────────────────────────────────────────────────┘
```

| Layer | Owns | Never does |
|---|---|---|
| **Shell** | the frame and its regions, shell-only zones, built-in components, rendering, responsive layout, right-to-left, number and date formatting, the recovery page | contain feature pages; load extension code into its own document |
| **Kernel** | storing and validating registrations; computing and serving the UI registry; the user's preferences (language, theme); storing notifications and checking their actions | know what a region looks like; register UI; draw a notification |
| **Extensions** | pages, nav, panels, toolbar and status items, actions, renderers, components, slots, catalogs | change the frame; draw in shell-only zones |
| **Presets** | which contributions are shown, their order and labels, frame layout options, their own pages and text | remove shell-only zones or the recovery page; grant anything by showing it |

The **frame slot catalog** (slot names, accepted kinds, limits) and every built-in component's spec (§8.8) live in `@kvman/protocol` and are versioned with the shell. That is how the kernel validates UI without containing UI code.

**Stack**: Vue 3 + Vite + Tailwind + Reka UI, TanStack Virtual, lucide icons, markdown-it + DOMPurify, `intl-messageformat` for translations. Built into `@kvman/shell` and served by the kernel.

## 8.3 The frame

```
┌─ risk banner (shell; only when there is something to say) ─────────────────────────────────────┐
├─ topbar ───────────────────────────────────────────────────────────────────────────────────────┤
│ [≡][icon] App title  [Workspace ▾] │ frame.topbar.start …      … frame.topbar.end │ [🔔][●][kvman ▾] │
├───────────────┬────────────────────────────────────────────────────────────────────────────────┤
│ frame.sidebar │ frame.main                                                                      │
│  ▾ navGroup   │  ┌─ page (pane 1) ─────────────────────┐  ┌─ page (pane 2, optional) ─────────┐ │
│     navItem   │  │                                     │  │                                   │ │
│     navItem   │  │                                     │  │                                   │ │
│  ───────────  │  └─────────────────────────────────────┘  └───────────────────────────────────┘ │
│  navItem      │                                                                                 │
├───────────────┴────────────────────────────────────────────────────────────────────────────────┤
│ frame.statusbar.start …                                                  … frame.statusbar.end │
└────────────────────────────────────────────────────────────────────────────────────────────────┘
 on top of everything: toasts · dialogs · frame.overlay (one panel at a time) · grant dialog (top-most)
```

In right-to-left languages the whole frame mirrors: the sidebar is on the right, and `start` means the right edge (§8.16).

**Panes.** `frame.main` shows the page for the URL path in the main pane. A second page can open in the side pane: an action `{ "navigate": "/files/abc", "pane": "side" }`, Ctrl/Cmd+click on a nav item, or an entity's "Open beside" action. The side pane's route is kept in the URL as `?side=<encoded route>`, so reload and links restore both panes. The side pane has a close button; navigating the main pane never closes it. Both panes render the same way; a pane that is not focused pauses its live subscriptions (§8.14).

**Routing.** The shell matches the URL path against the routes of the pages in the UI registry. The search parameters `ws` (workspace, §8.14), `side` (side pane), and `embed` (embedded shell, `11` §11.7) are reserved by the shell: they never appear in `$route`, and a page that declares one in `params` fails validation. Static segments win over `:param` segments. `/` opens `app.home`. A path that matches nothing shows "This page is not available" with a link home. `/_kvman` is the recovery page and is matched before any registry route.

### Frame regions

Each region is a slot declared by the shell. The namespace `frame` is reserved; extensions cannot register `frame.*` names.

| Slot | Accepts | Limit | What a preset controls | Narrow screens (< 768 px) |
|---|---|---|---|---|
| `frame.sidebar` | `navGroup`, `navItem`, `separator` | none (scrolls) | order, separators, hidden items, `expanded` / `collapsed` / `hidden` | drawer from the start edge, opened by ≡ |
| `frame.topbar.start` | `toolbarItem` | 3 | order, hidden items | moved into the ⋯ overflow menu |
| `frame.topbar.end` | `toolbarItem` | 4, the rest in a "More" menu | order, hidden items | moved into the ⋯ overflow menu |
| `frame.main` | `page` (by route) | 2 panes: main and side | home page, hidden pages | one pane with a bottom switcher |
| `frame.statusbar.start`, `frame.statusbar.end` | `statusItem` | 6 per side, the rest in a popover | order, hidden items, `shown` / `hidden` | hidden |
| `frame.overlay` | `panel` | 1 shown at a time: the first visible panel by `order`, then id, with a "1 of N" stepper | hidden items | full-screen sheet |

### Shell-only zones

The shell draws these. They accept no contributions, and presets can neither hide nor restyle them.

| Zone | Content |
|---|---|
| Brand | the preset's `app.title` and `app.icon` (defaults: "kvman" and the kvman icon); ≡ toggles the sidebar |
| Workspace switcher | open workspaces, open a folder (a path field sending `kernel.workspace.open`), Home; preview workspaces are not listed |
| Notifications 🔔 | the notification tray with the unread count (§8.11) |
| Toasts | the toast stack, bottom end corner (top on narrow screens), at most 3 visible (§8.11) |
| Connection ● | event stream state: connected, reconnecting, offline |
| **kvman menu** | Language · Theme · Show hidden pages · Keyboard shortcuts · Manage kvman (opens the recovery page) · About |
| Risk banner | the localhost trust notice (dismissible per browser), quarantine notices (until resolved), "extension needs approval" when an installed upgrade waits for grants |
| Grant dialog | power confirmation (§8.13) |
| Command palette (`Ctrl/Cmd+K`) | visible pages, nav items, and entity actions placed in the `palette` (those need no record); hidden pages only under "Show hidden" |
| Shortcuts modal (`?`) | keyboard shortcuts |

These zones exist for two reasons. There is always a way back: kvman menu → Manage kvman reaches the recovery page whatever the preset hides. And nothing an extension draws can pass for kvman itself.

### Screens the shell owns

- **Recovery page** (`/_kvman`): kernel health; the current workspace's extensions with status (active, disabled, quarantined, needs approval) and Enable (through the grant dialog), Disable, Rollback, and for a quarantined extension the actions its reason allows (`03` §3.6: Re-enable, Rollback, or Retry upgrade); Apply the Minimal preset; trust status with Revoke; language and theme. Built into the shell, uses only `kernel.*` messages and the `kvman:` catalog, renders no extension UI, and is always reachable (kvman menu, or the URL). It is also shown when the shell cannot run against the kernel's protocol version (`12` §12.9).
- **First-run**: shown when the current workspace has no applied preset. Language picker (pre-selected from the browser's languages; sends `kernel.user.preferences.set`), then "What do you want to do?" with one card per built-in preset except Minimal (Coding Agent, Assistant, Extension Builder) plus "Just the basics" (Minimal). Choosing one runs `kernel.preset.apply.stage` and opens the grant dialog; Confirm applies it (`07` §7.6).
- **Offline**: shown when the kernel cannot be reached; retries automatically.

## 8.4 Contribution kinds and slots

### Kinds

A **contribution** is one registered piece of UI. Its **kind** decides where it may go.

| Kind | Registered with | May be placed in | Shape (§8.5) |
|---|---|---|---|
| `page` | `ext.registerPage`, or a preset's `pages` | `frame.main`, by route | `PageDef` |
| `navGroup` | `ext.registerNavGroup`, or a preset's `navGroups` | `frame.sidebar` | `NavGroupDef` |
| `navItem` | `ext.registerNavItem`, or a preset's `nav` | `frame.sidebar`, optionally inside a group | `NavItemDef` |
| `separator` | a preset's `layout.order` (`"---"`) | `frame.sidebar` | — |
| `toolbarItem` | `ext.registerToolbarItem` | `frame.topbar.*`, and extension slots that accept it | `ToolbarItemDef` |
| `statusItem` | `ext.registerStatusItem` | `frame.statusbar.*` | `StatusItemDef` |
| `panel` | `ext.registerPanel` | `frame.overlay`, and extension slots that accept it | `PanelDef` |

Four more kinds are part of the contract but are not placed in slots:

| Kind | Registered with | Attached to |
|---|---|---|
| `action` | `ext.registerAction` | an entity type; shown in row menus and detail headers, and in the palette when it opts in and needs no record |
| `renderer` | `ext.registerRenderer` | a renderer target (`agent.entry`), an entity (`entity:pdf.file`), or a MIME type (`mime:application/pdf`) |
| `component` | `ext.registerComponent` | used by name inside views (§8.9) |
| `settingsSection` | automatic for every extension that calls `ext.registerConfig`; `ext.registerSettingsSection` replaces its generated form | listed in the registry's `settingsSections` and drawn by the built-in `settingsSections` component, which the `settings` extension's page uses; id `settings.section.<ns>` |

### Slots

A **slot** is a named place that accepts contributions of certain kinds. The shell declares the `frame.*` slots. An extension declares its own with `ext.registerSlot` and places them in its own views.

```ts
type SlotDef = {
  description: string;
  accepts: Array<'panel' | 'toolbarItem'>;   // the kinds an extension slot may accept
  props?: ZodType;                           // values the placing view passes in; contributions read them as $slot.*
  layout?: 'stack' | 'row' | 'tabs';         // how several items are arranged (default 'stack')
  max?: number;                              // items past the limit go into an overflow ("+2 more")
};
```

The agent declares two slots in its chat page:

```ts
ext.registerSlot('agent.chat.prompt', {
  description: 'Above the chat composer: questions and approvals for this session.',
  accepts: ['panel'], props: z.object({ sessionId: z.string() }), layout: 'stack',
});
ext.registerSlot('agent.chat.header', {
  description: 'Buttons in the chat header.',
  accepts: ['toolbarItem'], props: z.object({ sessionId: z.string() }), layout: 'row', max: 4,
});
```

Its page places them and fills their props:

```json
{ "type": "slot", "name": "agent.chat.prompt", "props": { "sessionId": "$route.sessionId" } }
```

Rules:
- Only a slot's owner may place it. A `{ "type": "slot" }` naming another extension's slot fails validation.
- A contribution names its slot, and the slot's `accepts` must include the contribution's kind. A panel aimed at `frame.sidebar`, or a toolbar item aimed at `agent.chat.prompt`, fails validation with a hint that names what the slot accepts.
- Contributions read the slot's props as `$slot.*`, and those binding paths are checked against the slot's `props` schema.
- A slot with no visible items renders nothing: no empty box and no gap.

### Order, limits, and ids

- Every item may set `order` (0–1000, default 500). Items sort by `order`, then extension name, then item name. A preset's `layout.order[<slot>]` replaces this with an explicit list; items it does not list follow in their default order.
- Inside `frame.sidebar`, nav items with a `group` are listed under that group, sorted the same way; the group's own position comes from its `order`. A nav item whose group is hidden or missing is shown at the top level. `layout.order["frame.sidebar"]` orders top-level entries only (groups, ungrouped items, and `"---"`).
- Items past a slot's limit go into an overflow menu or popover drawn by the shell. One extension can push another's item out of view only through `order`, and the preset decides the final order.
- **Ids.** Every contribution has an id `<ns>.<name>` from its `register*` name (preset contributions use `preset.<name>`). UI names are unique within an extension across all UI kinds (`05` §5.3), so an id names exactly one thing. Presets hide, reorder, and relabel by id.
- **Hiding cascades.** Hiding a page also hides every nav item that opens it and removes it from the palette. Hiding a nav group hides the group header; its items move to the top level unless they are hidden too.
- **Inactive contributions.** A panel or toolbar item aimed at a slot of an extension that is not enabled in the workspace, an action on an entity of such an extension, and a renderer for its target are left out of the registry (`06` §6.3). Enabling the owner makes them appear.
- **Routes** are unique among active pages in a workspace (`ROUTE_CONFLICT`, `06` §6.3).

## 8.5 Contribution shapes

Every user-facing string is a `Text`: a literal, a translation key, a binding, or a key with parameters (§8.16). These base types are shared by every shape below and by the view language (§8.7); all of them live in `@kvman/protocol`.

```ts
type Json = null | boolean | number | string | Json[] | { [key: string]: Json };
type ComponentName = string;                                // 'table', 'pdf.fileCard' (§8.8, §8.9)

// A string that is exactly a path starting with `$` (§8.7): '$item.name', '$query.files.items.0.id'
type Binding = `$${string}`;

type Text =
  | string                                                  // literal (validation warns, §8.16)
  | `$t.${string}`                                          // a key in the owner's catalog
  | Binding                                                 // a bound value, shown as plain text
  | { $t: string; [param: string]: Json | Binding };        // a key with ICU parameters

// Conditions: the storage filter language (04 §4.3) with binding paths as keys.
// Keys at one level are ANDed; a plain value means `eq`; `$or` holds alternatives.
type Operators = { eq?: Json; ne?: Json; gt?: number | string; gte?: number | string; lt?: number | string;
                   lte?: number | string; in?: Json[]; prefix?: string; exists?: boolean };
type Condition = { [path: string]: Json | Binding | Operators | Condition[] };   // '$or': Condition[]

type PageQuery = {
  query: string;                                            // a query type the view's owner may send
  payload?: Record<string, Json | Binding>;                 // bindings resolved first; undefined and null values are omitted
  refreshOn?: string[];                                        // durable or transient event types or patterns ('pdf.*'), never live events
};

type Format = 'date' | 'time' | 'dateTime' | 'relative' | 'number' | 'integer' | 'percent'
            | `currency:${string}` | 'bytes' | 'duration';  // §8.16

type FieldOverride = {
  label?: Text; help?: Text; placeholder?: Text; order?: number; group?: Text;
  widget?: 'text' | 'textarea' | 'number' | 'select' | 'checkbox' | 'switch' | 'date' | 'secret' | 'upload';
  options?: Array<[Json, Text]>;                            // for 'select'
};
type FormOverrides = {                                      // for `form: {…}` on actions and for the form component
  title?: Text; submitLabel?: Text;
  defaults?: Record<string, Json | Binding>; hidden?: string[]; fields?: Record<string, FieldOverride>;
};

type Column = {                                             // table columns (§8.8)
  field?: string; label: Text; format?: Format; visibleIf?: Condition; sortable?: boolean;
  as?: 'text' | 'badge' | 'liveText' | 'progress' | ComponentName;   // a component receives { value: $item[field], item: $item }
  live?: string;                                            // live event `<type>:<key>` for 'liveText', with {{ }} bindings
  width?: 'auto' | 'sm' | 'md' | 'lg';
};

type PageDef = {
  description: string;
  route: string;                           // '/files', '/files/:fileId'
  title: Text; icon?: string;              // lucide icon name
  params?: ZodType | Record<string, 'string' | 'number' | 'boolean'>;  // route and search params; JSON uses the map form
  state?: Record<string, Json>;            // initial $state
  queries?: Record<string, PageQuery>;     // §8.7
  view: ViewNode;
};
type NavGroupDef = { description: string; label: Text; icon?: string; order?: number };
type NavItemDef = {
  description: string; page: string;       // page id
  label: Text; icon: string; group?: string /* nav group id */; order?: number;
  badge?: { query: string; payload?: Json; field: string; refreshOn?: string[] };
};
type ToolbarItemDef = {
  description: string;
  slot: string;                            // 'frame.topbar.end', or an extension slot that accepts toolbarItem
  as: 'button' | 'menu' | 'badge';
  label: Text; icon?: string; order?: number;
  queries?: Record<string, PageQuery>; visibleIf?: Condition;
  action?: Action;                                                   // as: 'button'
  items?: Array<{ label: Text; icon?: string; action: Action }>;     // as: 'menu'
  badge?: { query: string; payload?: Json; field: string; refreshOn?: string[] };
};
type StatusItemDef = {
  description: string; side?: 'start' | 'end';                       // default 'end'
  label: Text; icon?: string; tone?: 'neutral' | 'info' | 'success' | 'warning' | 'danger';
  order?: number; queries?: Record<string, PageQuery>; visibleIf?: Condition;
  action?: Action;                                                   // on click
};
type PanelDef = {
  description: string; slot: string; title?: Text; order?: number;
  queries?: Record<string, PageQuery>; visibleIf?: Condition; view: ViewNode;
};
type ActionDef = {
  description: string; entity: string; label: Text; icon?: string; visibleIf?: Condition;
  placement?: Array<'row' | 'detail' | 'palette'>;                   // default ['row', 'detail']
} & (
  | { command: string; payload?: Json; form?: boolean | FormOverrides;   // run a command
      confirm?: { title: Text; body?: Text }; then?: Effect[] }
  | { navigate: string; pane?: 'main' | 'side' }                      // open a page, e.g. '/files/{{ $item.id }}'
  | { openDialog: { title: Text; view: ViewNode } }                   // show a dialog about the record
);
// In an action, $item is the record (a table row, a list item, or the detail page's record, §8.8).
// 'palette' is allowed only for actions whose bindings do not use $item: the palette has no record.
type RendererDef = {
  description: string; target: string;
  view?: ViewNode; component?: string; props?: Record<string, Json | Binding>;
};
```

Examples from the PDF extension:

```ts
ext.registerNavGroup('pdf.documents', {
  description: 'Document tools in the sidebar.', label: '$t.nav.documents', icon: 'folder', order: 200,
});
ext.registerNavItem('pdf.nav-files', {
  description: 'Files page in the sidebar.', page: 'pdf.files', group: 'pdf.documents',
  label: '$t.nav.files', icon: 'files',
  badge: { query: 'pdf.files.count', payload: { status: 'translating' }, field: 'count', refreshOn: ['pdf.*'] },
});
ext.registerToolbarItem('pdf.upload', {
  description: 'Upload button in the top bar.', slot: 'frame.topbar.end', as: 'button',
  label: '$t.toolbar.upload', icon: 'upload', action: { navigate: '/files?upload=1' },
});
ext.registerStatusItem('pdf.queue', {
  description: 'Number of translations in progress.', side: 'end', icon: 'loader',
  queries: { q: { query: 'pdf.files.count', payload: { status: 'translating' }, refreshOn: ['pdf.*'] } },
  visibleIf: { '$query.q.count': { gt: 0 } },
  label: { $t: 'status.translating', count: '$query.q.count' },
  action: { navigate: '/files' },
});
```

## 8.6 The UI registry (what the kernel serves)

The shell does not assemble the UI from `/schema`. It fetches one **UI registry** per workspace, already merged, ordered, and filtered by the kernel:

```ts
type UiRegistry = {
  workspaceId: string;
  revision: string;                              // equals the ETag
  app: { title: Text; icon?: string; accent?: string; themeMode: 'system' | 'light' | 'dark'; home: string };  // preset values with defaults
  layout: { sidebar: 'expanded' | 'collapsed' | 'hidden'; statusbar: 'shown' | 'hidden' };
  slots: Record<string, {                        // frame slots and extension slots
    owner: 'frame' | string; accepts: string[]; layout?: string; max?: number;
    items: UiItem[];                             // ordered; hidden, disabled, quarantined, and inactive items removed; preset labels applied
  }>;
  pages: Array<{ id: string; owner: string; route: string; title: Text; icon?: string; hidden: boolean;  // hidden pages kept for "Show hidden pages"
                 label?: PresetLabel }>;
  actions: Record<string /* entity type */, UiItem[]>;
  renderers: Record<string /* target */, UiItem[]>;
  components: Array<{ name: string; owner: string; form: 'composite' | 'widget'; visibility: 'public' | 'private';
                      def?: CompositeDef }>;                     // for composites used outside pages (ADR 0159)
  extensions: Record<string /* name */, { namespace: string; title: Text; icon?: string }>;   // for attribution and titles
  settingsSections: Array<{ id: string; owner: string; title: Text;          // title = the owner's meta.title
                            scopes: Array<'global' | 'workspace'>; schema: JsonSchema;   // with .meta labels
                            view?: ViewNode; label?: PresetLabel }>;       // from registerSettingsSection; hidden ones removed
  catalogs: { defaults: Record<string /* owner */, string /* default locale */>; locales: string[] };
};
type UiItem = { id: string; owner: string; kind: string; def: Json;    // def = the registered shape (§8.5)
                label?: PresetLabel };
type PresetLabel = string | Record<string /* locale */, string>;       // the preset's labels[id] as written (07 §7.3)
```

| Endpoint | Kernel query | Returns | Cache key |
|---|---|---|---|
| `GET /api/v1/ui?workspaceId=` | `kernel.ui.get` | the registry above, without page views | `ETag` = hash(applied preset revision, active digest of every enabled extension, the sorted names of the quarantined ones, protocol version): every input the registry is computed from |
| `GET /api/v1/ui/pages/:pageId?workspaceId=` | `kernel.ui.page.get` | `{ page: PageDef, components: Array<{ name, owner, def: CompositeDef }> }`: the page view plus every composite component it uses, transitively | the same ETag |
| `GET /api/v1/ui/translations?workspaceId=` | `kernel.ui.translations.get` | `{ locale, catalogs: Record<owner, Record<locale, Catalog>> }`: the catalogs of every active extension and of the preset, for the saved language (§8.16), its base language, and the owner's default locale | the ETag plus the saved language |

- The registry is **computed, not stored**: it is a function of the workspace's applied preset and the manifests of its enabled extensions. Validation already ran at install, enable, and apply, so computing it only merges, orders, and filters.
- **How it is computed** (ADR 0159). An item's `owner` is its extension's package name, `preset` for the preset's own items, and `frame` for frame slots; only extensions the preset enables that are not quarantined contribute. Items are left out when hidden, inactive (§8.4), or, for nav items, when their page is hidden or not active. `frame.main` has no items: pages are listed in `pages`. The sidebar list is flat: top-level entries in order, each group followed by its items; a nav item whose group is hidden or missing is top-level with `group` removed; a `"---"` is `{ id: '---<n>', owner: 'preset', kind: 'separator', def: {} }`. Preset labels are attached as `label`, never written into `def`.
- A workspace with no applied preset fails `PRESET_REQUIRED` in all three queries (the shell shows first run); `page.get` for a page that is not active in the workspace fails `NOT_FOUND` (a hidden page is answered). The ETag is `"<revision>"`, and `"<revision>:<locale>"` for translations; `revision` is the SHA-256 of the inputs above.
- **When the shell refetches** (with `If-None-Match`, so an unchanged registry costs a `304`):

| Event for this workspace | Why the UI changed |
|---|---|
| `kernel.preset.changed` | apply, update, enable, disable, grants, hidden items, order, labels, preset pages: every one is an edit of the applied preset |
| `kernel.extension.reloaded` | an enabled extension's code changed (upgrade, rollback, hot reload) without a preset edit |
| `kernel.extension.quarantined` | the kernel stopped an extension; the preset still lists it as enabled |
| `kernel.extension.unquarantined` | the person re-enabled a quarantined extension |

- A language change does not refetch the registry. It fetches catalogs (`kernel.user.preferences.changed`, §8.16). Config changes refresh the queries that read config, not the registry.
- Page views load on the first visit to a route and change only with the ETag.
- The shell re-validates props when it renders, as a second line of defense. A failing node renders an inline error box, never a broken page.

## 8.7 View language

### Nodes

```ts
type ViewNode = {
  type: ComponentName;           // 'table', 'form', 'card', 'pdf.fileCard', 'slot', 'children', …
  id?: string;
  visibleIf?: Condition;
  children?: ViewNode[];         // only where the component accepts children (§8.8)
  [prop: string]: Json | Binding | Text | Action | ViewNode | ViewNode[];   // validated per component
};
```

### Bindings

- A string that is exactly a path starting with `$` is a binding: `"$item.name"`.
- **Path grammar**: `$<root>` followed by `.<segment>` parts; a segment is a field name or an array index (`$query.files.items.0.name`). `.length` on an array gives its length. Nothing else (no calls, no filters). Exactly (ADR 0026): a segment is `[A-Za-z0-9_-]+` (an index has no leading zero); the roots are the 16 of the table below and no others; `$query.<alias>` and `$t.<key>` need a segment, the other roots may stand alone.
- **Missing values**: a path that does not resolve gives `undefined`. Text renders it as empty; conditions treat it as not existing; payloads omit the key.
- A string containing `{{ $path }}` is interpolated text: `"{{ $query.files.total }}"`. Anything a person reads should be a `$t` key instead (§8.16). In `navigate` routes and `live` addresses (`<type>:<key>`), interpolated values are URL-encoded.
- `$$` at the start of a string escapes a literal `$` (`"$$5"` renders `$5`).

| Root | Value |
|---|---|
| `$route` | route params and search params |
| `$query.<alias>` | result of a declared query |
| `$state` | page-local state (initial values in `page.state`) |
| `$form` | current form values |
| `$item` | the record the node is about: a table row, a list item, a renderer's item, an action's record, an entity's display, a detail page's record |
| `$value` | the value an event carries (`onChange` of an input, `onChange` of tabs) |
| `$selection` | the selected rows of a table (`onSelect`) |
| `$upload` | result of an upload component |
| `$reply` | the command's reply inside an action's `then` |
| `$slot` | values the placing page passes into a slot |
| `$props` | props passed to a composite component (inside its view only) |
| `$t.<key>` | translated text from the view owner's catalog (§8.16) |
| `$locale` | `{ code, dir: 'ltr' \| 'rtl' }` of the user's language |
| `$workspace` | `{ id, name, path, trusted }` of the tab's current workspace |
| `$user` | `{ id }` (`local` in v2) |
| `$app` | the registry's `app` (`title`, `icon`, `accent`, `home`) |

There are no operators, function calls, or loops. Lists are rendered by list and table components over query results. There are no load, timer, or visibility triggers: every action starts from a user gesture (click, submit, change, upload, row click).

### Conditions

`visibleIf`, `disabledIf`, and filters use the storage filter language (`04` §4.3: `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `in`, `prefix`, `exists`) with bindings as keys:

```json
{ "visibleIf": { "$item.status": { "in": ["ready", "translated"] }, "$state.mode": "edit" } }
```

### Actions and effects

```ts
type Action =
  | { command: string; payload?: Json; form?: boolean | FormOverrides; confirm?: { title: Text; body?: Text };
      busyLabel?: Text; then?: Effect[] }
  | { navigate: string; pane?: 'main' | 'side' }                      // route; {{ }} values are URL-encoded
  | { openDialog: { title: Text; view: ViewNode } }
  | { openGrantDialog: { command: GrantCommand; payload: Json } }     // shell-drawn confirmation (§8.13)
  | { set: Record<string, Json | Binding> }                           // update $state; keys are '$state.<field>'
  | `$props.${string}`;                                               // inside a composite: an action passed in (§8.9)

type Effect = { toast: Text; level?: 'info' | 'success' | 'warning' | 'error' }
            | { navigate: string; pane?: 'main' | 'side' }
            | { refresh: string /* query alias */ }
            | { set: Record<string, Json | Binding> }                 // keys are '$state.<field>'
            | { closeDialog: true };
```

- A `command` action (and a `form`, and a declared query) may target only types with access `all` or `user` (the sender is the person, `02` §2.4), and among those only: the view owner's own types; types covered by the owner's granted `calls`; and `kernel.*` types the owner may send (`03` §3.8: queries marked "any"; with `kernel.admin`, also admin queries and commands, `user` commands, and `kernel.cancel`; never `llm` types; ADR 0157). For a preset page, the allowed set is every type with access `all` or `user` of the preset's enabled extensions plus `kernel.*` queries marked "any". The one exception is a slash command chosen in a `composer` (§8.8).
- Power-granting kernel commands (`GrantCommand`: `kernel.trust.grant`, `kernel.extension.enable`, `kernel.extension.reload` with `grants`, `kernel.preset.import`, `kernel.preset.apply`, `kernel.preset.update` touching extensions) are never a `command` target. Views reach them only through `openGrantDialog`.
- `form: true` opens a generated form for the fields missing from `payload` (from the command's input schema, §8.12); `form: FormOverrides` does the same with overrides.
- A `command` action runs in this order: `confirm` dialog (if set) → form (if set) → send with `busyLabel` shown on the control → on success run `then` effects in order with `$reply` set → on failure show the error (below) and skip `then`.
- Every command action gets an idempotency key per click; retries reuse it. A control is disabled while its command is in flight, so a double click sends once.
- Errors show inline (validation issues map to form fields) or as a toast, in the user's language (§8.16).
- `openDialog` opens a modal drawn by the shell with the given view; the view is written by the same owner and follows the same rules. `closeDialog` closes the innermost dialog. Dialogs nest at most 2 deep: validation follows `openDialog` actions inside dialog views (and inside the composite components they use) and rejects a third level.

### Declared queries

Pages, panels, toolbar items, and status items declare the queries they read:

```json
"queries": {
  "files": { "query": "pdf.files.list", "payload": { "status": "$state.filter" }, "refreshOn": ["pdf.imported", "pdf.translated"] }
}
```

The shell fetches them in parallel with rendering and refetches when a `refreshOn` event arrives. `refreshOn` lists durable or transient event types or patterns with the same wildcard rules as `ext.subscribe` (`05` §5.3); live events are never allowed (they are previews, not changes). An event with a `workspaceId` refetches only pages of that workspace; an event without one (a global-scope event) refetches pages in every workspace. Several `refreshOn` events arriving within 100 ms cause one refetch.

## 8.8 Built-in components

### Component spec

Every built-in component is described in `@kvman/protocol`:

```ts
type ComponentSpec = {
  name: string; description: string;
  since: string;                                     // first shell version that has it
  props: ZodType;                                    // including Text, Binding, and Action props
  events: Record<string, { description: string; value?: ZodType }>;   // the value is $value in the action
  children: 'none' | 'any' | string[];               // the component names it accepts as children
  parents?: string[];                                // the only components it may be a child of (ADR 0024)
  childCount?: { min?: number; max?: number };       // e.g. split: exactly 2 (ADR 0029)
  examples: ViewNode[];
};
```

- **Events are props whose value is an `Action`** (`onClick`, `onChange`, `onSubmit`, …). No JavaScript crosses the wire: the event runs the declarative action, with the event's value available as `$value`.
- **`children` is the same rule as a slot's `accepts`**, applied to components: `tabs` takes only `tab`, `menu` takes only `menuItem` and `divider`, `actionGroup` takes only `button` and `menu`, `text` takes nothing. Validation rejects anything else.
- **`parents`** works the other way (ADR 0024): `tab` may appear only in `tabs` and `menuItem` only in `menu`, and a `children` node only in a composite that declares `children`. A parent whose `children` is `any` accepts every component whose `parents` is absent or names it.

### Library (v2)

Common props on every node: `id?: string`, `visibleIf?: Condition`. The input controls (every Input row except `form`, ADR 0029), `button`, and `menuItem` also take `disabledIf?: Condition`. This is the only action whose target comes from data at runtime, so the static view-authority rule of §8.7 cannot check it. It is allowed because the menu lists only commands that declare `slash` (access `all` or `user`, `05` §5.5): the declaration is the owner's consent to be run by a person from any composer.

## 8.9 Extension components

Extensions add components with `ext.registerComponent(name, def)`, named `<ns>.<name>`:

```ts
type CompositeDef = {
  description: string;
  props: ZodType;                           // z.text() for Text props, z.action() for event props
  view: ViewNode;                           // built-in and composite components with $props bindings
  children?: 'none' | 'any' | string[];     // default 'none'; placed inside the view with { type: 'children' }
  visibility?: 'private' | 'public';        // default 'private'
  examples?: Json[];
};
type WidgetDef = {
  description: string; props: ZodType;
  widget: string;                           // 'widgets/viewer.html', shipped in the snapshot
  visibility?: 'private' | 'public';
};
```

| Form | Renders | Use for |
|---|---|---|
| **Composite** | natively by the shell | reusable cards, rows, forms, prompt layouts, UI kits: most needs |
| **Widget** | sandboxed iframe (§8.15) | what the library cannot express (PDF viewer, charts, canvas) |

### Events on extension components: `z.action()`

A composite exposes an event by declaring a prop with `z.action()` and binding it to a built-in event inside its view:

```ts
ext.registerComponent('pdf.fileCard', {
  description: 'A PDF file with its status and an Open button.',
  visibility: 'public',
  props: z.object({
    file: File,
    onOpen: z.action().optional().describe('Runs when the person clicks Open'),
  }),
  view: { type: 'card', children: [
    { type: 'heading', text: '$props.file.name' },
    { type: 'badge', text: '$props.file.status' },
    { type: 'button', label: '$t.card.open', onClick: '$props.onOpen',
      visibleIf: { '$props.onOpen': { exists: true } } },
  ] },
});
```

The view that uses it decides what the click does:

```json
{ "type": "pdf.fileCard", "file": "$item", "onOpen": { "navigate": "/files/{{ $item.id }}" } }
```

### Private and public

| | `private` (default) | `public` |
|---|---|---|
| Who may use it | only the owner's own views | any view in a workspace where the owner is enabled, declared with `ext.requireComponents` |
| Command actions written inside it | allowed, checked against the owner's types and granted `calls` | **not allowed**. Only passed-in actions (`$props.*`), `navigate`, and `openDialog` whose view has no command actions |
| Changing its props | free | a change that breaks an enabled dependent's views blocks the upgrade |

### Whose click is it?

- Every action is checked against the owner of the view where it is **written**. An action written in pdf's page and passed into `acme-ui.dataCard` as `onAction` is pdf's action: it may target pdf's own types and pdf's granted `calls`, and it is checked when pdf's page is validated.
- Public components cannot write command actions, so a UI kit can never send commands, and no component can borrow the grants of the extension that uses it.
- Private components are used only by their owner, so their actions are the owner's.

### Depending on another extension's components

```ts
ext.requireComponents(['acme-ui.dataCard', 'acme-ui.statTile'], { reason: 'Uses the Acme card style' });
```

- Checked at enable and preset apply, like `requireTypes`: the owner must be enabled in the workspace and the components must be public.
- Disabling or uninstalling `acme-ui` while an enabled extension requires it fails `EXT_IN_USE`, listing the dependents.
- Upgrading `acme-ui` re-runs referential validation (`06` §6.3) of every enabled dependent's views against the new props schemas. Views are static JSON, so this check is exact. Any failure blocks the upgrade and lists the broken views.

### Example: a UI-kit extension

An extension that registers only components, for others to use:

```ts
export default defineExtension({
  name: '@acme/ui', namespace: 'acme-ui', description: 'Cards and tiles in the Acme style.',
}, (ext) => {
  ext.registerTranslations({ default: 'en', catalogs: { en: { more: 'More' }, ar: { more: 'المزيد' } } });
  ext.registerComponent('acme-ui.dataCard', {
    description: 'Card with a title, an optional subtitle, any content, and an optional primary button.',
    visibility: 'public', children: 'any',
    props: z.object({
      title: z.text(), subtitle: z.text().optional(),
      actionLabel: z.text().optional(), onAction: z.action().optional(),
    }),
    view: { type: 'card', children: [
      { type: 'heading', text: '$props.title' },
      { type: 'text', text: '$props.subtitle', tone: 'muted', visibleIf: { '$props.subtitle': { exists: true } } },
      { type: 'children' },
      { type: 'button', label: '$props.actionLabel', onClick: '$props.onAction',
        visibleIf: { '$props.onAction': { exists: true } } },
    ] },
  });
});
```

The PDF extension uses it, and the command action it passes in is checked against pdf:

```json
{ "type": "acme-ui.dataCard",
  "title": "$item.name",
  "subtitle": { "$t": "files.pages", "count": "$item.pages" },
  "actionLabel": "$t.actions.translate",
  "onAction": { "command": "pdf.translate", "payload": { "fileId": "$item.id" }, "form": true },
  "children": [ { "type": "badge", "text": "$item.status" } ] }
```

Text props (`z.text()`) passed in by pdf are resolved in pdf's catalog; `$t` keys written inside the component's own view are resolved in `acme-ui`'s catalog.

### Limits

- Composite components contain no code and cannot reference themselves, directly or through other extensions' components. Cycles are checked across extensions at enable and apply.
- At most 8 composite levels are nested.
- Props are validated at render. A props error renders an inline error box, not a broken page.

## 8.10 Runtime UI: registered, never pushed

Some UI appears only at certain moments, such as the interviewer's question or a pending approval. It was still registered at install: it is hidden, and data makes it visible.

**Example: the interviewer's question.** Registered once, in `setup`:

```ts
ext.registerPanel('interviewer.question', {
  description: 'The open question for this chat session, above the composer.',
  slot: 'agent.chat.prompt',
  queries: { open: { query: 'interviewer.questions.list', payload: { rootSessionId: '$slot.sessionId', status: 'open' },
                     refreshOn: ['interviewer.question.asked', 'interviewer.question.closed'] } },
  visibleIf: { '$query.open.items.0': { exists: true } },
  view: { type: 'interviewer.questionCard', question: '$query.open.items.0' },
});
```

What happens at runtime:

```
agent calls interviewer.ask ──▶ handler stores the question (status open) · publishes question.asked · ctx.defer()
every tab on /chat/<sid>: refreshOn fires ──▶ refetch questions.list ──▶ one item ──▶ the panel becomes visible
the person clicks a choice ──▶ POST /commands/interviewer.question.answer (access: user)
                              ──▶ ctx.reply(...) · status closed · publishes question.closed
every tab: refetch ──▶ no items ──▶ the panel hides
```

| Concern | Registered + data-driven (kvman) | Pushed at runtime (not supported) |
|---|---|---|
| Browser reload | comes back: the question is stored | lost with the pushed message |
| Two tabs, or a tab opened later | every tab shows it | only tabs connected at that moment |
| Validation | checked at install (components, props, slot accepts, authority) | cannot be checked |
| Security | the UI is fixed and reviewed; only data varies | any handler could draw anything at any time, e.g. an imitation grant dialog |
| Memory | nothing held; it is a query | someone must hold every open view |

There is no `ctx.ui.show(view)`, by design.

**What is pushed at runtime** is only one-way messages without layout: toasts and notifications (§8.11) and `ui.navigate`.

**Where to register UI that appears at runtime:**

| Need | Register | Visible when |
|---|---|---|
| Inline in another extension's page | a `panel` in that page's slot (`agent.chat.prompt`) | its query returns something |
| Over any page | a `panel` in `frame.overlay` | its `visibleIf` is true (typically "my pending prompts are not empty") |
| A global indicator | a `statusItem` with `visibleIf` | its query says so |
| A place of its own | a `page` plus a `navItem` with a `badge` | always; the badge shows the count |

## 8.11 Notifications

Notifications are part of the UI contract. Extensions send them as messages; the **shell** draws them in two shell-only zones (the toast stack and the 🔔 tray), so every notification looks the same, shows who sent it, and follows the user's language.

### Choosing how to tell the person

| Channel | Use for | Lives | Drawn by |
|---|---|---|---|
| **Toast** (`ui.toast`) | short confirmations and failures of something just done ("Imported report.pdf") | seconds (errors until dismissed); only tabs connected now | shell toast stack |
| **Notification** (`ui.notify`) | something that happened in the background or needs attention later ("Translation finished", "A question is waiting") | stored in the tray until read, dismissed, or expired; reaches tabs opened later | shell tray (🔔) |
| **Inline notice** (the `notice` component) | a condition of one page ("No AI model is set up") | as long as the view's data says so | the extension's view |
| **Status item** (`ext.registerStatusItem`) | ongoing state ("Translating 3 files") | while its `visibleIf` is true | the extension, in `frame.statusbar.*` |
| **Prompt** (§8.13) | a question that needs an answer | until answered or expired | the extension's panel; usually paired with an `attention` notification |

Errors from a person's own click need no extension code at all (see "Errors" below).

### Messages

All require the capability `ui`. The SDK has shorthands on `ctx.ui` (`05` §5.4) that send exactly these messages.

```ts
type Level = 'info' | 'success' | 'warning' | 'error';
type NoticeAction =
  | { label: Text; navigate: string }
  | { label: Text; command: string; payload?: Json };      // the sender's own types or granted calls

// ctx.ui.toast(t)  ≡  ctx.send('ui.toast', t)
type Toast = {
  text: Text; level?: Level;                  // default 'info'
  key?: string;                               // a later toast with the same key replaces this one
  action?: NoticeAction;                      // one button, e.g. "Undo" or "Open"
  durationMs?: number;                        // default 4 s (info, success), 8 s (warning); errors stay until dismissed
};

// ctx.ui.notify(n)  ≡  ctx.send('ui.notify', n)
type Notification = {
  title: Text; body?: Text; level?: Level;    // default 'info'
  key?: string;                               // same sender + workspace + key replaces the earlier one
  problem?: Problem;                          // for errors: shown translated, with "Copy details" (code, correlationId)
  route?: string;                             // clicking the notification opens this route
  entity?: { type: string; id: string };      // or opens this entity's page: the kernel renders its registered `route`
                                              // with the id at admission and stores it (ADR 0162); an unknown type, a
                                              // type without a route, a route needing other fields, or `route` and
                                              // `entity` together fail admission with VALIDATION_FAILED
  actions?: NoticeAction[];                   // at most 2 buttons
  attention?: boolean;                        // needs the person: highlighted until opened; desktop alert if enabled
  expiresAt?: number;                         // removed after this time (e.g. a prompt's deadline)
  global?: boolean;                           // default: the message's workspace; true = shown in every workspace
};

// ctx.ui.dismiss(key)  ≡  ctx.send('ui.dismiss', { key })   — removes the sender's own toast and notification with this key
//   (the entry in the message's workspace, or the global one for a global message, ADR 0162)
// ctx.ui.navigate(route) ≡ ctx.send('ui.navigate', { route }) — only the tab that started the current correlation;
//   dropped when the correlation did not start from a tab or that tab is closed
```

### Rules

- **Attribution.** The source is assigned by the kernel. The shell shows the sending extension's `meta.title` and `meta.icon` on every toast and notification; only the kernel's own show "kvman". An extension cannot appear as kvman or as another extension, and bidirectional control characters are removed from its text (§8.16).
- **Rows.** An admitted `ui.*` send is stored as a `done` command row with the reply `{ ok: true }` and its `target`: the tab that started the correlation for `ui.toast` and `ui.navigate` when there is one, else `user:local` (ADR 0162). Runtime `$t` keys are not checked against the sender's catalog; the shell's fallback shows a missing one.
- **Actions are checked like view actions.** A `command` in a toast or notification must be one of the sender's own types or covered by its granted `calls`. Because the click is sent as the person, it must have access `all` or `user`; it can never be a grant command (§8.7) or another extension's `access: 'user'` command; otherwise the kernel rejects the whole message with `CAPABILITY_DENIED`. The check happens at admission, because the payload is runtime data. A click on the button sends the command **as the user** (a click is a person's gesture), with one idempotency key per button.
- **Replacement by `key`.** A notification with the same sender, workspace, and `key` replaces the earlier one instead of adding a second. This is how progress becomes a result ("Translating report.pdf" → "report.pdf is translated"). A replacement updates the entry in place (id and `createdAt` kept); one that raises the level (to `warning` or `error`) marks it unread again, and a dismissed entry comes back unread (ADR 0162).
- **Dismissal.** `ui.dismiss { key }` removes the sender's own entry, e.g. when a question is answered in another tab. The person dismisses anything from the tray.
- **Language.** Stored as keys and parameters; the tray re-renders after a language change (§8.16).
- **Limits.** Per extension and workspace: 20 toasts and 10 notifications in the last 60 s (a sliding minute; key replacements count). The excess is stored as rows but not shown: it folds into one tray entry of the extension (`folded: n`, no title), which the shell draws as "PDF Translator sent 14 more notifications"; an unread folded entry grows, and after it is read or dismissed the next excess starts a new one (ADR 0162). `ui.dismiss`, `ui.navigate`, and the kernel's own notifications are not limited. At most 3 toasts are visible; the rest queue.
- **Muting.** The person can mute an extension's notifications per workspace from the tray. A mute covers that workspace's entries from the extension, not its global ones. Muted entries are stored and listed with `muted: true` but raise no toast, badge, or desktop alert: they are left out of the counts, and the kernel pushes no `ui` message for them (ADR 0163). Notifications from the kernel cannot be muted.
- **Desktop alerts** are off by default. When the person turns them on in the kvman menu, the shell uses the browser's Notification API for `attention` and `error` notifications while no kvman tab is visible. Only the title is shown.
- **No tab connected.** Toasts are dropped; notifications wait in the tray.
- **Where they appear.** A toast goes to every tab showing the message's workspace (a toast from a handler of a person's click goes only to the tab that clicked). A notification appears in the tray of its workspace, or of every workspace with `global: true` (stored with workspace `''`).
- **Capability and admission.** `ui.*` sends are buffered in the unit of work like any send and admitted at commit. Sending without the `ui` capability, or with an invalid action button, fails the unit of work with `CAPABILITY_DENIED` (a bug in the extension, not retried), so a handler never commits half its work with a broken notification. Every refusal of a `ui.*` send fails its unit, even when the send has `onReply` (ADR 0162).
- **Buttons after changes.** A button is checked again when clicked: if its command's extension is no longer enabled, the click shows the error toast (`HANDLER_UNAVAILABLE`) and the entry stays. A `navigate` to a hidden page still works (§8.17).
- **Order in the tray.** Newest first by `updated_at`; entries with `attention` that are unread are pinned to the top.
- **Retention.** The tray keeps the latest 200 notifications per workspace (applied when an entry is stored) for 30 days; read ones are removed after 7 days, dismissed and expired ones at the next housekeeping run (ADR 0163).

### Storage and kernel API

`ui.*` types are handled by the kernel. Notifications are stored in the kernel's `notifications` table (`04` §4.1), because the tray must work with any set of extensions, including none.

| Kind | Type | Notes |
|---|---|---|
| query | `kernel.notifications.list { workspaceId?, unreadOnly? }` → `{ items: NotificationItem[] }` | the user and `kernel.admin` only: the tray holds every extension's messages |
| query | `kernel.notifications.count { workspaceId? }` → `{ unread, attention }` | unread count for the 🔔 badge; muted entries are not counted |
| command | `kernel.notification.read { id }`, `kernel.notifications.read-all { workspaceId? }`, `kernel.notification.dismiss { id }` | `access: 'user'`; an unknown or dismissed id fails `NOT_FOUND` |
| command | `kernel.notifications.mute { workspaceId, extension, muted }` | `access: 'user'`; stored in `user_preferences`; `WORKSPACE_INVALID` / `NOT_FOUND` for an unknown workspace or extension |
| event | `kernel.notifications.changed { workspaceId? }` | transient, global; published with every change of an entry (absent `workspaceId` = a global entry); keeps the badge and read state in step across tabs |

```ts
type NotificationItem = {                    // ADR 0163
  id: string; workspaceId?: string;          // absent = global
  source: Address; key?: string; level: Level;
  title?: Text; body?: Text; problem?: Problem; route?: string; entity?: { type: string; id: string };
  actions?: NoticeAction[]; attention: boolean; expiresAt?: number;
  read: boolean; muted: boolean;
  folded?: number;                           // a folded entry: no title, n excess sends
  createdAt: number; updatedAt: number;
};
```

With `workspaceId`, the tray queries and `read-all` cover that workspace's entries and the global ones; without it, every entry. Dismissed and expired entries are never listed or counted. The list is newest first by `updatedAt`, with unread `attention` entries pinned to the top.

New toasts and notifications reach tabs as `ui` messages on the event stream, with the message's `workspaceId` (`12` §12.3).

### Errors: who tells the person

| Failure | Who reports it | How |
|---|---|---|
| A command the person started fails right away | the **shell**, automatically | validation issues next to form fields; otherwise an error toast with the translated problem and "Copy details". No extension code. |
| A command answered `202` fails later | the shell | error toast in the tab that sent it (the late `reply`); a tray entry if that tab is gone |
| A query behind a view fails | the shell | an inline error box in that view with Retry, never a notification |
| Background work fails in a way the person should know (scheduled sync, retry exhausted) | the extension | `ctx.ui.notify({ level: 'error', title, problem, actions })` |
| A message is dead-lettered and its correlation began with a person's action | the kernel | error notification "…could not finish" with the problem, key `dead:<messageId>`, and a Retry that sends `kernel.message.retry` |
| An extension is quarantined, a migration fails, a snapshot fails its integrity check, the secrets file cannot be written | the kernel | error notification, plus the risk banner for quarantine; keys, text, and buttons in ADR 0164 |

### Examples

Progress that turns into a result, with one entry in the tray:

```ts
ctx.ui.notify({ key: `translate:${fileId}`, title: { $t: 'notify.translating', name: file.name } });
// … later, in the same or a continuation handler
ctx.ui.notify({ key: `translate:${fileId}`, level: 'success', title: { $t: 'notify.translated', name: file.name },
                actions: [{ label: '$t.actions.open', navigate: `/files/${fileId}` }] });
// or, when the last retry fails
ctx.ui.notify({ key: `translate:${fileId}`, level: 'error', title: { $t: 'notify.failed', name: file.name }, problem,
                actions: [{ label: '$t.actions.retry', command: 'pdf.translate', payload: { fileId, lang } }] });
```

A prompt that needs attention, removed when answered:

```ts
ctx.ui.notify({ key: `question:${id}`, attention: true, title: '$t.notify.questionWaiting',
                route: `/chat/${sessionId}`, expiresAt: deadlineAt });
// in interviewer.question.answer
ctx.ui.dismiss(`question:${id}`);
```

A toast after a quick action needs no handler code: the view's `then: [{ "toast": "$t.toast.imported" }]` effect shows it in the tab that clicked.

## 8.12 Forms from schemas

```json
{ "type": "form", "command": "pdf.translate",
  "defaults": { "fileId": "$route.fileId", "lang": "ar" },
  "hidden": ["fileId"],
  "fields": { "lang": { "widget": "select", "options": [["ar", "$t.lang.ar"], ["fr", "$t.lang.fr"]] } },
  "submitLabel": "$t.actions.translate", "then": [{ "toast": "$t.toast.started" }] }
```

- Field types, validation, required markers, and defaults come from the command's input schema.
- **Labels are explicit.** A field's label and help come from `.meta({ label, help })` in the schema, where each is a `Text` (`.meta({ label: '$t.form.lang' })`), else from `.describe()`. `fields` in the view can override them. The same applies to forms generated from `ext.registerConfig`, so settings forms are translated as well.
- Other overrides come from `fields` or from `.meta({ ui: { widget, group, order } })`.
- Browser-side validation is a usability hint. The kernel's validation is authoritative, and its issues (Zod issue code plus parameters) are mapped back onto the fields and rendered in the user's language.

## 8.13 The user actor, prompts, and the grant dialog

**Prompts (asking a person).** An extension that needs an answer uses the prompt pattern (`02` §2.8), usually through `ext.registerPrompt` (`05` §5.5):

```
handler needing an answer                        the extension's own UI
  store prompt in own collection                    panel / page / component bound to <ns>.<prompts>.list
  publish <ns>.<prompt>.asked            ───────▶   (refreshOn asked/closed) shows the prompt its own way
  return ctx.defer({ onAbort })                      person submits ──▶ <ns>.<prompt>.answer  (access: 'user')
                                                                        ctx.reply(commandId, answer) · close prompt
cancel / deadline ──▶ <ns>.<prompt>.expire (access: internal) closes the prompt · UI shows "no longer active"
```

- **Placement is the extension's choice**: inside its own pages; inline in another page through a slot (`agent.chat.prompt` for chat questions and approvals); or as a dialog over any page through `frame.overlay` (§8.10). Pair it with `ui.notify` so a person who is elsewhere learns that something is waiting.
- **Every tab** sees the prompt because it is data (a live query). The first answer commits the reply; a second answer fails `REPLY_NOT_AWAITING` and its tab shows "already answered".
- **No tab connected**: the prompt waits in storage and appears when a tab opens, until the deferred command's deadline.
- **Only a person can answer**: the answer command has `access: 'user'`. Neither the agent (or any other extension), nor a process through `kv`, nor the extension's own widget can send it (`05` §5.5). Another extension's views cannot send it either unless the user granted that extension `calls` for it. Honest boundary: localhost has no authentication, so a raw shell command that calls the HTTP API is treated as the user (`13` §13.6).

**The grant dialog (shell-owned).** Prompts drawn by extensions are fine for answering *their own* questions, but not for granting power: an extension could draw a misleading "Continue" button. So the power-granting kernel commands (`kernel.trust.grant`, `kernel.extension.enable`, `kernel.extension.reload` with `grants`, `kernel.preset.import`, `kernel.preset.apply`, `kernel.preset.update` touching extensions) are confirmed only in a dialog the **shell** draws (D41):

- A view opens it with `{ "openGrantDialog": { "command": "kernel.extension.enable", "payload": { … } } }`. Extensions (`extensions`, `presets`, `builder`) and preset pages use this for their "Enable", "Apply", and "Publish" buttons.
- The shell fetches what to show from the kernel, never from the view (a dialog whose data cannot be fetched, e.g. an expired token, shows the error and has no Confirm button): for extensions, the stage result (name, title, summary, source, digest, isolation, requested and derived capabilities with reasons, native-code and other warnings, and the diff against the current grant), whose `translations` carry the staged extension's catalog entries for its title, summary, and reasons, so the shell can draw them in the person's language before the extension is installed; for trust, the files and hashes from `kernel.trust.preview`; for presets, the apply stage, including **what the preset hides** (every hidden item of the platform pack by name, and a count of the others, §8.17).
- The dialog's own text comes from the shell's catalog in the user's language. Extension-supplied text (title, summary or description, capability reasons) is shown as quoted plain text attributed to the extension, with Unicode bidirectional control characters removed (§8.16).
- The dialog's Confirm button sends the command as the user; Cancel sends nothing. The view that opened it receives the reply in `then` (`$reply`) like any action.
- The dialog cannot be styled or pre-confirmed by extensions, and it names the extension that opened it.

## 8.14 Data layer

- Everything the shell sends is HTTP; everything it receives live comes from one SSE stream per browser, held in a `SharedWorker` (or by a leader tab) and routed to tabs (`12` §12.3).
- **Boot**: `kernel.user.preferences.get` (language, theme) → shell catalog for that language → `GET /ui` for the current workspace → `GET /ui/translations` for the language → the route's page view. The registry, catalogs, and page views are cached and revalidated with their ETags. The current workspace comes from the URL query `?ws=<workspaceId>`, else the last one used in this browser (`localStorage`; an embedded shell, `?embed=1`, never writes it), else Home. A `?ws=` naming a workspace the kernel does not know (never opened, or forgotten) falls back to the last-used workspace, else Home, with a toast "That workspace is not available". A workspace whose folder is missing (`exists: false`, `07` §7.1) opens with a notice "This folder was moved or deleted" and a Forget button; its pages still show stored data, and file tools fail `WORKSPACE_INVALID`.
- **Workspace switch**: sets `?ws=`, drops the query cache for the old workspace, fetches the new registry and catalogs, and opens the new workspace's home (or its first-run screen when it has no applied preset).
- **Registry refresh**: on `kernel.preset.changed`, `kernel.extension.reloaded`, `kernel.extension.quarantined`, or `kernel.extension.unquarantined` for the current workspace, the shell refetches `GET /ui` with `If-None-Match` and re-renders only what changed. A page whose route no longer exists shows "This page is no longer available" with a link home.
- **Language switch**: on `kernel.user.preferences.changed`, every tab fetches the new catalogs, sets `<html lang dir>`, and re-renders. Query data is not refetched.
- Live query subscriptions are `POST /subscriptions`; the shared stream holder deduplicates identical subscriptions across tabs.
- **Query cache** keyed by `(type, payload, workspaceId)`. Stale-while-revalidate; `refreshOn` events invalidate matching entries; `refresh` effects force a refetch.
- **Live events**: components with a `live` prop subscribe to that `<type>:<key>` while mounted; `liveText` and `progress` update in place. They keep chunks per `run` and show the newest run; `{ reset: true }` removes that run (falling back to the previous run, else the initial state: `initial`, or indeterminate progress), and a gap in chunk numbers resets every run and refetches (`02` §2.3). `thread` drops a run's live entry when its data holds the committed entry with that run id.
- **Commands**: `POST /commands/:type` returns the handler's result in the response; only a deferred or very long command answers `202` and delivers its reply on the stream. Optimistic UI only where a component declares it (e.g. `composer` shows a pending bubble), with rollback on failure and a Retry that reuses the idempotency key. Pending state is keyed by the idempotency key, because an event caused by a command can arrive before the POST response.
- **Resume**: on reconnect the stream sends `Last-Event-ID`; missed durable events are replayed, lost subscriptions are re-created with `since`, and waiting commands are checked with `GET /messages/:id`. When the cursor is too old, a `resync` invalidates all queries and the registry.
- A split pane that is not focused pauses its live subscriptions and refetches once when focused.

## 8.15 Widget components

- An extension registers a widget component with `ext.registerComponent(name, { widget: 'widgets/<name>.html', … })` and ships the file (plus assets) in its snapshot. It is used by name in views and renderers like any component.
- The kernel serves widget files from a per-extension origin `http://w-<hash>.localhost:<port>/` (browsers resolve `*.localhost` to loopback).
- The shell embeds a widget in `<iframe sandbox="allow-scripts">` (no `allow-same-origin`), with a strict CSP (`default-src 'none'; script-src 'self'; style-src 'self'; img-src blob: 'self'; connect-src 'none'`).
- Communication only through `postMessage` via `@kvman/widget-bridge`:
  ```ts
  kvman.props() · kvman.onProps(cb) · kvman.query(type, payload) · kvman.command(type, payload)
  kvman.subscribe({ events?, live? }, cb)   // live: `<type>:<key>` addresses of its own extension's live events only · kvman.blob(blobId) → Blob · kvman.theme() · kvman.resize(h)
  kvman.locale() → { code, dir } · kvman.onLocale(cb)
  ```
- The shell forwards bridge calls to the kernel as the widget's extension, limited to the types that extension may send, the durable and transient events it may receive, **its own extension's live events** (another extension's live data is shown with `liveText` or `progress` placed next to the widget), the blobs it may read (`04` §4.6), and the page's workspace. Types with access `user` are therefore unreachable from widgets; a widget that needs a person's confirmation places a declarative button (or a composite component) next to itself.
- Widgets translate their own text (their catalogs ship with their files) and follow `kvman.locale().dir`. A public widget's props follow the same upgrade rule as public composites (§8.9).

## 8.16 Localization and right-to-left

### The language setting

- The language is a **user preference owned by the kernel**, not by an extension, because the shell needs it before any extension loads, including on the recovery page. It is stored in `user_preferences` (`04` §4.1) together with the theme.
- `kernel.user.preferences.get` returns `{ locale, theme, desktopAlerts }`. `kernel.user.preferences.set { locale?, theme?, desktopAlerts? }` has `access: 'user'`: only a person changes their preferences, from the kvman menu, first run, or the recovery page. It publishes `kernel.user.preferences.changed`, and every open tab switches without reloading (§8.14).
- **Theme**: `theme` is `'app' | 'system' | 'light' | 'dark'`, default `'app'`, which uses the applied preset's `app.theme.mode` (itself defaulting to `'system'`). Any other value is the person's own choice and wins over the preset. `'system'` follows `prefers-color-scheme`.
- `locale` is a BCP 47 tag. kvman v2 ships `en` and `ar` for the kernel, the shell, and the core extensions. The picker offers exactly three choices: English (`en`), العربية (`ar-u-nu-arab`, Arabic-Indic digits), and العربية — 0123 (`ar-u-nu-latn`, Western digits). Both Arabic choices name their digits, because the Unicode data (CLDR 48) now gives plain `ar` Western digits; their catalogs are found under `ar` through the fallback chain (ADR 0161). `set` accepts any valid tag (so later language packs need no API change); a language without catalogs renders through the fallback chain below.
- First run picks the best match from `navigator.languages`, else `en`, and shows the picker; the choice is saved as the preference at once.
- **The language never depends on the URL.** No route prefix, no `?lang=` or `?locale=` parameter, no language cookie, and no `localStorage` entry: the only source is the saved preference. The shell reads it at boot with `kernel.user.preferences.get`, fetches translations without naming a language (the kernel uses the saved one), and follows `kernel.user.preferences.changed`. Switching the language changes no URL, and a link opened in any tab renders in the saved language.
- **Handlers see the language.** At admission the kernel sets `locale` in the message context of every user-originated message from the preference; it is inherited by every message caused by it. `ctx.locale` returns it. Scheduled and kernel-originated messages without an inherited value use the preference.

### Catalogs

An extension ships one catalog per language and registers them explicitly. `setup` does no I/O, so they are imported statically:

```ts
import en from '../locales/en.json' with { type: 'json' };
import ar from '../locales/ar.json' with { type: 'json' };
ext.registerTranslations({ default: 'en', catalogs: { en, ar } });
```

Catalogs are JSON objects whose leaves are **ICU MessageFormat** strings. An excerpt of the pdf extension's catalogs (the full files hold every key its registrations use):

```json
// locales/en.json
{ "meta": { "title": "PDF Translator" },
  "nav": { "documents": "Documents", "files": "Files" },
  "files": { "title": "Files", "count": "{count, plural, =0 {No files} one {# file} other {# files}}",
             "pages": "{count, plural, one {# page} other {# pages}}" },
  "status": { "translating": "{count, plural, one {Translating # file} other {Translating # files}}" },
  "actions": { "translate": "Translate" },
  "toast": { "translated": "{name} is translated" },
  "problems": { "NOT_FOUND": "This file no longer exists." } }
```

```json
// locales/ar.json
{ "meta": { "title": "مترجم PDF" },
  "nav": { "documents": "المستندات", "files": "الملفات" },
  "files": { "title": "الملفات",
             "count": "{count, plural, =0 {لا توجد ملفات} one {ملف واحد} two {ملفان} few {# ملفات} many {# ملفًا} other {# ملف}}",
             "pages": "{count, plural, one {صفحة واحدة} two {صفحتان} few {# صفحات} many {# صفحة} other {# صفحة}}" },
  "status": { "translating": "{count, plural, one {جارٍ ترجمة ملف واحد} two {جارٍ ترجمة ملفين} few {جارٍ ترجمة # ملفات} many {جارٍ ترجمة # ملفًا} other {جارٍ ترجمة # ملف}}" },
  "actions": { "translate": "ترجمة" },
  "toast": { "translated": "تمت ترجمة {name}" },
  "problems": { "NOT_FOUND": "هذا الملف لم يعد موجودًا." } }
```

- Keys are **namespaced automatically**: `$t.files.title` in pdf's views is `pdf:files.title`. Two extensions can never collide, and an extension cannot use another extension's keys (it uses that extension's components instead).
- Presets carry their own catalogs for their pages and labels (`07` §7.3). kvman's own strings (shell, kernel problems, grant dialog, recovery page) are in the `kvman:` catalog shipped with the shell.
- ICU is used for plurals, gender, and choices; Arabic needs all six plural forms (`zero`, `one`, `two`, `few`, `many`, `other`). Formatting uses `intl-messageformat`, and its output is always plain text, never HTML: messages are parsed with tags ignored, so `<b>` is literal text (ADR 0160).

### Using keys

| Where | How |
|---|---|
| Views and contributions | any `Text` prop: `"$t.files.title"`, `{ "$t": "files.count", "count": "$query.files.total" }`, or inside interpolation `"{{ $t.files.title }}"` |
| Schemas (forms, settings) | `.meta({ label: '$t.form.lang', help: '$t.form.langHelp' })`; fallback `.describe()` |
| Notices from handlers | `ctx.send('ui.toast', { text: { $t: 'toast.translated', name: file.name } })`: stored and sent as key plus parameters, rendered by each tab |
| Problems | `throw ctx.problem('pdf/NOT_FOUND', { params: { fileId } })` for an error registered with `ext.registerError`: the shell shows `pdf:problems.NOT_FOUND` with the parameters when the catalog has it, else the registered English `title`. This is the one lookup-by-convention, because the code is already the problem's stable identifier. The CLI, logs, and the model receive the English title. |
| Text that leaves kvman | `ctx.i18n.t('export.header', { name })` returns a finished string in `ctx.locale` from the extension's own catalog (exact tag, base language, default locale): for files it writes, LLM prompts, or messages to other systems. A key in none of them, or a missing parameter, throws `VALIDATION_FAILED` (ADR 0161) |

**Whose catalog?** A `$t` key resolves in the catalog of the owner of the view where it is written, the same rule as action authority (§8.9). Text props passed into another extension's component are resolved by the passing view's owner before they are handed over.

**Fallback** for a missing key: the exact locale (`ar-EG`) → the base language (`ar`) → the owner's `default` locale → the key itself, shown as `⟨pdf:files.title⟩`. Rendering never throws.

### Validation

| Check | Result |
|---|---|
| A `$t` key written in a view, contribution, or schema is missing from the owner's default catalog | error |
| The key is missing from another shipped catalog | warning (the fallback is used) |
| A message is not valid ICU, or a view does not pass a parameter the message uses | error |
| A user-facing `Text` is a literal instead of a key | warning for installed extensions; error for builder-generated ones (`11`) |
| `description` fields | never translated: they are for developers and LLMs, and stay in English |

What counts as a key use, a literal, and a user-facing `Text` is in ADR 0160. A preset gets the same key, ICU, and parameter checks against its own catalogs (`PRESET_INVALID`), and no literal warning.

### What is localized where

| Text | Stored as | Rendered by |
|---|---|---|
| Extension labels, titles, and view text | keys in the manifest | the shell |
| Preset labels and preset pages | a per-language map or keys in the preset's catalog | the shell |
| Toasts and notifications | key plus parameters (also in the stored tray) | the shell, at display time |
| Problems | code, parameters, and an English title | the shell from the catalog; the CLI, logs, and the model use the English title |
| Validation issues | Zod issue code plus parameters | the shell (`kvman:` catalog) |
| Grant dialog | the `kvman:` catalog; extension reasons as quoted plain text | the shell |
| Agent replies | model output | the model, told the user's language by the agent (`09` §9.6) |
| Agent notices in history | code, parameters, and fallback text | the shell |
| Registry `description` fields | English | not translated |

### Right-to-left

- The shell sets `<html lang dir>` from the locale; `ar` (and any other right-to-left language) sets `dir="rtl"`.
- **The frame mirrors**: the sidebar moves to the right, `start` and `end` swap, drawers open from the start edge.
- **Logical CSS only**: shell and component styles use start/end utilities (`ms-*`, `me-*`, `ps-*`, `pe-*`, `start-*`, `end-*`, `text-start`, `rounded-s-*`). A lint rule fails the build on physical ones (`ml-*`, `mr-*`, `pl-*`, `pr-*`, `left-*`, `right-*`, `text-left`, `text-right`, `rounded-l-*`, `rounded-r-*`).
- **Directional icons flip** (arrows, chevrons, "back"); other icons do not.
- **Left-to-right islands**: `code`, `diff`, `json`, `liveText` for process output, file paths, and logs always render `dir="ltr"`.
- **Mixed-direction text**: text components wrap every bound value in `<bdi>` (`unicode-bidi: isolate`), so an English file name inside an Arabic sentence cannot reorder the sentence.
- **Spoofing**: Unicode bidirectional control characters (U+202A–U+202E, U+2066–U+2069) are removed from extension-supplied text shown in shell-only zones and the grant dialog.

### Formatting

Numbers and dates are formatted by components, never by expressions. Display components and table columns take `format`:

| `format` | Example (`en` / `ar`) |
|---|---|
| `date`, `time`, `dateTime` | Sep 23, 2026 / ٢٣ سبتمبر ٢٠٢٦ |
| `relative` | 5 minutes ago / منذ ٥ دقائق |
| `number`, `integer`, `percent` | 1,234.5 / ١٬٢٣٤٫٥ (`ar-u-nu-arab`) |
| `currency:USD` | $3.20 / ‏٣٫٢٠ US$ |
| `bytes` | 1.2 MB / ١٫٢ ميغابايت |
| `duration` | 2m 5s / ٢ د ٥ ث |

```json
{ "type": "text", "text": "$item.createdAt", "format": "relative" }
```

All formatting uses the browser's `Intl` APIs with the user's locale. Sortable table columns sort loaded rows with `Intl.Collator`; server-side `orderBy` sorts by raw byte order (a known limit, `15` R15).

### Widgets

`kvman.locale()` returns `{ code, dir }` and `kvman.onLocale(cb)` reports changes. Widgets ship and apply their own translations.

## 8.17 Presets and visibility

A preset shapes the UI of its workspace. The kernel applies these settings while it computes the registry (§8.6), so the shell simply renders the result.

| Preset field (`07` §7.3) | Effect |
|---|---|
| `app` | title, icon, accent color, theme mode, home route |
| `layout` | `sidebar: 'expanded' \| 'collapsed' \| 'hidden'`, `statusbar: 'shown' \| 'hidden'`, `order` per slot (with `"---"` separators in `frame.sidebar`) |
| `hidden` | contribution ids that are not shown: pages, nav groups and items, toolbar and status items, panels, actions, settings sections |
| `labels` | replacement label per contribution id: one string, or one per language |
| `pages`, `translations` | the preset's own pages and their catalogs |
| `extensions[x].disable` | functional switch for agent tools (not a UI setting) |

### What a preset can hide

| Thing | Can a preset hide it? | How |
|---|---|---|
| A core page or nav item (`/settings`, `/extensions`, `/inspector/*`) | yes | `hidden: ['settings.models', 'inspector.traces']` |
| One extension's settings section | yes | `hidden: ['settings.section.agent']` |
| A whole core extension | yes | `enabled: false`; its pages and panels disappear from the workspace |
| A frame region (sidebar, status bar) | yes | `layout.sidebar: 'hidden'`, `layout.statusbar: 'hidden'` |
| Built-in components (`button`, `card`) | not applicable | building blocks, not contributions |
| Shell-only zones (§8.3) and the recovery page | no | drawn by the shell |

### The way back

1. **The kvman menu** (a shell-only zone) always offers Language, **Show hidden pages**, and **Manage kvman**.
2. **Show hidden pages** lists the pages this preset hides and opens any of them for the current session, with a "Hidden by this app's preset" note. It edits nothing.
3. **Hidden is not blocked.** A hidden page's route still works from "Show hidden pages", a link, a notification, or the URL. If `app.home` itself is hidden, it still opens as the home page. Hiding keeps the interface simple; capabilities and grants are what restrict power.
4. **The recovery page needs no extension.** If a preset disabled `settings` or `extensions`, the recovery page re-enables them or applies the Minimal preset.
5. **The apply dialog says what gets hidden.** For an imported preset, the grant dialog lists the platform-pack items it hides by name ("This preset hides: Settings › Models, Extensions, Inspector") and counts the rest, so a preset cannot hide the Extensions page to conceal what it enabled.

Platform extensions (`settings`, `presets`, `extensions`, `inspector`) are ordinary extensions: they can be hidden or disabled like any other, and the kernel has no special cases for them. A kiosk-style app ("PDF Translator" with no sidebar) is legitimate; the person who applied it can always get out through the kvman menu.

## 8.18 Visual system

Design tokens for color, type, radius, and motion in one Tailwind theme with light and dark modes; system font stack with Inter fallback, plus Noto Sans Arabic (bundled) for Arabic; `rounded-xl` cards and `rounded-2xl` floating surfaces; neutral zinc base with a preset-controlled accent (the shell draws text on the accent in black or white, whichever has the higher WCAG contrast; if neither reaches 4.5:1, it shifts the accent's lightness, in each theme mode, until one does); status never shown by color alone (dot + label); 150 ms transitions; focus rings; AA contrast. Logical (start/end) spacing throughout (§8.16). Widgets receive the same tokens through `kvman.theme()`.

## 8.19 Rendering safety

- **Markdown**: one component only. `markdown-it` with `html:false`; image rendering disabled; code highlighting uses Shiki with `transformerStyleToClass` and a stylesheet generated at build time for the bundled light/dark themes, so no inline styles are produced (R-Q3); final DOMPurify pass with this allowlist (tags `a, blockquote, br, code, del, em, h1–h6, hr, li, ol, p, pre, span, strong, table, tbody, td, th, thead, tr, ul`; attributes `href, title, class, target, rel`; safe schemes `http, https, mailto`, relative, hash; external links get `target=_blank rel="noopener noreferrer"`). No `v-html` anywhere else.
- **Translations** are plain text: ICU output is inserted as text, never as HTML, so a catalog cannot inject markup.
- **Text** from tools, logs, and job output renders as plain text in `code`/`pre`, left-to-right.
- **Blobs** display inline only for allowlisted inert types (PNG, JPEG, WebP, GIF, plain text, PDF inside a widget); everything else is a download (`13` §13.7).
- **Shell CSP**: `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' blob:; connect-src 'self'; frame-src 'self' http://*.localhost:<port>; object-src 'none'; base-uri 'none'; frame-ancestors 'self'; form-action 'none'`. `frame-ancestors 'self'` lets the builder's preview pane embed the shell (`11` §11.7) while every other site is refused.

## 8.20 Performance and accessibility

- The UI registry and page views are static per ETag and cached; only data is fetched at runtime. Catalogs are cached per ETag and locale.
- Tables and threads are virtualized. Live-event updates patch text nodes in place.
- Route-level code splitting of the shell itself; the component library is lazy per family.
- Reka UI primitives for accessible dialogs, menus, and tabs; keyboard navigation for tables and the palette; screen-reader labels from translated contribution labels; `lang` set on the document and on left-to-right islands.

## 8.21 Example: the PDF Files page

`pages/files.json`, registered with `ext.registerPage('pdf.files', filesPage)` (`05` §5.2). Preset pages use the same shape plus a `name` (their id is `preset.<name>`, `07` §7.3). All text is keys from the catalogs in §8.16.

```json
{
  "description": "Uploaded PDF files with their translation status.",
  "route": "/files", "title": "$t.files.title", "icon": "files",
  "state": { "filter": null },
  "queries": {
    "files": { "query": "pdf.files.list", "payload": { "status": "$state.filter" }, "refreshOn": ["pdf.*"] }
  },
  "view": { "type": "stack", "children": [
    { "type": "row", "children": [
      { "type": "heading", "text": { "$t": "files.count", "count": "$query.files.items.length" } },
      { "type": "select", "value": "$state.filter", "placeholder": "$t.filter.all",
        "options": [["ready", "$t.status.ready"], ["translated", "$t.status.translated"]],
        "onChange": { "set": { "$state.filter": "$value" } } }
    ]},
    { "type": "upload", "accept": ["application/pdf"], "label": "$t.upload.drop",
      "onUpload": { "command": "pdf.import", "payload": { "blobId": "$upload.blobId" },
                    "then": [{ "toast": { "$t": "toast.imported", "name": "$upload.name" } }] } },
    { "type": "table", "entity": "pdf.file", "data": "$query.files.items",
      "emptyState": { "title": "$t.empty.title", "body": "$t.empty.body" },
      "columns": [
        { "field": "name", "label": "$t.columns.name" },
        { "field": "status", "label": "$t.columns.status", "as": "badge" },
        { "field": "createdAt", "label": "$t.columns.added", "format": "relative" },
        { "label": "$t.columns.progress", "as": "liveText", "live": "pdf.progress.updated:{{ $item.id }}",
          "visibleIf": { "$item.status": "translating" } }
      ],
      "rowActions": "auto",
      "onRowClick": { "navigate": "/files/{{ $item.id }}" } }
  ]}
}
```

`"rowActions": "auto"` shows every enabled action for `pdf.file`, including actions contributed by other extensions. In Arabic the same page renders right-to-left with Arabic plurals, Arabic-Indic digits in the "added" column, and file names isolated with `<bdi>`.

The row click opens `pages/file-detail.json` (id `pdf.file-detail`), which reads the route parameter and shows the viewer widget next to the translation:

```json
{
  "description": "One PDF file with its original and its translation.",
  "route": "/files/:fileId", "title": "$t.files.detail", "icon": "file-text",
  "params": { "fileId": "string" },
  "queries": { "file": { "query": "pdf.file.get", "payload": { "fileId": "$route.fileId" }, "refreshOn": ["pdf.translated"] } },
  "view": { "type": "page", "title": "$query.file.name",
    "entity": "pdf.file", "record": "$query.file",
    "actions": [ { "type": "button", "label": "$t.actions.back", "icon": "arrow-left", "variant": "ghost",
                   "onClick": { "navigate": "/files" } } ],
    "children": [ { "type": "split", "children": [
      { "type": "pdf.viewer", "blobId": "$query.file.blobId" },
      { "type": "section", "title": "$t.files.translation", "children": [
        { "type": "emptyState", "title": "$t.files.notTranslated", "visibleIf": { "$query.file.translatedBlobId": { "exists": false } } },
        { "type": "fileLink", "blobId": "$query.file.translatedBlobId", "name": "$query.file.name",
          "visibleIf": { "$query.file.translatedBlobId": { "exists": true } } } ] } ] } ] }
}
```

`entity` and `record` make the header show every `pdf.file` action with placement `detail` (Translate, and actions other extensions add to `pdf.file`), with `$item` = the file, so Translate is not written again in the page; `actions` holds only buttons that are not entity actions. `params` in a page definition is written in JSON as a map from parameter name to a JSON Schema type name (`string`, `number`, `boolean`); in TypeScript it may be a Zod object. The `pdf.file.get` query it reads is registered in `05` §5.2.

## 8.22 Edge cases

Behavior the shell and kernel implement for cases the sections above do not spell out:

| Case | Behavior |
|---|---|
| The registry changes while a page is open (preset edit, reload) | The shell refetches `/ui`; if the open page still exists it re-renders in place and keeps `$state`; if its route is gone it shows "This page is no longer available" with a link home. Open dialogs from a removed page close. |
| The registry changes while a form is half filled | The form keeps its values if its command still exists; otherwise it shows "This action is no longer available" and disables submit. |
| A page's declared query fails | The nodes bound to it show an inline error box with Retry; the rest of the page renders. |
| A `refreshOn` event arrives while the query is already refetching | One more refetch runs after the current one; events are coalesced, never queued. |
| A binding in a query payload resolves to `undefined` or `null` | The key is omitted from the payload, so optional input fields fall back to their defaults. |
| A command action's payload fails validation in the kernel | The form shows the issues on its fields; without a form, an error toast lists them. |
| Two panels in `frame.overlay` are visible at once | The first by `order`, then id, is shown with a "1 of 2" stepper; answering it shows the next. |
| A slot's props change (e.g. the chat page opens another session) | Contributions re-resolve `$slot.*`, and their queries refetch with the new payload. |
| An extension is quarantined while its page is open | The registry refresh removes its contributions; the open page shows "This extension was stopped" with a link to the recovery page. |
| A widget iframe fails to load or throws | The widget's box shows an inline error; the rest of the page works. |
| The event stream disconnects | The connection zone shows "reconnecting"; queries stay visible (stale); commands still work over HTTP; on reconnect missed events replay (§8.14). |
| The kernel restarts | Same as a disconnect; `hello` lists no subscriptions, so the shell re-subscribes all with their cursors. |
| The kernel version changes (upgrade) | `hello` reports a different `protocolVersion`: the shell reloads itself once; if still incompatible, it shows the recovery page. |
| The language changes mid-action | Open dialogs and forms re-render in the new language; values are kept; in-flight commands are unaffected. |
| A catalog key is missing in every catalog | The key itself is shown as `⟨ns:key⟩` and a warning is logged to the browser console once per key. |
| A preset hides every nav item | The sidebar is empty and hidden; the kvman menu and palette still reach every page. |
| A preset's `app.home` points to a page of an extension that is later quarantined | `/` opens the first page of the sidebar; if there is none, the recovery page. |
| A notification arrives for a workspace no tab shows | It is stored; the 🔔 badge in other workspaces shows the unread count of the current workspace plus global entries only. |
| A toast's `key` matches a toast already shown | The existing toast is updated in place and its timer restarts. |
| The same prompt is answered in two tabs | The first commits; the second gets `REPLY_NOT_AWAITING` and its tab shows "already answered" (§8.13). |
| A person opens a hidden page from a link | It opens normally with a "Hidden by this app's preset" note in the page header. |
