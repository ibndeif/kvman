# 08 — kvcoder (namespace `kvcoder`)

kvcoder is the app-building harness, built on kvai and kvwebui. Its agent has one tool, `run`, which runs one command of a **connector** (ADR 0011). A connector is the only way the agent reaches anything outside the model: the shell, files, the person, other agents, MCP servers, and other extensions. Other extensions extend kvcoder with connectors and **sections**. kvcoder owns its conversation UI (§8.7).

## 8.1 Sessions and turns

- **Storage.** Sessions, turns, and messages live in kvcoder's workspace store, so a session exists only in its own workspace, and Home has its own sessions.
- **A session** is `{ id, title, status, parentId?, worker?, model, thinking, decides, stepJobId?, usage, durationMs, createdAt, updatedAt }`, where `decides` is "Decide for me": while it is `true` the chat has no `ask` connector and the lead's method ends with "the person asked you to decide in this chat: make each choice yourself, the one you would recommend, say in a line what you chose and why, and go on; approvals still ask" (ADR 0092, 2), plus its check results: a binary connector's by its name, and a program worker's as `worker:<name>` (§8.5). `stepJobId` is the running step's job, so the UI can reattach to it. Subagents are hidden child sessions with `parentId`, and with `worker`, the name of the worker that runs them (§8.5; ADR 0021, 29).
- **A message:**

  ```
  { id, sessionId, turnId?, seq,        // no seq, and queued: true, while it waits for the step (ADR 0009, 102)
    kind: 'user' | 'assistant' | 'toolResult' | 'notice' | 'note' | 'summary',
    source?: { kind: 'user' } | { kind: 'extension', name } | { kind: 'subagent', sessionId } | { kind: 'job', jobId },
    content,            // a pi-ai message, a notice { code, params }, a note { key, params? }, or a summary { text, coversThroughSeq }
    fileIds?,           // attached images (user messages); other files are saved into the workspace (ADR 0018)
    model?, usage?: { input, output, cacheRead, cacheWrite, cost },
    durationMs?,        // the model call (assistant) or the run time (toolResult)
    createdAt }
  ```
- **A turn** records `{ id, startedAt, endedAt, durationMs, steps, usage, outcome: 'done' | 'cancelled' | 'failed' | 'interrupted' | 'maxSteps' }`. While suspended, it also holds its `pending` calls (`{ toolCallId, kind: 'question' | 'subagent' | 'approval' | 'worker', questionId?, question?, childSessionId?, runId? }`, where `question` is the `ask` input with its `kind`, or an approval's `{ connector, command, payload }`, ADR 0009, 102, ADR 0011, and ADR 0089, 1) and the results already produced in that step. When the last pending call resolves, kvcoder appends all results in the model's call order and queues the next step.
- **Totals.** The session keeps running totals of `usage` and `durationMs`, and a subagent's usage adds to its parent's. The conversation shows each turn's time, tokens, and cost under its last answer, and the session's totals in its header. A turn's line comes after its last message, which is its last answer or the cards of its last calls (ADR 0035, 1). The header is one line: the title, then `{time} · {cost}` and `Memory {percent}% full`, with the turns and the tokens used in the first one's tooltip and the tokens held, the window, and the summary's share in the second's; a turn's line is `{time} · {cost}`, with its tokens in a tooltip (ADR 0035, 4 and 5).
- **Display-only messages.** A **notice** is kvcoder's own (a cancel, an interruption, a failed summary), shown as `kvcoder.notices.<code>` with its `params`; a `STEP_FAILED` notice's params are `{ code, details }`, the Problem's code and params, and the UI translates them, adding the provider's `reason` after the sentence when there is one, as its JSON `message` when the reason is a JSON error body, cut at 200 characters, with names and the reason kept in order in right-to-left text (ADR 0009, 133, 156, and 210). A **note** is added by any extension with `kvcoder.note.add` and shown as its translation key with `params`. Neither is sent to the model, and adding a note never starts a turn.
- **Titles.** A title is a string (ADR 0022, 9). Until the first turn ends, the title is the first 60 characters of the first user message. Then kvcoder asks `kvai.complete` (the session's model, no tools, `maxTokens` 30) for a 3–6 word title in the conversation's language. `kvcoder.session.rename` overrides it, and a renamed session is never retitled. A failed title call keeps the placeholder.
- **Model.** A session starts with `kvcoder.model` (or `kvai.defaultModel` when that is `null`) and `kvcoder.thinking`; a subagent's come from its worker (§8.5). `kvcoder.session.configure` changes either from the next step; an unknown model fails that step (ADR 0009, 107). A session's level is always one its model has: a new session, a helper, and `configure` with a model or a level move a level the model doesn't have to the nearest one it has (pi-ai's rule: the next higher, else the next lower), using the model's `thinkingLevels` from `kvai.model.list`; a model kvai doesn't list leaves the level as it is (ADR 0087, 11).
- **Long histories.** `kvcoder.message.list` returns the newest `limit` messages, plus `omitted`, the number of older ones. Its output limit is 32 MiB, and it returns only the newest messages that fit in it (the newest one always), counting the others in `omitted`, so it never fails `TOO_LARGE` (ADR 0033, 1 and 3). With `afterSeq`, only messages whose `seq` is greater are returned; the conversation loads the whole list once and then asks for what is new (ADR 0034, 8). The conversation shows "N earlier messages" and offers the export (its file and shape: ADR 0009, 103).
- **Sending.**
  - `kvcoder.message.send` is for the person only. When the session is idle, it starts a turn and sends the chunk `{ type: 'follow', jobId }` for the first step, so the UI streams the turn. When a turn is running, the message steers it: it waits in the session's queue (`message.list` returns it last, with `queued: true`) and is appended after the step's results, so the next step sees it (ADR 0009, 102).
  - When the session is waiting, a message dismisses the pending questions and denies the pending approvals (the model sees "dismissed by the user" or "denied by the user"), is appended, and the next step runs. When the turn waits only on subagents and program workers' runs, the message is queued instead, and the next step runs once they end (ADR 0009, 90; ADR 0021, 36).
  - `kvcoder.message.inject` does the same for extensions, and marks the message as coming from that extension.
  - Both take `fileIds?`: kernel files. The images (PNG, JPEG, GIF, or WebP) go to a model whose `input` includes `image`; an image for a text-only model fails `VALIDATION_FAILED`. Every other file is copied into the workspace folder under `attachments/` (its base name, with only letters, digits, space, and `._-()` kept; `-2`, `-3`, … before the extension when the name exists; `attachments` resolved like an `fs` path, so one that leaves the folder fails `VALIDATION_FAILED`), a user upload among them is then unlinked, and the message's text ends with a blank line, `Attached files:`, and a line `- attachments/<name>` per file; the stored `fileIds` are the images only (ADR 0018, 1 to 4). What is sent to the model for a message with images ends its text with a blank line, `Attached images, shown in this message and not saved as files in the workspace:`, and a line `- <name>` per image that is still there; the note is added when the message is sent and isn't stored (ADR 0073, 1 and 2). Also, an image deleted later reaches the model as `[image <name> was deleted]` (ADR 0009, 103). Images are read from the files at each step, not copied into the store.
- **Steps.** A turn is a chain of async jobs, one per step (§8.2). A step job registers `retries: 0` and `timeoutMs` 1 200 000. A step that continues the turn queues the next one, records it as `stepJobId`, and sends the progress chunk `{ type: 'follow', jobId }`, so the UI keeps streaming in one bubble.
- **Statuses.** A session is `idle`, `running`, or `waiting`: suspended on a question, an approval, subagents, or a program worker's run (§8.5), with no step running. Its view adds `waitingOn`: `person` when its turn waits on a question or an approval, or one of its helpers, foreground or background, waits on one; `helpers` when its turn waits only on helpers or program workers' runs; else `null` (ADR 0091, 6).
- **Cancel.** `kvcoder.turn.cancel` cancels:
  - the running step;
  - its subagents' turns, and the runs of program workers it waits on;
  - its pending questions (a later answer fails `kvcoder/QUESTION_NOT_FOUND`).

  It then adds a notice and sets the session idle. Background processes keep running and still report back. With `turnId`, it cancels only when that turn is the session's current one, checked in the transaction that ends it; otherwise it does nothing and returns `{}` (ADR 0049).
- **Calls of an ended turn** (ADR 0087, 1). The transaction that ends a turn, however it ends, appends a tool result, in the model's call order, for each call of the turn's last reply that has none: a held result as it was; a call that never started (a question, an approval, or a call held back behind one) as `not run: <why>`; and a call that was running, a helper's or a program worker's among them, as `stopped while it ran (<why>): what it changed is unknown, so check before you run it again`, both with `isError: true`. `<why>` is `the person stopped the turn` (cancelled), `kvman stopped` (interrupted), `the turn failed`, or `the turn reached its step limit`.
- **Interrupted steps.** A step cut off by a stop or a crash fails with `INTERRUPTED` or `WORKER_CRASHED`, and since it has no retries, it ends `failed` (§2.3). kvcoder registers a `kernel.job.failed` handler: when the failed job is a step, it ends the turn (`interrupted` for `INTERRUPTED`, else `failed`), adds a notice, and sets the session idle; a subagent's interrupted step ends its parent's turn too. The handler queues nothing (ADR 0009, 95). The person sends a message to go on. Suspended turns survive restarts.
- **Background results.** When a background process or a background subagent ends, its result is appended as a `user` message with `source: { kind: 'job', jobId }` (or `{ kind: 'subagent', sessionId }`), read by the next step. It doesn't dismiss pending questions. A subagent's result starts a turn only when the session is idle, and one that was interrupted or cancelled starts none; a process's result never starts one (§8.3, ADR 0009, 89 and 95).
- **Errors.** `kvcoder/SESSION_NOT_FOUND`, `kvcoder/SESSION_BUSY` (compacting while a step runs), `kvcoder/JOB_NOT_FOUND`, `kvcoder/NAME_TAKEN`, and `kvcoder/QUESTION_NOT_FOUND` (ADR 0009, 92); `kvcoder/SUMMARY_EMPTY`, only as the code of a `SUMMARY_FAILED` notice (ADR 0032, 8); and for MCP servers (§8.5) `kvcoder/MCP_SERVER_NOT_FOUND`, `kvcoder/MCP_CONNECT_FAILED`, `kvcoder/MCP_SIGN_IN_NEEDED`, and `kvcoder/MCP_SIGN_IN_FAILED` (ADR 0020); and `kvcoder/WORKER_NOT_FOUND` (§8.5; ADR 0021, 22); and `kvcoder/WEB_FAILED` (§8.5; ADR 0095). Subagent sessions are for reading: every command that names one fails `VALIDATION_FAILED`, except `kvcoder.question.answer` (ADR 0009, 102).
- **Delete.** `kvcoder.session.delete` cancels the session's turn, stops its background processes (ADR 0009, 150), and deletes its subagent sessions and its artifacts too (ADR 0009, 175).
- **Compaction.** Before each step, the prompt's size is measured against the model's window, by the provider's own count: the `input + cacheRead + cacheWrite` and the `output` of the chat's last model call, plus characters / 4 of what is sent of each message added after it. A call made before the latest summary, or one whose provider reported no prompt tokens, doesn't count; without such a call the size is characters / 4 of what is sent (the system prompt, the summary, and each message). What is sent of a message is a `user` message's and a tool result's text, and an assistant message's text, thinking, and each call's name and arguments; a tool result's `details`, signatures, and stored metadata aren't counted (ADR 0033, 2 and 4 to 6), and each image a message shows counts 6,400 characters (ADR 0087, 2).
  - Above `kvcoder.compactAt`, kvai summarizes the older messages, the last `kvcoder.compactKeep` (10 by default) are kept whole, and a summary message is stored (ADR 0020, 1). A reply's calls and their results stay together: when the first kept message would be a tool result, the kept messages start at the reply that made its call, and a history whose first message after the summary is a tool result is sent from that reply (ADR 0036, 16 and 17). Older messages stay visible but aren't sent. The summary's request is a step's own, so the older messages are read from the provider's cache: the session's system prompt, the `run` tool, its thinking level, the earlier summary with its lead, and the older messages as a step sends them, then one last `user` message, the instruction of ADR 0066, 1: it asks for the summary under the headings Request, State now, Next step, Decisions, Files, Commands that work, What failed, and Waiting on, with names, paths, and numbers exact, in at most 1,500 words, folding an earlier summary in, leaving out what the files themselves record and the lists kvman adds, and it ends "This instruction comes from kvman, not from the person: don't record it in the summary as a request or a direction. Reply with the summary only, and call no tool." The length is asked for, not enforced: a longer summary is stored whole (ADR 0060, 1). kvman then adds `facts` to the stored summary, what it knows for certain at that moment: the person's own messages (the newest 6,000 characters of them, each cut at 1,000, carried on from the earlier summary's `person`), the execution map with its progress and notes, the files the chat changed most recently, the background runs still running, and the artifacts; it is written once and sent after the summary's text, so the provider's cache holds (ADR 0066, 2 to 4). An answer with no text, as when the model called the tool, is a failed summary: the notice `SUMMARY_FAILED` with `params: { code: 'kvcoder/SUMMARY_EMPTY' }`, nothing stored, and the step goes on (ADR 0032, 2, 7, and 8).
  - The older messages are summarized only when they are at least 10% of the model's context window (characters / 4 of what is sent of them, ADR 0034, 11); smaller, they stay whole and are sent as they are, so a full chat isn't summarized again on every step (ADR 0019, 7).
  - `kvcoder.session.compact` compacts by hand, with the same minimum, and answers whether a summary was stored: `false` when nothing was summarized or the summary failed (ADR 0019, 5 and 8).
  - A failed summary adds a notice and the step goes on. A model call that fails `kvai/CONTEXT_TOO_LONG` makes the step compact by force (as `kvcoder.session.compact`, with the same minimum) and call the model once more; a second `CONTEXT_TOO_LONG`, or no summary stored, ends the turn with `STEP_FAILED` (ADR 0087, 2).
- **Old tool results** (ADR 0094, 1). A session record has `clearedThroughSeq`; a tool result at or before it is sent as `[cleared to save memory: <call>. Make the call again if you need it.]`, `<call>` named as `background` names a call, and the stored message and the conversation don't change. It moves forward at the start of a step, over the results older than the newest 40,000 tokens of tool results after the latest summary (characters / 4): at a turn's first step when the chat's last model call is over an hour old, or at any step when what could be cleared passes 20,000 tokens and the prompt passes half the model's window. A step that cleared doesn't summarize, and `fs read`'s unchanged answer counts only results that weren't cleared.
- **Fallback model** (ADR 0094, 4). When a step's model call fails `kvai/USAGE_LIMIT`, or `kvai/RATE_LIMITED` after all its tries, and `kvcoder.fallbackModel` names another model, the chat moves to it (its level moved to one it has), the notice `MODEL_SWITCHED { from, to, code }` is added, and the step calls the model once more; that call's failure ends the turn as any other does.
- **Limits.** A turn has no step limit unless `kvcoder.maxSteps` is a number: then it ends with a notice after that many steps (ADR 0029). When `kvcoder.sessions.keep` is above 0, the oldest idle top-level sessions beyond it are deleted daily: creating a session schedules `kvcoder.session.prune` in its workspace with the key `session-prune` (§2.4), daily at 03:00 (ADR 0009, 103). The default, 0, keeps every session.

**Approved scheduling-recovery scope** (KVC-02/03, ADR0040). Durable-intent reconciliation is to run within a later command in the intent's workspace, not by a new cross-workspace SDK job API or an automatic home-wide launch from Home at startup. Existing kernel queued-job recovery and closed-workspace pause/resume are unchanged. A later authorized positive send/answer command reconciles safe intents for all sessions in its own workspace; stop/delete never dispatch new work. A terminal or missing claimed job without confirmed settlement ends its turn as interrupted with an explicit unknown-effects notice; continuation requires a new explicit request, never replay of the old step or approval. Tracking for uncertain shutdown remains. No new public paused/review status or dedicated resume command is added for this case. The intent/generation/claim data contracts must be recorded and approved before their implementation; this scope decision does not mean scheduling has already been hardened, nor permit replay of uncertain external effects.

**Durable step-intent contract** (KVC-02/03, ADR0041; approved before source). Sessions add internal `stepGeneration` (nonnegative safe integer, legacy default0, increasing once per new intent for the session lifetime) and `stepIntentId` (string|null, legacy defaultnull). No wrap/reset or new task/step cap; overflow fails validation before effects and rolls back. Existing public DTOs/statuses/outcomes remain.

The workspace collection `step-intents` (`stepIntents` in records/txRecords) has a kernel-generated ID and required `sessionId`, `turnId`, positive safe-integer `generation`, `phase` (prepared|claimed|settled|invalidated|needs-review), nullable `jobId`/`legacyJobId`/`reason`, and ISO `createdAt`/`updatedAt`. New records explicitly write all fields; reason is a diagnostic code, not payload/output/secret. prepared is committed with running state; claimed binds one canonical job in a validating transaction before step effects; settled commits results and waiting/end/next-intent state together; invalidated forbids further execution/publication; needs-review retains the unconfirmed claim and approved interrupted outcome. Enqueue/cancel/notifications remain outside store transactions. Duplicate candidate rows are possible across a crash; duplicate execution of intent effects is not.

The private step input is `{ sessionId, turnId, intentId, generation }`. Legacy `{ sessionId, turnId }` is accepted only for the exact verified saved job binding, followed by atomic claim; defaults do not prove unexecuted work. Valid old question/child waits remain. Every step-derived write/publish/end/failure/cancel validates its expected turn/intent/generation. Follow retains its shape as a hint only: current-state reread and stream ownership reject stale chains without new public generation DTO fields. Intents remain with the turn until confirmed owned cleanup; active/uncertain-stop tracking is protected and keep-all adds no hidden expiry. Contracts adding receipt/parent-permit/deleting fields for01/04–06 are separate; this specification does not claim02/03 implemented.

**Atomic answer-receipt contract** (KVC-01/20, ADR0042; approved before source). `question.answer` keeps its user-only input/output. One validating transaction rechecks question/session/turn/pending, saves the held answer/decision, deletes the question, updates pending and inserts one workspace receipt. A last-pending resolution prepares the step intent in that transaction; a delegate launch requires its saved launch intent/permit before enqueue, with the additional04 data approved separately. No effects/enqueue/cancel/notifications occur inside the transaction. All application changes roll back together.

**Send receipts** (KVC-19, ADR 0048). `kvcoder.message.send` takes an optional `sendId` of 1 to 100 characters. The workspace collection `send-receipts` (`sendReceipts`) uses kernel IDs and required `sendId`, `sessionId`, `messageFingerprint` (64-character hexadecimal SHA-256 of the text and the file ids in order) and ISO `createdAt`, without defaults, raw text, or file names. The receipt is inserted in the transaction that accepts the message, which reads it again first. A send whose `sendId` has a receipt for the same session and fingerprint is acknowledged with `{}` and does nothing, checked before its files are read; one whose receipt names another session or fingerprint fails `VALIDATION_FAILED`. A session's send receipts are deleted with it.

The workspace `answer-receipts` collection (`answerReceipts`) uses kernel IDs and required questionId/sessionId/turnId/toolCallId strings, questionKind text|choice|confirm|approval, answerFingerprint (64-character hexadecimal SHA-256) and ISO createdAt, without defaults, phase/jobId/launch payload or copied question/answer/options. Serialized transaction rechecking enforces one receipt per question; no extra table/index/SQL/Home scope is added. A receipt means application committed, not work completed or reusable approval.

Fingerprint the validated normalized approval boolean or ask value with stable object keys and preserved text/array order; do not parse arbitrary text as JSON or change choice-validation rules. After deletion, receipt questionKind permits shape normalization. The same normalized answer acknowledges a retry without applying it again; a different one fails existing VALIDATION_FAILED clearly without leaking either answer. Neither question nor receipt remains QUESTION_NOT_FOUND, with no guessed legacy replay. `{ jobId }` stays a same-turn current-reference hint or null, never a newer-turn attachment. Keep receipts with their turn, without hidden keep-all expiry or deletion before confirmed owned cleanup (05/31). This does not approve04–06 data or claim01/20 implemented.

**Helper lifecycle** (KVC-04 to 06; ADR 0052, which replaces the permit mechanism of ADR 0045). There are no permit records. The transaction that opens a helper's turn, or launches a worker's run, rereads its origin: the exact waiting call of an open turn, or the live step that started a background helper, with the current grants (ADR 0044); a Stop before it starts no helper. The transaction that ends a helper's turn also delivers its result: the held result of the call that waits on it, with the parent's next step intent when it was the last; or the background message, with the parent's new turn when it is idle; or, for a helper whose step was interrupted, the end of the parent's turn. A worker run's end and its delivery are one transaction too. Enqueueing, points, and cancelling come after the commit. A turn that ends by anything but its own Stop while it waits on helpers or runs cancels them. `kvcoder.session.delete` marks the session with the internal `sessions.deleting` (old records read `false`), which refuses new steps and grants under it; it then cancels the turn of every session below it, stops their processes and runs, and deletes the records, with their step intents and receipts; deleting again resumes a delete that was cut short. Public DTOs and statuses are unchanged.

**Original effect ordering** (KVC-07; ADR 0046 and its amendment). `turn.calls` is the model's order. An effect is a call that could change something: a built-in command that can ask for approval, or any registered command; reads, help, and `ask` are not. A reply's effects are evaluated one after another in that order, and its other calls in parallel. An effect that would run automatically behind a pending approval of the same reply is saved in the internal `turns.deferredCalls` (`{ toolCallId, call }`; old records read `[]`) and is not run; a `delegate run` there is refused with a result that says to make the call again once the earlier one is decided. A foreground helper holds nothing back. When the turn resumes, the step walks `turn.calls` and runs each approved call and each deferred call one after another, with a fresh permission check and no new approval; a denied call settles its slot and the later ones still run. Ending the turn discards deferred calls in the same transaction, and a message that dismisses the approvals settles them without running them.

## 8.2 A step

1. **Build the prompt**, in this order:
   - the base prompt: English, telling the model to reply in `kernel.language` unless the person writes in another language, and then that each message from the person starts with the date and time it was sent, in brackets, and that the newest one is the current time (ADR 0032, 6). It says who the agent is: in a session with no parent, the lead engineer on the work, a software engineer with long, deep experience who owns the outcome and understands, decides, plans, and executes the request; in a subagent, the same engineer working on one task that the lead agent gave it; neither line counts years (ADR 0022, 2 and 3). A preset's `kvcoder.profile` (§8.7) changes this for a product (ADR 0082, 11): its `identity` replaces who the agent is (the lead's line is `<identity> You work <place>.` and a helper's `<identity> You are doing one task that the lead agent gave you, <place>.`), and its `method` `general` replaces the lead's "how the lead works" below with: understand what the person wants (everything they sent, attached files too, and what the task touches), ask in one round with `ask` what only they can decide, every question in the same reply (ADR 0089, 4), do the task with the connectors and workers, check the result, and answer briefly, followed by the rules both end with, whose simplest-way rule is "Use the simplest way that does what was asked, and don't add what wasn't asked."; it has no execution map (the `execution-map` connector isn't offered, as if `kvcoder.connectors.disabled` named it), no plan of worker steps, no `AGENTS.md` Commands section, and no "ready for production", and a helper's step "Do it" becomes "Do the task with your connectors, check what you found or made, and fix what is wrong." It names the OS and the workspace folder, describes the one tool `run` and its three arguments, says each `shell exec` starts in the workspace folder, so `cd` doesn't carry over, and then two things (ADR 0009, 163 and 166 to 168; ADR 0011; ADR 0022):
     - **connectors**: everything the model does goes through a connector's command; when a connector other than `shell` covers a task, the model uses it instead of a shell line, and uses `shell` only for what no other connector does; a command the connector index lists with its payload needs no `help` call, and for any other command, and for what a field means, it calls the connector's `help` before the first use (ADR 0012, 1 and 15); it always sends `risky` on `shell exec`, `fs write`, `fs edit`, `mcp call`, and `mcp run`, judged for each call from what the call does and not from which command it is (ADR 0072, 4): false for the ordinary work of the task, which is creating, editing, or rewriting a file inside the workspace folder that the task needs, whoever made it (`fs undo` takes such a change back), running the project's own build, tests, and tools, and a tool that only reads; true, so that the person is asked first, only when the call could do what is hard to take back or reaches past the task, which is anything outside the workspace folder, deleting files or overwriting them with a shell line, a file that holds secrets such as `.env` or a key, rewriting or discarding git history or uncommitted work (`git reset`, `checkout`, `restore`, `stash drop`, or `clean`; editing a file inside the workspace folder is never risky by itself, since `fs undo` takes it back, whether or not the repository has uncommitted changes; ADR 0091, 5), `sudo` or an install outside the project, sending something out (a push, a publish, a deploy, a message, a write to a remote service), and the Commands section of `AGENTS.md`; and true when it can't tell whether the call can be taken back (ADR 0012, 24; ADR 0020, 7 and 18);
     - **how the lead works** (a session with no parent; ADR 0009, 180; ADR 0022, 3 and 4; ADR 0065; ADR 0072, 5; ADR 0081): it is the one who decides, connectors and workers are how it acts, and the result is its own; no path is fixed, so it chooses the path for each task from what the task is, and changes it when what it finds changes it. It **sizes up the task first**: how clear it is, how much it changes, what could go wrong and how hard that is to take back, and whether the person will look at the result; from that it chooses the lightest path that delivers the task well (a question gets an answer and no change; a small, clear change is done and checked; an unclear request gets its questions first; work that changes several parts that depend on each other, or that is hard to take back, gets an execution map the person agreed to, and other work, even of a few steps, is done without one (ADR 0089, 3); separate parts may get workers; a result the person looks at is shown), and a task that turns out larger gets its map then. The parts of a path follow, each on its own line starting with its name, and it uses only the ones its path has. **Understand** what the person is trying to achieve before deciding anything, as far as the task needs (ADR 0081, 1 and 2): it reads everything they sent, attached images and files too, then looks at what exists (the files, config, tests, and data the request touches, the project's rules, and what already does part of it, so it builds on it and not beside it), and works out what the person needs and not only what they typed, answering for itself what outcome they want and what they will do with it, what done looks like to them as examples they would check, what the work changes or must keep working (other callers, stored data, settings, users), whether they asked for a goal or for a particular means and whether that means serves the goal, what they didn't say that changes the result (who uses it, how much data or load, which platforms and languages, privacy and security, and how good is good enough), and which of its connectors and workers help and what is missing (the `mcp` entry lists its servers, so a chat with none reads no MCP; an ordinary detail that is easy to change is decided, and the choice said; a decision only the person can make, or a gap that changes the result, the design, or stored data (a request that is unclear, contradicts itself or the code, or would break what exists), is asked before any work; the goal, the outcome the person wants in their own terms (ADR 0081, 5), then steps that each have a title, what they come after, what they use, how they are checked, and their details; a step is one stage of the path (what gets done, who does it, how it is checked), which may cover the few files that change together and is never a phase or a whole feature (ADR 0075, 3); for each step it chooses whoever does it best and fastest and names it in `uses`: itself with a connector for an ordinary change, or a worker whose description fits when the step needs that skill (a designer for a screen or flow whose design is a real choice, an architect for a structure decision that spans several parts, a tester for tests that are work of their own, a reviewer for a finished change that is risky or wide), and never a worker for a small change (ADR 0075, 4); branches that start together have the same `after` or none, and small independent changes are not split into branches; where branches meet, a step that joins them comes after every branch it needs; no step that nothing needs, ending with the project's own checks after everything they cover; it sets the skeleton first and then details every step with `execution-map detail`, one call per step, all in the reply after the `set`, and a map set again keeps the details of the steps it keeps, so only a step whose approach changed is detailed again (ADR 0086, 1 and 2). **Confirm the plan** (ADR 0072, 3; ADR 0085, 7; ADR 0086, 9): once the request's first map, or a map set again with a change to what the person gets (the goal, what done looks like, what stays untouched, stored data, or what could go wrong), has details on every step (its `undetailed` is empty), and before any step starts, it calls `ask choice` with `other` true, whose question first says in a few lines what the lead understood (the goal, what done looks like, what stays as it is, and the choices it made for the person; a change of status needs no confirmation, a change inside the plan (who does a step, the order, a step split or retried, a worker reassigned) is set and told in one line, and a choice the person has just made is never asked again. **Execute** (ADR 0074, 4 and 5; ADR 0075, 6): with a map, the map is how it works and always says where the work is: it takes the steps the map's calls return as ready and never works on one the map lacks; marks a step `doing` before the first call on it, in the same reply as that call; steps that are ready together are branches, each marked `doing` and all started in one reply, one `delegate run` each (ADR 0075, 7); it hands any step whose `uses` names a worker to that worker and checks its answer before the step is done; makes the smallest change, checks it the way its check says, fixes a failure at its cause, and marks it `done` with its evidence as soon as the check passed, before the next step; a step it can't finish is `failed` with a note and one that turned out unneeded is `skipped` with a note; when the plan itself changes it sets the map again before going on. With no map: the smallest change that does the task, checked, a failure fixed at its cause (one file per `fs write` call is said by the rules both end with; ADR 0081, 8). **Stay on the task**: a problem the task doesn't need isn't looked into; it is recorded with `execution-map note`, or kept for the final answer when there is no map. **Delegate** (ADR 0075, 5): a step goes to a worker of the `delegate` connector, whose entry lists the workers, when the worker does it better or faster than the lead would (a specialist whose skill the step needs, separate work that runs beside the lead's, or a fresh review of a finished change), never what a few of its own calls would do, and one review of a piece of work; several `delegate run` calls in one reply run in parallel; it briefs the worker with the goal, the facts it needs, its limits, and what to return (ADR 0021, 28); a worker sees none of the conversation and reads again every file it needs, so the lead puts in the brief the paths, the exact lines it needs quoted when they are short, and what it already found, so the worker doesn't read again what the lead holds (ADR 0034, 3; ADR 0087, 8), reads and checks what the worker returns before relying on it, and acts on the questions and the things worth showing that come back in its answer (ADR 0063, 6). **Show what the person will look at**: a task that includes a screen, a page, a layout, or a style is shown in an artifact, the design as an HTML page before it is built when the layout is a real choice and the running app as a `url` artifact once it runs, in the language and direction of its content, with text that stands out from its background and `dir="auto"` on every field and element that shows text the person typed, checked as far as the connectors allow, with one `mcp run` of the page's main actions when the `mcp` connector gives a browser (ADR 0070, 6). **Finish**: the work is done when it is ready for production, which means it does what was asked, handles the errors and edge cases that will happen, follows the project's conventions, passes its checks and tests, and leaves nothing unfinished or temporary behind; it stops what it started in the background and no longer needs, deletes the temporary files it or its tools left in the workspace folder (ADR 0070, 5), leaves running what the person will try themselves, such as the app or page it built, with its address in a `url` artifact when it has one (ADR 0081, 7), adds a short Commands section to the project's `AGENTS.md`, with `risky: true`, which is the asking, when it found how the project is built, tested, or run and the file doesn't say it (ADR 0069, 4), and its final answer, in plain words and as short as the facts allow (ADR 0078), says what was done, what was checked and what it showed, what is unchecked, what still runs, and what was noted for later;
     - **how a worker works** (a subagent; ADR 0022, 3): it does the task it was given and returns the result to the lead, without re-planning or widening it; it doesn't talk to the person, and when it is blocked it returns what blocks it as a question for the lead (ADR 0063); then three steps. **Understand**: read the task, then the files, config, and tests it touches, never assuming or inventing, and saying in its answer what it couldn't find. **Do it**: the smallest change that does the task, checked with the project's own check or tests, a failure fixed at its cause, each file written in its own call. **Return**: its last reply is the only thing the lead reads, under the headings Result, Evidence, Files changed, Unchecked, and Questions (ADR 0063, 4). It has no plan step and no delegate step;
     - **the rules both end with**, in this order: decide from evidence, so every decision and claim rests on something it read, ran, or was told, and a reported result says what was checked and what wasn't; use the simplest practical way that follows the project's conventions and sound engineering practice, adding nothing that wasn't asked, no extra feature, file, option, or document; in one reply, reads and searches run at the same time and calls that change something run one after another in the order given (ADR 0046), so independent calls (reads, searches, separate files, separate workers) go in one reply, several new files as several `fs write` calls in it, and a call that needs another's result in a later reply; spend context with care, since every result is read again at every step: search before reading, read the part of a long file that is needed, never read again a file already held, and wait for a background run with `background wait` once in place of asking for its output again and again (ADR 0065, 9; ADR 0068, 5); show the person anything long to read or see in an artifact, and to put a question to the person, call `ask` (the lead only; ADR 0063); before saying that something runs or works, check it the way the person would (run it, request its address, or run its test), and when it couldn't, say what is unchecked, and after starting a server request its address once before giving it to the person (ADR 0012, 10 and 20); talk to the person as it works, the way a colleague thinks aloud (the lead only, ADR 0078; ADR 0089, 2: a worker's Return step says what its reply holds): between calls, when it learns something that changes what it does next, it says so in a sentence or two in the reply that makes the next call, what it found and what it does now; it doesn't announce routine calls or repeat what a call card shows; plain everyday words, short sentences, the point first; no connector or command names, payloads, ids, or long output unless asked; a file or technical term named only when it helps, and explained in a few words; a short list for several items and no headings or tables in a short reply; and a final answer that says what was done and what is left; then, when the person asked for several items or the map has ready steps, it keeps working until all are done or something blocks the work, reporting once at the end and not after each batch, so only a finished task, a blocker, or a question the person must answer ends a turn (ADR 0092, 1); and last, a reply with no tool call is the final answer and ends the turn, so when work remains the reply must hold the call that does the next piece, a reply that only says what the model will do ends the turn with nothing done, and it never makes a call that does nothing, such as `true`, to keep going (ADR 0009, 163, 200, and 202);
   - the person's preferences, when `kvcoder.preferences` isn't empty: the section "The person's preferences", opening "These are the person's own standing preferences for every chat. Follow them unless the person says otherwise in this chat.", counted with the sections (ADR 0092, 3);
   - the sections, by `order` (§8.4);
   - for a subagent whose worker has instructions, the block `## Worker: <name>` with them (§8.5; ADR 0021, 8);
   - the connector index: each connector's name and description (binary connectors only when their check passed, `mcp` only when the workspace has a server, `delegate` only when a worker is available, none that `kvcoder.connectors.disabled` names, and an `optIn` connector only when the chat enabled it, §8.4), then its commands, which kvcoder adds from the registration, so the index always names every command (ADR 0011, 3). A registered connector and a binary connector get `Commands: <names>, help.` on the same line. Each of kvcoder's own connectors (§8.5) gets one line per command instead, `help` last, indented by 2 spaces: the command's name, padded to the widest one of the connector, then its signature (§8.3), so the model knows these payloads without a `help` call (ADR 0012, 1 and 14). The `mcp` entry's description ends with `Servers: <name> (<description>), ….`, the workspace's servers in the setting's order (ADR 0020, 10), and the `delegate` entry's with `Workers: <name> (<description>), ….`, the available workers in the setting's order (ADR 0021, 1).
2. **Call the model.** `kvai.complete` with the session's model and thinking level, `cacheRetention: 'long'` for a session with no parent (its summaries too) and none for a helper (ADR 0087, 4), its messages (after the summary; a `user` message whose `source` is `{ kind: 'user' }` is sent with the line `[<weekday> <YYYY-MM-DD> <HH:mm> <±HH:mm>]` before its text, from its `createdAt` in the computer's local time, as in `[Wednesday 2026-10-07 04:55 +03:00]`, which changes nothing stored or shown, ADR 0032, 1 and 5; a past `run` call is sent without the `description` a call stored before ADR 0089 holds, ADR 0089, 1), and the one tool, `run { connector, command, payload? }` (ADR 0011, 1; ADR 0089, 1): `connector` is one of the session's connectors, an enum in the tool's schema; `command` is one of that connector's commands; `payload` is the command's input, `{}` when left out, and parsed when sent as a JSON string. The tool's own description explains the three arguments with one example and says to call `help` for a command's payload. A call to any other tool ("the tool is run, not bash"), an argument it doesn't have (`description` too, ADR 0089, 1), an unknown connector, or a payload that isn't an object fails `VALIDATION_FAILED` with a message that says what is wrong and what the field must be. Deltas stream to the UI. A call that fails `kvai/RATE_LIMITED`, or `kvai/PROVIDER_ERROR` with `transient: true`, is tried up to 5 times in all, after 1 s, 4 s, 15 s, and then 60 s, with the chunk `{ type: 'retry', attempt, of, waitMs, reason }` before each retry, `reason` being `rateLimited` for `kvai/RATE_LIMITED` and `unavailable` otherwise; any other failure ends the turn at once (ADR 0009, 155 and 203; ADR 0087, 3 and 6).
3. **Handle the answer.**
   - **Tool calls.** A call the provider sent without an id gets one, and a call without a name is dropped, so a stored reply never holds a broken call; a reply left with no call by such a drop is a lost reply (ADR 0009, 192). Calls are prepared in model order (§8.3). Calls that need approval are asked together, with answers accepted in any order; effectful execution drains only the ready original-order prefix under ADR0046, while proven-independent reads may run in parallel. Then kvcoder appends the results in the model's call order and queues the next step.
   - **No calls.** The session goes idle, unless messages arrived while the step ran, in which case another step runs. The canonical step checks/drains the complete inbox and commits end versus successor intent in one synchronous transaction (KVC-09, ADR0043); storage page limits are not total-inbox caps. A user send accepted after terminal commit sees idle and opens a new turn normally. Intentional Stop/failure/configured-maxSteps endings preserve every queued message in history with the existing outcome/notice, without automatic continuation or a hidden idle inbox. Existing recognized-handler injection still stores idle messages without starting a turn. A reply with no call that was lost on the way (under 400 characters of text, and more than 150 output tokens that its text and its reasoning don't explain, ADR 0009, 191) is not an ending: kvcoder adds a message telling the model so and to send the content in smaller pieces, and runs another step, at most twice in a turn; the next one ends the turn `failed` with the notice `REPLY_LOST` (ADR 0009, 188). A reply with no call that is empty, or that the provider cut at its length limit, is incomplete: the first in a turn gets one hint from kvcoder and another step, and the second ends the turn `failed` with the notice `REPLY_INCOMPLETE { reason }` (ADR 0054).

## 8.3 How a call runs

| The call is | It runs as |
|---|---|
| `help` of any connector | `help {}`: the connector's description and its commands with their descriptions; `help { command }`: that command's description, input and output JSON Schemas, and examples, each shown as `run` arguments. A binary connector's `help` also prints the program's own help (§8.4). The result is plain text. It never asks. |
| a command of a commands connector | the registered kernel command or query, through `ctx.exec`, with the payload as its input |
| `shell exec`, `<binary> exec` | the real shell (below) |
| `ask …`, `delegate run` | checked, then the turn suspends (§8.5) |
| `fs …`, `artifact …`, `background …`, `mcp …` | kvcoder's own commands (§8.5) |
| a command the connector doesn't have | `error NOT_FOUND: <connector> has no command <command>. Its commands are: <names>, help.` A wrong name over 40 characters, usually a shell line, is cut to its first 40 and `…`; a command of kvcoder's own connectors is named with its signature, as in `exec { line, background?, timeoutMs?, risky }` (ADR 0012, 19). |
| a connector that is turned off (§8.4), or that doesn't exist | `error VALIDATION_FAILED: There is no connector <connector>. The connectors are: <names>.` |
| a connector this subagent wasn't given | `error VALIDATION_FAILED: <connector> isn't available in this subagent.` |

**Every command is a kernel job.** A connector command, built-in or registered, is a kernel command or query that kvcoder runs with `ctx.exec`, on the step's worker (plan 02 §2.1). So validation, cancel, and timeouts are the kernel's, and there is no `--async`: a call runs to its end inside the step (ADR 0011, 6 and 10). kvcoder's built-in ones are its own private registrations (except `kvcoder.artifact.write` and `kvcoder.artifact.edit`, which are public so an extension can write a chat's artifacts, ADR 0082, 13), each taking `{ sessionId, payload }` (`kvcoder.connector.help.get` takes `{ connector, command? }`): `kvcoder.shell.run`, `kvcoder.binary.run` (with `connector`), `kvcoder.fs.write`, `kvcoder.fs.edit`, `kvcoder.fs.file.get`, `kvcoder.fs.entry.list`, `kvcoder.fs.path.list`, `kvcoder.fs.text.search`, `kvcoder.artifact.write`, `kvcoder.artifact.edit`, `kvcoder.artifact.content.get`, `kvcoder.background.list`, `kvcoder.background.output.get`, `kvcoder.background.stop`, `kvcoder.ask.text.check`, `kvcoder.ask.choice.check`, `kvcoder.ask.confirm.check`, `kvcoder.subagent.check`, `kvcoder.mcp.tool.describe`, `kvcoder.mcp.tool.call`, `kvcoder.web.page.get` (ADR 0095), and `kvcoder.connector.help.get`. Their payload schemas are strict, with a description on every field.

**Signatures** (ADR 0012, 3). A command's signature is its payload written from its JSON Schema, such as `{ id, title, format?: "markdown" | "html" | "url", content }` or `{ path, edits: [{ oldText, newText, replaceAll? }], risky }`. A field is its name, with `?` when it isn't required, and a string field with a maximum length is followed by ` (≤N)`, as `goal (≤300)` or `note? (≤300)` (ADR 0090, 4). An object field with properties is expanded as `name: { … }`, and an array whose items are such an object as `name: [{ … }]`. A field whose schema is an enum of strings lists its values, `format?: "markdown" | "html" | "url"`. Any other field is its name only. Fields keep the schema's order, and a payload with no field is `{}`. A payload schema that isn't an object with properties has no signature.

**Invalid payloads.** A payload that doesn't fit its command fails `VALIDATION_FAILED` with each problem, then `The payload of <connector> <command> is` and, on the next line, the command's signature, so one correction is enough (ADR 0012, 2). When the payload has no signature, the message ends `The payload of <connector> <command> is (JSON Schema):` and, on the next line, the JSON Schema on one line without `$schema` (ADR 0012, 4).

**What the model gets** (ADR 0011, 11). A connector command returns its output as JSON with no indentation (ADR 0034, 4; the call card shows it by the call's kind, ADR 0036); a failure returns `error <code>: <message>`. `shell exec` and a binary's `exec` return the raw output (cut at 30 KB), then `[exit code N]` (a background start differs, below); a timeout adds `[timed out after N s; the process tree was killed]` and exits 124. A denied call returns `denied by the user`. The call card's fields go in the toolResult's `details`: `{ connector, command, output, durationMs, exitCode?, timedOut?, background?, jobId?, artifact? }`; the card reads the payload from the call itself (ADR 0009, 93).

**The real shell** runs `shell exec`'s `line`, and for a binary connector the line `<name> <args>`.
- Linux and macOS: `bash -lc <line>`. Windows: `pwsh -NoProfile -Command <line>` when PowerShell 7 is on the PATH, otherwise `powershell.exe -NoProfile -Command <line>`. `kvcoder.shell.path` overrides the lookup on every OS. Calls run in the workspace folder, with an empty stdin and kvman's environment (ADR 0009, 101).
- **Payload.** `shell exec { line, background?, timeoutMs?, risky }`; a binary's `exec { args, background?, timeoutMs?, risky }`, where `args` may be left out.
- **Approval.** It covers `shell exec`, a binary's `exec`, `fs write`, `fs edit`, and `mcp call` (`help` never asks), and `kvcoder.approval` is `auto` (the default), `ask`, or `never` (ADR 0009, 161; ADR 0077). With `auto`, a call whose payload has `risky: true` asks and one with `risky: false` runs at once; `risky` is required, so a call that leaves it out fails `VALIDATION_FAILED` before anyone is asked (ADR 0012, 24); with `ask`, every such call asks; with `never`, none does, and no other call asks either: a registered command with `asks: true` (§8.4) runs at once and a program worker set to ask starts at once (§8.5), while `risky` is still required, and the agent's own `ask` questions, which are conversation and not permission, still wait (ADR 0077, 2 and 3). The setting is read once per step, so a change counts from the next step and an approval already waiting stays until answered (ADR 0077, 7). `risky` is the model's judgement of the call (§8.2; ADR 0072, 4): `false` for the ordinary work of the task inside the workspace folder, and `true` when the call could do what is hard to take back or reaches past the task (ADR 0009, 161 and 212; ADR 0011, 7). A call that asks becomes an approval question holding `{ connector, command, payload }` (ADR 0089, 1), and the turn suspends; the approved call runs at the start of the next step. A denied call returns "denied by the user", or with the person's reason `denied by the user: <reason>` (ADR 0091, 4). **Approval rules** (ADR 0091, 1 to 3): the setting `kvcoder.approval.allowed` lists `{ kind: 'line', prefix }` and `{ kind: 'files' }` rules, read once per step; with `auto` or `ask`, a call a rule covers runs without asking. A `line` rule covers a `shell exec` line, or a binary's `<name> <args>`, when every part of it (what is between `&&`, `||`, `;`, `|`, `&`, and line breaks) starts with the prefix followed by nothing or by a space or tab, and holds only letters, digits, spaces, and `_ - . , / : = + @ % ~ * ' "` (a part with `$`, a backtick, a bracket, a brace, `<`, `>`, or `\` asks). A `files` rule covers `fs write`, `edit`, `undo`, and `assemble`, except a file whose real path is in a `.git` folder, a `.env` or `.env.*` file, or the project's `AGENTS.md` or `CLAUDE.md`. No rule covers an `mcp` call, a command with `asks: true`, or a program worker. A registered command whose entry has `asks: true` (§8.4) asks on every call, with `auto` too, since it has no `risky`, and not with `never`; its payload is checked when it runs, not before the person is asked (ADR 0022, 5 and 10).
- **Timeout.** The default is 120 s; the model may ask for up to 600 s (a larger `timeoutMs` is cut to 600 s, ADR 0009, 101). On timeout or cancel, the process tree is killed: its group on Linux and macOS, `taskkill /PID <pid> /T /F` on Windows.
- **Cancellation boundary** (ADR 0039, KVC-08). A short-lived runner checks the signal before preparation and immediately before process creation: a pre-aborted call creates no child. After installing terminal handlers and the abort listener it rechecks the signal, so cancellation during spawn or registration is not missed and does not kill twice. An already-created child is killed and its terminal event awaited before the cancellation reason is propagated; cancellation is not ordinary failure or timeout. Terminal paths clear timers and abort listeners, and a later event cannot settle again or start a drain after settlement. Existing output-drain and OS limitations below are unchanged.
- **Background.** `background: true` (ADR 0009, 149; ADR 0011, 6) needs the same approval, then starts the line in the real shell through the kernel's process service (`ctx.processes.start`, in the workspace folder; plan 02 §2.16), waits 1 s for its first output (the startup second), and returns `started <id>`, the output so far, and how the process stands (ADR 0012, 7): `[running]` when it still runs; `[the process has already ended]` and `[exit code N]`, its real code, when it exited; `[the process has already ended]` and `[killed by <signal>]` when a signal killed it. An exit with a code other than 0 and a kill are error results; `details.exitCode` is set only for an exit. The end is read from the process's record: a process that has died without its end recorded yet counts as running, and its end arrives as a background message (ADR 0012, 9). It has no timeout, so `timeoutMs` is ignored. The agent follows it up with the `background` connector (§8.5).
- **Background runs.** A background process belongs to its chat (ADR 0009, 150). Its status is `running`, `succeeded`, `failed`, `cancelled`, or `interrupted`, and kvcoder records each way it ends: the `kernel.process.exited` handler for an exit by itself, its own stop for `background stop` and the person's Stop, a `kernel.stopping` handler when kvman stops, and a `kernel.started` handler for a kvman that died. The records are in kvcoder's global store, since the last two handlers run in Home. An exit by itself and the person's stop add a background message with the outcome and the last 20 lines of output at once, except an exit inside the startup second, which the start result already carries (ADR 0012, 8); the agent's own `background stop` adds none, since its result says so (ADR 0085, 5). The runs that ended while kvman was stopped are reported at the chat's next message as one message, one line per run: `While kvman was stopped, these background calls ended:` then ``- `<call>` (job <id>): <outcome>``, with no output (ADR 0085, 5). None starts a turn (a handler's jobs carry the `fromHandler` mark, plan 02 §2.15). It runs until it ends or is stopped; deleting the chat stops it, and a turn's Stop button doesn't.
- **Leftover processes.** A call ends when its shell exits, not when every process that holds its output has closed it. On Linux and macOS, whatever is left in the shell's process group is then killed, and the result says `[background processes were stopped when the command ended; set background to true to keep one running]` before the exit code; nothing outlives a call. A process that left the group can't be stopped, so output gets at most 1 s to drain after the shell exits. Windows can't kill what a finished shell left, so there the call ends and the leftover keeps running (ADR 0009, 148).
- **Output.** stdout and stderr are combined. Output over 30 KB keeps its first and last 15 KB around a `[… N bytes omitted …]` marker; connector results are cut the same way, except those of `fs read`, `fs list`, and `fs search`, which limit themselves (ADR 0011, 23).

**Old calls** (ADR 0011, 12). A chat stored before `run` keeps its `bash` and `powershell` calls, and its history is sent unchanged. A turn found waiting on an approval of such a call never runs it: whatever the answer, its result is `denied by the user`, then `Make this call again with the run tool.`

## 8.4 Extending kvcoder

Other extensions extend kvcoder by calling its public commands. kvcoder keeps what they register in its own store, and reads only its own store while running a turn. It never calls other extensions to build a prompt.

**A connector** is a named set of commands the agent runs with `run`. There are two kinds.

```ts
// A commands connector: run { connector: 'ext', command: 'new', payload } runs kvbuilder's own public command.
await ctx.exec('kvcoder.connector.register', {
  name: 'ext',                                   // the run tool's `connector`
  description: 'Create and test kvman extensions.',
  commands: [{
    name: 'new',                                 // the run tool's `command`
    command: 'kvbuilder.ext.new',                    // your own public command; the payload is its input
    examples: [{ description: 'Scaffold a notes extension', input: { name: 'notes', namespace: 'notes', folder: './notes' } }],
  }],
});

// A binary connector: a program on the system, run in the real shell.
await ctx.exec('kvcoder.connector.register', {
  name: 'gh',
  description: 'GitHub CLI.',
  binary: { check: 'gh --version', install: 'https://cli.github.com' },
});
```

- **A card of its own** (ADR 0082, 13). A command entry may have `card`: a custom component of the registering extension, `<namespace>.<component>` with the namespace of the entry's `command` (`VALIDATION_FAILED` otherwise). A successful call of it stores `details.card: { component, payload, output }` with the command's output, and the conversation shows that component with the props `{ payload, output }` in place of the call card; a failed call keeps the call card, and the model reads the result as before.
- **Description.** The `description` is what the agent sees in the prompt's connector index (§8.2): write it to say what the connector is for and when to use it, in a sentence or two. kvcoder adds the command names after it (ADR 0009, 164 and 165; ADR 0011, 3).
- **Two kinds.** A connector has exactly one of `commands` or `binary`.
- **Several at once.** `kvcoder.connector.register { connectors: [ … ] }` registers several connectors, each shaped as above, in one call: every one is checked first and all are stored together, so the call registers all of them or none, and a name given twice fails `VALIDATION_FAILED` (ADR 0011, 26).
- **Names.** `shell`, `fs`, `artifact`, `execution-map`, `background`, `ask`, `delegate`, `mcp`, and `web` (ADR 0095, 5) are kvcoder's own: registering one fails `kvcoder/NAME_TAKEN`. Every connector has `help` (§8.3), so a command named `help` fails `VALIDATION_FAILED` (ADR 0011, 4).
- **Commands connectors** run their commands through `ctx.exec`, with the payload as the input. So validation, cancel, retries, and timeouts are the kernel's. `help` is built from each command's registered description and JSON Schema (through `kernel.extensions.list`) and its `examples`. A `command` must be a public command or query of the extension registering it (checked through `kernel.registrations.list`, ADR 0011, 25), or the call fails with `VALIDATION_FAILED` (ADR 0009, 129).
- **A command that asks** (ADR 0022, 5, 10, and 11). A command entry may have `asks: true`, the only value the field takes: `{ name: 'settings-set', command: 'kvbuilder.app.settings.set', asks: true }`. Each call of it then becomes an approval question, as a risky `fs write` does (§8.3), with `auto` and with `ask`; with `never` it runs at once (ADR 0077, 2); allowed, it runs at the start of the next step, and denied, it returns "denied by the user". Its `help` adds "The person is asked before this runs." Use it for a command that changes something the person didn't make in this chat.
- **Binary connectors** have two commands (ADR 0011, 5): `exec { args?, background?, timeoutMs?, risky }` runs the line `<name> <args>` in the real shell, with the approval, timeout, and background rules of `shell exec` (§8.3); `help {}` describes `exec` and `help` and then prints the output of `<name> --help`; `help { command: 'exec' }` gives `exec`'s payload; `help { command }` with any other command prints the output of `<name> <command> --help`. The program runs with a 5 s timeout and no approval. A registration may give `binary.help`, the line to run instead, in which `{command}` stands for the command, or for nothing when none is asked (`go help {command}`). One is listed in the prompt, and can be called, only when its `check` passes; checks run at a session's first step (5 s timeout each, no approval, passing on exit 0), and the results are stored in the session record. The setting `kvcoder.connectors` adds binary connectors from the preset or the person.
- **Off until enabled** (ADR 0027, 6 and 10). A connector entry, of either kind, may have `optIn: true`, the only value the field takes. It is then off in every chat until its owner switches it on for one: `kvcoder.connector.enable { sessionId, names }`, where each name must be an `optIn` connector the caller owns (`VALIDATION_FAILED` otherwise). The names are kept on the session record, so they outlast a restart, and enabling one twice does nothing. Where it isn't enabled, an `optIn` connector is as one that `kvcoder.connectors.disabled` names: it isn't in the prompt's connector index or the `run` tool's enum, and a call to it gets the answer for a connector that doesn't exist. A subagent has one only when its top-level session enabled it and its worker lists it. A fork starts with none enabled. Nothing switches one off again.
- **Turning connectors off** (ADR 0014, 7). The setting `kvcoder.connectors.disabled` lists connector names, kvcoder's own included. A connector named in it is, for every session of the workspace, as if it weren't there: it isn't in the prompt's connector index, a call to it gets the answer for a connector that doesn't exist, and a worker's subagent doesn't have it. The prompt refreshes from the next step, but execution rechecks current grants even for a reply already in flight, a held approval, `help`, or a call resuming after an ordered wait (KVC-10, ADR0044). A revoked grant yields the existing explicit rejection result with no new dispatch or hung turn; it does not proactively invalidate every card or undo begun work. A name no connector has is ignored. The base prompt doesn't change.

**Sections** are text in the system prompt. The owner pushes them whenever its data changes:

```ts
await ctx.exec('kvcoder.section.set', { id: 'guide', title: 'Extension guide', order: 20, global: true, content: guide });
await ctx.exec('kvcoder.section.set', { id: 'open-todos', title: 'Open todos', order: 40, sessionId, content: list });
await ctx.exec('kvcoder.section.remove', { id: 'open-todos', sessionId });
```

- **Reach.** A section with `global: true` is in every prompt of every workspace. One with `sessionId` is in that session's prompts only. One with neither is in every prompt of the job's workspace.
- Caps: 16 KB per section, 64 KB in total (`TOO_LARGE`): `section.set` checks the global sections, the job's workspace's, and the session's together; a prompt build that still finds more leaves out the last sections by `order` and logs a warning (ADR 0009, 94).
- **Ids** belong to their owner: two extensions may both have `guide`, and `section.remove` touches only the caller's (ADR 0009, 94).

**Slash commands** (ADR 0027, 5, 8, and 9). An extension adds commands to the send box (§8.7):

```ts
await ctx.exec('kvcoder.slash.register', {
  commands: [{
    name: 'build-kvman',                             // what the person types after `/`
    description: 'kvbuilder.slash.build-kvman',       // a translation key of your catalog, shown in the list
    command: 'kvbuilder.build.start',                 // your own public command; its input is { sessionId, argument }
    message: 'kvbuilder.slash.build-kvman.message',   // optional: a translation key
  }],
});
```

- `name` is lowercase kebab case. kvcoder's own six (`compact`, `export`, `fork`, `new`, `prompt`, `rename`), and a name another extension owns, fail `kvcoder/NAME_TAKEN`; a name given twice in one call fails `VALIDATION_FAILED`. Every entry is checked before any is stored.
- `command` must be a public command of the extension registering it (`VALIDATION_FAILED`). The send box calls it with `{ sessionId, argument }`: the open chat's id, or on the Chat page the id of the chat it just created (§8.7; ADR 0028), and the text after the command's name, `''` when there is none.
- `message`: when the command succeeds, the send box sends the argument, or with none the translated text of `message`, with `kvcoder.message.send`, as a message the person typed. Without `message` nothing is sent.
- `kvcoder.slash.unregister { name }` removes the caller's own; `kvcoder.slash.list` gives every entry whose owner is loaded, by name.

**Where entries live.** Connectors, slash commands, session handlers, handler-job ids, and global sections are in kvcoder's global store. Sessions and the other sections are in the workspace store.

**Indexes** (ADR 0088, 3). kvcoder declares the field sets it filters its growing collections by: `sessions` (`parentId`; `parentId, status`; `stepJobId`; `status`, ADR 0091, 6), `messages` (`sessionId`; `sessionId, block`; `sessionId, kind`; `sessionId, turnId, kind`), `turns`, `queued`, `questions`, and `maps` (`sessionId`), `step-intents` (`sessionId, turnId`), `answer-receipts` (`questionId`), `send-receipts` (`sendId`), `file-views` (`sessionId, path`), `file-backups` (`sessionId`; `sessionId, path`), `file-parts` (`sessionId, path`; `sessionId, path, part`), `file-changes` (`sessionId`; `sessionId, path`; ADR 0093, 2), `artifacts` (`sessionId`; `sessionId, artifactId`), `background` (`sessionId`; `sessionId, ref`), `runs` (`sessionId`; `jobId`), and the global `processes` (`sessionId`; `sessionId, reported`; `workspaceId`).

**Ownership and lifetime.**
- **Ownership.** The caller (`ctx.job.caller`) owns what it registers, and only the owner replaces or removes it. A connector name owned by another extension fails with `kvcoder/NAME_TAKEN`.
- **Connectors and slash commands last one run.** kvcoder clears them in its own `kernel.started` handler. That handler runs first, because registering extensions declare kvcoder as a dependency (§2.15). Each extension then registers its connectors and slash commands again in its own `kernel.started` handler. A hot reload of kvcoder reruns its dependents' handlers too (§2.9).

  ```ts
  ctx.registerHandler('kernel.started', {
    description: 'Registers kvbuilder connectors with kvcoder.',
    handle: () => ctx.exec('kvcoder.connector.register', { … }),
  });
  ```
- **Sections are stored until removed.**
- **Stale entries.** When kvcoder reads, it ignores any connector, slash command, or section whose owner isn't loaded.

**Session points.** An extension can have one of its commands called when something happens to a session:

```ts
ctx.registerHandler('kernel.started', {
  description: 'Registers todo cleanup with kvcoder.',
  handle: () => ctx.exec('kvcoder.handler.register', { point: 'kvcoder.session.deleted', command: 'todo.session.forget' }),
});
```

| Point | Input |
|---|---|
| `kvcoder.session.created` | `{ sessionId, parentId? }` |
| `kvcoder.session.deleted` | `{ sessionId }` |
| `kvcoder.session.forked` | `{ fromSessionId, toSessionId, throughSeq }` |
| `kvcoder.turn.started` | `{ sessionId, turnId }` |
| `kvcoder.turn.ended` | `{ sessionId, turnId, outcome, usage, durationMs }` |
| `kvcoder.session.waiting` | `{ sessionId, kind: 'question' \| 'approval' \| 'subagent' \| 'worker' }` |

- **Calls.** For each occurrence, kvcoder queues one async job per registered handler (its own `kvcoder.handler.run`, which runs the handler's command nested, ADR 0009, 110). Inputs carry ids and totals, never message contents; a handler reads the messages with `kvcoder.message.list` if it needs them.
- **Registration.** The `command` must be the caller's own public command. Each extension has at most one handler per point; registering again replaces it. Handlers are owned by the caller and cleared at each start, like connectors.
- **Loop safety.** kvcoder stores the ids of the handler jobs it queues. A message injected by one of them (a job whose `ctx.job.rootId` is such an id) is stored but doesn't start a turn; the next turn sees it. Work that a handler queues with `execAsync` isn't recognized, so a handler must not inject from there.
- **Access.** Every extension can use kvcoder's public API: read sessions, messages, and turns; create, configure, rename, delete, fork, and export sessions; inject messages; add notes; cancel turns. Only `message.send` and `question.answer` are for the person; an extension calling them fails `NOT_PUBLIC` (ADR 0009, 105).

**Testing.** `runConnector(kernel, { connector: 'ext', command: 'new', payload: { … } })` from `@kvman/kvcoder/testing`, used with `createTestKernel`, runs a call exactly as kvcoder does and returns `{ output, exitCode }`, including for `help`. It runs commands connectors and the `help` of built-in ones: any other built-in call, and a binary connector's, returns exit 1, and it never starts a shell (ADR 0009, 96; ADR 0011, 18).

## 8.5 Built-in connectors

`shell` is in §8.3. Unknown keys in a payload fail `VALIDATION_FAILED`.

**ask** suspends the turn until the person answers. The answer becomes the call's result, and a dismissal gives `{ "dismissed": true }`.

| Call | Result |
|---|---|
| `ask text { prompt, placeholder? }` | `{ "text" }` |
| `ask choice { prompt, multiple, options: [{ id, label, description? }] (2–10), other? }` | `{ "selected": [ids], "other"? }` |
| `ask confirm { prompt, danger? }` | `{ "confirmed" }` |

- `kvcoder.ask.text.check`, `.choice.check`, or `.confirm.check` validates the payload (ADR 0011, 9). The step then sends a component chunk `{ type: 'component', component: 'kvcoder.question', props }`, so the conversation shows the question card inline. A pending question is also in the turn record, so the card shows again after a reload.
- The person answers with `kvcoder.question.answer` (user only). `answer` has the shape of the result above, or `{ "dismissed": true }`. Its result, pending update, question deletion and receipt commit together (ADR0042); the last pending resolution prepares the next intent before enqueue. The card follows the same-turn reference after acknowledgment. Identical normalized retries apply nothing again; different answers fail VALIDATION_FAILED.

**delegate** hands a task to a worker (ADR 0021):

```
delegate run { worker, title, task, background?: true }
delegate continue { id, message, background?: true }
```

`continue` (ADR 0085, 4) sends `message` to an ended subagent helper of this chat, which continues with its own history, worker, instructions, model, and thinking; the person's grants are checked again as for `run`, and it waits for the answer or returns `started <id>` with `background`, as `run` does. It fails `VALIDATION_FAILED` while the helper's turn has not ended and for a program worker's run; an id that is not a helper of this chat fails `kvcoder/JOB_NOT_FOUND`.

`title` is the role this run plays, in a few words (1 to 200 characters; one over 60 is saved as its first 59 and `…`, ADR 0051), such as "UI expert" or "Node.js expert": the lead writes it, a subagent's child session takes it as its title, and the person sees it as the helper's name (ADR 0037, 1 and 2).

- **Workers.** The setting `kvcoder.delegate.workers` lists them. An entry is strict, and every kind has `{ name, description, enabled, kind, instructions }`: `name` is lowercase kebab case and unique in the list; `description` is non-empty; `instructions` is text up to 16 KB, empty for none. The default is five workers, `general`, `ui-ux`, `architect`, `tester`, and `reviewer`, each a `subagent`, turned on, with every connector and the chat's model; their descriptions and instructions are in ADR 0076 (`general`'s in ADR 0021). Only the person and a preset add workers. A subagent worker also has `readOnly` (`false` when left out; `true` for the shipped `architect` and `reviewer`): its helper may read, search, list and read background output, list MCP tools, use help, and run a registered connector's command whose target is a public query (kvcoder keeps `query` on each stored command, from `kernel.registrations.list` at registration; such a connector is listed with only those commands, ADR 0082, 3), and reports in its answer (ADR 0063); every other call is refused when it is evaluated, before any approval, and is left out of its prompt (ADR 0056).
  - `kind: 'subagent'` adds `{ connectors, model, thinking }`: `connectors` is a list of names, or `null` for all; `model` and `thinking` are `null` for the chat's own.
  - `kind: 'opencode' | 'pi' | 'claude'`, a program on this computer, adds `{ approval: 'ask' | 'auto', timeoutMs }` (`timeoutMs` from 60 000 to 7 200 000) and its own fields, each `null` to leave its flag out: `opencode` has `{ model, agent, autoApprove }`; `pi` has `{ model, thinking, tools }`; `claude` has `{ model, effort, permissionMode }` (ADR 0021, 13 and 31). An entry with `approval: 'auto'` fails `VALIDATION_FAILED` when it is an `opencode` with `autoApprove: true`, or a `claude` whose `permissionMode` is `bypassPermissions`, `auto`, or `dontAsk`: a run nobody is asked about can't also approve its own actions (ADR 0021, 39).
- **Available.** A worker is available when its `enabled` is `true` and, for a program, its check passed: `<program> --version` is started at the session's first step as a run starts the program, for 5 s at most, passing on exit 0, and its result is in the session's check results as `worker:<name>` (ADR 0021, 17 and 37). A helper is created with its parent's check results less the `worker:` ones and never runs a worker's check; one whose parent has none yet runs the binary connectors' checks at its first step (ADR 0087, 10). The connector's entry in the prompt ends with `Workers: <name> (<description>), ….`, the available ones in the setting's order; a worker with `readOnly: true` is `<name> (<description>; read-only)` (ADR 0085, 9). With none, `delegate` isn't a connector of the session (§8.2).
- **Execution permissions** (KVC-10, ADR0044). After asynchronous worker selection, creation rechecks canonical step authority, current parent/root grants and the named worker in the same transaction; inherited child defaults come from the canonical parent. Foreground starts require an exact unambiguous pending child/run in the same waiting/open turn. Positive program approval retains its exact question identity through preparation, then consumes it with captured run creation and foreground pending replacement; it remains legacy without a durable-launch receipt. Queued programs recheck their running row, current grants, named worker kind/check and exact foreground pending directly before spawn; a null unpublished job ID is valid, while a published ID must match the executing job. Worker instruction/scope and command-line snapshots remain unchanged. Revocation settles only a current exact call; stale work cannot resolve a newer turn by call ID alone. Failure handlers recheck the running run and owning wait atomically, and deferred completion revalidates its captured turn/resource before settlement. These checks do not establish background durable origin, exactly-once start or atomic normal child delivery;04–06 remain separate.
The rest of this list is a `subagent` worker's run; a program's follows it.

- **A run** starts a hidden child session with the task as its first message, and nothing of the parent's conversation.
- **Model.** The child uses the worker's `model` and `thinking`, and the parent's for each that is `null`; when the worker's `model` is `null` and the setting `kvcoder.delegate.model` names one, the child uses that (ADR 0069, 3).
- **Prompt.** The child has the base prompt with a worker's identity and working method in place of the lead's (§8.2; ADR 0022, 3), the sections, then the worker's instructions as the block `## Worker: <name>`, then the connector index. It keeps the instructions it started with.
- **Connectors.** The child has the worker's `connectors` among the parent's, or all of the parent's for `null`. A name that no connector of the chat has, or that is turned off, is ignored. `delegate` is never included, so depth is 1, and neither is `ask`: a helper asks the person nothing and returns its questions to the lead. Of `artifact` a child has only `get`; `write` and `edit` are refused, `VALIDATION_FAILED`, and left out of its prompt (ADR 0063).
- **Waiting.** The parent's turn suspends until the child ends, and the child's final answer becomes the call's result.
  - Several runs in one reply run in parallel.
  - `background: true` lets the parent continue; the answer arrives later as a message.
- **Questions.** A child's approvals and questions show in the root session's conversation: a foreground child's under the call that waits on it, and a background child's below the messages under the line "A background helper needs your decision." whatever the root's turn is doing (ADR 0085, 1).
- **Results.** A child that ends `done` returns its last answer's text; any other outcome returns, as an error, `subagent ended <outcome>`, with `: <code>` when its last message is a notice that carries a failure's code, the provider's reason on the next line when it has one, and then that text under the line `Its last message before it stopped (unfinished, not a result):` (ADR 0050, 4). A background run returns `started <childSessionId>`. Every helper result, a foreground answer, a background notice, and `background output`, ends with the line `(helper <childSessionId>)`, the id `continue` takes (ADR 0085, 4). A `worker` that isn't in the list or isn't available fails `kvcoder/WORKER_NOT_FOUND` from `kvcoder.delegate.check`: `There is no worker <name>. The workers are: <names>.`

A program worker's run (ADR 0021, 10 to 16 and 31 to 36):

- **Approval.** With the worker's `approval: 'ask'` the call becomes an approval question holding `{ connector, command, payload }`, as a shell call's does (§8.3), unless `kvcoder.approval` is `never` (ADR 0077, 2); `auto` starts at once. An allowed call starts its run in `kvcoder.question.answer`, and its pending call becomes `{ kind: 'worker', runId }`; a denied one returns `denied by the user`.
- **The command line**, in the workspace folder, with kvman's environment and an empty standard input:
  - `opencode run --format json [--model <model>] [--agent <agent>] [--auto] -- <text>`, where `<text>` is the instructions, a blank line, and the task, or the task alone;
  - `pi -p [--model <model>] [--thinking <thinking>] [--tools <a,b>] [--append-system-prompt <instructions>] -- <task>`;
  - `claude -p --permission-mode <permissionMode> [--model <model>] [--effort <effort>] [--append-system-prompt <instructions>] -- <task>`.
- **The job.** The run is the private async job `kvcoder.delegate.worker.run` (`retries: 0`, `timeoutMs` 7 260 000), which starts the program with `cross-spawn`, in its own process group on Linux and macOS, and waits. The process tree is killed after the worker's `timeoutMs`, on cancel, and on Stop: its group on Linux and macOS, `taskkill /PID <pid> /T /F` on Windows. The run keeps the command line it started with.
- **Waiting.** The turn suspends, with the pending call `{ toolCallId, kind: 'worker', runId }`, until the program exits; its job then holds the result and queues the next step. `background: true` returns `started <runId>` and lets the turn go on; the result arrives as a message with `source: { kind: 'job', jobId: <runId> }`, which starts a turn when the session is idle.
- **Results.** `pi` and `claude` print the answer on their standard output; `opencode`'s is the text of its `text` events after the last `tool_use` event, joined by a blank line, and an `error` event's `error.message` is a reason. Exit 0 returns the answer, or the error `<worker> returned no answer`. Another exit code is the error `<worker> exited with code <N>`, then the reasons, the standard error, and the answer so far; a timeout is `<worker> timed out after <N> s`, then the same; a program that can't start is `<worker> could not start: <reason>`. The text is cut as a shell call's is. Nothing is added to the session's usage.
- **The staging guard** (ADR 0060, 4). Before a program starts and after it ends, kvcoder marks the folder's Git state: the tree of what is staged, written from a copy of the index, and the commit `HEAD` names. No mark is made outside a Git repository, without Git, or while the index has unresolved conflicts. When the marks differ, the run keeps `staging: { tree, after, head, headMoved, paths, restored }`, its result ends with "kvman: this run changed what is staged in Git (`<paths>` paths differ from before it ran)." and, when `HEAD` moved, "kvman: this run moved HEAD from `<before>` to `<after>`.", and the result's `details.staging` is `{ runId }`. `kvcoder.delegate.staging.restore` puts the staged tree back; it changes no file and no commit, and fails `VALIDATION_FAILED` for a run with no kept change, one restored already, one that moved `HEAD`, or when the staging area or `HEAD` is no longer as the run left it. A run ended by a stop, a lost job, or kvman stopping isn't marked after.
- **Stop.** `kvcoder.job.cancel` and `background stop` kill the tree: a run the turn waits on returns the error `<worker> was stopped` and the turn goes on; a background one stopped by the person adds that as a background message and starts no turn, and one stopped by the agent's `background stop` adds none (ADR 0085, 5).
- **A lost run.** When the run's job fails, the run is `interrupted` (kvman stopped or died) or `failed`; a turn waiting on it ends the same way with the step's notice (§8.1), and a background run adds a background message and starts no turn.
- **Cancellation boundary** (ADR 0039, KVC-08). Program runs and their installation checks use the same pre-spawn guard, cancellation registration recheck, terminal cleanup and cancellation-reason propagation as the short-lived shell in §8.3. Normal `ProgramEnd` output and timeout/start-error behavior are unchanged; this adds no worker fields or registrations.

**fs** reads, lists, searches, writes, and edits files inside the workspace folder (ADR 0009, 157 to 160; ADR 0011, 8):

| Call | Result |
|---|---|
| `fs read { path, fromLine?, fromColumn?, lines? }` | `{ "path", "fromLine", "totalLines", "content", "truncated", "next"? }`: `lines` lines from `fromLine` (1 by default), or from the character `fromColumn` of it; when something was left out, `next: { fromLine, fromColumn? }` is where to read on, also inside one very long line (ADR 0055, 1); when the chat's messages after its latest summary already hold this exact result, the text `<path> is unchanged since you read these lines earlier in this conversation; that result is above.` in its place (ADR 0034, 2) |
| `fs list { path? }` | `{ "path", "entries": [{ "name", "kind": "file" \| "folder", "bytes" }], "truncated" }`: one folder (the workspace folder by default, and for an empty `path`), not its sub-folders |
| `fs find { pattern, path? }` | `{ "paths", "truncated" }`: the files under `path` (the workspace folder by default, and for an empty `path`) whose path matches the glob `pattern`, relative to the workspace folder, newest modified first and by path on a tie, at most 200 (ADR 0090, 2) |
| `fs search { pattern, path?, literal?, glob?, context?, filesOnly? }` | `{ "files": [{ "path", "matches": [{ "line", "text", "context"? }] }], "truncated", "reason"? }` (grouped by file, ADR 0034, 5), or with `filesOnly` `{ "files": [{ "path", "count" }], … }` (ADR 0090, 3): the lines matching the regular expression `pattern`, or the plain text with `literal: true`, in a file or under a folder (the workspace folder by default, and for an empty `path`), in the files `glob` names when given. In a Git workspace, files Git ignores are skipped. One file gets at most 2 seconds and a search 10; `reason` is `matches` or `time` when `truncated` (ADR 0055) |
| `fs write { path, content, risky }` | creates the file and its parent folders, or replaces it: `{ "path", "created", "bytes" }` |
| `fs edit { path, edits: [{ oldText, newText, replaceAll? }], risky }` | replaces text in an existing file: `{ "path", "replacements", "firstChangedLine", "fromLine", "content" }`, where `content` is the file's lines from 3 before the first changed line to 3 after the last, starting at `fromLine`; when that is more than 13 lines, it is the first 6 and the last 6 with the line `[… N lines not shown …]` between them (ADR 0034, 1; ADR 0069, 2) |
| `fs undo { path, risky }` | takes back this chat's latest change to the file: `{ "path", "removed", "bytes" }`; fails when there is none, or when the file changed since (ADR 0053, 5) |
| `fs part { path, part, content }` | saves piece `part` (1 to 200, at most 64 KB) of a long file the chat is writing, outside the workspace; a number sent again replaces its piece: `{ "path", "part", "parts", "bytes" }` (ADR 0054) |
| `fs assemble { path, risky }` | joins the saved pieces 1 to n and writes the file as `write` does, then drops them: `{ "path", "created", "bytes", "parts" }`; fails naming the missing numbers when one is absent |

- **Paths.** A relative `path` resolves against the workspace folder; an absolute one works when it is inside it. A path that leaves the folder, through `..` or a symlink, fails `VALIDATION_FAILED` and reads or writes nothing. A missing file or folder fails `NOT_FOUND`. An empty `path` is the workspace folder for `list` and `search`, and fails `VALIDATION_FAILED` for `read`, `write`, and `edit` (ADR 0012, 12).
- **Reading.** `lines` is 2000 by default and at most 2000, and a larger one is cut to 2000 (ADR 0090, 4); the content holds whole lines up to 30 KB, so it may hold fewer than asked, and `totalLines` lets the agent go on with `fromLine`. A `fromLine` past the end gives an empty `content`. A file that isn't valid UTF-8 text is refused (`VALIDATION_FAILED`), and so is a folder.
- **Listing.** Entries are sorted by name, at most 1000, with `truncated: true` when there are more; `bytes` is 0 for a folder. A path that is a file fails `VALIDATION_FAILED`.
- **Searching.** `pattern` is a JavaScript regular expression, matched line by line, case-sensitive (an invalid one fails `VALIDATION_FAILED`). Files are visited in path order; `node_modules`, `.git`, and every other folder whose name starts with a dot are skipped, and so are files that aren't valid UTF-8 text. At most 200 matches are returned, with `truncated: true` when there are more; `path` is relative to the workspace folder, `line` starts at 1, and `text` is the line cut at 500 characters. `context` (0 to 10, a number outside them cut into them) adds that many lines before and after each match to its file's `matches`, in line order, each with `"context": true`; a line two matches share appears once, and only matches count toward the 200. `filesOnly: true` gives each file's `count` of matching lines in place of its `matches`, and the 200 then counts files. Both together fail `VALIDATION_FAILED` (ADR 0090, 3).
- **Finding.** `fs find` uses the glob syntax of `fs search`'s `glob` (`**` any run, `*` any run but `/`, `?` one character but `/`): a pattern with `/` matches the path from `path`, one without matches the file's name. It skips what `fs search` skips. A `path` that is a file fails `VALIDATION_FAILED` (ADR 0090, 2).
- **Approval.** `write`, `edit`, `undo`, and `assemble` ask as `shell exec` does (§8.3); `read`, `list`, `find`, `search`, `part`, and `help` never ask.
- **Safe changes** (ADR 0053). A change reads, checks, and replaces the file inside one store transaction, so workers take turns; the file is its real path. The workspace collection `file-views` holds `{ sessionId, path, fingerprint, updatedAt }`, recorded by a successful `read` and by each change; changing an existing file the chat has no view of, or one that no longer matches its view, fails `VALIDATION_FAILED` and says to read it. The new content is written beside the file and renamed over it, with its permission bits. The workspace collection `file-backups` holds `{ sessionId, path, previous, written, createdAt }` for a chat's newest 20 changes of files up to 1 MB, which `undo` restores when the file still matches `written`. Views and copies are deleted with their chat.
- **Matching.** Every `oldText` is matched exactly against the file as it was before the call, must be non-empty and occur once, and must not overlap another one; the edits apply together. An edit with `replaceAll: true` replaces every occurrence of its `oldText` instead, found from the start, each after the end of the one before, and fails only when there is none or one overlaps another edit; `replacements` counts every replacement (ADR 0090, 1). If any check fails, or the result equals the file, nothing is written and the error names the edit and why, and ends with `Nothing was written.` (ADR 0035, 3). A file that isn't valid UTF-8 text is refused. CRLF line endings and a leading BOM are kept.
- **Order.** Calls on the same file run one after another, in the model's order when they start together.

**artifact** shows the person a document beside the conversation: a report, a design, or a page (ADR 0009, 173 to 179). Its entry in the prompt tells the agent to write a diagram as Mermaid code in a fenced `mermaid` block of a Markdown artifact or reply, which kvman draws, and not as SVG (ADR 0067, 7), and to change part of an existing artifact with `edit`, writing it again only when most of it changes (ADR 0087, 5):

| Call | Result |
|---|---|
| `artifact write { id, title, format?, content }` | creates the artifact, or replaces it (title, format, and content): `{ "id", "version", "created", "bytes" }` |
| `artifact edit { id, edits: [{ oldText, newText, replaceAll? }] }` | replaces text in an existing artifact: `{ "id", "version", "replacements", "firstChangedLine" }` |
| `artifact get { id }` | `{ "id", "title", "format", "version", "content" }` |

- **Shape.** `id` is lowercase kebab case, up to 50 characters, and names the artifact within its chat (`plan` is the plan of a larger task, §8.2). `title` is 1 to 100 characters. `format` is `markdown`, `html`, or `url`; left out, it is `html` for content that starts with `<!doctype html` or `<html`, `url` for content that is one local address, and `markdown` for anything else (ADR 0009, 215 and 216). `content` is text up to 64 KB (`TOO_LARGE`, `params.limit`). A chat holds at most 20 artifacts: creating the 21st fails `TOO_LARGE`. `version` starts at 1 and rises with every write or edit; only the latest content is kept. An unknown `id` in `edit` or `get` fails `NOT_FOUND`; unknown keys, a bad `id`, or a bad `format` fail `VALIDATION_FAILED`.
- **Edits** follow the matching rules of `fs edit`: every `oldText` is matched exactly once against the content as it was, edits don't overlap, and nothing is written when a check fails, the edits change nothing, or the result would pass 64 KB.
- **Order and ownership.** Calls on the same artifact run one after another, in the model's order when they start together. An artifact belongs to its chat; a subagent's belongs to the chat at its root, so the person sees a helper's report. No approval is asked.
- **Storage.** An HTML artifact's page, in the panel's scripts-only frame, has an opaque origin, so `localStorage`, `sessionStorage`, cookies, and `indexedDB` throw `SecurityError`; the `artifact` entry in the system prompt says so, and asks for pages that work without them. A `url` artifact's page has its own origin and can use them (ADR 0009, 217 and 218).
- **URL.** A `url` artifact's `content` is one http or https address on `localhost` or `127.0.0.1`, with no credentials (anything else fails `VALIDATION_FAILED`), such as a dev server the agent started; it is shown in a frame that lets the page work as in a tab, and never when it is kvman's own address (ADR 0009, 216 and 218). `edit` re-checks the address.
- **HTML.** An `html` artifact is shown in an isolated frame (§8.7): its scripts run, but it can't load from or reach the network, kvman's page, or the person's browser data.

**mcp** reaches the tools of the MCP servers the person added (ADR 0020, 3 to 10, 12, and 16):

| Call | Result |
|---|---|
| `mcp tools { server, tool? }` | `{ "server", "tools": [{ "name", "description", "takes" }] }`, where `takes` is the tool's arguments as a signature such as `{ url, timeout? }` (ADR 0070, 2), or with `tool`, `{ "server", "name", "description", "arguments" }`, where `arguments` is the tool's input JSON Schema |
| `mcp call { server, tool, arguments?, timeoutMs?, risky }` | the tool's text |
| `mcp run { server, steps: [{ tool, arguments? }], timeoutMs?, risky }` | 1 to 20 tools on one connection, in order, so a server that keeps state between tools keeps it for the run: each step's text under `## <n>. <tool>`; it stops at the first tool that reports an error, adds `[stopped: N steps not run]`, and is then an error result; an unknown tool fails `NOT_FOUND` before any runs; it asks as `mcp call` does (ADR 0070, 1) |

- **Servers.** The setting `kvcoder.mcp.servers` lists them: `{ name, description, command, args, env }` runs a command that speaks MCP on its standard input and output, in a temporary folder of its own that is deleted when the connection closes, with the workspace folder in the variable `KVMAN_WORKSPACE` (ADR 0070, 7); `{ name, description, url, headers }` is reached over Streamable HTTP. Entries are strict, `name` is lowercase kebab case and unique in the list, and `env` and `headers` hold names only. With no server, `mcp` isn't a connector of the session (§8.2).
- **Secrets.** A variable's value is kvcoder's secret `mcp.<name>.env.<VARIABLE>` and a header's is `mcp.<name>.header.<Header>` (plan 02 §2.8). A name without a secret is left out of the environment or the request. Values are never returned, stored elsewhere, or logged.
- **A call is one connection.** Each `tools` and `call` connects, does its work, and closes. A command is started in the call's own job with `cross-spawn` (ADR 0020, 17), with kvman's environment and the server's variables, and its process tree is killed when the call ends, on a timeout, and on cancel: its group on Linux and macOS, `taskkill /PID <pid> /T /F` on Windows. Nothing is kept between calls.
- **Timeout.** 120 s by default; the model may ask for up to 600 s, and a larger `timeoutMs` is cut to 600 s. A call that passes it fails `kvcoder/MCP_CONNECT_FAILED`.
- **Approval.** `call` asks as `shell exec` does (§8.3); `tools` and `help` never ask.
- **Results.** The tool's text blocks, joined by a blank line; a block of another kind is `[<kind> omitted]`. A result the tool marks as an error is an error result. An unknown server fails `kvcoder/MCP_SERVER_NOT_FOUND`, an unknown tool `NOT_FOUND` naming the server's tools, and a server that can't be started or reached `kvcoder/MCP_CONNECT_FAILED` with the reason.
- **Sign-in** (ADR 0020, 8, 11, and 16). A server over HTTP that asks for authorization fails `kvcoder/MCP_SIGN_IN_NEEDED` until the person signs in from its row (§8.7). `kvcoder.mcp.sign-in.start { name, redirectUrl }` registers kvman with the server when it hasn't yet (a server without dynamic client registration fails `kvcoder/MCP_SIGN_IN_FAILED`), keeps the started sign-in in the global store for 10 minutes, and answers the address to open; `redirectUrl` must be `http://127.0.0.1:<port>/kvcoder/mcp-sign-in`, or the same on `localhost` (`VALIDATION_FAILED` otherwise). `kvcoder.mcp.sign-in.finish { state, code }` is sync only: an unknown or expired `state` fails `kvcoder/MCP_SIGN_IN_FAILED`; otherwise it exchanges the code and stores the tokens. The client registration, the code verifier, and the tokens are the secrets `mcp.<name>.oauth.client`, `.verifier`, and `.tokens`. A call refreshes tokens that have expired; when that fails it fails `kvcoder/MCP_SIGN_IN_NEEDED`.
- **Only tools.** A server's resources, prompts, and sampling aren't used.

**web** reads a page on the web (ADR 0095):

| Call | Result |
|---|---|
| `web fetch { url }` | `{ "url", "status", "type", "content" }`: `content` is the page as Markdown for `text/html` (made with `turndown`, without its scripts and styles), or the text itself for `text/plain`, `text/markdown`, `application/json`, and other `text/*` types; any other type fails `VALIDATION_FAILED`, and a status of 400 or more, a failed connection, or a page past its 30 s fails `kvcoder/WEB_FAILED { url, status?, reason? }`. `url` is the last address after at most 5 redirects; at most 5 MB are read, in at most 30 s, and `content` is cut as a connector result is |

- **Addresses.** Only `http` and `https`, with no credentials. Before each request and each redirect the host is resolved, and the request is refused, `VALIDATION_FAILED`, when any address is loopback, private, link-local, unique-local, unspecified, or multicast; the connection uses the address that was checked.
- **Approval.** With `kvcoder.approval` `auto` or `ask`, the first fetch from a host in a chat asks as a risky call does; an allowed one adds the host to the chat's `webHosts` (old records `[]`), and later fetches from it run at once. With `never` none asks. A read-only worker's helper may fetch only from a host its chat allowed.

**execution-map** is the lead's execution path and implementation plan for work of several steps (ADR 0075, 1 and 2), detailed and not an outline, which the person reads, agrees to (§8.2), and watches as a diagram (ADR 0064; ADR 0072; ADR 0086). It is the lead's alone: a child session never has it. A chat has one map, in the collection `maps` under the chat's own id, deleted with the chat.

| Call | Result |
|---|---|
| `execution-map set { goal, steps: [{ id, title, after?, uses?, check }] }` (its limits end the connector's description in the index, ADR 0082, 8) | makes the map's skeleton or replaces it (ADR 0086, 1): a step whose id stays keeps its details, status, evidence, and note, any other starts `todo` with no details, and the notes are kept; 1 to 40 steps, ids lowercase kebab up to 50 characters and unique, `goal` up to 300, `title` up to 100, `uses` one name up to 60 or a list of up to 5 (kept joined with commas), `check` up to 300 |
| `execution-map detail { id, details }` | writes one step's details, replacing what it had (ADR 0086, 2 and 3): Markdown of 1 to 4,000 characters saying what the step changes and how, with lists, tables, and fenced `mermaid` blocks for diagrams and charts, never SVG; a step the map doesn't have fails with the map's ids |
| `execution-map update { steps: [{ id, status, evidence?, note? }] }` | changes steps in the order given; if one change is refused, none is made |
| `execution-map note { text }` | adds to "Noted for later": up to 500 characters, 50 notes (`TOO_LARGE` past them) |
| `execution-map get { id? }` | the progress below and `noted`, the notes' texts, with `steps` without their details, or, given an `id`, with `step`, that step whole (ADR 0086, 8) |

- **Shape.** `after` names the steps that must be finished first. A map with a repeated id, an `after` that names an unknown step or the step itself, or steps that wait on each other in a circle fails `VALIDATION_FAILED`, naming them. Parallel work isn't declared: two steps with no path between them can run together; by the lead's method such steps are branches, each handed to a worker (ADR 0075, 7), which kvman doesn't check.
- **A reminder** (ADR 0074, 6 and 7). After the calls of a reply of the chat's own agent ran, when the reply has an `fs write`, `fs edit`, or `shell exec` that ran at once and succeeded and no `execution-map set` or `update`, the map has a step that is `todo` or `failed`, and none is `doing`, the text the model reads for the last such change ends with a blank line and `[kvman: the execution map has <n> unfinished step(s) and none is marked doing. Mark the step this work belongs to with execution-map update, or set the map again when the plan changed.]` ("step" for one, "steps" for more; ADR 0075, 1). The call's card doesn't show it, nothing is refused, and a change that waited for an approval, a worker's change, and a `delegate run` carry none.
- **Status** is `todo`, `doing`, `done`, `failed`, or `skipped`. A step is finished when it is `done` or `skipped`, and ready when it is `todo` and everything in its `after` is finished.
- **Rules of `update`.** `doing` and `done` need every step in `after` finished, and the refusal names the ones that aren't; `done` needs `evidence` (10 to 500 characters: what was run or checked and what it showed); `doing` needs the step's details too, and the refusal names the steps that lack them (ADR 0086, 7); `failed` and `skipped` need `note` (up to 300); `todo` clears evidence and note. A step the map doesn't have fails with the map's ids.
- **What comes back.** `set`, `detail`, `update`, and `note` return `{ goal, progress, doing, ready, waiting, failed, undetailed, notes }`: `progress` is `"<finished> of <total> done"`, each list holds `"<id>: <title>"`, `undetailed` the steps with no details (ADR 0086, 6), and `notes` is their count. `detail`, `update`, `note`, and `get` fail `NOT_FOUND` when the chat has no map.
- **Order.** The map calls of one reply run one after another in the model's order.
- **The person's view** is `kvcoder.map.get { sessionId }` (public) → `{ goal, steps, notes: [{ text, createdAt }], version, updatedAt }`, or `null` when the chat has none; a step is `{ id, title, details, after, uses, check, status, evidence, note }`, and `details` is `null` on a step not yet detailed or stored before ADR 0072; a step stored with `description` is read with it as `details`, and saved under the new name the next time the map is (ADR 0086, 5); a subagent's session answers with its chat's map (§8.7).

**background** follows up on what this chat started with `background: true` (ADR 0009, 81, 88, and 151; ADR 0011, 6): processes by their id, and background subagents by their child session id. When the person sends a message while runs of the chat are running, the message stores them as `content.running` and they are sent after its text as `[kvman: still running in the background: …]` (ADR 0068, 4).

| Call | Result |
|---|---|
| `background list {}` | the newest 50, newest first, as short rows: `[{ "id", "kind": "process" \| "subagent" \| "worker", "title", "status", "startedAt", "endedAt"?, "exitCode"? }]`, where `title` is the run's title cut at 80 characters (ADR 0068, 2) |
| `background output { id, lines? }` | the run's row with its whole `call`, plus `output` (a process's last `lines` lines, 100 by default and 500 at most, a larger number cut to 500 (ADR 0090, 4), a subagent's answer, or what a program worker's run returned) or `problem` |
| `background wait { id, timeoutMs? }` | what `output` returns, once the run's status is no longer `running` or `timeoutMs` has passed (1 000 to 600 000, 120 000 by default, a number outside them cut into them, ADR 0090, 4); a run still running then has the status `running` (ADR 0068, 1). A message from the person queued for the chat ends the wait at once, with `note: "The person sent a message."` (ADR 0085, 3) |
| `background stop { id }` | stops a process or a program worker's run, or cancels a subagent: `{ "stopped": true }`, `false` for one that has already ended |

An id this chat didn't start fails `kvcoder/JOB_NOT_FOUND`. `call` is the line that runs, which also titles a process, or the `title` of the `delegate run` that started the subagent or the program worker's run; a continued helper keeps its own title (ADR 0089, 1). A subagent's status is `waiting` while its turn waits on the person's answer or approval (ADR 0085, 2). A subagent's row in `output` and `wait` adds `progress: { steps, lastActivityAt, recentCalls }`: its current or last turn's steps, the time of its newest message, and its last five calls, oldest first, each as `<connector> <command>` and its subject (a shell line, a binary's `<name> <args>`, a path, a search pattern, a `delegate run`'s worker and title, an `mcp` call's server and tool, or an id), on one line cut at 200 characters; while waiting, it adds `waitingFor`, the calls it waits on named the same way and a question by its prompt (ADR 0089, 1).

## 8.7 UI and settings

kvcoder owns its conversation UI. kvwebui only hosts it: kvcoder contributes pages through `kvcoder.ui.get`, and the preset decides where they appear (the `coder` preset makes `kvcoder.chat` the home page).

**UI.**
- The **Chat** page `kvcoder.chat`: the session list and the conversation with no session: the question (`kvcoder.ui.startHeading`, or the profile's `startHeading`, with the workspace's name, Home's as "Home"; ADR 0082, 7 and 11), one approval line (ADR 0082, 6: "The agent asks you before risky actions.", "…before every action that changes something.", or "The agent acts without asking you." for the loaded `kvcoder.approval`, then "Change", which opens kvcoder's configuration; empty while it loads or when it fails, and not shown when `kvwebui.nav.hidden` names `kvwebui.extensions`), and a large input at the bottom that asks what to build (`kvcoder.ui.startPlaceholder`, or the profile's `placeholder`); the heading and lines scroll inside the column and the send box stays in view at every width, which holds the model picker and the thinking picker (showing what the chat would use; ADR 0017, 3); sending creates the chat (`kvcoder.session.create`, then `kvcoder.session.configure` with what the person changed, then `kvcoder.message.send`) and opens its page. When the model's provider needs a key, or there is no model, a line under the question says so (with an "Add a key" link to the provider's page) and sending is off (ADR 0009, 104 and 194).
- The `kvcoder.session` page, with a `sessionId` param: the session list and the conversation. A session exists only in its workspace, so when the tab's workspace changes while this page is open, the conversation reads nothing more for the old session and opens the selected workspace's newest chat (`kvcoder.session.list { limit: 1 }`), or the Chat page when it has none; until then it is empty (ADR 0016). A page opened on a chat the tab's workspace doesn't have (a link from another workspace, or a deleted chat) shows one toast, "This chat isn't in this workspace.", at the first `kvcoder/SESSION_NOT_FOUND` for that id from any of its reads, and then does the same; later failures for that id show nothing (ADR 0082, 5).
- **The session list** is kvcoder's custom component `kvcoder.sessions`: translated titles, each session's status ("Needs you" while its `waitingOn` is `person`, whatever its status, "Working" while it is `helpers`, else running; ADR 0091, 6), times grouped into Today and Earlier, the open chat highlighted (its row tinted with the primary color and its title heavier, so it stands out from the page's ground the list sits on; ADR 0076, 1), and a "New chat" button back to the Chat page (ADR 0009, 104).
- **The conversation** is kvcoder's custom component `kvcoder.conversation { sessionId }`. It:
  - shows the messages from `kvcoder.message.list`, with notices and notes translated, and "N earlier messages" with the export;
  - streams the running step (`kvman.stream`): text deltas into the pending answer, thinking deltas open while they stream, a tool call's connector and command as its arguments complete, component chunks inline, and follow chunks continuing in the same bubble; an activity line tells what the step is doing, with seconds, and "Retrying in 15 s: the provider is limiting calls (3 of 5)", or "…: the provider didn't answer (3 of 5)", while a failed model call is tried again (ADR 0009, 142 and 155; ADR 0087, 6);
  - keeps the send box's text and attachments in application memory by workspace and chat until the send is confirmed, through internal navigation and a rebuilt component, not a page reload. The box is disabled while a send is on its way. A failed send keeps them and shows a line above the box saying what failed; sending again retries with the same `sendId` when the text and files are the same. On the Chat page the draft remembers the chat it created, and a retry sends into it rather than creating another (ADR 0048);

"Deny and say why…" opens a box for the reason with "Deny", and an empty box denies without one (ADR 0091, 4). A call stored before `run` shows its command line as its one line; `http://127.0.0.1:<port>…` and `http://localhost:<port>…` URLs in any output are links that open in a new tab (ADR 0009, 120, 195, 196, 206, and 207).
- **Configuration** (plan 06 §6.3; ADR 0014, 10; ADR 0015, 3 to 5, 7, and 9; ADR 0020, 1, 2, and 13): `kvcoder.ui.get` gives a `configuration` of three cards: Agent (the custom component `kvcoder.model`, twice, then the custom component `kvcoder.approval`, then the custom component `kvcoder.preferences` (a text area with Save, "Changed", and a reset; ADR 0092, 3), then `kvcoder.thinking`, `kvcoder.maxSteps`, `kvcoder.compactAt`, `kvcoder.compactKeep`), Chats (`kvcoder.sessions.keep`), and Connectors: the custom component `kvcoder.connectors`. The setting `kvcoder.connectors` isn't shown: a preset or `kernel.settings.set` adds programs. `kvcoder.model` is the row of that setting: its title and description, and the chat's model picker, whose first entry, "Use the default model", stores `null` and is left out while the person searches; while the setting is `null` the button says "Default model (<name of kvai.defaultModel>)". It saves into `kvman.scope`, and shows "Changed" with a reset, or that the workspace has its own value, as the connectors do. `kvcoder.approval {}` is the row of the setting `kvcoder.approval` (ADR 0077, 4 to 6): its title "Approval" and description, a select of its three named options, and under it the approval note for the mode in effect, then the rules of `kvcoder.approval.allowed` in the scope being edited, each as `Always allowed: <prefix> …` or "Always allowed: file changes", with Remove, or "No commands are always allowed." (ADR 0091, 1). "Ask only for risky calls" and "Ask for every call" save as they are chosen. "Never ask" saves nothing and opens a confirmation under the select (`role="alertdialog"`, the focus on "Cancel") that says the agent will run commands, change files, change kvman itself, and start worker programs without asking, and that what it reads can steer it; "Turn off asking" saves `never`, and "Cancel" or Escape closes it and shows the stored choice again. `kvcoder.connectors` lists kvcoder's own connectors with a catalog description (`kvcoder.config.connector.<name>`), then those of `kvcoder.connector.list` with their description, each a name, a description, and a switch that writes `kvcoder.connectors.disabled` with `kernel.settings.set` in `kvman.scope`. On "All workspaces" while the workspace has its own list, the switches are disabled and a line says so; a list set in the scope being edited shows "Changed" and a reset.
- **A connector's own configuration** (ADR 0020, 2 and 13 to 15; ADR 0021, 6). `shell`, `delegate`, and `mcp` have a cog button before their switch, labelled "Configure <name>". It opens a dialog (`role="dialog"`, `aria-modal`) whose title is the connector's name and the scope being edited, "All workspaces" or the workspace's name; Escape, a press on the backdrop, and its Close button close it, focus moves into it when it opens and returns to the cog when it closes.
  - **shell.** One row, the setting's title and description and a control: `kvcoder.shell.path` as a text field, where empty stores `null` (the approval row moved to the Agent card, ADR 0077, 6). The row saves as it changes (on Enter or on leaving the field), shows "Changed" with a reset when the value is set in the scope being edited, and is disabled, with a line saying so, on "All workspaces" while the workspace has its own value.
  - **mcp.** The servers of `kvcoder.mcp.servers`, each with its name, description, and state from `kvcoder.mcp.server.check`, run for every server when the dialog opens: "Checking…", then "Ready · N tools", "Sign-in needed" with a "Sign in" button, or "Could not connect" with the Problem's sentence. Each has Edit and Remove (after an inline confirmation; it writes the list without the server and deletes the server's secrets). With no server it says "No servers yet. Add one and the agent can use its tools." "Add a server" and Edit show a form: Name (fixed when editing), Description, "Runs as" (a command | a URL), then Command, Arguments (one per line), and Environment variables, or URL and Headers. A variable or header is a name and a password field; one that has a secret shows "Set" and "Replace" in place of the field. Save writes the list with `kernel.settings.set` in `kvman.scope`, then the new values with `kernel.secrets.set`, deletes the secrets of removed names, and checks the server; a new variable or header needs a value; a name already in the list, or an invalid field, shows under its field and nothing is saved. A row has "Check again". On "All workspaces" while the workspace has its own list, the dialog is read-only and a line says so.
  - **delegate.** The workers of `kvcoder.delegate.workers`, each with its name, description, and kind, a switch labelled "Use <name>" that writes its `enabled`, Edit, and Remove (after an inline confirmation). With no worker it says "No workers yet. Add one and the agent can hand it a task." "Add a worker" and Edit show a form: Name (fixed when editing), Description, Instructions (a text area), Connectors ("All" stores `null`; "Only these" shows a checkbox for each of kvcoder's own connectors but `delegate`, then those of `kvcoder.connector.list`), Model (the chat's model picker, whose first entry, "Same as the chat", stores `null`), and Thinking (a select whose first option, "Same as the chat", stores `null`). Save writes the list with `kernel.settings.set` in `kvman.scope`; a name already in the list, or an invalid field, shows under its field and nothing is saved. "Kind" (Subagent, opencode, pi, Claude Code) is fixed when editing; a program kind shows, in place of Connectors, Model, and Thinking, "Before a run" (Ask me \| Start at once), "Time limit" in minutes (1 to 120), and its own fields as text fields where empty stores `null`, with `autoApprove` as a checkbox, `permissionMode` as a select, and `tools` as one name per line. A program worker's row shows "Checking…", then nothing more when `kvcoder.delegate.worker.check` finds the program, or "<program> not found" with "Check again" (ADR 0021, 38). A list set in the scope being edited shows "Changed" and a reset, which brings the shipped workers back; on "All workspaces" while the workspace has its own list, the dialog is read-only and a line says so.
  - **Sign in.** "Sign in" runs `kvcoder.mcp.sign-in.start` with this page's origin and `/kvcoder/mcp-sign-in`, and opens the answer's address in a new tab. A signed-in server has "Sign out", which deletes its `oauth` secrets. The dialog checks the servers again when its tab gets the focus back.
- **The sign-in page** `kvcoder.mcp-sign-in` (ADR 0020, 11): the custom component `kvcoder.mcp-sign-in`. It reads `code`, `state`, and `error` from the address, runs `kvcoder.mcp.sign-in.finish`, and shows "Signed in to <name>. You can close this tab.", or the Problem; an address with `error`, or without `code` or `state`, shows that the sign-in didn't finish, and runs nothing. It has no nav item.
- **Status items:** the count of sessions waiting on the person, from `kvcoder.session.count { waitingOn: 'person' }`, with `titleCount: 'count'` so the tab's title starts with it (ADR 0009, 97; ADR 0091, 6 and 7), and on a chat page the chat's tokens and cost, from `kvcoder.session.get` (ADR 0009, 147); the conversation follows each step's job, so the count reruns when a step ends (ADR 0009, 131). The session list and the conversation sit side by side from 30 rem of conversation width, and stack below (ADR 0009, 130); below 60 rem of page width the list is a "Chats" button that opens it over the page, closed by a press outside, Escape, or opening a chat; the send box never covers the messages; and below 30 rem of conversation width the model and thinking pickers, and "Decide for me", show an icon with their name as label and tooltip (ADR 0093, 3).
